# Alder — ユーザーと、業務設計書で話そう

[English](README.md) | 日本語

システムの要件は、ユーザーとの会話から始まり、レビューと合意を経て確定します。その過程で必要なのは、開発者が設計に使え、ユーザーも読んで確認できる資料です。

Alderは、この資料を**業務設計書**として定義します。ユーザーが読める自然言語で業務を記述し、意味やつながりを追える構造を与えます。その構造を使って、AIが記述の不備、考慮漏れ、業務間の不整合をレビューし、現場の困りごとに対する改善候補も提案します。

この**業務設計書をユーザーとの共通言語にして**、実際の仕事と、これから実現したい仕事を確かめます。AIが示す問いや提案も判断材料にしながら、同じ文書を見て話し合い、合意した内容を反映します。こうして業務設計書を、業務上の要件を記録・共有する正本（SSOT）として育てます。

その役割は、要件の合意で終わりません。Alderは、合意した業務設計書を検査項目とテストへつなぎ、テストを通じて実装を検証することで、設計した業務がシステムとして実現されているかを確認する手順も提供します。

**ユーザーと合意した業務を、動くシステムへ。**

## Alderが支援できること

業務設計では、ユーザーの話を整理するだけでなく、仕事のつながりや例外、責任の境界を捉え、業務そのものの見直しも検討します。さらに、合意した業務をシステムにするには、何を検査すべきかを明らかにし、実装がその期待を満たしているかを確かめる必要があります。

業務への理解と、設計・実装・検証をつなぐ経験が求められます。

Alderは、業務設計書を軸に、この一連の作業をAIで支援します。分析や改善では、見落としやすい点や別の選択肢を判断材料として整理します。実装・検証では、合意した内容を検査項目へ具体化し、実装やテストと照合することで、意図とのずれや確認が足りない点を明らかにします。

| 場面 | 支援内容 |
| --- | --- |
| **業務分析** | ヒアリング内容を業務設計書へ整理し、記述の不備や業務間の不整合、未決の条件を、ユーザーに確認できる具体的な問いにする |
| **業務仮説の検証** | これから実現したい業務を業務設計書として具体化し、仕事のつながり、情報の受け渡し、例外や責任の境界を確認して、業務として成立するかを確かめる |
| **業務改善** | 現場の困りごとから改善候補を考え、期待する効果、変更の難しさ、採用前に確かめることを整理する |
| **実装・検証** | 合意した業務から検査項目を導き、実装やテストがその期待結果に沿っているかを確認する |

目的に応じて、必要な支援を選べます。既存業務の分析や改善だけでなく、新規システムや新しい業務の構想を業務仮説として具体化し、業務として成立するかを確かめるためにも使えます。実装後は、合意した業務設計書をもとにレビューできます。

## 業務設計書とは — ユーザーが読めて、AIがレビューできる形にする

業務設計書は、**ユーザー・設計者・AIの共通言語として、業務の全体像を共有し、一連の仕事が成立するかを確かめるための文書**です。誰が何を担い、どんな情報を受け渡し、次の仕事へどうつなぐのかを、ユーザーが読んで確認できる自然言語で記述します。

Alderでは、その内容を二つに分けて整理します。

- **仕事＝Activity**：予約する、申請を承認するなど、担当者が進める仕事。
- **扱う情報・文書・台帳・外部の相手＝Object**：予約台帳、申請書、利用者など、仕事の中で情報を読み書きしたり、やり取りしたりする対象。

### Activity — 一つの仕事を定義する

Activityは5W1Hを基本に、HowをInput・Procedure・Outputへ分け、正常終了後に成立する状態をResultに書きます。主な項目は次のとおりです。

| 項目 | 記述する内容 |
| --- | --- |
| Who | 業務を担うロール |
| When | 業務を始める具体的なきっかけ |
| Input / Output | どのObjectから何を受け取り、どのObjectへ何を渡すか |
| Procedure | 業務ルールと、確認・判断・更新の流れ |
| Result | 正常終了後に成立する状態と、次の業務へのつながり |
| Scope | その仕事が今回の責任範囲に含まれるか |
| Problem / Pain level | 現行業務の困りごとと、その大きさ。困りごとがある場合に記述する |

### Object — 仕事で扱う情報や相手を定義する

Objectには、対象の名前と、そこで扱う情報を記述します。たとえば「予約台帳」なら、予約者、対象会議室、利用時間帯、予約の状態などです。

| 項目 | 記述する内容 |
| --- | --- |
| Object名 | 情報・文書・台帳・外部の相手を識別する名前 |
| Information | そのObjectが持つ、またはやり取りする業務上の情報 |
| Scope | そのObjectが今回の業務範囲内で成立・管理されるものか |

### 業務のつながり — 開始条件と情報の受け渡しを分けて書く

ひと続きで進む仕事は、一つのActivityにまとめます。一方、別の依頼や判断、待ち時間などを挟んで始まる仕事は、必要に応じて別のActivityとして記述します。Activity同士を並べた順序で実行順を決めるのではなく、Objectを通じた情報の受け渡しと、Whenに書いた開始条件で実際のつながりを表します。

たとえば予約と取消は、必ず連続して行う仕事ではありません。予約する仕事は予約台帳に情報を残し、取消の仕事は利用者から取消依頼を受けたときに、その台帳から対象を特定して始まります。このように、実際の業務で独立して始まる仕事はその事実をそのまま記述します。逆に、連続して行う必要がある仕事まで無理に分離する必要はありません。

Whenには、依頼の受領や状態の変化など、具体的な開始のきっかけを書きます。「必要に応じて」で済ませず、人間の判断が必要なら、何を見て判断するかを示します。これにより、前後の仕事がどの条件でつながるのかをレビューできます。

例外による差し戻しは、通常の情報の受け渡しとは分け、Activity間の関係として記述します。

### 詳細設計へのつなぎ方

記述した情報は、後続のデータ設計や実装の手掛かりにもなります。ただし、この段階でテーブル定義などを決めきる必要はありません。分かっている条件や手掛かりは残しつつ、業務全体を見渡せる粒度を保ち、必要な詳細化を後続の設計へつなぎます。

各欄の詳しい意味、見出しの順序、参照の書式は[業務設計書の文書構造](docs/business-design-structure.ja.md)を参照してください。

## 業務分析 — 仕事の流れを、ユーザーと確かめる

ユーザーへのヒアリング内容を、まず業務設計書の形へ整理します。仕事ごとに担当者、手順、受け渡す情報を書き、前後の業務と共有するObjectをつなぎます。

会議室予約なら、たとえば次のように書けます。以下は一つのActivityの抜粋です。

```markdown
# Activity 会議室を予約する

## Scope
true

## Why
会議に必要な時間帯の会議室を確保するため。

## When
利用者から予約希望を受け付けたとき。

## Who
予約受付担当者

## Where
規定なし

## How

### Input
- 利用者 — 対象会議室 / 利用開始・終了日時 / 利用目的 / 予約者
- 会議室台帳 — 会議室の利用可否
- 予約台帳 — 既存予約の時間帯と状態

### Procedure
1. 会議室が利用可能で、利用開始が受付時点より後、終了が開始より後であることを確認する。
2. 同じ会議室の有効な予約と時間帯が重ならないことを確認する。同時の申込みでも重複予約を成立させない。
3. 予約内容と登録日時を予約台帳に記録し、利用者へ予約結果を伝える。

### Output
- 予約台帳 — 登録された予約内容 / 登録日時
- 利用者 — 予約結果

## Result
利用者が指定した会議室と時間帯の予約が成立し、その予定で会議の準備を進められる。
```

Objectや例外を含む[予約受付の全文](docs/examples/meeting-room-reservation.ja.md)と、複数の業務が同じObjectを使う[予約・取消の記述例](docs/examples/meeting-room-lifecycle.ja.md)も用意しています。

AIへの最初の依頼は、たとえば次の形です。

```text
../alder/docs/business-design-structure.ja.md と ../alder/docs/adoption.md に従い、
次のヒアリング内容から docs/business-design/meeting-room.md に草案を作ってください。
本文はユーザーがレビューできる日本語にし、未決の業務ルールは確認事項として残してください。
草案を提示する前に、手順と情報の受け渡し、前後の業務のつながりを確認してください。

目的: 社内の会議室を予約できるようにしたい。
対象: 空き確認、予約、変更、取消、利用不可・利用再開の管理。
確認したルール: 重複予約は成立させない。変更できない場合は元の予約を維持する。
```

### 書いた内容をレビューし、ユーザーと合意する

書式に沿って書くだけでは、業務設計書は完成しません。Alderでは、記述そのもの、業務間のつながり、必要に応じて未記載の条件を順に確かめます。

```text
ヒアリング → 業務設計書へ構造化 → 記述品質レビュー → 業務相関レビュー
           → 必要なら考慮漏れレビュー → ユーザー確認・修正・合意
```

1. **記述品質を確かめる。** Inputにない情報をProcedureで使う、WhyとResultに同じ説明を書くなど、単純な書式でも役割を混同することがあります。誰が何を扱い、何が成立するかを読めるように整えます。[確認観点](docs/business-design-quality-review.md)と[依頼用プロンプト](docs/business-design-quality-check.ja.md)を用意しています。
2. **業務のつながりを確かめる。** 個々の仕事が読めても、前工程の結果が次の開始条件につながらない、必要な情報が渡らない、といった問題は残ります。共有Objectの意味や例外時の差し戻しも含めて[業務相関をレビュー](docs/business-design-correlation-check.ja.md)します。
3. **必要なら、考慮漏れを探す。** 正常な手順のヒアリングだけでは決まらない条件を、具体的な結果の違いが生じる場面から探します。一般的な必須機能を押し付けず、「この場合はどう扱うか」という問いにします。[考慮漏れレビュー](docs/behavior-derivation/functional-considerations.md)は任意です。

AIは業務上の答えを代わりに決めません。ユーザーと問いを確認し、修正を重ね、合意した業務設計書を正本にします。実際にレビューで見つかった問いと、その扱いは[会議室予約のレビュー事例](docs/business-design-review.ja.md)で紹介しています。

## 業務改善 — 困りごとから、別のやり方を探す

今の業務は成立していても、作業の負担や待ち時間が大きいことがあります。困りごとがある場合は、ユーザーと内容を確認し、該当ActivityのResultの後に`Problem`と`Pain level`を記録します。全業務に埋める必要はありません。

たとえば、購買担当者から「承認済みの申請ごとに購入と結果登録を繰り返す負担が大きい」と確認できた場合です。

```markdown
## Problem
承認済みの購入申請が増えると、購買担当者が申請ごとに購入し、結果を登録する負担が大きい。

## Pain level
High
```

この記録をもとに、AIへ業務改善レビュー（Optimization Review）を依頼します。

```text
../alder/docs/optimization-review.md に従い、業務改善レビューをしてください。
対象: docs/business-design/purchase-request.md の合意済みの版。
同書に記録した購買作業のProblem / Pain levelを起点にしてください。
期待する効果、業務変更の難しさ、守るべき条件、採用前の確認事項を示してください。
候補は最大3件とし、採否は決めず、ファイルは変更しないでください。
```

購買の例では、次のような候補を比較できます。

| 改善候補 | 期待できる効果 | 採用前に確かめること |
| --- | --- | --- |
| 条件の合う申請をまとめて購入する | 購入操作や確認の繰り返しを減らす | まとめてよい条件、待機できる期間、申請ごとの実購入金額の記録方法 |
| 定型的な申請の購入と結果取得を自動化する | 個別の購入操作と結果転記を減らす | 自動購入の権限、結果を取得できるか、失敗時の責任者 |
| 購入事務を外部の購買サービスに委ねる | 自社で行う手配作業を減らす | 利用可能なサービス、契約・費用、申請ごとの結果照合 |

これは[購買改善の提案例](docs/examples/purchase-improvement.ja.md)の要約です。効果や実現性は現場の条件によって変わります。承認権限や「実際に購入したものだけを購入済みにする」という意味を保ちながら、変更範囲と関係者の調整の難しさも検討します。

採否を決めるのは人間です。採用する場合は、**業務設計書を先に更新・再合意**してから、必要な検査項目や実装へ反映します。有益な候補がなければ、現状を維持できます。

## 実装 — 合意した期待結果を、コードとテストへつなぐ

業務設計書の合意後、AIが検査項目（Check Item）の草案を作り、人間が期待結果を確認します。会議室予約なら、次のような一覧になります。

| ID | タイトル | 期待結果 | レビュー状態 |
| --- | --- | --- | --- |
| MR-001 | 同じ会議室で重複予約が成立しない | 同時に申し込まれても、同じ会議室・重なる時間帯の予約が複数成立しない。 | 未レビュー |
| MR-002 | 変更できなくても元の予約が残る | 予約変更の条件を満たさない場合、元の予約内容が維持される。 | 未レビュー |

これは予約・変更業務を含む設計から作る一覧の一部です。AIの草案は、人間が確認するまで「未レビュー」です。修正と確認を繰り返し、合意した業務設計書と検査項目を、版とIDが分かる形で実装へ渡します。ここまでで標準の設計業務が完了します。

```text
確認済みの docs/business-design/meeting-room.md と
docs/checks/meeting-room.md を読み、今回合意した範囲を実装してください。
プロダクトの技術要件と既存の開発ルールに従い、コードとテストを作成・更新してください。
テストの期待結果は、確認済みの検査項目と業務設計書を根拠にしてください。
未決の業務ルールは具体的な問いとして人間に戻し、重要な前提・判断と理由をレビューへ引き継いでください。
```

実装・テスト実行の後は、別のAIエージェントや新しいセッションで、合意した業務と期待結果が実現されているかをレビューします。見つかった業務上の疑問はユーザーと確認し、業務設計書へ反映します。

検査項目の作成からレビューまでのプロンプトは[導入ガイド](docs/adoption.md)、粒度やレビュー状態は[検査項目の作成・保守](docs/check-item-traceability.md)を参照してください。

## インストール・導入

Alderを使うための専用パッケージは不要です。必要なのは、業務設計書とAlderの文書を読めるAIエージェントです。以下ではGitを使い、作業中のプロダクトの隣にAlderを配置します。

プロダクトのルートディレクトリで実行します。

```sh
git clone --depth 1 --branch main https://github.com/mk3008/alder.git ../alder
git -C ../alder rev-parse HEAD
```

2行目に表示されたコミットIDを記録し、次の`<コミットID>`をその値に置き換えて実行します。ブランチから離れ、そのコミットの文書を参照する状態に固定します。

```sh
git -C ../alder checkout --detach <コミットID>
git -C ../alder rev-parse HEAD
```

表示されたコミットIDが記録と一致することを確認します。このチェックアウトは参照専用とし、利用版を更新するときはcheckout先と記録を一緒に変更します。文書は、たとえば次のように配置します。

```text
workspace/
  alder/                         # Alderのガイド・レビュー知識
  product/
    AGENTS.md
    docs/
      business-design/            # 業務設計書
      checks/                    # 実装へ渡す検査項目
      decisions/                 # 重要な判断とその理由
    src/
    tests/
```

`AGENTS.md`またはタスクの指示に、次の参照先を追記します。`<コミットID>`は先ほどの値に置き換えてください。

```text
業務設計書: docs/business-design/
検査項目: docs/checks/
判断記録: docs/decisions/
Alderの参照版: ../alder/ の <コミットID>
業務設計書の書き方: ../alder/docs/business-design-structure.ja.md
各工程の手順: ../alder/docs/adoption.md
業務改善: ../alder/docs/optimization-review.md
実装後のレビュー知識: ../alder/docs/phase2/review-knowledge-v0.3.md

業務上の意味は業務設計書を正本とし、未決事項は人間に確認する。
業務改善の候補は、人間が採用を決めてから業務設計書へ反映する。
実装には、確認済みの業務設計書と人間がレビューした検査項目を渡す。
```

AIがこれらのパスを読めれば準備完了です。既存の文書配置を使う方法や版の選び方は[導入ガイド](docs/adoption.md)を参照してください。
