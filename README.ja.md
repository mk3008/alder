# Alder — 依頼者と業務設計書で話そう

[English](README.md) | 日本語

**依頼者と合意した業務を動くシステムへ。**

Alderは依頼者の要求を、依頼者・設計者・実装を担うAIの共通言語となる**業務設計書**（Business Design）に整理します。依頼者と設計者が合意した内容を**業務上の正本**（SSOT）として検査項目・コード・テストへつなげます。

フレームワークや実行時パッケージは不要です。

## 導入する

ChatGPT / Codexを利用できる契約・権限のあるアカウントと環境を用意してください。Alderの導入にはCodex CLIとPlugins Directoryを利用できるChatGPTデスクトップアプリを使います。ターミナルで次のコマンドを実行してAlderをインストールできる配布元（marketplace）を登録してください。

```sh
codex plugin marketplace add mk3008/alder --ref plugin-v0.2.8
```

コマンド実行後はChatGPTデスクトップアプリを再起動してPlugins Directoryで**Alder development**を選び、**Alder**をインストール・有効化してください。その後は新しいチャットを開始してください。

## まず使ってみる

業務ヒアリングから業務設計書を作るには、新しいチャットで次のプロンプトを送ってみてください。

```text
このヒアリング結果をAlder業務設計書にして。

対象は登録済みの地域住民です。
返却時は窓口で番号と付属品を照合して返却日時を記録します。
貸出の受渡しは署名と引き渡しの記録、返却の受領は照合と返却日時の記録で確認します。
返却された組は整備担当の点検を待ちます。
```

次のような構造化された業務設計書が得られます。

```markdown
# Activity 工具の返却受付

## When

住民が貸し出された工具を返却するとき。

## Who

窓口

## How

### Input

- 登録済み地域住民 — 返却する工具と付属品
- 貸出・返却の記録 — 貸し出した備品番号と引渡しの記録

### Procedure

1. 窓口は貸し出した番号と返却された現物の番号・付属品を照合し、返却日時を記録する。記録媒体は未確認。
2. 返却された組は整備担当の点検を待つ。具体的な引渡し方法は未確認。

### Output

- 貸出・返却の記録 — 照合結果と返却日時の記録
- 団体の工具 — 返却され点検を待つ組

## Result

番号と付属品の照合および返却日時の記録により受領が確認され、組は整備担当の点検を待つ。
```

この業務設計書を起点に業務設計書の記述品質・業務間のつながり・考慮漏れを確認し、合意した業務からCheck Itemを作ってコードとテストへつなげられます。具体的な流れは[業務設計書の作成](#業務設計書を作成する)、各項目の意味と構造の理由は[文書構造](docs/business-design-structure.ja.md)を参照してください。

## できること

- ヒアリング結果や要求から業務設計書を作成・改訂できます。
- 業務設計書の抜けや矛盾、前後の業務とのつながりを確認できます。
- 現在の業務の具体的な困りごとに対する改善案を比較できます。
- 合意した業務から検査項目を作り、期待結果を確認できます。
- 実装・DDL・テストが合意した業務に沿っているかをレビューできます。

<a id="標準的な使い方"></a>

## 業務設計書を作成する

Alderは既存業務の分析と新しい業務の仮説に使えます。業務設計書は依頼者・設計者・実装を担うAIが同じ業務を理解し、認識を合わせるために使います。依頼者自身が読んで誤りを指摘し、合意できるように、専用の記法を覚えるDSLではなく、普段使う言葉を決まった項目に沿って記述します。

設計者はヒアリング結果から草案を作り、自分でレビューしたうえで依頼者へ確認します。回答を設計へ反映し、合意までレビューと確認を繰り返します。AIは草案作成、抜けや矛盾の発見、確認事項の整理、回答に沿った改訂を手助けできます。

[![業務設計書作成業務。設計者が草案作成、自己レビュー、依頼者確認、回答反映を進め、AIが各作業を支援する。合意まで繰り返して業務設計書をまとめる。](docs/images/business-design-workflow.ja.png)](docs/images/business-design-workflow.ja.png)

<a id="1-草案を作り質問に答える"></a>

### 1. 草案を作る

対象プロジェクトのチャットへヒアリング結果や要求を渡し、次のように依頼してください。

```text
このヒアリング結果をAlder業務設計書にして。
docs/business-design/ に草案を作って。
```

設計者は草案を読み、入力した事実と合っているかを確かめます。不明な条件は推測で埋めず、確認する問いとして残します。

業務設計書は自然言語を決まった項目に沿って書きます。**書式を暗記する必要はありません**。AIが5W1HのHowをInput / Procedure / Outputへ分け、必要なExceptionと正常終了後のResultを整理します。たとえば予約結果の通知はOutput、予約が成立した状態はResultです。

<a id="2-業務設計をレビューし依頼者と合意する"></a>

### 2. 自分でレビューする

設計者は草案を読み、仕事の意味や前後の業務とのつながりを確かめます。AIにも次のように依頼すると、記述の曖昧さ、抜けや矛盾、確認すべき問いを探す補助になります。

```text
業務設計書をAlderでレビューして
```

AIの指摘をそのまま仕様にせず、入力事実と照らし合わせてください。設計者が判断できる記述上の問題は直し、責任、条件、例外、保証など依頼者に判断してもらう問いを整理します。

### 3. 依頼者に確認する

設計者は**業務設計書を依頼者と一緒に読み**、記述した仕事が依頼者の理解や意図と合っているかを確かめます。確認したい業務の入出力・手順・例外など、問いに関係する箇所を示して説明してください。レビューで見つけた問いや案も同じ箇所に結び付け、何が未決で、回答によってどこが変わるかを伝えます。

依頼者は業務設計書を見ながら事実を補足し、解釈の違いや業務上の未決事項を判断します。回答はこの業務設計書へ反映し、設計者や実装を担うAIも同じ内容を参照できるようにします。

確認事項の整理をAIに手伝わせる場合は、Alderの業務設計書とレビュー結果を渡して次のように依頼してください。

```text
このAlderの業務設計書とレビュー結果を使い、
依頼者に確認する問いと理由を、業務設計書の該当箇所に結び付けて整理して。
```

設計者は問いと業務設計書の該当箇所を確かめ、依頼者と同じ文書を見ながら確認してください。

### 4. 回答を設計へ反映する

設計者は依頼者の回答の意味を確かめ、草案を更新します。回答と業務設計書をAIへ渡して次のように依頼してください。

```text
この回答を反映して、Alder業務設計書を改訂して。
残る未決事項は分けて残して。
```

変更箇所を読み、回答と食い違っていないかを確認してください。

改訂後は再びレビューと依頼者確認を行います。**依頼者と設計者が合意した版が正本**です。合意した内容と残る未決事項を区別してまとめてください。品質要求のために項目を増やさず、[各項目の役割](docs/business-design-structure.ja.md)に沿って関係する既存項目へ書きます。技術的な実現手段はSystem Designへ分けてください。

## チェック項目を作成する

合意した業務設計書から、システムが満たすべき条件と期待結果をチェック項目（Check Item）にします。設計者がAIの草案作成・更新の支援を受け、依頼者と期待結果を確認する業務です。

設計者は草案を作り、依頼者と条件・期待結果を確認して修正します。AIは草案作成、確認事項の整理、回答に沿った更新を支援できます。確認結果と残る未決事項を記録し、確認済みの項目と未確認の候補を区別して引き渡します。

[![チェック項目作成業務。設計者が草案を作り、依頼者と期待結果を確認し、修正して引き渡す。AIは各作業を支援し、業務上の未決事項は業務設計へ戻す。](docs/images/check-item-workflow.ja.png)](docs/images/check-item-workflow.ja.png)

### 1. チェック項目の草案を作る

チェック項目の作成には専用のPlugin機能がないため、Alderの[検査項目の作成・保守](docs/check-item-traceability.md)と合意した業務設計書を、添付するかAIが読める場所に置いて渡してください。更新する場合は既存のチェック項目も渡します。

```text
渡したAlderの検査項目の作成・保守ガイド（docs/check-item-traceability.md）に従って、
この業務設計書からチェック項目の草案を作って。
```

一つの項目には、独立して確認できる条件と期待結果をまとめます。たとえば「同時申込みでも重複予約が成立しない」を確認する項目なら、どのような申込みが重なったときに何が成立してはいけないかを記述します。設計者は草案が合意した業務に沿っているかを確かめます。

<a id="3-check-itemを作り人間が期待結果を確認する"></a>
<a id="check-itemを作り人間が期待結果を確認する"></a>

<a id="2-依頼者と期待結果を確認する"></a>

### 2. 依頼者に説明する

設計者はチェック項目案と確認事項を依頼者へ説明し、条件と期待結果が望む業務に合っているかを確認します。説明の整理は、作成済みのチェック項目を材料にしたAIの補助作業です。次のように依頼してください。

```text
このAlderのチェック項目から、依頼者に確認する条件と期待結果を整理して。
```

設計者は説明を確かめてから伝え、期待結果の意味は依頼者が確認します。

確認結果は`未レビュー / 要確認 / 確認済み / 要修正`として区別します。**Test成功だけでは業務承認になりません**。Testは書かれた期待値と実装を照合します。その期待値が依頼者の望む業務かを確認するレビューとは別です。

<a id="3-修正して引き渡す"></a>

### 3. 回答を反映する

設計者は依頼者の回答を受け、チェック項目を直します。回答・チェック項目と、草案作成で使ったAlderのガイドをAIへ渡して次のように依頼してください。

```text
渡したAlderの検査項目の作成・保守ガイド（docs/check-item-traceability.md）に従って、
この回答をチェック項目に反映して。
確認できた項目と未決の項目を分けて残して。
```

設計者は修正結果が回答に沿っているかを確かめてください。既存のID、業務設計書や既存Testとの対応を保ち、レビュー状態を更新してください。必要な説明・確認・修正を行い、確認できた内容と残る未決事項を記録します。

業務の意味・条件・保証が未決だったり変更が必要だったりする項目は、チェック項目だけで決めずに業務設計書へ戻します。設計者が依頼者と設計を再合意してから、影響するチェック項目を更新してください。

**未決事項が残っていても、確認済みの期待結果と未確認の候補を区別して引き渡せます**。未確認の候補を確定した要件として実装へ渡さないでください。新しく作るTestの実行結果や対応関係は、この引き渡しの時点ではまだ必要ありません。実装後のレビューで確認します。

<a id="合意した業務を実装へつなぐ"></a>

## 設計とチェック項目を実装へ引き渡す

合意した業務設計書とレビュー状態を整理したチェック項目に、実装で守る技術条件を添えて引き渡します。その後は実装・独立レビュー・follow-upの開発ループへ進みます。

Alder Pluginは実装レビューを短い依頼から実行できます。System Requirementsなど、ほかの手順では下記の参照文書を使います。

<a id="4-先に守る制約をsystem-requirementsとして伝える"></a>

### 先に守る制約をSystem Requirementsとして伝える

技術条件の整理はプロダクト側の作業です。既存制約と希望をAIへ渡し、次のように依頼してください。

```text
この制約と希望から、実装で守る技術条件を整理して。
```

| 先に伝えるもの | 実装へ委譲できるもの |
| --- | --- |
| 既存インフラ・DB/schema、必須クラウド/外部サービス、公開API、移行・互換性、安全性・法的義務 | 変更しやすいクラス/関数分割、内部モジュール、命名 |
| 保守体制・既存資産・好みなど、言語や主要製品を指定する理由 | 制約や希望がなければ技術の選択も委譲可能 |

**なぜ全技術判断を先に決めないか：** 変更しやすい選択は実装時に具体化できます。先に必要なのは守るべき性質・制約と変更リスクです。

**なぜ詳細設計を独立必須工程にしないか：** 詳細はDDL・SQL・Code / Testと一緒に具体化し、レビューできます。移行や外部契約など変更費用が大きい判断は必要な範囲で先に設計してください。[詳細設計の位置づけ](docs/detailed-design.ja.md)を参照してください。

<a id="5-合意した設計とcheck-itemをaiへ渡す"></a>

### 合意した設計とCheck ItemをAIへ渡す

設計の版、確認済みCheckのID、技術条件、今回の範囲を指定して依頼してください。実際の配置に合わせてパスを置き換えてください。

```text
確認済みの docs/business-design/meeting-room.md と
docs/checks/meeting-room.md、プロダクトの技術要件を読み、
今回合意した範囲のコードと実行可能なテストを作成・更新してください。
既存の開発ルールに従い、確認済みCheckの条件と期待結果を検証してください。
未決の業務判断は人間へ問いとして戻し、独立して進められる作業は続けてください。
重要な前提・判断と理由を、別コンテキストのレビューへ引き継いでください。
```

合意済み範囲のCode / Test、検証結果、重要な判断の根拠を次のレビューへ渡してください。未決の取消期限をTestの期待値にせず、独立した予約処理は進められます。

<a id="6-別コンテキストでレビューし対応を分ける"></a>

### 別コンテキストでレビューし対応を分ける

新しいチャットで設計・実装のファイルを参照できるようにし、版と範囲を指定して次のように依頼してください。

```text
コードをAlderでレビューして
```

Skillは**Business Design → 判断記録 → 実装・DDL・Test**を読み、ファイルを変更せず、根拠・業務への影響・分類・必要な確認を報告します。人間は未決の業務判断だけに答え、別follow-upで意味が変わるなら業務設計書を先に更新・再合意し、Code / Testを合わせます。

**人間が指摘への対応とCheck ↔ Test/assertionの根拠を確認して実装変更の受入れを判断します**。[follow-upと追跡の詳細](docs/check-item-traceability.md)を参照してください。

## 業務改善案を検討する

現在の業務に具体的な困りごとがあるときは、業務改善案を検討できます。設計者は誰がどの仕事で困っているかを依頼者と確かめ、現行の業務設計書にProblemと困り度合い（Pain level）を記録します。

現行の業務設計書とAlderの[改善レビューの手順](docs/optimization-review.md)を、添付するかAIが読める場所に置いて渡し、次のように依頼してください。

```text
渡したAlderの改善レビューの手順（docs/optimization-review.md）に従って、
この業務設計書の困りごとに対する改善案を検討して。
```

AIは候補、比較根拠、採用前に確認すべき事項を整理します。**採用・修正・保留・見送りは依頼者や責任者が判断します**。有用な候補がなければ、無理に案を作る必要はありません。

採用した場合は[業務設計書を更新して再合意](docs/business-design-improvement.ja.md)し、必要に応じて検査項目や実装を合わせます。未採用の案を現在の業務へ反映しないでください。

改善提案に対応したPluginでは、現行の業務設計書と確認済みの困りごとを渡して次のように依頼できます。[提供版と利用範囲](#版とpluginの提供範囲)を確認してください。

```text
Alderで改善提案して
```

## 必要に応じて使う

- **見直す関係を探す：** 確認済みの業務関係から[Structural Discovery](docs/optimization-review.md#optional-structural-discovery-before-a-problem-is-known)で問いを探せます。構造だけからProblemを認定することはできず、専用のStructural Optimization工程はありません。
- **業務を可視化・解析する：** 任意の[Business Graph JSON v1 / CLI](docs/business-graph.md)を使えます。JSONは中間形式で、業務設計書が正本です。未承認の改善候補は投影しません。

## 詳しく読む

### 版とPluginの提供範囲

版・更新・クライアント対応・[導入手順](docs/plugin-adoption.md#install-once)は[Plugin導入ガイド](docs/plugin-adoption.md)を参照してください。上の導入例はPlugin 0.2.8をタグ`plugin-v0.2.8`で固定しています。実クライアントでは業務設計書の作成・レビューとコードレビューの短文routingを確認済みです。安定タグ`plugin-v0.1.0`は実装後レビュー専用で、作成・業務設計書レビューSkillは含みません。Pluginなしの利用は[手動プロンプト](docs/adoption.md)で進められます。

標準配置`docs/business-design/`ではPlugin専用の`AGENTS.md`設定や知識コピーは不要です。別の配置ではパスを伝えてください。手動作成でも文書構造と導入ガイドをAIへ渡してください。

**開発版Plugin 0.3.3は上の導入例で固定した0.2.8の三つの用途に読み取り専用の改善提案を追加しています。** 現行の業務設計書と確認済みのProblem / Pain levelを渡し、[改善提案の依頼例](#業務改善案を検討する)を使えます。0.3.3の実クライアントroutingは未検証です。[版と導入手順](docs/plugin-adoption.md)を確認してください。Check Item作成、Graph出力、follow-upは参照文書とプロンプトでAIへ依頼してください。

現在のmain / PRは未リリース仕様です。標準の設計業務ではCheck Itemの設計と人間レビューが必須で、released v0.6では任意でした。Plugin版、Alder手法の版、レビュー知識v0.3は別です。Alder全体は研究候補であり、効果や検証範囲は[検証記録](docs/validation.md)を参照してください。
