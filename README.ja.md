# Alder

[English](README.md) | 日本語

**ユーザーと業務設計書で話そう**

誰が、いつ、何を受け取り、どんな仕事をして、次へ何を渡すのか。
Alderは、業務の流れをユーザーが読める言葉で整理し、**業務分析・業務改善・実装**につなぐための設計・レビュー手法です。

AIと一緒に業務設計書を作り、ユーザーと確かめる。困りごとがあれば改善案を比べる。システム化するときは、期待する結果を確認して実装へ渡す。そのための文書構造、ガイド、レビュー知識を提供します。

## Alderでできること

| 工程 | Alderを使ってすること | 得られるもの |
| --- | --- | --- |
| 業務分析 | 担当者、手順、情報の受け渡しを整理し、抜けや矛盾をレビューする | ユーザーと合意した業務設計書 |
| 業務改善 | 現場の困りごとから、まとめる・省く・自動化するなどの代替案を検討する | 期待する効果、変更の難しさ、確認事項を添えた改善候補 |
| 実装 | 確認済みの期待結果をAIへ渡し、実装後に別のAIで照合する | 業務設計書・検査項目・テストのつながりと、残る確認事項 |

三つは目的に応じて使う別の工程です。業務分析だけでも使えます。業務改善は困りごとがあるときに行い、システム化が必要になったら実装へ進みます。

どの工程でも、**業務上の意味を決めるのは人間、その合意を残す正本は業務設計書**です。改善候補やコードを根拠に、合意した業務ルールを勝手に変えることはありません。

## インストール・導入

Alderを使うための専用パッケージは不要です。必要なのは、業務設計書とAlderの文書を読めるAIエージェントです。以下ではGitを使い、作業中のプロダクトの隣にAlderを配置します。

プロダクトのルートディレクトリで実行します。

```sh
git clone --depth 1 --branch main https://github.com/mk3008/alder.git ../alder
git -C ../alder rev-parse HEAD
```

2行目に表示されたコミットIDを、利用するAlderの版として記録します。文書は、たとえば次のように配置します。

```text
workspace/
  alder/                         # Alderのガイド・レビュー知識
  product/
    AGENTS.md
    docs/
      business-design/            # 業務設計書
      checks/                    # 実装へ渡す検査項目
      decisions/                 # 重要な判断とその理由
    src/
    tests/
```

`AGENTS.md`またはタスクの指示に、次の参照先を追記します。`<コミットID>`は先ほどの値に置き換えてください。

```text
業務設計書: docs/business-design/
検査項目: docs/checks/
判断記録: docs/decisions/
Alderの参照版: ../alder/ の <コミットID>
業務設計書の書き方: ../alder/docs/business-design-structure.ja.md
各工程の手順: ../alder/docs/adoption.md
業務改善: ../alder/docs/optimization-review.md
実装後のレビュー知識: ../alder/docs/phase2/review-knowledge-v0.3.md

業務上の意味は業務設計書を正本とし、未決事項は人間に確認する。
業務改善の候補は、人間が採用を決めてから業務設計書へ反映する。
実装には、確認済みの業務設計書と人間がレビューした検査項目を渡す。
```

AIがこれらのパスを読めれば準備完了です。既存の文書配置を使う方法や版の選び方は[導入ガイド](docs/adoption.md)を参照してください。

## 業務分析 — 仕事の流れを、ユーザーと確かめる

業務設計書には、**仕事を表すActivity**と、**受け渡す情報や相手を表すObject**を書きます。Activityは5W1Hを基本に、HowをInput・Procedure・Outputに分け、正常終了時に成立する状態をResultに記します。

会議室予約なら、たとえば次のように書けます。以下は一つのActivityの抜粋です。

```markdown
# Activity 会議室を予約する

## Scope
true

## Why
会議に必要な時間帯の会議室を確保するため。

## When
利用者から予約希望を受け付けたとき。

## Who
予約受付担当者

## Where
規定なし

## How

### Input
- 利用者 — 対象会議室 / 利用開始・終了日時 / 利用目的 / 予約者
- 会議室台帳 — 会議室の利用可否
- 予約台帳 — 既存予約の時間帯と状態

### Procedure
1. 会議室が利用可能で、利用開始が受付時点より後、終了が開始より後であることを確認する。
2. 同じ会議室の有効な予約と時間帯が重ならないことを確認する。同時の申込みでも重複予約を成立させない。
3. 予約内容と登録日時を予約台帳に記録し、利用者へ予約結果を伝える。

### Output
- 予約台帳 — 登録された予約内容 / 登録日時
- 利用者 — 予約結果

## Result
利用者が指定した会議室と時間帯の予約が成立し、その予定で会議の準備を進められる。
```

「同時に申し込まれても重複予約が成立しないか」「予約できなかった場合は何が残るか」。こうした問いを、AIのレビューで具体化してユーザーと確認します。ヒアリング内容だけでなく、前後の業務のつながりも読み合わせ、合意した内容と未決事項を区別します。

AIへの最初の依頼は、たとえば次の形です。

```text
../alder/docs/business-design-structure.ja.md と ../alder/docs/adoption.md に従い、
次のヒアリング内容から docs/business-design/meeting-room.md に草案を作ってください。
本文はユーザーがレビューできる日本語にし、未決の業務ルールは確認事項として残してください。
草案を提示する前に、手順と情報の受け渡し、前後の業務のつながりを確認してください。

目的: 社内の会議室を予約できるようにしたい。
対象: 空き確認、予約、変更、取消、利用不可・利用再開の管理。
確認したルール: 重複予約は成立させない。変更できない場合は元の予約を維持する。
```

Objectや例外を含む[コピーして使える予約受付の記述例](docs/examples/meeting-room-reservation.ja.md)と、各欄の意味・見出しの順序を説明する[業務設計書の文書構造](docs/business-design-structure.ja.md)を用意しています。

## 業務改善 — 困りごとから、別のやり方を探す

今の業務は成立していても、作業の負担や待ち時間が大きいことがあります。困りごとがある場合は、ユーザーと内容を確認し、該当ActivityのResultの後に`Problem`と`Pain level`を記録します。全業務に埋める必要はありません。

たとえば、購買担当者から「承認済みの申請ごとに購入と結果登録を繰り返す負担が大きい」と確認できた場合です。

```markdown
## Problem
承認済みの購入申請が増えると、購買担当者が申請ごとに購入し、結果を登録する負担が大きい。

## Pain level
High
```

この記録をもとに、AIへ業務改善レビュー（Optimization Review）を依頼します。

```text
../alder/docs/optimization-review.md に従い、業務改善レビューをしてください。
対象: docs/business-design/purchase-request.md の合意済みの版。
同書に記録した購買作業のProblem / Pain levelを起点にしてください。
期待する効果、業務変更の難しさ、守るべき条件、採用前の確認事項を示してください。
候補は最大3件とし、採否は決めず、ファイルは変更しないでください。
```

購買の例では、次のような候補を比較できます。

| 改善候補 | 期待できる効果 | 採用前に確かめること |
| --- | --- | --- |
| 条件の合う申請をまとめて購入する | 購入操作や確認の繰り返しを減らす | まとめてよい条件、待機できる期間、申請ごとの実購入金額の記録方法 |
| 定型的な申請の購入と結果取得を自動化する | 個別の購入操作と結果転記を減らす | 自動購入の権限、結果を取得できるか、失敗時の責任者 |
| 購入事務を外部の購買サービスに委ねる | 自社で行う手配作業を減らす | 利用可能なサービス、契約・費用、申請ごとの結果照合 |

これは[購買改善の提案例](work/optimization-review/issue-81/outputs/raw.md)の要約です。効果や実現性は現場の条件によって変わります。承認権限や「実際に購入したものだけを購入済みにする」という意味を保ちながら、変更範囲と関係者の調整の難しさも検討します。

採否を決めるのは人間です。採用する場合は、**業務設計書を先に更新・再合意**してから、必要な検査項目や実装へ反映します。有益な候補がなければ、現状を維持できます。

## 実装 — 合意した期待結果を、コードとテストへつなぐ

業務設計書の合意後、AIが検査項目（Check Item）の草案を作り、人間が期待結果を確認します。会議室予約なら、次のような一覧になります。

| ID | タイトル | 期待結果 | レビュー状態 |
| --- | --- | --- | --- |
| MR-001 | 同じ会議室で重複予約が成立しない | 同時に申し込まれても、同じ会議室・重なる時間帯の予約が複数成立しない。 | 未レビュー |
| MR-002 | 変更できなくても元の予約が残る | 予約変更の条件を満たさない場合、元の予約内容が維持される。 | 未レビュー |

これは予約・変更業務を含む設計から作る一覧の一部です。AIの草案は、人間が確認するまで「未レビュー」です。修正と確認を繰り返し、合意した業務設計書と検査項目を、版とIDが分かる形で実装へ渡します。ここまでで標準の設計業務が完了します。

```text
確認済みの docs/business-design/meeting-room.md と
docs/checks/meeting-room.md を読み、今回合意した範囲を実装してください。
プロダクトの技術要件と既存の開発ルールに従い、コードとテストを作成・更新してください。
テストの期待結果は、確認済みの検査項目と業務設計書を根拠にしてください。
未決の業務ルールは具体的な問いとして人間に戻し、重要な前提・判断と理由をレビューへ引き継いでください。
```

実装・テスト実行の後は、別のAIエージェントや新しいセッションで、業務設計書・判断記録・実装・テストを照合するAlderレビューを行います。読み取り専用のレビューの後、フォローアップで検査項目とテストの対応、検証根拠の不足を確認・保守します。

検査項目の作成からレビューまでのプロンプトは[導入ガイド](docs/adoption.md)、粒度やレビュー状態は[検査項目の作成・保守](docs/check-item-traceability.md)を参照してください。
