## 要件解釈と未規定事項

| 論点 | 扱いと理由 |
| --- | --- |
| 状態遷移 | submitted→approved/rejected、approved→purchasedのみ。再承認・再購入・却下後の復活・編集は現在の業務にないため操作を設けない。 |
| 識別子 | SQLiteの自動採番整数。入力方法は未指定なので操作者の採番負担をなくす。 |
| 金額 | 希望・実購入とも申請全体の金額と解釈。非負の十進文字列を保持し、浮動小数点丸めを避ける。通貨、税、桁数上限、端数処理は保留し、円や小数2桁を強制しない。同一業務内の金額は同じ単位で入力する運用を仮定。集計・換算は行わない。ゼロを許容し、負額は購入額の入力として拒否する。 |
| 数量 | 備品個数として正の整数を仮定。SQLite整数上限を超える値を拒否。分量・単位換算は導入しない。 |
| 必須文字列 | 未指定・空白のみを拒否し、前後の空白を除去して保持する。 |
| 実購入額と希望額 | 上限・一致条件がないため超過も許容する。追加承認の要否は定義せず、勝手に承認段階を増やさない。 |
| 日時 | 入力項目に日時がないため、各業務の登録時刻をUTCで自動記録。購入日時は結果登録時刻とする実装上の仮定。実購入時刻の事後指定は提供しない。 |
| ロール | 操作者がCLIに申告するコンテキストに対して操作を制限する。認証はローカル検証の範囲外。申請者名は入力パラメータではなくactorから記録。兼務・自己承認禁止は規定されないため追加しない。 |
| 一覧・参照 | 業務手順の「確認・選択」を成立させるために追加。申請者の他者申請参照は不要なので制限。承認者・購買担当者は状態を問わずID指定で結果を確認可能。 |
| 明示された未決定事項 | 多段承認、在庫、発注、納品、検収、支払、購入先、資産管理、外部連携、監査履歴、通知は保留。業務意味の確定や実装を行わない。 |

以上の仮定で現在の4業務を実行可能と判断した。人間の判断がないと処理を成立させられない矛盾は見つからなかった。金額の単位、数量の単位、購入日時の意味を実運用で拡張する場合は要件確認が必要。

## Data Model / DDL

購入申請が承認・却下・購入を通じて同じ対象なので、単一のpurchase_requestテーブルに申請内容と結果を保持する。ロールマスター、商品マスター、イベント履歴は現在の要件にないため作らない。主キーはid。状態別の日時・理由・金額のNULL条件をCHECKで表現し、矛盾したスナップショットを拒否する。STRICTで数量などの型を制約する。金額の十進形式と業務遷移はアプリケーションで検証する。DDLだけで過去の遷移履歴や金額の書式まで保証する設計ではない。

今回の実装中にスキーマの意味変更はなかった。初期化はCREATE TABLE IF NOT EXISTSのみ。既存の異なるスキーマを自動移行する機能はない。将来変更時には移行方針を別途記録する。

## 構造と整合性

Python標準ライブラリを選び、パッケージ取得なしでSQLiteとCLIを検証可能にした。app.pyに業務サービスと引数・JSON変換、schema.sqlにDDLを分離。4操作は業務名に対応し、共通の永続化対象にアクセスする。

更新はBEGIN IMMEDIATEで書込みロック取得後に状態を読み、検証・更新・結果取得を同一トランザクションで行う。競合する承認・却下は片方だけ成立し、後続は変更後の状態を見て拒否される。不正入力・状態違反はロールバックする。SQLiteのタイムアウトもエラーとして返す。SQL値は全てバインドし、利用者入力でSQLを構築しない。スナップショットのCHECKはアプリ不具合に対する追加防御であり、DBへの直接書込みはサポートする業務入口ではない。

- 独立SQLite接続で競合する承認・却下の片方のみ成功。
- DDLによる状態と記録項目の矛盾拒否。
