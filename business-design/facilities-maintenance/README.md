# 設備保全 — 業務設計

この文書は、設備保全で必要となる業務を記述する。

業務設計者の書き漏らしや読み手との認識齟齬を減らすため、各業務を5W1Hを基礎にした共通形式で記載する。ここで記述するのは業務上の意味・前提・入力・手順・結果であり、入力値の文字列表現、画面部品、API、クラス、モジュール、データアクセス方法などの実装方式は規定しない。

各業務は次の観点を必ず記載する。

- **What / なにを** — 業務名と、何を成立させる業務か
- **Why / なぜ** — その業務を行う目的
- **When / いつ** — 業務の開始契機、先行業務との関係、成立に必要な業務状態
- **Who / だれが** — 業務を行うロール
- **Where / どこで** — 場所・チャネルに業務上の意味がある場合の制約。規定がなければ「規定なし」
- **How / どうやって** — 業務で受け取るInput、業務手順、成立するOutput

Inputでは、業務担当者がその業務を行うために与える・選択する情報を記載し、必須・任意を明示する。識別子の採番方法、認証情報、空欄や文字種の判定方法など、業務担当者の入力ではない技術上の詳細はInputに含めない。

## 業務上のロール

- **現場報告者** — 設備故障を報告する。
- **保守調整担当者** — 保守作業の日程を設定する。
- **技術者** — 予定された保守作業を実施し、完了を記録する。
- **安全検査担当者** — 安全検査の結果に基づいて設備の安全閉鎖を記録・解除する。

ロールは業務上の責任と権限を表す。本番環境で誰をそのロールとして認証・認可するかは、この業務設計では規定しない。

## 業務で扱う情報

### 設備

各設備は識別可能であり、少なくとも次の業務状態を持つ。

- `available` — 通常の保守日程を設定できる状態
- `safety_closed` — 安全上の理由で保守日程を新たに設定できない状態

### 保守依頼

保守依頼は、報告された設備故障を後続の保守業務で扱うための記録である。

少なくとも次の情報を持つ。

- 対象設備
- 報告者
- 報告日時
- 症状
- 状態: `open` / `scheduled` / `completed`
- 日程設定後の予定日時
- 完了後の完了日時

保守依頼は一意に識別できるものとする。識別子の採番・入力方法はこの業務設計では規定しない。

---

## 業務1 — 故障報告を登録する

### What / なにを

設備故障の報告を、保守依頼として登録する。

### Why / なぜ

発見された設備故障を保守対象として記録し、保守調整担当者が後続の保守業務で扱える状態にするため。

### When / いつ

設備故障の報告を受けたとき。

前提として、対象設備は既に識別可能な設備として登録されているものとする。同じ設備について既存の保守依頼が存在していても、新しい故障報告を受け付けることができる。重複とみなす条件や重複排除の業務ルールは定めない。

### Who / だれが

現場報告者。

### Where / どこで

規定なし。

### How / どうやって

#### Input

次の項目を入力する。**すべて必須**とする。

- 対象設備
- 報告日時
- 報告者
- 症状

#### 業務手順

1. 現場報告者が、受けた故障報告の内容を入力する。
2. その内容を新しい保守依頼として登録する。
3. 新しい保守依頼を `open` として扱う。

#### Output

- 故障内容が `open` の保守依頼として記録される。
- 入力した対象設備、報告日時、報告者、症状が保守依頼に保持される。
- 保守調整担当者が、後続の「保守日程を設定する」業務の対象として扱える状態になる。

---

## 業務2 — 保守日程を設定する

### What / なにを

未着手の保守依頼について、保守作業の予定日時を決める。

### Why / なぜ

`open` の保守依頼を、技術者が作業を実施できる予定済みの状態に進めるため。

### When / いつ

`open` の保守依頼について、保守作業の日程を決めるとき。

次の業務条件を満たしていることを前提とする。

- 対象保守依頼が `open` である。
- 対象設備が `safety_closed` ではない。
- 予定日時は、日程を設定する時点より未来である。

`completed` の保守依頼はこの業務の対象にならない。

### Who / だれが

保守調整担当者。

現場報告者であることだけでは、この業務を行う権限にはならない。

### Where / どこで

規定なし。

### How / どうやって

#### Input

次の項目を入力・選択する。**すべて必須**とする。

- 対象保守依頼
- 予定日時

#### 業務手順

1. 保守調整担当者が、日程設定の対象となる `open` の保守依頼を選択する。
2. 保守作業の予定日時を決める。
3. 予定日時を保守依頼に記録し、依頼を `scheduled` とする。

#### Output

- 対象保守依頼が `scheduled` になる。
- 決定した予定日時が記録される。
- 技術者が後続の「保守作業を完了する」業務の対象として扱える状態になる。

対象設備が `safety_closed` であるなど、Whenに記載した業務条件を満たさない場合は、この業務は成立せず、保守依頼の状態は変わらない。

---

## 業務3 — 保守作業を完了する

### What / なにを

予定されていた保守作業の完了を記録する。

### Why / なぜ

保守作業が完了したという事実を残し、その保守依頼を完了済みとして扱えるようにするため。

### When / いつ

`scheduled` の保守依頼について、技術者が保守作業を完了したとき。

`open` の保守依頼は、この業務の対象にならない。

### Who / だれが

技術者。

現場報告者であることだけでは、この業務を行う権限にはならない。

### Where / どこで

規定なし。

### How / どうやって

#### Input

次の項目を選択する。**必須**とする。

- 完了した対象保守依頼

完了日時は技術者が入力する項目ではない。成功した完了操作に対応する信頼できる時刻を、この業務における完了日時として記録する。

#### 業務手順

1. 技術者が、完了した `scheduled` の保守依頼を選択する。
2. 保守作業の完了を記録する。
3. 保守依頼を `completed` とし、完了日時を記録する。
4. 既に記録されている予定日時は保持する。

予定日時は計画であり、実際の完了日時の下限ではない。予定日時より前に作業が完了してもよい。ただし、業務上の完了日時が故障の報告日時より前になることはない。

#### Output

- 対象保守依頼が `completed` になる。
- 予定日時が保持される。
- 完了日時が記録される。

オフラインで行った作業を後から完了として登録する場合や、外部システムから完了を受け取る場合の業務は、この設計では定めない。

---

## 業務4 — 安全閉鎖を登録する

### What / なにを

安全検査で危険と判断された設備を、安全閉鎖状態として登録する。

### Why / なぜ

安全上使用できない設備について、新しい保守日程が設定されない状態を成立させるため。

### When / いつ

安全検査の結果、設備が危険であり安全閉鎖が必要と判断されたとき。

この業務は保守依頼の進行とは別に発生する。対象設備に `open` の保守依頼が存在する場合、その保守依頼との関係にも影響する。

### Who / だれが

安全検査担当者。

### Where / どこで

規定なし。

### How / どうやって

#### Input

次の項目を選択する。**必須**とする。

- 安全閉鎖する対象設備

#### 業務手順

1. 安全検査担当者が、安全検査の結果に基づいて対象設備を選択する。
2. 対象設備を `safety_closed` として登録する。
3. 対象設備に既存の `open` な保守依頼があっても、その依頼自体は変更しない。

#### Output

- 対象設備が `safety_closed` になる。
- 既存の `open` な保守依頼は `open` のまま残る。
- `safety_closed` の間、その設備の `open` な保守依頼について「保守日程を設定する」業務は成立しない。
- 既に `completed` となっている保守依頼は変更されない。

未解決の故障と設備の安全状態は別の業務上の事実として扱う。

---

## 業務5 — 安全閉鎖を解除する

### What / なにを

安全閉鎖されている設備について、安全閉鎖を解除する。

### Why / なぜ

後の安全検査で利用可能と判断された設備を通常状態へ戻し、通常の保守日程設定を再び可能にするため。

### When / いつ

後の安全検査の結果、安全閉鎖を解除できると判断されたとき。

対象設備が `safety_closed` であることを前提とする。

### Who / だれが

安全検査担当者。

### Where / どこで

規定なし。

### How / どうやって

#### Input

次の項目を選択する。**必須**とする。

- 安全閉鎖を解除する対象設備

#### 業務手順

1. 安全検査担当者が、後の安全検査の結果に基づいて対象設備を選択する。
2. 対象設備の安全閉鎖を解除し、`available` とする。
3. 既存の `open` な保守依頼そのものには変更を加えない。

#### Output

- 対象設備が `available` になる。
- 既存の `open` な保守依頼はそのまま残る。
- 保守調整担当者は、通常の業務条件を満たせば、その `open` な依頼について再び「保守日程を設定する」業務を行える。

安全閉鎖の解除そのものが保守日程を設定するわけではない。

---

## 業務相関

現在定義している主な業務相関は次のとおりである。

1. 故障報告を登録すると、`open` の保守依頼が成立する。
2. `open` の保守依頼に日程を設定すると、`scheduled` になる。
3. `scheduled` の保守作業を完了すると、`completed` になる。
4. 安全検査で設備を閉鎖すると設備は `safety_closed` になり、既存の `open` な保守依頼は残るが日程設定できなくなる。
5. 後の安全検査で閉鎖を解除すると設備は `available` になり、既存の `open` な保守依頼は通常条件のもとで再び日程設定の対象となる。

## 現在の業務設計で未決定の事項

次の事項は現在の業務設計では定めない。

- 既に `scheduled` の保守依頼が存在する設備を `safety_closed` にした場合の扱い
- 既に `safety_closed` の設備について新しい故障報告を受けた場合の扱い
- 安全閉鎖や安全閉鎖解除を繰り返した場合の扱い
- 存在しない設備について安全閉鎖または解除を行う場合の扱い
- 監査履歴や通知に関する業務
- オフラインまたは外部から報告される保守完了

これらは、現在の業務設計を実装するために決定済みであるとはみなさない。
