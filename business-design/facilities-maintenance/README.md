# 設備保全 — 業務設計

この文書は、設備保全アプリケーションで必要となる業務上の振る舞いを記述する。

実装方式やアーキテクチャを指定する文書ではない。各業務は、第三者が業務の開始条件・実行者・入出力・前後関係を追えるよう、次の観点で記述する。

- **業務名（What）** — 何という業務か
- **実行者（Who）** — 誰がその業務を行う権限を持つか
- **実行契機・前提（When）** — 何が起きたとき実行可能になるか。前の業務や現在の状態との関係を含む
- **目的（Why）** — その業務で何を成立させたいか
- **Input** — 業務を実行するために与えられる情報
- **手順（How）** — 業務上必要な処理の流れ。技術的な実装手順は規定しない
- **Output・事後条件** — 成功後にどの業務上の事実・状態が成立するか

`Where`に相当する場所の制約は、現在の業務要件では定義しない。

## 業務上の役割

- **現場報告者** — 観測した設備故障を報告する。
- **保守調整担当者** — 保守作業の日程を設定する。
- **技術者** — 予定された保守作業を完了する。
- **安全検査担当者** — 設備の安全閉鎖を記録し、後に解除する。

ここでの役割名は、以下の業務を実行するために必要な業務上の権限を表す。この設計では、本番環境の本人確認や権限管理の仕組みまでは定義しない。

## 業務データ

### 設備

各設備は識別子を持ち、状態は次のいずれかである。

- `available`
- `safety_closed`

### 保守依頼

保守依頼には次の情報を記録する。

- 依頼の識別子
- 設備の識別子
- 報告者の識別子
- 観測・報告時刻
- 説明
- ライフサイクル状態: `open`、`scheduled`、`completed`
- 日程設定済みの場合は予定時刻
- 完了済みの場合は完了時刻

保守依頼は、存在する設備を参照する。

---

## 業務1: 設備故障を報告する

### 業務名（What）

設備故障の報告。

### 実行者（Who）

現場報告者。

### 実行契機・前提（When）

- 設備の故障が現場で観測されたとき。
- 対象となる設備が既に存在していること。
- この業務は、後続の日程設定・完了・安全閉鎖より前に単独で発生できる。
- 同じ設備に既存の保守依頼があっても、新しい故障報告を行える。重複排除の方針は定義しない。

### 目的（Why）

観測された設備故障を、後続の保守業務で扱える未完了の保守依頼として記録する。

### Input

- 新しい保守依頼の識別子
- 対象設備の識別子
- 報告者の識別子
- 故障を観測・報告した時刻
- 故障の説明

### 手順（How）

1. 対象設備が存在することを確認する。
2. 説明が空文字列または空白文字だけではないことを確認する。
3. 入力された設備、報告者、観測・報告時刻、説明を保守依頼として記録する。
4. 新しい保守依頼を `open` とする。

有効な空白以外を含む説明は入力された内容のまま保持し、先頭や末尾の空白だけを理由に書き換えない。

### Output・事後条件

- 成功時、新しい保守依頼が1件存在する。
- その依頼は入力された設備・報告者・時刻・説明を保持する。
- 依頼状態は `open` である。
- 対象設備が存在しない、または説明が無効な場合は報告を受け付けず、新しい保守依頼を成立させない。

---

## 業務2: 保守の日程を設定する

### 業務名（What）

保守日程の設定。

### 実行者（Who）

権限を持つ保守調整担当者。

報告者であることだけでは、保守調整担当者としての権限にはならない。

### 実行契機・前提（When）

- 業務1によって `open` の保守依頼が存在し、保守作業の日程を決めるとき。
- 対象依頼が `open` であること。
- 対象設備が現在 `safety_closed` ではないこと。
- 指定する予定時刻が、日程設定操作を行う時点より未来であること。

`completed` の依頼を再度日程設定することはできない。

### 目的（Why）

未完了の保守依頼について、実施予定を確定し、後続の保守完了業務へ進める状態にする。

### Input

- 日程設定を行う者の識別・権限情報
- 対象保守依頼の識別子
- 予定時刻

### 手順（How）

1. 実行者が保守調整担当者として日程設定を行う権限を持つことを確認する。
2. 対象保守依頼が `open` であることを確認する。
3. 対象設備が現在 `safety_closed` ではないことを確認する。
4. 予定時刻が日程設定時点より未来であることを確認する。
5. 予定時刻を記録し、依頼を `scheduled` にする。

### Output・事後条件

- 成功時、対象依頼は `scheduled` になる。
- 指定した予定時刻が保守依頼に記録される。
- 上記前提のいずれかを満たさない場合、日程設定は成立せず、保守依頼の業務上の状態を変更しない。

---

## 業務3: 保守作業を完了する

### 業務名（What）

保守作業の完了。

### 実行者（Who）

権限を持つ技術者。

報告者であることだけでは、技術者としての権限にはならない。

### 実行契機・前提（When）

- 業務2によって保守依頼が `scheduled` となった後、技術者がその保守作業を完了したとき。
- 対象依頼が `scheduled` であること。
- `open` の依頼は直接完了できない。

### 目的（Why）

予定されていた保守作業が完了したという業務上の事実を記録し、依頼を完了状態にする。

### Input

- 完了操作を行う者の識別・権限情報
- 対象保守依頼の識別子

呼び出し元や技術者が指定する完了時刻は正とはしない。

### 手順（How）

1. 実行者が技術者として完了操作を行う権限を持つことを確認する。
2. 対象保守依頼が `scheduled` であることを確認する。
3. 成功した完了操作に対応する信頼できるシステム時刻を取得する。
4. その完了時刻が依頼の報告時刻より前でないことを確認する。
5. 予定時刻を保持したまま、完了時刻を記録し、依頼を `completed` にする。

`scheduled_for` は計画であり、実際の作業完了時刻の下限ではない。予定時刻より前に完了することを許可する。

### Output・事後条件

- 成功時、対象依頼は `completed` になる。
- 既存の予定時刻は保持される。
- 成功した完了操作に対応する信頼できるシステム時刻が完了時刻として記録される。
- 完了時刻が報告時刻より前になる場合は完了を拒否し、依頼を変更しない。

ここで記録する時刻は、このアプリケーションにおける業務上の完了事実を表す。アプリケーションが物理的な作業完了を自動検出することまでは想定しない。オフラインでの完了や、後から報告される完了はこの設計では定義しない。

---

## 業務4: 安全閉鎖を記録する

### 業務名（What）

設備の安全閉鎖。

### 実行者（Who）

権限を持つ安全検査担当者。

### 実行契機・前提（When）

- 安全検査の結果、設備が危険であると判断されたとき。
- 対象設備が存在すること。
- この業務は保守依頼のライフサイクルとは独立して発生し得るが、対象設備を通じて業務1〜3へ影響する。

### 目的（Why）

危険と判断された設備について、新たな保守日程を設定できない状態を成立させる。

### Input

- 安全閉鎖を記録する者の識別・権限情報
- 対象設備の識別子

### 手順（How）

1. 実行者が安全検査担当者として安全閉鎖を記録する権限を持つことを確認する。
2. 対象設備を `safety_closed` にする。
3. その設備に既存の `open` な保守依頼があっても、その依頼自体は変更しない。

### Output・事後条件

- 対象設備は `safety_closed` になる。
- 既存の `open` な保守依頼は `open` のまま保持される。
- 設備が `safety_closed` の間、その `open` な依頼に対する業務2の日程設定は成立しない。
- 既に `completed` となっている保守依頼は遡って変更しない。

未解決の保守依頼と設備の安全状態は別の業務上の事実である。故障が未解決のままでも、設備の安全状態によって現在の日程設定可否が決まる場合がある。

---

## 業務5: 安全閉鎖を解除する

### 業務名（What）

設備の安全閉鎖解除。

### 実行者（Who）

権限を持つ安全検査担当者。

### 実行契機・前提（When）

- 業務4によって設備が `safety_closed` となった後、後続の安全検査で安全閉鎖を解除できると判断されたとき。
- 対象設備が `safety_closed` であること。

### 目的（Why）

設備を再び利用可能な状態に戻し、既存の保守依頼について通常の日程設定条件を再び適用できるようにする。

### Input

- 安全閉鎖解除を行う者の識別・権限情報
- 対象設備の識別子

### 手順（How）

1. 実行者が安全検査担当者として安全閉鎖を解除する権限を持つことを確認する。
2. 対象設備を `available` にする。
3. 既存の `open` な保守依頼には、解除操作そのものによる変更を加えない。

### Output・事後条件

- 対象設備は `available` になる。
- 既存の `open` な保守依頼はそのまま保持される。
- 権限を持つ保守調整担当者は、業務2の通常の日程設定ルールを満たせば、その依頼へ再び日程を設定できる。
- 安全閉鎖の解除そのものでは、保守依頼の日程設定やその他の状態変更は行わない。

---

## 業務相関の要約

現在の業務設計で確定している主な相関は次のとおりである。

1. **設備故障の観測**を契機に、業務1で `open` の保守依頼が成立する。
2. `open` の依頼は、設備が日程設定可能な状態であれば、業務2によって `scheduled` になる。
3. `scheduled` の依頼は、技術者が作業を完了すると、業務3によって `completed` になる。
4. **安全検査で危険と判断されること**を契機に業務4が発生し、設備は `safety_closed` になる。既存の `open` 依頼は残るが、業務2は成立しなくなる。
5. **後続の安全検査で解除可能と判断されること**を契機に業務5が発生し、設備は `available` に戻る。保持されていた `open` 依頼には、再び業務2を適用できる。

この相関は業務上の前後関係と状態条件を示すものであり、実装上の呼び出し順序、モジュール境界、トランザクション境界、アーキテクチャを指定するものではない。

## この設計で未決定の業務上の振る舞い

現在の設計では、次の事項について追加の方針を定義していない。

- すでに `scheduled` の依頼がある設備を `safety_closed` にした場合の扱い
- すでに `safety_closed` の設備について新しい故障を報告する場合の扱い
- 安全閉鎖や解除を繰り返した場合の扱い
- 存在しない設備に対して安全閉鎖の解除を行う場合の扱い
- 監査履歴や通知
- オフラインまたは外部から報告される完了

これらは、現在の業務設計で要求する振る舞いには含めない。
