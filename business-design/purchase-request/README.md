# 備品購入申請 — 業務設計

草案（採用した改善方針を反映した変更後の業務案。全体の人間レビュー・合意前）。

社内で使用する備品の購入申請から購入完了までに必要となる業務を記述する。

業務上の意味・前提・入力・手順・結果を記述し、画面部品、API、クラス、モジュール、データアクセス方法などの実装方式は規定しない。

## 業務上のロール

- **申請者** — 業務に必要な備品の購入を申請する。
- **承認者** — 申請内容を確認し、購入を承認または却下する。
- **購買担当者** — 承認済みの申請に基づいて購入を行い、購入結果を登録する。
- **総務** — 別システムで使用される権限マスタを管理する。
- **人事** — 別システムで使用される従業員マスタを保守する。

ロールは業務上の責任と権限を表す。

## 購入申請の扱い

購入申請は、申請者が業務上必要とする備品の購入要求を、承認および購買の対象として扱うための記録である。

購入申請は、後述のObject 購入申請のInformationに挙げる情報を少なくとも持つ。

購入申請は一意に識別できるものとする。識別子の採番・入力方法はこの業務設計では規定しない。

## 業務相関

現在定義している主な業務相関は次のとおりである。

1. 申請内容が権限マスタに適合すると自動判定できた場合に、`submitted` の購入申請が成立する。不適合または判定不能の場合は申請を成立させない。
2. `submitted` の購入申請を受けて承認業務を開始し、その業務中に承認者が可否を判断する。正常に承認すると、`approved` になる。
3. 承認業務中に購入を認めないと判断した場合は、例外として拒否（却下）し、`rejected` になる。
4. `approved` の購入申請に基づいて購入すると、`purchased` になる。
5. `rejected` の購入申請は購買対象にならない。

## 現在の業務設計で未決定の事項

次の事項は現在の業務設計では定めない。

- 申請金額によって承認者や承認段階が変わる場合の扱い
- 在庫確認、発注、納品、検収、支払に関する業務
- 購入先の選定方法
- 購入後の備品管理、資産管理、廃棄
- 権限マスタ・従業員マスタの参照以外の外部システム連携
- 監査履歴や通知に関する業務
- 役職別上限額の具体的な値、申請者と従業員マスタの照合に使う識別情報、別システムのマスタを参照する際の運用条件
- 一括却下の採用（今回の改善では採用していない）

これらは、現在の業務設計を実装するために決定済みであるとはみなさない。

## 確認が必要な事項（未確認）

購入と結果登録の範囲、申請者と従業員マスタの照合方法は、末尾のFindings F02・F03に未解決の確認事項を記載する。承認と拒否の業務境界はF01に解消内容を記録する。

- **購入できない場合・結果登録できない場合**：購入できない場合や、購入後に結果登録できない場合の扱いは未確認である。
- **入力不足・状態が変わった場合**：権限マスタへの適合を判定できない情報不足は申請不可とする。それ以外の必須入力不足時の具体的な扱い、数量・金額の有効範囲は定めていない。承認業務の対象は `submitted`、購入の対象は `approved` としているが、選択後に対象が別の状態になった場合や、再実行時の結果は定めていない。

権限マスタに不適合または判定不能の場合の申請不成立と、承認業務中の拒否は後述のとおりとする。それ以外の未記載の操作結果や、再承認・取消などの扱いは未決である。

## 参照するマスタ

- **権限マスタ** — 別システムで使用されるデータベース。総務が管理し、役職ごとに決裁単位の上限額を定める。決裁単位は購入申請1件であり、申請者の役職に対応する上限額を用いる。
- **従業員マスタ** — 別システムで使用されるデータベース。人事が保守し、従業員の識別情報と役職を持つ。

両マスタのデータベースを再利用する。今回の業務はその情報を参照して判定し、マスタの保守は扱わない。具体的な上限額、申請者を従業員マスタと対応させる識別情報、参照時の運用条件は未確認である。

# Scope

社内の備品購入について、権限マスタに基づく申請可否の自動判定、申請、承認業務中の承認・拒否、購入と購入結果の登録を扱う。購入申請はこの業務で成立・更新する記録である。申請者・承認者・購買担当者のObjectは、各業務で情報を入力・選択する人を表し、人自体を成立・管理する業務は扱わない。権限マスタと従業員マスタは別システムのデータベースを再利用するスコープ外のObjectであり、その保守は今回の業務に含めない。前述の対象外業務や未採用の一括却下は含めず、未確認の条件を決定済みとはみなさない。

# Activity 備品購入を申請する

## Scope

true

## Why

購入の必要性と希望内容を記録し、承認者が購入可否を判断できる状態にするため。

## When

申請者が、業務上必要な備品を購入したいと判断したとき。

## Who

申請者

## Where

規定なし。

## How

### Input

- 申請者 — 品名 / 数量 / 希望購入金額 / 購入理由（すべて必須）
- 権限マスタ — 役職ごとの決裁単位の上限額
- 従業員マスタ — 従業員の識別情報 / 役職

### Procedure

業務に必要な備品の購入要求を、購入申請として登録する。

1. 申請者が購入したい備品の品名と購入理由を入力する。
2. 数量と希望購入金額を入力する。
3. 申請者に対応する従業員マスタの情報から、申請者の役職を確認する。
4. 購入申請1件の希望購入金額が、その役職に対応する権限マスタの上限額以下であるか、自動判定する。
5. 適合すると判定できた申請を、新しい購入申請として登録する。
6. 登録した申請を `submitted` として扱う。

### Exception

権限マスタに適合しない場合、または規定の矛盾・必要情報の不足などで適合すると判定できない場合は、申請を成立させず、`submitted` の購入申請を作成しない。この申請不成立を、提出済み申請の `rejected` への変更とは扱わない。

### Output

- 購入申請 — 申請者 / 品名 / 数量 / 希望購入金額 / 購入理由 / 申請日時 / `submitted` の状態

## Result

- 権限マスタへの適合を自動判定で確認した購入要求が、`submitted` の購入申請として記録される。
- 申請者、品名、数量、希望購入金額、購入理由、申請日時が保持される。
- 承認者が購入可否を判断できる状態になる。

# Activity 購入申請を承認する

## Scope

true

## Why

申請内容が妥当であることを確認し、購買担当者が購入を進められる状態にするため。

## When

購入申請が `submitted` として提出されたとき。

## Who

承認者

## Where

規定なし。

## How

### Input

- 承認者 — 承認可否を判断する対象購入申請の選択（必須） / 拒否する場合の却下理由（必須）
- 購入申請 — 対象購入申請の内容と `submitted` の状態

### Procedure

提出された購入申請の購入可否は、承認者が業務中に人間として判断し、その責任を負う。以下は承認する場合の正常手順である。

1. 承認者が、対象となる `submitted` の購入申請を選択し、その内容を確認する。
2. 購入してよいと判断する。
3. 対象の購入申請を `approved` とする。
4. 承認日時を記録する。

### Exception

承認者が業務中に購入を認めないと判断した場合は、例外として拒否（却下）する。承認者が却下理由を記録し、対象購入申請を `rejected` として、却下日時を記録する。この場合は正常な承認結果を成立させず、購買対象にしない。

### Output

- 購入申請 — 承認の結果（`approved` の状態 / 承認日時）、または拒否の結果（`rejected` の状態 / 却下理由 / 却下日時）

## Result

- 対象購入申請が `approved` になる。
- 承認日時が記録される。
- 購買担当者が購入対象として扱える状態になる。

# Activity 承認済み備品を購入する

## Scope

true

## Why

承認された購入要求を実際の購入として完了させ、購入済みであることを記録するため。

## When

`approved` の購入申請について、購買担当者が対象備品を購入するとき。

## Who

購買担当者

## Where

規定なし。

## How

### Input

- 購買担当者 — 購入した対象購入申請の選択 / 実購入金額（すべて必須）
- 購入申請 — 対象購入申請の内容と `approved` の状態

### Procedure

承認済みの購入申請に基づいて備品を購入し、その結果を登録する。

1. 購買担当者が `approved` の購入申請を確認する。
2. 対象備品を購入する。
3. 購入した対象購入申請を選択し、実購入金額を記録する。
4. 対象購入申請を `purchased` とする。
5. 購入日時を記録する。

### Output

- 購入申請 — `purchased` の状態 / 実購入金額 / 購入日時

## Result

- 対象購入申請が `purchased` になる。
- 実購入金額と購入日時が記録される。
- 対象申請が購入済みとして扱える状態になる。

# Findings

## Finding F01

### Kind

### Status

resolved

### Scope

items

### Targets

- 購入申請を承認する

### Summary

承認・拒否の判断を業務中へ移し、承認業務の入口へ統合した

### Content

旧版では承認・却下のWhenが可否判断後である一方、Procedureは内容確認から始まり、開始条件と判断の範囲が整合していなかった。

人間の判断に基づき、submittedの購入申請の提出を入口として承認業務を開始し、可否はその業務中に承認者が判断する。独立していた却下Activityは承認業務へ統合し、拒否（却下）をHowのExceptionに記載した。承認の正常結果はapproved、拒否の例外結果はrejectedとして区別する。

## Finding F03

### Kind

question

### Status

open

### Scope

items

### Targets

- 備品購入を申請する

### Summary

申請者と従業員マスタを照合する識別情報が未確定

### Content

申請者情報と役職の参照元は、人事が保守する別システムの従業員マスタと確認された。一方、申請時に誰の申請として扱うかを特定し、その従業員情報と照合するための識別情報や受け取り方は未確定である。

申請者をどの識別情報で従業員マスタと対応させるか。本人による申請だけか、代理申請も扱うかも含めて未決であり、認証方式は決めていない。対応する従業員情報や役職を確認できず判定不能となる場合は、既決のとおり申請不可とする。
