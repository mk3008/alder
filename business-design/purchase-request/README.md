# 備品購入申請 — 業務設計

草案（人間レビュー・業務上の合意前）。

社内で使用する備品の購入申請から購入完了までに必要となる業務を記述する。

業務上の意味・前提・入力・手順・結果を記述し、画面部品、API、クラス、モジュール、データアクセス方法などの実装方式は規定しない。

## 業務上のロール

- **申請者** — 業務に必要な備品の購入を申請する。
- **承認者** — 申請内容を確認し、購入を承認または却下する。
- **購買担当者** — 承認済みの申請に基づいて購入を行い、購入結果を登録する。

ロールは業務上の責任と権限を表す。

## 購入申請の扱い

購入申請は、申請者が業務上必要とする備品の購入要求を、承認および購買の対象として扱うための記録である。

購入申請は、後述のObject 購入申請のInformationに挙げる情報を少なくとも持つ。

購入申請は一意に識別できるものとする。識別子の採番・入力方法はこの業務設計では規定しない。

## 業務相関

現在定義している主な業務相関は次のとおりである。

1. 備品購入を申請すると、`submitted` の購入申請が成立する。
2. `submitted` の購入申請を承認すると、`approved` になる。
3. `submitted` の購入申請を却下すると、`rejected` になる。
4. `approved` の購入申請に基づいて購入すると、`purchased` になる。
5. `rejected` の購入申請は購買対象にならない。

## 現在の業務設計で未決定の事項

次の事項は現在の業務設計では定めない。

- 申請金額によって承認者や承認段階が変わる場合の扱い
- 在庫確認、発注、納品、検収、支払に関する業務
- 購入先の選定方法
- 購入後の備品管理、資産管理、廃棄
- 外部システムとの連携
- 監査履歴や通知に関する業務

これらは、現在の業務設計を実装するために決定済みであるとはみなさない。

## 確認が必要な事項（未確認）

- **承認・却下の判断範囲**：承認者は申請内容を確認して購入可否を判断する。ただし、承認・却下のWhenは「判断したとき」、Procedureは「確認する」から始まっている。各Activityは内容確認・可否判断まで含む仕事か、判断済みの結果を確定・記録する仕事か。開始条件を変更するかは未確認である。
- **購入と結果登録の範囲**：「承認済み備品を購入する」のWhen・Procedureは購入から結果登録までを含むが、購買担当者からのInputは「購入した対象購入申請」と実購入金額である。購入前から始める一続きの仕事か、購入後の結果登録を始める仕事か。購入できない場合や、購入後に結果登録できない場合の扱いも未確認である。
- **申請者の情報**：「備品購入を申請する」のOutput・Resultには申請者が含まれるが、Inputには申請者自身を示す情報が明記されていない。誰の申請として記録するかをどの情報で確定するかは未確認である。本人による申請だけか、代理申請も扱うかは定めていない。
- **入力不足・状態が変わった場合**：必須入力は明示しているが、不足した場合の結果、数量・金額の有効範囲は定めていない。承認・却下の対象は `submitted`、購入の対象は `approved` としているが、選択後に対象が別の状態になった場合や、再実行時の結果は定めていない。

未記載の操作結果は未決であり、拒否・再承認・取消などの動作が定まっているわけではない。

# Scope

社内の備品購入について、申請・承認・却下・購入と購入結果の登録を扱う。購入申請はこの業務で成立・更新する記録である。申請者・承認者・購買担当者のObjectは、各業務で情報を入力・選択する人を表し、人自体を成立・管理する業務は扱わない。前述の未決定事項は今回の対象に含めない。

# Activity 備品購入を申請する

## Scope

true

## Why

購入の必要性と希望内容を記録し、承認者が購入可否を判断できる状態にするため。

## When

申請者が、業務上必要な備品を購入したいと判断したとき。

## Who

申請者

## Where

規定なし。

## How

### Input

- 申請者 — 品名 / 数量 / 希望購入金額 / 購入理由（すべて必須）

### Procedure

業務に必要な備品の購入要求を、購入申請として登録する。

1. 申請者が購入したい備品の品名と購入理由を入力する。
2. 数量と希望購入金額を入力する。
3. 新しい購入申請として登録する。
4. 登録した申請を `submitted` として扱う。

### Output

- 購入申請 — 申請者 / 品名 / 数量 / 希望購入金額 / 購入理由 / 申請日時 / `submitted` の状態

## Result

- 購入要求が `submitted` の購入申請として記録される。
- 申請者、品名、数量、希望購入金額、購入理由、申請日時が保持される。
- 承認者が購入可否を判断できる状態になる。

# Activity 購入申請を承認する

## Scope

true

## Why

申請内容が妥当であることを確認し、購買担当者が購入を進められる状態にするため。

## When

`submitted` の購入申請について、承認者が購入してよいと判断したとき。

## Who

承認者

## Where

規定なし。

## How

### Input

- 承認者 — 承認する対象購入申請の選択（必須）
- 購入申請 — 対象購入申請の内容と `submitted` の状態

### Procedure

提出された購入申請について、購入を承認する。

1. 承認者が、対象となる `submitted` の購入申請の内容を確認する。
2. 購入してよいと判断した対象購入申請を選択する。
3. 対象の購入申請を `approved` とする。
4. 承認日時を記録する。

### Output

- 購入申請 — `approved` の状態 / 承認日時

## Result

- 対象購入申請が `approved` になる。
- 承認日時が記録される。
- 購買担当者が購入対象として扱える状態になる。

# Activity 購入申請を却下する

## Scope

true

## Why

購入を認めないと判断した申請について、購買対象から外すため。

## When

`submitted` の購入申請について、承認者が購入を認めないと判断したとき。

## Who

承認者

## Where

規定なし。

## How

### Input

- 承認者 — 却下する対象購入申請の選択 / 却下理由（すべて必須）
- 購入申請 — 対象購入申請の内容と `submitted` の状態

### Procedure

提出された購入申請について、購入しないことを確定する。

1. 承認者が、対象となる `submitted` の購入申請の内容を確認する。
2. 購入を認めないと判断した対象購入申請を選択する。
3. 却下理由を記録する。
4. 対象の購入申請を `rejected` とする。
5. 却下日時を記録する。

### Output

- 購入申請 — `rejected` の状態 / 却下理由 / 却下日時

## Result

- 対象購入申請が `rejected` になる。
- 却下理由と却下日時が記録される。
- 購買担当者の購入対象にはならない。

# Activity 承認済み備品を購入する

## Scope

true

## Why

承認された購入要求を実際の購入として完了させ、購入済みであることを記録するため。

## When

`approved` の購入申請について、購買担当者が対象備品を購入するとき。

## Who

購買担当者

## Where

規定なし。

## How

### Input

- 購買担当者 — 購入した対象購入申請の選択 / 実購入金額（すべて必須）
- 購入申請 — 対象購入申請の内容と `approved` の状態

### Procedure

承認済みの購入申請に基づいて備品を購入し、その結果を登録する。

1. 購買担当者が `approved` の購入申請を確認する。
2. 対象備品を購入する。
3. 購入した対象購入申請を選択し、実購入金額を記録する。
4. 対象購入申請を `purchased` とする。
5. 購入日時を記録する。

### Output

- 購入申請 — `purchased` の状態 / 実購入金額 / 購入日時

## Result

- 対象購入申請が `purchased` になる。
- 実購入金額と購入日時が記録される。
- 対象申請が購入済みとして扱える状態になる。
