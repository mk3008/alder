# Alderの開発業務 — Business Design

この文書は、任意で採用する工程も含め、Alder自身の開発業務を記述する。業務上の意図の唯一の正本（SSOT）はBusiness Designであり、コード、テスト、Check Item、Decision Record、生成されたGraph JSONはその代わりにならない。この初版はIssue #79で人間のレビューを受けるための案であり、exportやテストが成功しても、人間が承認したことにはならない。

Business Designは依頼者との合意に使う文書である。本文は依頼者が実際に使用する言語で書き、依頼者自身が内容を理解し、誤りを指摘し、合意できることを前提とする。今回の本文は日本語とする。ヘッダーやセクション名は英語でもよい。

各Activityは責務を示しており、必ず順番に実行する工程ではない。1人が複数の役割を担ってもよい。**Whoはその業務を行うロール**を表し、同じ役割には同じ短い名称を使う。AIや人間への割り当て、支援者、確認者の分担はProcedureに記す。一方、`requester` Objectは、担当者が意図を受け取ったり、質問や結果を返したりする外部の相手を表す。同じ人が両方に関わる場合も、この2つの役割は区別する。

既存の運用規則の参照元は、[導入ガイド](../../docs/adoption.md)、[レビュー知識 v0.3](../../docs/phase2/review-knowledge-v0.3.md)、[Checkの追跡関係](../../docs/check-item-traceability.md)、[任意のDrift試行](../../docs/traceability-drift/study.md)、[研究判断の索引](../../docs/research-decisions.md)である。見出しの業務名・Object名と、Input / Outputに書いたObject名から接続を読み取る。人間がヒアリング結果をまとめ、単独でも読み書き・保守できる文書とし、AIも同じ表面上の情報を編集して協業する。IconはAIが提案しても、人間が変更してもよい。非表示のIDや機械専用の注釈は管理しない。生成JSONは手で編集しない。Input / OutputはObjectと業務の間で実際に受け渡す情報を表し、一般的な参照資料の一覧にはしない。業務要件の問題による業務間の差し戻しは、発生側のHow / Exceptionと、再開側のException Whenまたは末尾の例外フローで表す。Graphの関係は再開側で一度だけ記述する。

`Alder: 検査項目設計ナレッジ` の現行内容は[検査項目の作成・レビュー手順](../../docs/adoption.md#draft-and-review-check-items-required)と[追跡関係](../../docs/check-item-traceability.md)にある。

# Scope

Alderのガイド、研究の証拠、任意ツールを開発・保守する。対象は、業務上の意図の定義、必須のCheck Itemの設計、実装、任意のDrift検査、検証、独立したレビュー、研究上の変更の評価、承認された変更の提供である。Graph exportは、この設計から必要な情報を取り出す任意の処理である。システム設計そのものはAlderの対象外であり、前後のObjectと実装へのつながりを理解するために隣接業務として記載する。各ActivityのScopeは、trueをAlderの責任範囲内、falseを責任範囲外の隣接業務として扱う。UIやViewerの設計、レイアウト、課金、業務上の自動承認、任意の研究手法の必須化、Checkとコードの物理位置の恒久的な対応管理は対象外とする。この開発業務では、プロダクトのデータベースや本番サービスを運用しない。

# Activity 業務設計

## Scope

true

## Why

業務上の意味と保証の合意

## When

目的・変更要求を受領したとき

## Exception When

- 検査項目の設計 — 検査項目レビューで業務上の意味・条件・保証の修正や未決事項の解消が必要と判明したとき。業務設計書を修正・合意してから、検査項目と影響するテストの対応関係を更新する
- 実装 — 未決定の業務上の意味が見つかったとき。業務設計書を更新して人間の確認を得てから、影響する検査項目・判断記録・テスト・コードを修正する
- 実装レビュー — 業務上の意味の変更や未決事項の判断が必要になったとき。業務設計書を更新して人間の確認を得てから、影響する検査項目・判断記録・テスト・コードを修正する

## Who

業務設計者

## Where

規定なし

## How

### Input

- 依頼者 — システム要件 / フィードバック
- 依頼者 — レビュー結果 / 判断
- Alder: 業務相関ナレッジ — 状態遷移フィードバック
- Alder: 業務ナレッジ — 考慮漏れフィードバック
- Alder: 業務設計品質レビュー知識 — 5W1H・I/O・Procedure・Exceptionの記述品質観点（PR #80試行）

### Procedure

1. 業務設計者は依頼者からシステム要件とフィードバックをヒアリングし、5W1H + Input / Outputの形式で業務設計書を作成する。本文は依頼者が実際に使用する言語で書き、スコープ、業務手順、業務相関を整理する。AIは草案作成を支援できるが、責任を持つ人間の業務設計者が意味を確認する。
2. Alder: 業務相関ナレッジを使って業務相関レビューを行い、状態遷移と前後業務のつながりの漏れを確認する。状態遷移フィードバックを業務設計書へ反映し、未決事項を整理する。
3. Alder: 業務ナレッジを使って業務知識レビューを行い、手順・条件・考慮事項の漏れを確認する。考慮漏れフィードバックを業務設計書へ反映し、未決事項を整理する。
4. PR #80の試行では、Alder: 業務設計品質レビュー知識を使って業務設計書の全Activityを確認する。正常手順、実際の受け渡し、発生側と再開側の例外を読み直し、記述品質の問題を業務設計書へ反映する。業務上の意味はAIのセルフレビューで確定しない。
5. 作成した業務設計書を基に依頼者へ仮案を説明し、業務レビューを依頼する。未決事項を相談し、必要な判断を依頼する。依頼者から返されたレビュー結果と判断に基づき、業務設計書と未決事項を更新する。
6. 依頼者や責任者の判断で未決事項が解消された時点で、確定した重要な判断と結果を判断記録（Decision Record）へ残す。どの未決事項を誰が判断し、何が確定したかを記録する。業務上の意味は業務設計書にも反映し、判断記録だけを正本の代わりにしない。
7. 業務設計書と未決事項が依頼者と合意できる状態になるまで、必要なレビューと修正を繰り返す。確認済みの内容と未決事項を区別し、将来のあらゆる方針の確定は求めない。

### Output

- 業務設計書 — スコープ、業務手順、業務相関
- 判断記録 — 判断 / 結果
- 依頼者 — 業務レビュー依頼 / 仮案説明 / 未決事項相談 / 判断依頼

# Activity 検査項目の設計

## Scope

true

## Why

期待結果と検証範囲の確認

## When

業務設計書の合意完了

## Who

業務設計者

## Where

規定なし

## How

### Input

- 業務設計書 — 業務要件 / 期待結果
- Alder: 検査項目設計ナレッジ — 検査項目の導出・レビュー・追跡関係の保守方法
- 依頼者 — 検査項目レビュー結果 / 修正要求 / 確認結果

### Procedure

業務設計者は、Alder: 検査項目設計ナレッジを使い、AIの草案・更新支援を受けて検査項目を整え、依頼者と期待結果を確認する。

1. 業務設計者は、業務設計書全体の業務要件・期待結果とAlder: 検査項目設計ナレッジを確認し、AIの草案作成支援を受けて検査項目の初版または更新案を作る。更新時は既存IDと業務設計書との対応を確認する。
2. 業務設計者は依頼者へ検査項目の期待結果を説明し、レビューを依頼する。確認が必要な項目は明示して伝える。
3. 業務設計者は依頼者から検査項目のレビュー結果、修正要求、確認結果を受け取る。
4. 業務設計者はAIの更新支援を受けて、検査項目自体の修正で解消できる結果を反映する。既存IDと業務設計書・既存Testとの追跡関係を保ち、レビュー状態（未レビュー / 要確認 / 確認済み / 要修正）を更新する。直接編集した場合も対応関係を確認する。
5. 業務設計者は依頼者と合意できるまで説明、レビュー、更新を繰り返す。確認済みの期待結果と未確認の候補を区別し、検査項目を実装へ渡す。

### Exception

- 検査項目レビューで業務上の意味・条件・保証の修正や未決事項が判明したときは、検査項目側で決めずに業務設計へ戻す。業務設計書が修正・合意された後、その内容から検査項目を更新し、レビューを再開する。

### Output

- 検査項目 — 期待結果、レビュー状態、Business Designとの対応、検証不足
- 依頼者 — 検査項目の説明 / レビュー依頼 / 確認事項

# Activity 実装

## Scope

true

## Why

意図した業務の実現

## When

確認済み検査項目の実装依頼を受領したとき

## Exception When

- 実装レビュー — 明確な実装の不一致が見つかった場合は、範囲内の修正へ戻す
- テスト・検証 — テストで実装不具合が明らかになった場合は、提供前に修正する

## Who

システム開発者

## Where

規定なし

## How

### Input

- 業務設計書 — 業務要件
- システム要件書 — 技術要件
- 検査項目 — 確認済みの期待結果、Business Designとの対応、検証不足
- コード — 既存の実装
- テスト — 既存の実行可能なテスト
- ガイド・レビュー知識 — ガイド変更依頼で更新対象となる現行文書

### Procedure

システム開発者は確認済み検査項目と現在の技術条件に基づき、コードとテストを作成・更新する。この役割はAI担当が担うこともある。

1. 業務設計書の業務要件、システム要件書の技術要件、確認済み検査項目の期待結果と検証不足を読み、今回実装する範囲を確認する。既存のコードとテスト、ガイド変更の依頼では更新対象の現行ガイドを確認する。
2. 確認した期待結果と技術条件に沿ってコードを作成・更新する。ガイド変更の依頼では対象のガイドを更新する。
3. 確認済み検査項目の意味に対応するTestを、既存のテストを踏まえて作成・更新する。テストを成功させるために期待結果を弱めない。
4. 業務設計書・検査項目のリビジョンとCheck IDを代表的なTest / assertionに対応づけ、対応関係と残る検証不足を検査項目へ記録する。
5. 重要な技術的選択をしたときは、その理由と残る制約を判断記録へ記録する。

### Exception

- 実装中に未決定の業務上の意味が明らかになったときは、コードやテストで方針を決めず、具体的な問いを業務設計へ戻す。

### Output

- コード — レビュー対象となる変更済み実装
- テスト — 変更した振る舞いを確認する実行可能なアサーション
- ガイド・レビュー知識 — ガイド変更依頼に対する更新案
- 検査項目 — 代表的なTest / assertionとの対応と残る検証不足
- 判断記録 — 重要な技術的選択の理由と残る制約（該当する場合）

# Activity 同期漏れ検査

## Scope

true

## Why

原文・検査項目・テストの同期漏れの検出

## When

原文項目・検査項目・テスト一覧の変更（任意試行の利用時）

## Who

システム開発者

## Where

規定なし

## How

### Input

- 業務設計書 — 選択した試行用アダプターが扱える、識別済みの現行原文項目
- 検査項目 — 現在のCheck本文
- 同期照合情報 — 照合を済ませた原文・Check・Testのfingerprintと、現在のテストランナーが検出したTest ID

### Procedure

システム開発者は、試行用のフィクスチャまたはプロダクト用アダプターで読み取り専用の検出器を実行し、候補を解釈する。対象は範囲を限定した任意試行とし、文章の更新状態と業務上の正しさを区別する。

1. 照合基準として保存した値（pin）や人間のレビュー状態を変更せず、更新状態と参照の不一致を算出する。
2. 古くなった関係や欠落した関係を再確認の候補とする。不具合として自動分類しない。
3. 影響するCheckを原文と照合する。Check本文の変更と原文の再確認を区別して同期照合情報を更新する。
4. 変更したCheckの期待結果をTestと照合する。照合を完了した関係だけpinを更新し、検査結果と残る再確認候補をまとめる。

### Output

- 同期漏れの候補 — 古い関係・欠落・対応関係の再確認候補と理由。プロダクトの不具合とは区別する
- 同期照合情報 — 別途照合を完了したpinのみ。検出器の実行自体では確認済みにしない

# Activity テスト・検証

## Scope

true

## Why

実装の検証結果と限界の確認

## When

実装変更の完了、期待結果の変更

## Who

システム開発者

## Where

規定なし

## How

### Input

- コード — テスト対象の現行実装
- テスト — 実行可能なテスト一式
- 検査項目 — 必要なケース、期待結果、代表的なTest / assertionとの対応、検証不足
- 同期漏れの候補 — 任意試行を使う場合に確認する影響候補

### Procedure

システム開発者は関連するテストとゲートを実行し、結果と残る検証不足を記録する。

1. 検査項目の確認済み期待結果、Testとの対応、検証不足を読み、現行コードに対して関連するテストとゲートを実行する。
2. 実際の結果、再現手順、残る検証不足を検証結果に記録する。研究の評価を依頼されたときは、意図的な失敗を期待するシナリオとプロダクトとしての成功を区別して記録する。

### Exception

- テストで範囲内の実装不具合が明らかになったときは、実装へ戻して修正し、関連する検証を再実行する。

### Output

- 検証結果 — 成功・失敗した検証、観測した振る舞い、再現手順、残る検証不足

# Activity 実装レビュー

## Scope

true

## Why

業務設計と実装の不一致の検出

## When

実装・重要な修正のレビュー準備完了

## Who

レビュー担当者

## Where

規定なし

## How

### Input

- 業務設計書 — 現在の業務上の意図、対象範囲、業務間の関係
- 判断記録 — 記録された実装上の選択と前提
- ガイド・レビュー知識 — 選択した版のレビュー知識と、レビューを打ち切る条件
- コード — 実装によって具体化された業務上の意味
- テスト — 選択された振る舞いの証拠となるアサーション
- 検証結果 — 実際のテスト・ゲートの結果と限界

### Procedure

レビュー担当者は、元の設計とDecision Recordを使い、実装を担当した者から独立した視点でレビューする。この役割には別のAI担当または新しいコンテキストのAIを割り当てられる。未決定の業務上の意味は、責任者である人間が判断できる問いに絞る。

1. Business Design → Decision Record → 実装とテストの順に読む。
2. 代表的な業務をたどり、Q1–Q3 / P1 / P2 / Sを使って、具体的な実装上の選択を原文まで追跡する。
3. 明確な不一致、業務確認、技術改善、十分な振る舞いを分類する。無関係なアーキテクチャや将来の範囲を要求しない。

### Exception

- 業務上の意味の変更や未決事項の判断が必要と判明したときは、選択肢を業務設計へ返す。Business Designの修正と人間の確認を受けてから、後続の成果物を更新する。
- 明確な実装の不一致が見つかったときは、実装へ戻して範囲内で修正する。

### Output

- レビュー結果 — 具体的な条件、影響、原文の根拠、分類を伴うレビュー結果。十分な振る舞いも含む

# Activity 研究評価

## Scope

true

## Why

手法変更の採否判断に必要な証拠の整理

## When

手法変更の提案、再検討条件の成立

## Who

研究担当者

## Where

規定なし

## How

### Input

- 依頼者 — 研究の目的と許可された評価範囲
- ガイド・レビュー知識 — 現行の手法と変更候補
- 研究の証拠と採否判断 — 既存の結果、限界、再検討条件
- 検証結果 — 関連する再現可能な観測結果
- レビュー結果 — 候補に関係するレビュー結果

### Procedure

研究担当者は変更案を評価する。恒久的なガイドの変更案の採用はメンテナーが判断する。範囲の明確な証拠に基づき、観測結果と一般的な主張を区別する。

1. 既存の証拠から考え、判断に関係する不確実性に実験の範囲を絞る。
2. 述べた観測結果を再現するために必要なプロンプト、原文のリビジョン、結果を保全する。新しいコンテキストでの評価と、既存コンテキストを再利用した評価を区別する。
3. 採用・不採用・証拠不足の判断を、理由と限界とともに研究判断の索引へ記録する。実験結果を暗黙に普遍的な規則へ変えない。

### Output

- 研究の証拠と採否判断 — 証拠、採否などの判断、理由、限界、再検討条件
- 判断記録 — タスク固有の評価上の選択と、検討を打ち切った理由

GitHub

## How

### Input

- テスト — 更新済みの回帰テスト
- ガイド・レビュー知識 — ガイドや文書の変更案

### Procedure

システム開発者は変更を準備し、メンテナーから受け入れやリリースの許可を受ける。許可されたAI担当やリリースワークフローがマージ・リリースを実行できる。採用前に実際の範囲、証拠、残る限界をレビュー可能にする。

# Activity 業務グラフ出力

## Scope

true

## Why

業務相関の機械可読化

## When

出力要求の受領、原文変更に伴う生成例の更新

## Who

システム開発者

## Where

規定なし

## How

### Input

- 業務設計書 — 独立したObject、ラベル付きInput/Output、明示的な例外関係を含む、人間可読な5W1H原文

### Procedure

システム開発者は任意のexport CLIを実行する。人間可読なMarkdownのBusiness Designから形式のバージョンを持つJSONを生成し、別の正本や意味の二重管理を作らない。ネットワークや外部サービスは不要とする。

1. 対応する原文形式から、業務名（Activity見出しのWhat）、Why/When/Who/Where、Scope、Objectのアイコン名、ラベル付き関係を、同じ入力なら同じ結果になるように抽出する。JSONのIDと接続先には見えている名前を使い、名前が変わればIDも変わる。名前の変更時は、その名前を使う接続も更新する。
2. 名前の一意性、参照、接続先の種別を検証する。通常のデータ接続はObject → Business（Input）またはBusiness → Object（Output）のみとする。対応形式に従わない不正な入力は、非ゼロの終了コードで拒否する。
3. business-exception（Business → Business。データ接続ではない制御上の関係で、破線表示の意味を持つ）とobject-exception（Object → Object。明示的な例外関係）を区別し、それぞれにラベルを付ける。
4. アイコンが省略されていれば汎用アイコンを補う。アイコンの文字列にはLucideのアイコン名を使い、ここではSVG一式を管理しない。
5. 検証に成功した後にだけ、順序が安定したJSONを出力する。入力設計を上書きしない。Procedureは意図的に出力対象から除くため、Graph JSONを完全な仕様や業務上の承認の証拠として扱わない。

### Output

- 業務グラフJSON — 形式のバージョンを持つ生成JSON。手で編集せず、Business Designから再生成する

# Graph exceptions

- object-exception テスト → コード — テストは実行によってコードを検証する。Checkとコードの位置対応を維持するものではない
