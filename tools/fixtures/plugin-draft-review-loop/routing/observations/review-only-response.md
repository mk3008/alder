# 備品返却業務設計書のレビュー

対象は `draft.md` 全文と `notes.md`。受付から点検への受け渡し、各Activityの欄と入出力、三つのObjectを確認した。原資料は「業務の合意はまだ」と明記しているため、以下は業務上の承認ではない。文書の範囲説明と二つのActivity名は対象業務・仕事を識別でき、Scopeへの手順の混入やActivity名への単なる開始条件の混入は見当たらない。文書全体の `# Scope` は推奨欄だが省略可能であり、冒頭の対象説明だけを理由に必須修正とはしない。

## 原資料・書式から修正内容が定まるもの

1. **受付控えの交付と受付完了条件が抜けている。** `返却を受け付ける` のProcedure、Output、Result（27–35行）。原資料は受付番号を記した返却控えを返却者に渡し、台帳への記録と返却者の受領の両方を終了状態としている。草案は台帳記録だけで正常終了としており、返却者が控えを受け取らないまま受付完了と読める。控えの交付をProcedureと返却者へのOutputに、受領をResultに反映する。受付番号の払い出し方法は原資料にないので補わない。
2. **受付の正式な開始条件の見出しが誤記。** `返却を受け付ける` 13行の `## Whne` は正式欄 `## When` に直す。本文の開始条件は原資料と一致する。
3. **Input／Outputの参照書式が規定と異なる。** 25、32、57、64行の `[[Object名]] から／へ 情報` は、ガイドの `- Object名 — 受け渡す情報` に合わせる。参照している三つのObject名自体は文書内の宣言と一致している。書式修正だけで後述の情報不足は解消しない。

## 業務上の判断が必要なもの

4. **点検の開始条件が前段からつながらず、点検の結果を開始条件にしている。** `返却品を点検する` のWhen（45–46行）は「点検済みであることを確認したとき」だが、Procedure（59–61行）でこれから故障の有無を判断する。受付のResult（34–35行）も点検済みを保証しない。原資料では「受付済みの返却品を受け取ったら」と「点検済みであることを確認してから」が対立し、未決のまま。何を確認・受領した時点で点検を始めるのかを決め、Whenと受付からの引継ぎを一致させてほしい。どちらかをこちらで選ばない。
5. **点検担当を受付担当と確定している根拠がない。** 点検のWho（48–49行）は受付担当だが、原資料は点検の役割を未決とする。同じ窓口で作業することは同じ担当者が行う根拠にはならない。誰が点検を担い、受付からどう引き継ぐかを決めてほしい。
6. **返却品と故障判断の材料が点検のInputから手順へ届かない。** 点検のInput（56–57行）は台帳の管理番号・受付番号だけで、Procedure（60–61行）はその確認から故障の有無の判断へ飛ぶ。受付のWhenには返却品の受渡しがあるが、受付のInput／Procedureにも返却品の受領・後段への扱いが書かれていない。原資料も判断材料・基準とその受け取り方を欠くと明記している。どの返却品と何の情報・基準を、誰からどう受け取り、管理番号と対応づけて判断するのかを確認してほしい。その判断に応じて受付から点検へのInput／Outputと手順を記述する。未記載の検査基準を推定して追加しない。

会議後の「部長の追加承認」「QR読取機能」は改善アイデアであり、採用済みの業務条件ではない。今回の成立性に必要な修正・未決事項には含めない。任意の追加提案はない。

レビューは同じagent内で記述品質と業務相関・漏れを別工程として確認したもので、独立した別agentによる検証ではない。確認できた根拠は指定された原資料と草案に限られ、担当・開始条件・判断基準についての合意記録はない。原資料と草案は編集していない。
