# Issue #54: error-resistant operational design

**Decision: add a bounded implementation principle to adoption §3 and route the implementation prompt to it. Keep philosophy and review knowledge v0.3 unchanged.** Existing knowledge can expose consequential operational traps, but does not explicitly prefer removing a cheap implementation-created trap over compensating with remembered procedures.

## Scope, baseline and method

This responds to [Issue #54](https://github.com/mk3008/alder/issues/54) and the [owner's scope and investigation order](https://github.com/mk3008/alder/issues/54#issuecomment-5657834997). Baseline: `b51c63ea830d6e5a53c63ebed4dc3c5d45879e25`, after the v0.2 release preparation.

Read the baseline adoption, philosophy and review knowledge before evaluating the six requested thought cases. The analysis below first applies existing guidance, then identifies what the proposed addition changes. These are authored analytical cases, not executed applications, observed operator incidents or fresh-agent outputs. The migration motivation is reported by the Issue; this investigation does not independently reconstruct Velvet's migration history or modify Velvet.

The bounded scope is one source comparison, six cases, one minimal guidance addition and document-integrity checks. Stop when placement, overlap, plausible remedies and counterexamples are reviewable. No broad benchmark or human-factors framework is needed for this normative clarification.

## Six thought cases: baseline first, then the proposed addition

The assumptions below deliberately bound when a remedy is cheap. They are part of each authored case, not inferred facts about an existing product.

| Case and concrete setup | Existing-guidance analysis | Application of the proposed wording | Boundary and stopping condition |
| --- | --- | --- | --- |
| **Migration / deployment ordering.** Two unreleased, unapplied migrations have no external identity references. `0018` requires `0025` to run first; the runner sorts names and the runbook says to override that order. | Adoption's risk/convention guidance permits renaming. P1/Q3 can expose the failed prerequisite if deployment is within the described work, but review does not necessarily inspect technical migration order. | Rename the dependent migration after its prerequisite and check fresh-install/upgrade ordering. The normal runner now follows the required order; no extra warning layer is needed. | Do not rename already-applied migrations blindly: recorded identities, checksums, supported upgrade paths or external references can make this a different compatibility decision. Stop once the supported paths have unambiguous order; do not demand a dependency framework. |
| **Destructive command with an unsafe default.** A new maintenance CLI is intended for tenant-scoped cleanup. Omitting the tenant currently selects all tenants; the manual says always supply it. No existing callers depend on omission. | Adoption allows a requirement-aligned default. P1/Q1 can trace unintended deletion; if scope contradicts the stated contract, that is already a definite mismatch. A correctly scoped command's ergonomic improvement remains technical. | Require the tenant argument and make missing scope non-mutating. An authorized all-tenant operation, if needed, must be explicit; do not invent that permission. Verify missing scope and valid scoped execution. | Stop after removing implicit scope widening. No universal confirmation dialog, second approval or prohibition on legitimate bulk maintenance. Existing callers would require compatibility assessment. |
| **Interruption / retry / re-entry.** A transfer uses an existing durable operation ID and status lookup. The response is lost after completion, but the retry command creates a new ID; the runbook says to look up the original first. | P1/Q1 directly support asking whether facts and continuation survive interruption. Q3 can check the completion receipt. Established external reconciliation may already satisfy business meaning; it does not force the easiest retry shape. | Reuse the existing operation identity and reconcile its recorded result on re-entry, within the actual duplicate-handling contract. Exercise the lost-response case. This removes the avoidable new-ID path rather than adding a reminder. | Do not claim an ID alone prevents duplicate external effects. If the downstream contract cannot resolve uncertainty, report that limit and the established reconciliation responsibility; do not invent exactly-once delivery or blindly retry. Stop when continuation is truthful within that contract. |
| **Ambiguous business handoff status.** A dispatch record is labelled “Ready” after packing, although agreed dispatch readiness also requires recorded carrier acceptance. Both facts already exist; staff are told to remember that Ready only means packed. | Q3 already explicitly checks Output names/procedures against downstream conditions. P1 exposes a dispatcher acting on the label; this can be a definite guarantee mismatch, not merely a missing safety feature. | Label the existing packing result “Packed” and expose readiness from the agreed facts, choosing the smallest change consistent with actual consumers. Check the packed-but-not-accepted scene. | If the meaning of Ready or the acceptance responsibility is undecided, retain a Human Decision rather than inventing a gate. If Ready already has a clear, established narrower meaning and no misleading consumer contract, do not manufacture a defect. No mandatory state-machine rewrite. |
| **Partial configuration state.** A feature's effective enabled flag can be stored before its required endpoint; a second save writes the endpoint. Current intent requires a complete configuration before activation, while the runbook compensates with save ordering. | Q1 can expose interruption between saves; Q2 traces what the flag permits, and Q3 tests whether “enabled” supports consumers' prerequisites. Adoption can already choose a coherent update. | Where both values are locally owned and one atomic save is available, validate the complete candidate and publish it together, retaining the previous valid configuration on failure. Check interruption and invalid input. | Do not shut down a working service merely because a proposed change is incomplete. Distributed configuration may not admit a cheap atomic change; retain truthful effective status and established continuity behavior instead of demanding transactions everywhere. Stop at the actual activation contract. |
| **Legitimate manual judgment.** An authorized claims specialist evaluates contextual evidence and records an exception decision; Business Design intentionally delegates this judgment. Meaning, responsibility and continuation are clear. | P1/Q3/S allow the established judgment and close sufficient meaning. P2 prevents the implementation from substituting an invented business policy. | Preserve the manual decision. There is no cheap equivalent structural prevention if it would decide which claims deserve exceptions; speculative automation fails the business-meaning condition. | No automatic approval threshold, forced checklist or new sign-off. Useful documentation remains appropriate. Stop with sufficiency unless a separate concrete implementation-created trap is evidenced. |

Across the cases, “documented” does not by itself establish that the operating shape is proportionate. Equally, a documented external responsibility can fully establish business meaning even when a technical improvement is available. The implementation preference does not turn every such improvement into a blocking Alder review finding.

Stopping on ambiguity is conditional on serious incorrect-execution consequences and lack of safe continuation. The configuration case preserves the last valid service state; the retry case preserves uncertainty and reconciliation instead of inventing certainty. Neither “always continue” nor “always fail closed” follows.

## Placement and wording

The permanent text is [adoption §3, “Prefer error-resistant operation”](adoption.md#prefer-error-resistant-operation). Its core principle is:

> Predictable operator mistakes are real implementation risks. When a plausible mistake can be removed by a cheap, clear structural choice without changing business meaning or adding disproportionate complexity, prefer that structure over relying on memory, documentation, or a non-obvious exception.

The surrounding paragraphs prefer removing the trap first, qualify the migration example by deployment history, preserve availability and legitimate judgment, and bound scope and effort. The implementation prompt adds a route to the versioned subsection instead of copying its rules.

No philosophy amendment is necessary: risk-based technical selection already covers the rationale. No change to Q1–Q3/P1/P2/S or the review prompt is justified by these cases. There is no evidence here that existing review questions systematically miss consequential traps. No new approval gate, named architecture, mandatory tool or release-version change is introduced.

## Validation, limits and stop decision

All six requested domains were checked analytically against baseline coverage and the final proposed wording, including cases where a structural remedy is cheap, changes business meaning, threatens compatibility or harms continuity. This supports the bounded placement and exposes overreach to avoid; it does not demonstrate how reliably an agent chooses the remedy.

Fresh-agent sampling was optional in the owner comment and was not performed. The decision does not rely on a claim that existing agents tend to stop at “read the manual.” A small unblinded trial could provide examples but would not establish that tendency or causal improvement. The visible instruction gap and bounded countercases suffice for this minimal clarification; no review-rule expansion depends on unmeasured behavior.

Document verification checks relative link targets and explicit local heading anchors, balanced code fences, and that the patch is limited to adoption and this record. Philosophy, review knowledge, Business Design and historical evaluation records remain unchanged. Application tests and migration executions are not relevant gates for this documentation-only change and were not rerun.

Limitations: the same author selected and assessed the cases; the fixtures simplify real compatibility and ownership constraints; operator error frequency, agent behavior, error reduction and production fitness are unmeasured. Stop here with a reviewable normative addition rather than claiming empirical efficacy or expanding to a general human-factors study.
