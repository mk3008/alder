# Alder 0.4.8 — 業務設計レビューとCheck Itemの改善

業務設計の草案レビュー・再改稿、Check Itemの生成・更新・整合性レビュー、業務設計上の指摘と関連先の表示をまとめた版です。

## 変更

- Check ItemはActivity単位で一般条件・業務行為・期待結果を一度だけ示し、各Check IDからその保証と具体例へ辿れる形にします。同じ条件の再掲を避けつつ、元のCheck ID、人間レビュー状態、保留した判断、根拠とTest証拠を保持します。条件の成立・不成立など比較が有益な場合は表を使い、対象・説明内容・相手などの差は短文と表から選びます。**サンプルは人間が期待結果を理解するための具体例であり、一般保証の代わりにはしません。** 式や操作の欄は一律必須にせず、必要条件と保証、未決の結果を区別します。
- Check Itemの初稿・更新後、既存のConsistency review-onlyを別の読取工程として実施します。Business Designに照らしてActivity名、各Checkの一般保証・適用条件、例から観察できる違い、欠落・重複・共有参照を確認し、根拠のある指摘のみ作者が修正・再レビューします。独立した読取ができない環境ではその限界を明示し、人間の業務判断を代行しません。
- 相談受付の検証用Business Designを現行のGraph Markdown書式へ移行し、現行Viewerで全体図とActivity詳細を閲覧できることを確認しました。これは架空の例の書式移行であり、業務ルールを追加・確定するものではありません。

- 草案作成後に既存の品質レビューを実行し、原資料や記述規則で裏付けられる問題を修正して再レビューします。情報不足は質問として残し、改善がない反復やレビュー不能時は確認できた範囲を報告して停止します。人間の業務判断を代行しません。

- 業務設計Markdownの任意のFindings欄で、要確認と要修正の内容・状態・関連先を記述できます。既存のProblem / Pain levelによる業務上の困りごとと区別します。
- ViewerはActivity / Objectの右上バッジと、左ドロワーの指摘一覧・詳細を表示します。項目・関連先の選択で左右のドロワーを勝手に開閉せず、明示的な開閉操作を維持します。複数項目への関連、文書全体、関連先未設定、参照先不一致を扱い、解消済みは既定で隠します。
- Pythonのparse_documentは図と指摘を返します。既存のparse_designとCLIのJSON出力はGraph v1のままです。CLIは指摘を出力から除外する場合、標準エラーに警告します。

## 互換性と限界

指摘がない既存MarkdownとGraph JSON v1のキーは変更しません。指摘があっても業務上の事実や承認の根拠になるわけではありません。構文、対象名、読み方は[指摘の記述ガイド](design-findings.ja.md)を参照してください。

自動テストは構文、変換、表示の対象範囲を確認します。業務判断の正しさ、AIレビューの網羅性、利用者の操作確認を代替しません。プレビューでの人間の確認と採用判断は別途必要です。

草案ループはSkillの指示による調整であり、決定的なワークフローエンジンではありません。静的契約検査は実クライアントでのループ実行や一般的な意味検出能力の実証ではありません。既存インストールは自動更新されません。

Check Itemの書式もSkillによる指示です。4つの限定ケースの生成・更新と別読取・修復を検証しましたが、一般的な自律生成精度や人間の読解時間・誤読率の改善は実測していません。具体例は網羅性の証明や個別テストとの対応契約ではなく、未決事項の確定や人間の意味確認を代行しません。既存の折り畳み形式は一括移行せず、Viewer Webの関連Check読込との新書式互換性は未検証です。
