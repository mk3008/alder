# Issue #64 — Functional Interfaceの小規模評価

## 評価対象と進め方

[Issue #64](https://github.com/mk3008/alder/issues/64)の目的は、完成済みBusiness Designと検査項目・コードの間に観測可能な操作契約を置く価値の評価である。業務設計の穴探しやベンチマーク実装の完成は行わない。

設計はPR #63のM1/M2承認済み会議室snapshot、Checkは同じ設計からのc3生出力24項目をそのまま再利用する。いずれも今回の開始main `ac48516aabc2358cb7a01f0ec123fa91b38702c7` で固定する。Business Designは評価範囲の完成済み入力、Checkと今回のInterfaceは人間レビュー前の初稿であり、研究のAI評価を人間承認と呼ばない。

mainには会議室アプリを保持していないため、既存評価と同じ `94f6f639b850a92ce5ad55812a4899e7a2c7bc33` の `apps/meeting-room/` を実装・テストの対象とする。この実装はM1/M2より古い。新設計への対応差を調べるのであり、旧設計に違反したバグと断定しない。過去レビューからM1/M2の差は既知であり、独立した発見率試験ではない。

予算は会議室1件、候補f1一つ、既存テスト1回、判断に必要な小さな挙動probeのみ。Fresh反復・モデル比較・別業務追加はしない。同じ評価者が導出と対応付けを行うためblind比較ではない。既存コードを読んだ知識による影響も残る。

## 操作契約の最小定義

Functional Interfaceは「ある主体が入力・契機を与え、業務上の結果を観測し、次の仕事へ対象・事実を渡す責務境界」。コードの入口の数、transport、ファイル配置は定義しない。

[候補prompt f1](prompt.md)を一度適用し、[7契約の初稿](interfaces.md)を整理する。空き確認、登録、保存済み対象の照合、変更、取消、利用不可化、再開である。Activity 2の登録と照合を分けるのは、新しい予約を作る責務と既にある対象を取り戻す責務が異なり、結果喪失後には後者だけが必要になるため。各条件検査やDB操作は独立した業務能力ではないため分割しない。

利用不可化と再開は同じコードへ対応しても、担当判断・成立する状態・占有の観測が異なるため2契約とする。コード上の統合を妨げない。この分解は唯一の正解ではなく、人間が修正・統合してよい。

## 検証方法

1. c3の24 Checkを再生成せず、主担当1つと必要な関連先へ割り当てる。
2. 意味の差が分かる条項だけを詳細mappingする。Check内の複数ケースを全件検証済みにしない。
3. 既存テストの名前だけでなくアサーションを読み、実装の条件・更新・SQL制約へ戻る。
4. 既存20テストを実行し、未来条件、0/1/複数件、ID喪失時の継続を対象に短いprobeを行う。期待と異なる結果も観測として保存し、テストを書き換えて通さない。
5. 初期化・時刻変換・権限・共有transactionから逆引きし、Interfaceのない技術支援を不要機能と誤判定しない。
6. 同じ根拠を使う直結mappingと比較する。新しい欠落発見や工数削減を測定できなければ、その限界を明示する。

## 観測した意味対応とgap

[対応表](mapping.md)は24 Checkの所属と12代表条項の根拠・テストのアサーション・コードを示す。主担当を一つ持たせつつ接続先を残したので、MR-18の本人/同一性、MR-21の対象なし等を複数の操作契約へ横断できる。主担当は読み始めるための索引であり、責務をそこだけに閉じない。

[実行記録](../../work/functional-interface/records/evaluation.json)では、Python 3.12.14 / SQLite 3.53.1で既存20テストすべて成功。新設計に対する合格ではない。追加probeはP1〜P5の5群で、製品コード・既存テストは変更していない。

| 判定 | 実例と根拠 | どこまで言えるか |
| --- | --- | --- |
| mapped（7条項） | M03/04/05/09/10/11/12。占有、同一予約、競合、対象なし、取消、利用不可/再開、Roleを対応付け | 各行に記した条件/アサーションの範囲。Check全文の全例を通したとはしない |
| implementation gap: 意味不一致 | M02。IF-01の未来条件に対し`availability`は時刻を見ない。旧テストも過去候補を正解とする。P1では過去・開始=現在の双方で候補1室 | M1承認後の契約との差。古い仕様の実装が壊れたのではない。テストの存在/成功だけではmappedにできない |
| implementation gap: 経路なし | M06。IF-03に対し、CLI入口とPython操作層にID喪失後の本人照合経路がない。P4では保存1件を研究者SQLで確認できても、再要求はoverlapのみ | M2承認後の契約との差。研究者のDB参照を利用者の機能に数えない。特定APIの不足ではなく意味を満たす経路が見つからない |
| missing check/test（2条項） | M01の0/1候補の直接assert、M08の変更拒否から同一対象取消への連続証拠は既存suiteにない。P2/P5では期待する挙動を観測 | missing implementationではない。分割された既存テストも部分証拠になる。1Check=1Testや全シナリオ追加は要求せず、人間が証拠の十分性を判断 |
| ambiguous mapping（1条項） | M07 / MR-09の未保存中断はc3の未承認候補 | 意図/適用範囲が未承認なので実装違反に数えない。型や関数の探索では解決しない |
| orphan implementation | 確認した入口・支援処理では確定0。初期化、時刻変換、identity、transactionは技術支援として説明できる | 「対応するBusiness Activityがない関数」は不要機能の証拠ではない。全行の不存在証明ではない |

`owned(db, reservation_id)`は、名前だけならIF-03に対応しそうだが、既知のIDを入力として所有者とreservedを検査する内部処理だった。結果喪失時にそのIDを得る契約とは違うため対応候補を棄却し、IF-04/05の支援へ位置付けた。これは「曖昧な対応候補→意味照合→経路不足」という評価過程であり、曖昧なままmappedにしていない。

対して`set_available(room_id, available)`一つは、False/TrueでIF-06/07の二つを実現する。重複禁止はPythonの条件検査、transaction、SQL trigger、複数テストにまたがる。一契約が複数実装箇所へ、同じ実装箇所が複数契約へ対応することを許容した。

## 直結mappingとの比較

比較対象は「Business根拠→既存c3 Check→テスト/コード」に直接つなぐ同じ12条項である。同じ評価者が同じ根拠を読んだ構成比較であり、独立した人間/Agentの探索時間を比較したものではない。

| 判断する作業 | c3からの直結 | Interfaceを加えた場合 | 今回の判断 |
| --- | --- | --- | --- |
| M1の未来検索の不一致 | MR-02の根拠と`availability`・旧assertの比較で分かる | IF-01のOutput保証としてまとまる | 発見にInterfaceは必須でない |
| M2の結果喪失後の照合 | MR-08に既に明記され、既知ID前提を検出できる | 登録成功と照合能力がIF-02/03として別枠になり、実装対応のない契約を示せる | 責務の索引として価値。新しい能力を発見したとは言わない |
| 変更が占有や取消へ与える影響 | MR-11/13/15/16等を横断してたどれる | IF-04/05と関連先で、変更影響の入口を集約できる | 探索の入口は明確化。探索工数の削減は未測定 |
| 共有関数と技術支援の説明 | コード/Decision Recordから直接説明できる | IF-06/07→同じ関数、IF-03≠ownedを短く整理できる | 物理分割の要求を避けて責務を説明可能 |
| 単純な業務で文書を維持 | c3と対応表で足りる | 同じ前提・結果をカードにも更新する必要がある | 常設の独立仕様書にする利益は未証明 |

既存アプリREADMEにもActivity→検証内容の表があった。Interfaceなしではtraceabilityが作れないという仮説は採らない。今回の同じ12条項は、Interface列を除いてもBusiness/Check/Test/Codeの根拠・gap分類を失わない。Interfaceの増分は操作の責務と関連項目をまとめる名前・索引であり、意味照合そのものの代替ではない。

### 維持コストと変更箇所の例

追加したのは7契約カード、24主担当リンク、35関連リンク。これに12条項のmappingと逆引き6例を作った。mapping自体は直結案にも必要であり、すべてをInterfaceの追加コストとはしない。一方、カードの契約要約と所属リンクは明確な追加保守対象である。対応表のMarkdownはJSONから生成し、二重の手修正を避けた。

- 検索時点の未来条件を変更するなら、直結ではMR-02、Interface案ではIF-01から同じCheck/`availability`/時刻テストへ進む。どちらも正本の変更が先で、IF-01の契約要約が追加更新箇所となる。
- 結果喪失後の継続を実装対象にするなら、IF-03は責務の入口になる。ただし既存の`owned`を改名するだけでは成立しない。新方式やファイル位置はこの研究で決めない。
- 内部で`set_available`を統合/分割するだけなら、Business契約は変わらず、実装対応先だけを見直す。逆に契約の変更がない内部リファクタリングのたびに新Interfaceを作らない。

機械検査はID/参照/版の存在を確かめられるが、古い契約要約が意味として正しいかは判定できない。対応が変わった版の参照を機械的に書き替えるだけでは意味の再照合にならない。

## 人間レビューで見る箇所

1. IF-02/03を分ける責務、IF-06/07を分けて同じコードへ対応させる粒度が、業務上読みやすいか。
2. 主担当だけを見て接続先・共有制約を落としていないか。特に照合→変更/取消、変更失敗→取消。
3. テストの存在でなく、どの条件・アサーションが契約のどこを支えるか。古い成功テストが新しい期待と逆でないか。
4. 未承認候補と真の対応不足、支援処理と根拠不明の業務能力を混同していないか。
5. 今のプロジェクトでc3からの直結より分かりやすく、追加カード/リンクを更新する価値があるか。

## 採否・限界・停止

**機能契約を必要箇所の中間索引として使うことを任意・限定採用する。独立したFunctional Design文書を全案件に追加する標準工程は採用しない。** Activity内に独立した能力がある、複数Checkとコードにまたがる責務を追いにくい、といった具体的な理由がある場合に使う。既存のCheckの見出しや対応表にID/契約を併記してもよく、別ファイルを必須にしない。人間がInterfaceとCheckをレビュー・修正して完成させる。今回の初稿を人間承認済みとはしない。

主な利益は責務単位の可視化と変更探索の入口である。日本語→コードの意味差は検出できたが、直結より検出率が高い、人間の読解/レビュー時間が減る、AIの保守効率が上がるとは未証明。既知のM1/M2版差を用いた1ケースの同一評価者試行であり、候補の分割最適性や一般化も未証明。c3/v0.3を置換せず、業務設計・実装の改修へ広げない。

会議室1件で利益と重複コストの両方が見えたので停止する。2ケース目、Fresh比較、製品の不足実装、全Check/全コード行の網羅mappingは追加しない。実利用で直結の対応が追えない具体的な事例、またはInterfaceの二重更新による誤りが出たとき、該当範囲だけを再検討する。常設工程への昇格には、人間の修正負担・探索時間・対応漏れの比較が必要である。

## 再現と検証

開始mainのgit checkoutで、以下を実行する。固定実装commitが手元にない場合はそのcommitを取得してから行う。製品コードは一時ディレクトリへ固定版を展開し、DBも一時生成して終了時に削除する。

```sh
python3 work/functional-interface/evaluate.py
python3 work/functional-interface/verify.py
python3 work/functional-interface/render_mapping.py
```

`evaluate.py`は既存suiteとP1〜P5の観測を出力する。終了コード0は研究処理の正常終了であり、resolved契約への製品適合を意味しない。P1の不一致を出力に残す。`verify.py`は根拠hash、全Checkの主担当、参照行/実在symbol、候補状態、旧研究証拠46ファイルの不変性を検証する。意味の分類は本文の評価と分ける。[manifest](../../work/functional-interface/records/manifest.json)と[機械検証結果](../../work/functional-interface/records/verification.json)を保存する。
