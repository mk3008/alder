# テスト仕様・テストコード・実装の評価責務（S / X / A / B）

Alderでは、**テスト仕様そのものの品質、テスト仕様とテストコードの対応、テストによる要求達成の保証、実装・検証経路の品質**を別々に判断する。同じ事象が複数に影響しても、主たる欠陥と他の責務への引継ぎを区別し、重複して不合格にしない。

業務意味の正本は **Business Design**、合意した論理的なテスト仕様は **Check Item**（条件・入力・操作・期待結果・必要な具体例）である。Test/assertionはその検証証拠であり、実装コードや既存Testの挙動から業務上の期待を逆算して正当化しない。Check Itemは業務上の論理仕様であり、クラス・API・DB等の物理構造を強制しない。詳しいトレース規則は [Check Item traceability](check-item-traceability.md) に従う。

## 4つの責務

| 評価 | 主な問い | 担当範囲 | 主担当にしないもの |
| --- | --- | --- | --- |
| **テスト仕様作成・品質評価（便宜上 S）** | BDの要求が、重要な条件・テストパターン・期待結果として十分に定義されているか | Check Itemの導出・更新・整合性レビュー。正常／異常、境界値、0／1／複数、状態・例外・継続など、要求にとって重要な条件差を明示する。未決・未承認は区別する | Testコードとの実行対応、コード構造の評価 |
| **X：テスト仕様とTestの対応付け** | Check Itemで**定義済み**の期待は、実在するTest/assertionによって検証され、実行されたか | Check ID／定義済みのサンプル識別子 ↔ 実際のTest ID・入力・assertion・実行証拠の意味対応。テスト実装欠落、入力・期待結果の取り違え、無効／古い対応を検出する | 新しい業務テストパターンの設計、実装全体の要求達成判定 |
| **A：要求達成・テスト品質評価** | 実装が合意要求を実際に満たし、テスト成功がその達成について有効な保証になっているか | BD・合意済みCheck・適用SRに対する実挙動を独立に確認する。重要な誤動作を通してしまう偽green、誤ったテストの検出力、要求の縮小・すり替え、境界での不成立を検出する | Check Itemの勝手な改訂、Xの恒久マッピング保守、Bの構造最適化 |
| **B：コード・達成経路の品質評価** | 同じ要求を保ったまま、実装構造と検証経路をより適切にできるか | 責務・データ所有・依存・結合・変更波及・保守費用（B-S）、反証速度・検証依存・重複と固有境界（B-V）を、効果とリスクで判断する | 業務期待の承認、Aの要求適合・Xの対応成立の代行 |

ここでの **Sは責務を説明する仮称**であり、新しいSkillの登録を意味しない。既存の Check Item作成・整合性レビューが該当する。Aは「テスト品質だけ」ではなく、もともとの**要求・目的の達成**と、その達成をテストがどこまで保証するかの両方を扱う。Bの「コード品質」は見た目の好みや短さではなく、要求を維持する達成経路の妥当性で判断する。

## 境界の具体例：モルックの50点

| 観測・不足 | 主担当と判定理由 |
| --- | --- |
| 「50点で特別扱いしない」という一般則はあるが、必要な50点ちょうどの境界パターンがCheck Itemに明示されていない | **S**：テスト仕様の具体例・条件選定の不足。一般則だけの記述と、十分なテストパターン設計を混同しない |
| Check Itemには50点のパターンと期待結果があるが、対応するTest/assertionがない、または期待値を検査していない | **X**：定義済み仕様のテスト実装／対応の不足 |
| 50点を25点に変える故障注入でも全Testが成功してしまう | **A**：テストの検出力不足を観測。原因がパターン欠落ならS、定義済みパターンのTest欠落ならXへ引き継ぐ。これだけで元コードの実故障とは断定しない |
| 実際の製品コードが、合意した規則に反して50点を25点として返す | **A**：要求に対する実挙動の不一致 |
| 同一保証を重いBrowser Testで重複して反復し、固有の故障検出を増やしていない | **B**：反証経路・費用の改善候補。異なる実境界の保証を削って高速化しない |

**すべての値や条件の直積を列挙する義務はない。** Sは重要な境界・同値類・条件差と期待結果を、見逃したくない誤りを識別できる形で選ぶ。BDから決まらない期待は創作せず、人間の確認へ戻す。Xは仕様にないテストパターンを独断で「必要な既定仕様」に追加せず、Sの品質上の疑問として報告する。

## 独立判定と証拠

- SはBDを根拠にCheck Itemの意味とテストパターンを点検する。**Checkの人間承認状態と品質評価は別**であり、AI評価で業務意味を承認しない。
- Xは実在するTest/assertionと実行証拠まで追跡する。1 Check = 1 Testを強制せず、共有Checkや複数assertionを許容する。**対応が存在すること**と**テストが誤りを検出できること**は別である。
- AはTestのgreenやXの対応結果を、実装が正しい証明とみなさない。必要に応じて実挙動・反証例・実行境界を独立確認し、**コードの不成立**と**テストの保証不足**を区別する。
- BはAの要求・保証を前提条件として改善を評価する。Aの結果を入力必須とはせず、根拠があれば改善不要（NO_CHANGE）も正しい判断とする。
- **E（証拠の信頼性）は横断観点**。版・対象・runner・実行結果・握りつぶし・未実行を区別するが、必須の独立Skillを増やすものではない。
- 指摘は主因を一つ選び、他軸への影響は引継ぎで記録する。S・X・A・Bの評価結果を互いの合否の代用にしない。恒久トレースは **Business Design ↔ Check Item ↔ Test/assertion** とし、Check ↔ Codeの恒久マップを新設しない。

この文書は**責務の判断基準**であり、新しい必須工程・JSON Schema変更・Plugin Skillの自動登録・正式Skillの挙動変更を伴わない。それらの適用と検証は別途判断する。JSONのCheck ItemとTestを直接照合でき、Viewer表示はこの評価契約の前提ではない。
