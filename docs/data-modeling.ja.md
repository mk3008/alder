# Alderにおけるデータモデリング

[English](data-modeling.md) · [Alderへ戻る](../README.ja.md) · [業務設計の書き方](adoption.md#business-structure-requirements-follow-the-work-they-change)

Alderはデータモデリングを省略しません。**業務側の構造要求と、システム要件・既存制約・明示的な設計制約を合わせて、データの表現方法を選ぶ設計行為**として扱います。Business Designは選んだテーブルを指定する文書ではなく、どの状態・操作・保証を実現しなければならないかを依頼者と確認する文書です。

```text
業務側の構造要求 ＋ システム要件・既存制約・明示的な設計制約
                         ↓ データモデリング
                 データの表現・制約の選択
```

業務側では、何を一件とするか、複数件をまとめられるか、何が必須か、同じ対象をどう識別するか、変更履歴を残すか、どの単位で承認するかなどが問題になります。システム側には性能、保存量、既存スキーマ、移行、統合、技術上の制約があります。同じ業務上の意味を満たす表現は複数あり得ます。採用したいデータ配置や技術があらかじめ決まっているなら、その理由とともに明示的な設計制約として渡し、業務上の要求と整合するか確認します。

## なぜテーブル設計を独立した必須工程にしないのか

必要に応じて、人が実装前にER図やテーブルを設計しても、System Designで扱っても、実装中に具体化しても構いません。Alderが要求するのは、**選んだ構造の業務上の効果を、確認済みの要求や明示的な制約へ遡って説明できること**です。業務上の判断をすべて事前に確定してから実装する工程順は必須にしません。

実装、DDL、テストによって選択が具体化したら、その選択が許す状態や拒む操作をBusiness Designと照合します。確定済みの意味と食い違えば修正し、業務上の選択が未決なら依頼者へ具体的な問いとして戻します。実装されたことやテストが通ったことだけで業務上の承認が済んだことにはなりません。これは、要求からモデルを設計する従来の原理を変える主張ではありません。[設計思想](philosophy.md#why-not-settle-every-decision-before-implementing)も参照してください。

## なぜBusiness Designに専用のデータ構造欄を設けないのか

構造が重要になるのは、依頼者から見た仕事の結果が変わるときです。「一注文で複数品目を注文できる」「店頭受取には配送先が要らない」「申請全体を承認する」といった条件は、実際のActivityの**Procedure / Result / Input**や対象の**Object.Information**、必要な例外に沿って書けば、その業務上の意味を読めます。この書き方を意図して設計されています。独立した関係一覧を作らなくても、後続の設計者は一件のまとまり、任意性、同一性、履歴、承認単位などを、その仕事の文脈から読み取れます。未決の条件は決まったものとして書かず、問いとして残します。

専用欄を設けると、同じ条件を業務の手順と欄の両方で維持したり、依頼者と業務上の意味を確認する前にキーや多重度だけを固定したりするおそれがあります。[#114の机上比較](data-structure-requirements-study.md)では現行欄を採用し、[#116のFresh比較](../work/data-structure-requirements/public-repeat.md)では既存欄に書く指針を試しました。単一の合成入力による定性的な比較であり、専用欄の効果を一般的に否定する実験ではありません。現時点では専用欄や定型行を正当化する差は確認できなかったため、既存欄を維持します。具体的な配置とレビュー方法は[導入ガイド](adoption.md#business-structure-requirements-follow-the-work-they-change)に記載しています。

## 業務上の意味とデータ表現の例

| Business Designで確認すること | 後続のデータモデリングで選ぶこと |
| --- | --- |
| 一注文に複数品目を含められ、注文全体を一件として確定する。 | 注文ヘッダーと明細を分けるか、どう関連付けるか。品目を一つしか保存できない構造では要求を満たさない。 |
| 配送注文には配送先が必要だが、店頭受取には不要。 | NULLを許す列、配送用の別構造、条件付きの検証など。配送先を常に必須とする制約では店頭受取を表せない。 |
| 同じ組織内では会員番号を重複させず、別組織なら同じ番号を使える。 | 組織と番号の組合せで一意性を強制する方法。会員番号だけを全体で一意にする制約は業務条件と異なる。 |

表の分割数や主キーの列は例から一意に決まりません。一方、「品目ごとの部分確定を認めるか」が未決なら、どの構造を選ぶ前にも業務判断として確認します。

## 人が設計し、制約の根拠を確認する

人がデータモデルを作る方法とも、AIが候補を作って人がレビューする方法とも両立します。実装者がAIでも、業務側の要求とシステム側の条件から候補を選び、その効果を検証する原理は同じです。依頼者が決める業務上の意味をAIやDDLの既成事実に委ねません。

正しいPK / FK / UNIQUE / NOT NULL / CHECKなどの制約は、許されない状態を保存できなくし、システムの安定性に役立ちます。逆に誤った制約は正しい業務状態まで拒みます。選んだ制約がどのBusiness Designの条件、または明示的なシステム制約を守るのかを確認してください。権限、時点、外部で確定する事実、並行更新などはDBの列や制約だけではすべて表現できません。アプリケーションの処理や運用上の保証も含めて検証します。

この立場の根拠と検証範囲は[構造要求の研究記録](data-structure-requirements-study.md)と[公開revisionでのFresh追試](../work/data-structure-requirements/public-repeat.md)にあります。実案件の記述・レビューでの効果や、別の業務領域での一般化はまだ検証していません。
