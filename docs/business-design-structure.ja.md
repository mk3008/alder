# 業務設計書の文書構造

[READMEへ戻る](../README.ja.md) · [記述例](examples/meeting-room-reservation.ja.md) · [導入ガイド](adoption.md)

業務設計書（Business Design）は、仕事の目的、担当者、手順、受け渡す情報、成立すべき結果を、ユーザーと合意するための文書です。本文はユーザーが普段使う言語で書きます。人間が単独でも読み書きでき、AIも同じ文書を使って草案作成やレビューを支援します。

このページでは、新しく書くときの基本構造を説明します。見出しは[Business GraphのMarkdown形式](business-graph.md#opt-in-markdown-profile-v1)に合わせているため、同じ文書をレビューにもJSON化にも使えます。既存の別形式の文書をレビューする場合まで、一律の書き換えを要求するものではありません。

## まず、業務の範囲を決める

冒頭に文書のタイトルと目的を書き、`# Scope`で今回扱う業務と対象外の業務を示します。現在の運用と、これから実現する合意済みの業務を混同しないよう、どちらを記述しているかも説明します。

業務ルールが未決なら、決まったように書かず、未決であることと確認先を本文に残します。JSON化する場合は、文書全体の未決事項を冒頭の説明に、個別のものを関係する既存の欄に書きます。独自の見出しを追加すると、exporterが受け付けないことがあります。

文書の骨格は次の形です。

```text
# 文書タイトル
目的・前提・未決事項などの説明

# Scope
今回扱う業務の範囲

# Object 受け渡す情報や相手の名前
## Scope
## Icon
## Information（任意）

# Activity 業務名
## Scope
## Why
## When
## Exception When（必要な場合のみ）
## Who
## Where
## How
### Input
### Procedure
### Exception（必要な場合のみ）
### Output
## Result
## Problem（困りごとがある場合のみ）
## Pain level（Problemと対で記載）
```

これは構成図です。実際の見出しに括弧書きは含めません。ObjectとActivityは必要な数だけ追加します。

## Object — 何を、誰と受け渡すか

Objectには、業務で実際に読み取る情報、更新する台帳、作成する文書、情報をやり取りする相手を書きます。たとえば会議室予約なら「利用者」「会議室台帳」「予約台帳」です。データベースのテーブルを先に決めるための欄ではありません。

| 欄 | 書くこと | 例 |
| --- | --- | --- |
| `# Object 名前` | 文書内で一意に識別できる短い名前 | `# Object 予約台帳` |
| `## Scope` | 今回の業務範囲内で成立・管理するなら`true`、外部の相手や範囲外の業務が管理するなら`false` | 予約受付で管理する台帳は`true` |
| `## Icon` | 可視化で使うLucideアイコン名。不明なら`(generic icon)` | `calendar` |
| `## Information` | 含まれる業務情報を箇条書きにする。任意だが、受け渡しの意味を理解する手掛かりになる | 対象会議室、利用時間帯、予約者、状態 |

`Information`では業務上の情報を整理します。主キー、型、正規化、厳密なテーブル対応は後続の技術設計で扱います。ObjectのScopeは接続の向きから決めず、その情報や相手を誰が管理するかで判断します。

## Activity — 一つの仕事を説明する

Activityは、担当者がひと続きに進められる仕事を目安に分けます。別の担当者の判断や待ち時間を挟むなら、分ける必要がないか考えます。一方、同じ目的の作成・確認・修正を細分化しすぎると流れが読みにくくなります。

### 目的・開始・担当・環境

| 欄 | 書くこと | 混ぜないもの |
| --- | --- | --- |
| `# Activity 業務名` | 短い仕事の名前。5W1HのWhatに相当する | 別の`## What`欄は作らない |
| `## Scope` | 今回の責任範囲内なら`true`。受け渡しを説明するために載せる隣接業務なら`false` | 文書全体のScopeの説明文 |
| `## Why` | 仕事の目的 | 作業手順や成果物の一覧 |
| `## When` | 通常、何をきっかけに始まるか | 例外からの再開条件、漠然とした「随時」 |
| `## Who` | 仕事を担う短いロール名。同じ役割には同じ名前を使う | AIの支援方法や承認の細則 |
| `## Where` | 業務の成立や手順に影響する場所・環境・チャネル。特になければ「規定なし」 | 採用するフレームワークやDB |

たとえば「顧客の現場」で行う仕事なら、通信環境や利用端末について確認する手掛かりになります。それだけでネイティブアプリなどの技術手段を決定するものではありません。

### How — 入力から出力までをたどる

`## How`の下に、次の欄を順に置きます。How自体には本文を書きません。

| 欄 | 書くこと | 会議室予約の例 |
| --- | --- | --- |
| `### Input` | どのObjectから、何の情報を受け取るか | `- 利用者 — 対象会議室 / 利用開始・終了日時 / 利用目的 / 予約者` |
| `### Procedure` | WhoがInputを使い、確認・判断・更新する正常な手順 | 利用可否と時間帯を確認し、予約を登録して結果を伝える |
| `### Exception` | 正常に進められない状況と、そのときの扱いや戻り先。必要な場合だけ書く | 重複している場合は登録せず、理由を利用者へ伝えて終了する |
| `### Output` | どのObjectへ、何の情報を書き出す・渡すか | `- 利用者 — 予約結果` |

InputとOutputは、`- Object名 — 受け渡す情報`の形にします。Object名は宣言した名前と完全に一致させ、情報がない場合は`(none)`と書きます。ここには実際に扱う情報を書き、単なる参考資料一覧にはしません。

Procedureでは「予約台帳を更新する」だけでなく、何を確認し、どの内容を記録するかまで示します。入力・出力に書いた情報が手順に現れるか、逆に手順で扱う情報の出所と行き先が分かるかを読み合わせます。確認できない事実や業務条件はAIに補わせず、人間への問いにします。

### Result — 終わった後、何が成立しているか

`## Result`には、正常に終わった時点で成立する状態と、そこから可能になる後続の業務を書きます。

| 欄 | 会議室予約で書く内容 |
| --- | --- |
| Why | 会議に必要な時間帯の会議室を確保するため |
| Output | 予約台帳へ登録した予約内容、利用者へ伝える予約結果 |
| Result | 予約が成立し、その予定で会議の準備を進められる |

Resultは成果物の一覧や手順の繰り返しにしません。後続Activityがある場合は、そのWhenとつながるか確認します。「次へ進められる」と「必ず次を実行する」も区別します。

## 例外と差し戻しを書く

正常な開始条件はWhen、実行中に起こる例外はHowのExceptionへ分けます。別のActivityへ差し戻す場合は、受け側の`## Exception When`をWhenの直後に置きます。

たとえば、検査項目の確認中に業務ルールの未決事項が見つかり、業務設計へ戻す場合です。

- 発生側「検査項目の設計」のExceptionには、確認を中断して業務設計へ戻すことを書く。
- 受け側「業務設計」のException Whenには、`- 検査項目の設計 — 検査項目のレビューで未決の業務ルールが見つかったとき`と書く。

JSON上の業務間の例外関係は、受け側の記述から一度だけ作られます。発生側のExceptionは動作の説明です。同じ関係を重ねて宣言せず、両方の説明が一致するかを人間が確認します。単にその業務を終了する例外まで、架空の戻り先を作る必要はありません。

## Problem / Pain level — 改善したい困りごとを書く

成立している業務に負担や遅延などの困りごとがある場合、ユーザーと確認した事実を、該当ActivityのResultの後へ記録します。

```markdown
## Problem

承認済みの購入申請が増えると、購買担当者が申請ごとに購入し、結果を登録する負担が大きい。

## Pain level

High
```

Problemには、どの仕事で何に困っているかを書きます。頻度や作業時間が分かれば添えますが、数値を推測で埋めません。Pain levelは相対的な困りごとの大きさで、`Low`・`Medium`・`High`のいずれかを使います。困りごとがない業務には、両方とも不要です。JSON化できる形式では、一つのActivityに一組だけ記録します。

「誰が承認するか未決」のような仕様の未決事項は、業務分析で解消する問いです。「承認を待つ時間が長い」のような現行業務の困りごとと区別します。

この記録から[業務改善レビュー](optimization-review.md)を行えます。候補の期待効果やDifficultyはレビュー結果として扱い、採否は人間が判断します。候補を現在の業務上の事実として自動転記せず、採用時に責任や手順の変更を業務設計書へ反映し、ユーザーと再合意します。

文書内のActivity/Objectの`Scope`は責任範囲を表す真偽値です。改善候補を評価するときのScope（Narrow / Keep / Expand）とは別のものです。

## コピーして書き始める・JSON化する

[会議室予約の記述例](examples/meeting-room-reservation.ja.md)は、Object・Activity・例外を含む一つの完結したサンプルです。予約受付だけを扱うので、実際の対象に合わせて空き確認や変更・取消などを加えてください。内容をコピーするだけで業務上の合意が成立するわけではありません。

可視化・解析用のJSONが必要な場合は、Python 3.12以上で、Alderのルートから実行します。

```sh
python tools/business_graph/export.py docs/examples/meeting-room-reservation.ja.md -o graph.json
```

JSON化するときは、次も確認します。

- Object名とActivity名は文書全体で一意にし、参照名を揃える。名前を変えたら参照箇所も直す。
- Scopeには説明文を混ぜず、`true`か`false`だけを書く。理由は本文で説明する。
- 上記の見出し順を守り、必要な欄を空にしない。任意欄も、書く場合は内容を入れる。
- HTMLコメントによる隠しIDや、機械だけが読む別の定義を持たない。

exporterは構文や参照先を検査します。**業務上の意味の正しさや、ユーザーの合意は検査しません。** ProcedureとExceptionの本文はJSONに含まれないため、手順や例外のレビューには元の業務設計書を使います。外部ツールで修正点を見つけた場合も、元の文書へ反映します。

JSON形式やエラー条件の詳細は[Business Graph export](business-graph.md)を参照してください。

## ユーザーと読み合わせる

代表的な一件を、InputからProcedure、Output、Resultまでたどります。

1. 誰が何を受け取り、何を判断・更新するかを説明できるか。
2. 業務の結果から、次の業務を始める条件へ自然につながるか。
3. 進められない場合の扱いと、戻り先が具体的か。
4. 合意済みの条件、未決事項、現場の困りごとを区別できるか。

指摘を文書へ反映し、ユーザーと合意します。システム化する場合は、合意した内容から[検査項目を作成・レビュー](check-item-traceability.md)して実装へ渡します。
