# Issue #62 — 導出研究の範囲と方法

[依頼](https://github.com/mk3008/alder/issues/62)。開始時main: `d1c7c67f4208a8958a7063bb09ede8f9c254ed4d`。現行v0.3、元Business Design、過去の実装は変更しない。

本書は初回計画を保存する。後続の[継続指示](https://github.com/mk3008/alder/pull/63#issuecomment-5738020150)では、未決検出を研究成果として認め、全ケースresolved化を完了条件から外した。現行の追加評価は[第3段階](stage3.md)を参照。

## 少数の導出観点

既存[Sources](../sources.md)と[Research Decision Index](../research-decisions.md)を先に確認した。requirements validationと業務シナリオは既存Q1–Q3/P1/Sで扱われている。新たなレビュー原則を増やす必要はない。P2の実装からの逆引きは実装前の一覧には適用できず、後続レビューとして残る。

一次資料は2026-09-19に次の2点だけ確認した。

- [NASA Systems Engineering Handbook §4.2.1.2.4](https://www.nasa.gov/reference/4-0-system-design-processes/): 要求と期待の追跡・妥当性確認の既存基盤を再利用する。
- [ISTQB CTFL v4.0.1 §§4.2, 4.5.2](https://istqb.org/?download_id=3345&sdm_process_download=1): 同値分割、境界値、決定表、状態遷移、受入基準の概要を確認した。条件と観測結果を結び付ける書き方、結果が変わる区分・境界・遷移の選択に利用する。

今回の候補は「業務の成立と引継ぎ」「結果が変わる代表条件」「根拠へ戻して未決を分離」の3手順。これは本研究の選択であり、資料がこのpromptの有効性を証明するものではない。

| 候補 | 今回の扱い | 理由 |
| --- | --- | --- |
| 利用シナリオ・受入基準 | 各業務の条件→結果→次の仕事を短い項目にする | 既存P1を検査入力へ具体化できる |
| 同値分割・境界・状態遷移 | 結果が変わる代表場面を選ぶ補助手段 | 日時・占有・状態の明示規則を展開できる |
| 決定表 | 条件の交差が判断を変えるときだけ任意 | 全組合せや別成果物を必須にしない |
| Negative / error cases | 業務根拠のある禁止・不成立を同じ書式に含める | 未定義を一律拒否に変えない |
| 網羅的checklist・white-box coverage | 不採用 | 実装前の派生一覧の目的を超える |

## 実行設計

最終候補c1を一つ作り、3つの固定HEADのBusiness Designをそのまま保存する。[入力manifest](../../work/behavior-derivation/records/inputs.json)にrevision、path、SHA-256を記録する。mainの会議室文書は固定HEADの承認反映版とは異なるため代用しない。

各Fresh Agentはc1と対象snapshotだけを読む。過去会話を継承せず、oracle・実装・他ケースは渡さない。各ケース1回、実行中の内容フィードバックなし。明示されたIssueのFresh Agent要求に基づく3実行であり、モデル比較や大量反復はしない。出力は生のまま残し、評価者の補正は別文書に書く。

評価者だけが#32/#33/#36を読み、#34の結果喪失も補助oracleとして保持する。oracleは過去の実装レビューなので、実装特有の暫定拒否の再発見まではBusiness DesignのみのAgentに要求しない。文章・件数一致ではなく、未決の意味を断定していないかを照合する。

評価では全項目の根拠・分類・期待値を点検し、既知論点への対応、有用な境界、過剰保証、観測可能性、優先確認の絞り込みを記録する。人間レビュー時間は計測できないため、優先項目数は候補絞り込みの代理値にとどめる。確度は未校正であり、通常項目の誤りも探す。

既存の人間判断は固定snapshotと関連Issue/PRの明示承認から再利用する。実装者のDecision Recordや成功テストは人間判断ではない。判断がない場合はdecision packetまで作って停止する。未決を隠して完成版を捏造しない。resolved試験は承認後の別snapshotで行い、今回の穴あり試験とは分ける。

後続への接続は、代表項目をテスト設計へ渡す小さなprobeで必要に応じ確認する。実行可能なプロダクトテストを完成させる目的ではない。判断を変える情報が得られない追加試験は行わない。
