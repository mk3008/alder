# 機能・検査項目の導出候補 c1

研究用。標準workflowへの採用・業務承認を意味しない。

## 導出指示

入力は指定されたBusiness Designと本指示のみとする。Business Designと同じ言語・普段使う業務用語で、コードを読まない人が確認できる機能・検査項目一覧を作る。実装・過去レビュー・他の導出結果は参照しない。

本来の適用条件は、人間が完成させ業務相関レビューを通したBusiness Designである。未決事項が残る入力では「未解決入力の試行」と明記し、完成済み扱いしない。Business Designが正本であり、派生一覧で意味を決定・上書きしない。

1. 各業務の担当、開始条件、入力、結果と次の仕事への引継ぎを追い、何を観測すると成立したと言えるかを書く。
2. その条件から結果が変わる代表的な許可・禁止・状態遷移・境界を選ぶ。0件・1件・複数件、重複、中断、再実行、判断変更、変更しない結果は、現在の仕事への具体的影響がある場合だけ扱う。全組合せ・全例外を要求しない。
3. 各項目を根拠へ戻す。一意に決まらない意味は要確認に残し、合理的な解釈の違いと影響、判断すべき担当を示す。一般的なシステムの機能、UI、DB構造、実装方式、数値制限、全操作の無変更保証を補わない。未記述だけを理由に質問を増やさない。

## 固定書式

冒頭に入力の版・完成状況、優先確認IDの索引を置く。その後、業務ごとに以下の短い項目を並べる（幅広い表は不要）。IDは当該成果物内で一意にする。

### ID — 機能・振る舞い
- 対象業務:
- 条件・契機・入力:
- 期待する結果（観測対象）:
- 起きてはいけないこと: 該当なしの場合も明記。根拠のない失敗時全項目無変更は要求しない。
- 根拠: 指定入力の行番号と短い該当内容。複数記述を使う場合は結び付きも1文で示す。
- 導出分類: 明示 / 強い導出 / 要確認
- 確度: 高 / 要精査。これは記述した期待結果を根拠から導ける確かさであり、業務承認・網羅性・モデルの校正済み確率ではない。要確認の未確定結果は必ず要精査。
- 人間レビュー: 優先 / 通常。要確認・要精査・推論の結び付きが長い項目は優先。通常も承認済みという意味ではない。

要確認項目の期待結果は「未確定」とし、選択肢・業務への影響・判断担当を書く。仮の一案を期待値にしない。明示された部分と未決の部分は分ける。要確認項目をそのまま合否テストに変換しない。

末尾に、扱った代表場面と扱わなかった範囲を短く記す。網羅性や実利用者の読解容易性を自己申告で実証済みにしない。項目と根拠の対応、通常項目からも代表的な明示・導出を確認することが、人間レビューを優先項目へ集中させる前提となる。

後続AIは、確定した項目のIDを検査へ対応付け、前提・操作・観測・禁止の照合を保つ。新しい意味判断が必要ならBusiness Designへ戻す。テスト方式は指定しない。Business Design更新時には入力版と対応項目を再確認し、古い一覧や成功テストを新しい承認として流用しない。
