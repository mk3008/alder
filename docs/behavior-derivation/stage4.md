# 第4段階 — 全文から人間レビュー用の初稿を導出する

## 実行前の変更と評価範囲

[目的・導出方向の修正](https://github.com/mk3008/alder/pull/63#issuecomment-5738263778)を受け、標準採用の評価対象を「AIだけで抜けなく抽出し、優先項目の確認で承認できる仕組み」から「人間が修正・追加して完成させる初稿をAIが作る仕組み」へ訂正する。Business Designは人間が初稿を作り、検査項目はAIが初稿を作る。どちらもレビューと人間の修正を経て完成する。

c3は、全文を入力とすること、前後の業務接続、Data/Role/Ruleの横断制約、0件・対象なし等の検査例を明記した。c2の要確認を、具体的な期待結果案を持つ「考慮候補」と、本当に業務意味を決め直す「Business Designへ戻す事項」に分ける。新理論や個別業務policyは追加しない。c1/c2と過去の生出力は保持する。

予算はまず**resolved会議室 × c3をFreshで1回**。会議室は完成条件を満たす既存snapshotがあり、0件、日時・占有境界、変更失敗、結果喪失後の継続、複数予約を同じ入力で評価できる。設備保全・購入の過去結果は観点の補正根拠と制限の資料にとどめ、穴あり入力を主評価にしない。既知の未決の再発見をc3の採否基準にしない。

Fresh Agentにはc3と会議室全文のみを渡す。過去会話、oracle、過去出力、ケース別の評価基準は見せない。途中フィードバックなし、生出力の修正なし。

評価者は全項目を原文へ照合し、次を確認する。

- 0件/1件/複数件、対象なし、成立/不成立後の接続が具体的な期待結果として現れるか。
- Procedure以外のRole/Data/Rule、前後の成立条件を根拠として使うか。
- 承認済みM1/M2を再質問せず、候補と確定根拠を区別できるか。
- 欠落や修正点を人間が扱える初稿か。根拠付きの項目があっても完全性や工数削減を主張しない。
- 下流へ渡すときに必要な前提・操作・観測・禁止と、候補の未承認状態を保持できるか。

残る不確実性が研究判断を変えない場合、この1回で停止する。人間の実際のレビューや承認を評価者のAIが代行したとは記録しない。

## c3の出力と全文への照合

[生出力](../../work/behavior-derivation/stage4/outputs/meeting-room-c3.md)は24項目（明示3・強い導出20・考慮候補1）、優先7。別枠のBusiness Design差戻しは0。評価者は全24項目の条件、期待結果、根拠、分類と禁止を入力全文に照合した。生出力を修正して合格にしたものではない。

| 観点 | 具体的な出力 | 評価 |
| --- | --- | --- |
| 0/1/複数件 | MR-01が0室（全室利用不可、占有済み、会議室自体なし）から再確認/予約せず終了へ接続。MR-20/22は予約件数と室の状態を分離 | Procedureにない件数別の具体例を抽出条件・Output・後段Inputから導出 |
| 対象がない | MR-10/14/17/21が会議室・変更予約・取消予約・管理対象の不在を区別し、不成立と再選択/終了を示す | 一意性・必須対象・成立条件から導出。別対象への暗黙代用を禁止し、架空の元予約保持は要求しない |
| 成功から後続開始 | MR-05が同じ予約を変更/取消へ渡す。MR-11/16は変更・取消による旧枠解放を次の空き確認へ接続 | 対象の同一性と後段で別途必要な条件を区別 |
| 不成立から継続 | MR-13/15が変更失敗後の元予約維持と別案・取消への接続を示す | 単なるエラーの検査で終わらない。UIや自動遷移は指定しない |
| 中断と再特定 | MR-08は保存済みの同一対象を本人が特定し後続条件を再検査。MR-09だけ未保存中断を考慮候補に分離 | M2の保存済み責務を再質問しない。未保存までの拡張は採用前の確認対象 |
| 部分成立・何もしない | MR-13は一部だけ条件を満たした変更で元予約を失わせない。MR-23は複数予約の異なる結果を維持。MR-04/20/24は予約しない・変更しない・再開しない場合 | 代表的な場面を結果へ展開。万能な部分成功機構や新規状態を要求しない |
| 横断制約 | MR-18がRoleとData identity、MR-03/07/12が共通の占有・隣接規則、MR-19〜24が管理判断と予約者の仕事を横断 | ActivityのProcedureだけの転記ではない |
| 過剰要求 | M1/M2の再承認、代理制度・通知・UI/API・自動再開の要求を追加しない | 境界を保持。候補を含む全項目が人間レビュー前であると明記 |

c2も0/1/複数候補、本人照合、変更・取消の占有接続は抽出していた。c3で新たに目立つのは、対象なしを複数の業務で具体化したこと、失敗/見送り後の再選択・終了・別業務への接続、未承認候補を具体案として独立させたことである。16→24件という増加そのものは改善尺度ではなく、実行者の差もあるためprompt変更の因果効果は主張しない。

## 人間が完成させるためのレビュー例

以下は**AI評価者による確認・修正の提案**であり、人間の承認結果ではない。項目書の意味を勝手に修正せず、人間がどこを判断・補足するかを具体化する。

| 初稿の対象 | レビュー時の扱い・具体化 | 理由 |
| --- | --- | --- |
| MR-01「再確認または終了できる」 | 予約しないまま終える/別時間帯で再検索するという業務結果として確認する。「戻るボタン」「自動遷移」は要求しない | 検査項目がUI設計へ変質しないようにする |
| MR-10/14/17/21の対象なし | 存在しない対象を指定するケースと、有効対象を選び直して別試行を行うケースを分ける。対象削除機能の追加は不要 | 通常の対象不在を検査するために、新しい管理業務を発明しない |
| MR-11の同一予約・属性保持 | 予約の業務上の同一性、予約者・目的・登録日時・状態を確認対象にする。内部レコードの更新方法までは固定しない | Dataと変更対象の限定からの強い導出を実装方式と区別 |
| MR-09の未保存中断 | 候補の採用/修正/除外を人間が判断する。M2の既承認部分を再度決定させず、未保存まで広げた部分だけを確認 | 具体的な候補として有用だが、初稿が勝手に承認する範囲ではない。意味の変更があるなら先に正本へ反映 |
| 通常項目全体 | 人間は優先7件だけで完了せず、本文の期待結果と扱った場面を見て不足を追加する | 初稿生成と項目書の完成を区別する |

MR-09は安全な成功条件の試行を妨げるものではない。採用するか決まるまでその期待値だけを保留し、業務全体を再び設計レビュー待ちにはしない。

## 下流テスト設計へつながる具体例

次は生出力と正本を読んだ評価者が作った設計例で、Fresh Agentによる追加probeでも、実行済みテストでもない。人間レビュー後にこれらの条件・観測を確定するための材料とする。Tは操作時点、日時はTより未来に置く。

| 初稿ID | 前提・操作 | 観測する結果 |
| --- | --- | --- |
| MR-01 | 会議室0室、有効な未来の時間帯で空き確認 | 選べる室が0件。対象予約を得た扱いにせず終了。別の空室あり・別時間帯のケースでは再検索で候補を得る |
| MR-10→05 | 存在しない会議室で予約試行。その後、実在するavailable室・競合なし・必須入力ありで新たに試行 | 初回は予約不成立。別室の暗黙代用なし。次の試行ではその室・本人・指定時間・目的を持つ同一性の確認できるreservedを得る |
| MR-13→16 | 自分のreservedを利用不可室へ変更しようとした後、元予約を取り消す | 変更不成立時は元内容と占有を維持。その同じ予約の取消でcancelledと取消日時を確認し、占有を解く |
| MR-08 | 保存済みだが結果未受領。本人には他の予約も存在する。対象を再特定し、条件を満たす変更を行う | 今回の成立済み予約を特定し、その予約だけが変更される。単なる再試行成功表示を代用しない |
| MR-23 | 不可中にAを別室へ変更、Bを取消、Cを維持して元室を再開 | Aの旧枠はAでは占有されず、Bは非占有、Cは元室を占有。元の一覧への一律復元はしない |
| MR-09 | 保存済み対象が0件で中断後の確認をする候補場面 | 人間が候補を採用/修正するまで確定アサーションにしない |

これらはBusiness Design全文を根拠に、初稿を人間がレビューしてテスト設計へ渡せる粒度の例である。AIだけで全テストを確定してよいという意味ではない。

## 採否と停止

**c3を、人間がレビュー・修正・追加して完成させる初稿作成の任意手順として限定採用する。** [adoption](../adoption.md#optional-draft-a-human-reviewed-behaviorcheck-list)に入口と役割分担を追記する。必須工程、AIによる完成品、優先項目だけの承認、人間レビュー不要の仕組みとしては採用しない。v0.3は変更しない。

根拠は、完成済み入力から正常・境界・0件・対象不在・成功/失敗後の接続を根拠付きで具体化し、追加レビューが必要な案を分離した初稿が得られたこと。今回確認した24項目には、人間が一から書く代わりに点検・補正の出発点とできる内容がある、という実用判断である。負荷軽減を比較実験で証明したわけではない。

新規Freshは1回で停止。c3で他2業務の再導出、全ケースresolved化、追加の下流Fresh試行、製品実装は行わない。以前の保留は「優先項目中心の確認で承認できるか」という過大な基準に寄っていたため、今回の限定採用と区別する。過去結果は消さず、今回から評価対象を変更したことを索引へ記録する。

限界: c3は既存の完成済み会議室1件のみ。候補分類は1例であり、分類の安定性、他業務での再現性、人間の理解・修正負担、ゼロから書く場合との比較、実行可能テストの品質は未検証。実利用で初稿修正がゼロからの作成より重い、候補がpolicyの発明へ逸れる、根拠のある接続や0件が繰り返し欠落する場合に、当該観点だけを再検討する。

[manifest](../../work/behavior-derivation/stage4/records/manifest.json)に入力・c3・指示・生出力hashと担当IDを保存。モデル/effortは継承設定で、独立証明はない。第4段階の検証scriptはhash、参照範囲、8欄と分類/Confidence、過去証拠40ファイルの不変性を確認する。意味の妥当性は上記の文書評価と分ける。
