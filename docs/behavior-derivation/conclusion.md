# 機能・検査項目のたたき台 — 観点・promptと利用範囲

**判断: c3を、人間がレビュー・修正・追加して完成させる検査項目の初稿作成手順として限定採用する。** [adoptionの任意手順](../adoption.md#optional-draft-a-human-reviewed-behaviorcheck-list)に反映した。完成済み会議室への追加1回で、0件・対象なし・業務接続を含む24項目を得た。AIによる完成品や必須工程としての採用ではなく、人間の工数削減は未測定である。

## 役割分担と評価対象

[目的の再確認](https://github.com/mk3008/alder/pull/63#issuecomment-5738263778)に従い、今回の成果物を、**完成済みBusiness Design全文から、人間がレビュー・修正・追加して完成させる検査項目の初稿を作るためのprompt**とする。

- Business Design: 人間がゼロから作る → AIが業務相関レビュー → 人間が修正して完成。
- 機能・検査項目: 完成済みBusiness DesignからAIが初稿を作る → 人間がレビュー・修正・追加して完成 → AIが自動テストを実装。

初稿の作成主体が異なる。AI生成直後の一覧や高Confidenceの項目は完成品ではない。業務設計の穴探し、全ベンチマークの完成、AI単独での完全抽出を本研究の達成条件にしない。c2までの不確実性中心の評価、優先項目だけで確認を終えられることへの偏重は訂正する。

## 実用promptと最小の観点

利用する全文は[c3 prompt](candidate-c3.md)。入力はBusiness Design全文、出力の整理単位だけをActivityとする。次の5点は既存のQ1–Q3/P1/Sと[選定済みの要求検証・テスト設計知識](plan.md)を具体例の導出へ適用したもので、新たなレビュー理論ではない。

| 観点 | 具体的な検査項目への展開 |
| --- | --- |
| 対象業務の成立と結果 | 前提・主体・入力・契機を与え、成功結果と禁止を観測する |
| 前後の接続 | 前段Output→対象Input/When→後段開始条件をたどる。成功後の対象特定、不成立・対象なしの終了/継続、残る条件を見る |
| 横断制約 | What/Why、Dataの意味・件数・同一性、Role/権限、Rule、不変条件、Scopeを横断する |
| 代表場面 | 0/1/複数件、対象なし、重複、境界、禁止、一部成立、不要化、中断、何もしない場合から結果を変える場面を選ぶ |
| 根拠のレベリング | 期待結果をどこまで導けるかと、人間が確認すべき推定部分を分ける |

「0件」をProcedureに明記されているときだけ扱うのではない。一覧の抽出条件・Outputの意味から候補0件を導き、選択対象がないことと別条件での再確認を具体化する。ただし、専用画面・自動的な業務遷移・再試行方式まで定めない。前段が成功しても、後段が別時点の条件を再検査する設計ならその境界を保つ。

c2の引継ぎの取りこぼしは、Activity内の状態展開へ寄り、全文から接続を展開する指示が弱かったという補正対象として扱う。c3はそれを明示した最小の指示変更である。過去の穴あり設備保全入力に欠けている意味をAIが確定してよいという意味ではなく、今回の主評価には既に完成した会議室snapshotを使う。

## 固定書式・分類・Confidence

先頭に「人間レビュー前のたたき台」、入力版、適用条件、優先IDを示す。ActivityごとにID・検査名と8欄（対象業務、条件/契機/入力、観測結果、禁止、根拠、分類、確度、レビュー優先度）の短いカードを並べる。幅広い表やコード知識を必須にしない。

| 分類 | 期待結果と人間確認 |
| --- | --- |
| 明示 | 直接書かれた結果。転記誤りや不足する具体例も人間レビューの対象 |
| 強い導出 | 全文の複数記述からほぼ一意。根拠間の結び付きと条件を確認 |
| 考慮候補 | 自然な重要場面に対する具体的な期待結果案を「候補・未承認」と表示。推定部分を人間が採用・修正・除外 |

Confidenceは「高 / 要精査」。期待結果の根拠の強さであり、承認・網羅性・校正済み確率ではない。考慮候補は要精査。レビュー優先度は「優先 / 通常」と別に示し、候補・要精査・長い推論を先に読む目安とする。通常を自動承認せず、人間は一覧全体の不足・誤りを修正・追加する。

本当に業務意味・決定権の選択が必要なものだけ、別枠「Business Designへ戻す事項」にする。推定可能な候補をすべて「未確定」に落とさず、逆に候補名義で新たなpolicyを決めない。すでに承認された事項は再質問しない。

## 人間レビューとテストへの受渡し

人間は項目ごとに根拠、条件、期待結果を読み、候補の採用/修正/除外と不足項目の追加を行う。Business Designの意味を変更するなら先に正本へ反映する。項目書の完成を記録してから、同じ版の正本とともにテスト実装へ渡す。

項目の対応は**入力版＋項目書版＋ID**で保持する。異なる出力間で同じMR-07が別の意味になったため、ID単独では対応させない。後続AIは前提・操作・観測・禁止をテストへ対応付け、未承認候補や業務設計への差戻し事項を合否期待値にしない。テスト成功は人間の承認を代替しない。

この運用は人間による完成を明示するもので、人間が今回の生出力を承認したという記録ではない。研究のAI評価者による点検は、人間レビューの実測・代行とは区別する。

## 境界

UI/API/DB方式、明示的な非対象、数値上限、新しい状態・Role、一律の無変更保証は発明しない。全代表場面を全業務へ機械的に当てはめない。外部業務を実装する要求と、現在の結果を次の判断へ引き継ぐ検査を区別する。

AIの取りこぼしは人間が追加する対象となる。取りこぼしがあるだけで初稿生成の価値を否定しない。一方、誤った確定期待値や根拠の薄い候補が多ければ初稿としても使いにくいので、具体例と修正点を評価する。人間がゼロから作る場合との時間差・見逃し差は計測していないため、負荷軽減を実証したとはしない。

## 既存3ケースの位置付け

| 証拠 | 本研究で使えること | 使えない主張 |
| --- | --- | --- |
| 設備保全 c1/c2（穴あり） | 通常条件の広がり、実作業と依頼件数、不要化、引継ぎへの観点補正の材料 | 完成済み入力からのc3導出が成功/失敗したという評価 |
| 購入 c1/c2（穴あり） | 記録の意味・一部成立・不要化を具体例として考える動機、未承認policyを確定しない境界 | 未決4点をすべて解決しなければ検査項目研究が完了しないという条件 |
| 会議室 c1/c2（穴あり・resolvedを分離） | 承認済み意味、日時・占有・継続を具体例へ展開した既存の証拠 | 要確認0件だから一覧が完成・網羅しているという評価 |
| 初回の下流設計probe | 正本と一覧を併読し、6項目中4項目を限定条件の37設計ケースへ展開、2項目を保留できた | c3の全項目から実行可能なテストが完成したという評価 |

各段階の実行条件と生出力は[初回](results.md)、[第2段階](stage2.md)、[第3段階](stage3.md)に残した。最新のcompleted-input試行と具体的なレビュー例は[第4段階](stage4.md)に記録する。業務設計の完成や過去oracleとの件数一致を目的に、追加の業務判断や総当たりを行わない。

## 最新の観測と再検討条件

[c3の第4段階評価](stage4.md)では、完成済み会議室から24項目（明示3・強い導出20・考慮候補1）を得た。優先7件。0件後の再確認/終了、対象なしの不成立/再特定、変更失敗後の元予約維持と取消、保存結果喪失後の同一対象への継続が具体化された。M1/M2の確定部分は再質問せず、未保存中断への拡張案1件を未承認の候補とした。全24項目を評価者が原文へ照合し、人間向け確認点と下流設計例を記録した。

c2にも有用な境界や接続があり、c3の件数増を品質改善とはみなさない。分類の安定性やprompt単体の因果効果は未証明。追加Freshは1回、通算8導出と初回の下流設計probe1回で終了した。c3については評価者による下流設計例のみで、追加Fresh probe・実行可能テストはない。

限定採用は、人間が点検・補正できる実用的な初稿を得たことに基づく。AI単独の漏れゼロを条件にせず、同時に人間のレビュー負担が減ったとは断定しない。c3は完成済み入力1件の観測であり、別業務への一般化、人間の理解・修正負担、ゼロからの作成との比較は未検証。

実利用で、初稿修正がゼロからの作成より重い、考慮候補がpolicy発明を招く、根拠のある接続や0件が繰り返し落ちるとき、問題の観点に限って再検討する。必須化やレビュー省略を求めるなら、その効果と誤りの実測を別途必要とする。全F/Pの業務判断や全ケースresolved化を追加の完了条件にはしない。
