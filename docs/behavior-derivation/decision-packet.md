# 業務判断の記録と未決事項（研究完了のゲートではない）

[継続指示](https://github.com/mk3008/alder/pull/63#issuecomment-5738020150)に従い、F1–F4/P1–P4の回答依頼は取り下げる。以下の未決事項は検出能力を評価する資料として残す。実際に当該場面を仕様化・テスト化する際には判断が必要だが、ベンチマーク完成のために解決する必要はない。

これは[Issue #62](https://github.com/mk3008/alder/issues/62)の研究用snapshotに必要な判断であり、実サービスの運用変更依頼ではない。M1/M2は2026-09-19の[人間判断](https://github.com/mk3008/alder/pull/63#issuecomment-5737722908)で確定した。F1–F4/P1–P4は未承認。元Business Designは変更せず、承認済み部分をevaluation用snapshotへ出所付きで反映する。

## 承認済み — 会議室予約

M1は下記B、M2は利用者自身による保存確認・成立済み対象予約の特定・後続業務の継続で確定した。[resolved snapshot](../../work/behavior-derivation/stage2/inputs/meeting-room.md)と[業務相関再確認・評価](stage2.md)へ反映済み。以下は判断時の選択肢を残した記録であり、再承認の依頼ではない。

**M1: 空き確認の「予約可能」は何を意味するか。**

Activity 1は開始＜終了、現在の会議室状態、占有の有無で候補を選ぶ。一方Activity 2は開始が予約時点より未来であることも要求する。過去の時間帯を一覧に含めるかで、前段のOutputが変わる。[#36の根拠](https://github.com/mk3008/alder/issues/36#issuecomment-5633135941)。

| 選択肢 | 研究用Business Designに反映する意味 | 影響 |
| --- | --- | --- |
| A: 状態・占有に合う空き候補 | 過去の時間帯も検索できる。空き確認は未来条件を保証しない。予約時には未来条件を含め再検査する | 現行Activity 1の手順を維持し、Outputの限定を明記する |
| B: 検索時点で時間条件も満たす予約候補 | 検索時も開始が未来であることを条件にする。後からの競合・状態変化については予約時に再検査する | Activity 1の条件を追加し、検索結果の意味を揃える |

評価コストだけで選ぶならAが小さいが、業務上どちらが正しいかをAIは決定しない。どちらも枠の仮押さえ・実利用保証・通知の追加は含まない。判断担当: 業務設計責任者。

**M2: 保存後に予約結果を受け取れなかった場合の照合責任。**

同じ予約の再試行が重複として成立しないことと、元の予約を利用者が特定して変更・取消できることは別である。[#34](https://github.com/mk3008/alder/issues/34#issuecomment-5632329045)はこの責務を未決としている。利用者自身が既存予約を照合するか、会議室管理担当者が外部で照合・引継ぎするか、という選択肢を提示していた。現在は利用者自身による照合・継続で承認済み。方式・UIは指定しない。

M1/M2とも回答済み。照合のUI/API/識別方法は指定せず、単純な再試行成功を対象特定の代わりにしない。

## 後続の判断 — 設備保全

[既存oracle #32](https://github.com/mk3008/alder/issues/32#issuecomment-5630178622)。以下の条件における意味・担当を決める。システム内機能追加を必須にしない。

| ID | 判断すること | 未決のまま試験すると変わる期待値 |
| --- | --- | --- |
| F1 | 予定済み依頼がある設備を危険と判断したとき、新規日程と既存作業を誰が止めるか。閉鎖中の新規故障報告も受け付けるか | 閉鎖・日程・報告の許可、後続作業の継続 |
| F2 | 閉鎖原因への対処が必要なとき、外部対処から再点検までを誰が引き継ぐか | 再点検判断と現実に利用可能になる原因の接続 |
| F3 | 一つの実作業が複数依頼を解消した場合、依頼ごとに何を確認して完了・終了とするか | openの残存、未実施の作業を完了したと記録しない保証 |
| F4 | 日程設定後に作業不要・対象誤りと分かった場合の終了担当と方法 | scheduledの残存と閉鎖への影響 |

反復閉鎖・解除、不存在対象など設計に明示保留された境界も、resolved snapshotの適用範囲を宣言するときに扱いを確認する。すべてを実装要求にするのではなく、通常業務の意味へ影響する保留を残したまま完成としない。

## 後続の判断 — 備品購入申請

[既存oracle #33](https://github.com/mk3008/alder/issues/33#issuecomment-5630314919)。

| ID | 判断すること | 未決のまま試験すると変わる期待値 |
| --- | --- | --- |
| P1 | 購入日時は実際の購入時刻か、結果登録時刻か | 翌日登録した場合の日時 |
| P2 | 希望額・実購入額は同じ単位の申請全体額か。希望額超過を誰が購入前に判断するか | 承認の効力と購入成立の条件 |
| P3 | 全量購入のみで完了するか。一部購入後に残部が不要・購入不能な場合はどう終了するか | purchasedの意味と対象数量 |
| P4 | 承認後に不要となった申請を誰が購買対象から外し、引き継ぐか | 未購入の事実と購買対象資格 |

数量・金額の値域など導出時に新たに現れる問いは、その業務への影響を評価して追加判断の要否を決める。既存実装の仮定をそのまま採用しない。
