# Alderにおける詳細設計の位置づけ

[Alderへ戻る](../README.ja.md) · [設計思想（英語）](philosophy.md#where-detailed-design-fits)

Alderでは、詳細設計を実装前の独立した必須工程とはしていません。これは「設計しない」という意味ではありません。**人間が先に決める価値が高いことと、実装しながら具体化してレビューできることを分けます。**

従来は、実装前に言語、構成、テーブル、クラス、アーキテクチャなどを広く決めてからコーディングへ進むことがあります。Alderでは、技術的な詳細をすべて先に固定すること自体を完了条件にはしません。AIを使った実装では、DDL、SQL、コード、テストを短い反復で一緒に具体化し、実際に成立する形を見ながら修正できます。先に固定した詳細が、まだ確認されていない制約として実装を縛ることも避けます。

一方で、後から変えるコストが高いこと、既存環境によって既に制約されていること、業務上の意味や外部との約束に関わることは、実装前に明示する価値があります。

## 何を先に決めるか

| 扱い | 例 | 理由 |
| --- | --- | --- |
| **先に明示する価値が高い** | 既存インフラへの配置、既存DB / schemaとの互換性、利用が決まっているクラウドサービス、公開済みAPI、データ移行条件、セキュリティ・法令上の制約 | 実装の選択肢を実際に制約し、後から変えるコストが高い |
| **希望や組織上の理由があれば明示する** | 使用言語、DB製品、クラウド製品、主要ライブラリ | 保守体制、既存資産、組織標準、本人の希望など理由があれば重要。理由がなければ、実装時に選んでもよい |
| **通常は実装時に具体化しやすい** | クラスや関数の分割、内部モジュール構成、局所的な実装方式、命名、可逆な小さな技術選択 | 実装とテストを見ながら低コストで変更でき、人間が事前に一つずつ決める効果が小さい |

ここで「通常は実装時に具体化しやすい」とした項目も、重要でないという意味ではありません。**人間が実装前に決める必要性が低い**という意味です。AI実装者が現在の要求・制約から選び、コードやテストとして具体化した後でレビューできます。

## 既存インフラや外部サービス

「既存のECS環境へ配置する」「既存PostgreSQLを使う」「認証は既存のEntra IDへ統合する」のような条件が既に決まっているなら、実装者へ先に渡します。これらは自由な技術選択ではなく、現在の実装条件です。

外部サービスは、なぜそのサービスを使うのかによって位置づけが変わります。

- 「決済APIとしてStripeを選ぶ」は、代替可能な技術選択ならSystem Design側の判断です。
- 「会社がStripeを決済事業者として契約しており、この業務はStripeで決済する」は、業務成立条件や既存制約にも関わります。

製品名だけでBusiness / Systemを分類するのではなく、**その選択が業務上の約束なのか、実現手段なのか**を確認します。

## 言語は希望があれば伝える

使用言語も、必ず事前に決める項目ではありません。

既存コードがC#である、チームがTypeScriptを保守している、組織標準がある、自分が特定言語で保守したい、といった理由があれば明示します。そうした理由がなければ、実行環境や既存Repositoryを見て実装者が選んでも構いません。

Alderが避けたいのは「言語を決めてはいけない」ことではなく、**理由のない選択まで人間の必須判断として増やすこと**です。

## アーキテクチャ名より、必要な理由を伝える

AlderはClean Architecture、DDD、Ports and Adapters、CQRSなどの採用を禁止しません。ただし、アーキテクチャ名そのものを要求へ変換することは勧めません。

たとえば、

- 「Clean Architectureで作る」
- 「CQRSを使う」

と先に指定するより、

- 外部I/Oなしでコアロジックを検証できる必要がある
- 既存DBを将来置き換える具体的な予定がある
- 参照負荷と更新負荷が大きく異なり、別々にスケールさせる可能性がある

のように、**守りたい性質や具体的なリスクを渡します。** 実装者はそれを満たす構造を選びます。

特定のアーキテクチャを使う組織標準や明確な既存制約があるなら、それも実装条件として伝えて構いません。問題なのはアーキテクチャを使うことではなく、理由のない名前を要求そのものとして扱うことです。

## なぜ全部を先に決めないのか

Alderが技術詳細をすべて事前確定しない理由は、設計を軽視するからではありません。

- 実装、DDL、SQL、テストによって、設計判断を実際の振る舞いとして確認できる
- AIによって可逆な実装変更の反復コストが下がる
- まだ必要性が確認されていない詳細を先に固定すると、その選択自体が不要な制約になり得る
- 人間の判断を、業務意味、不可逆な変更、既存制約、外部契約など、本当に先に決める価値が高い箇所へ集中できる

AIを使っても、永続データ、公開済みインターフェイス、外部契約、運用移行まで簡単に可逆になるわけではありません。そのため、**「詳細設計工程を置くか」ではなく、「この判断は今固定する必要があるか、後から安全に変えられるか」**を基準にします。
