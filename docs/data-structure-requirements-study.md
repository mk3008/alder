# データ構造要求の記述・レビュー — Issue #114 研究結果

対象: Alder `7a9e94eaf01be8ade0ce7f3aef4984056f7f628e`。これは業務上の構造的要求をBusiness Designで扱う方法の検討であり、形式・Plugin・review knowledgeの改訂ではない。

## 結論

**A: 現行セクションを使い、構造が業務上の可能な状態・操作・保証を変える箇所に、その意味を自然言語で書く**ことを推奨する。新しい欄やObject.Informationの構文は現時点では追加しない。既存の記述指針に、次の確認観点を後続Taskで短く加える価値がある。

Business Designが与えるのは**データモデルが満たすべき業務側の構造要求**であり、最終データモデルを一意に規定するものではない。最終的なデータ構造は、その業務上の要求と、性能・既存スキーマ・移行・保存量などのシステム要件や既存制約の双方を満たすよう、後続の設計・実装で選択する。同じ業務意味を満たす構造は複数あり得る。

> 同じBusiness Designを満たすように見える二つの構造で、依頼者から見た「何を一件として扱えるか」「何を独立に変更できるか」「どの状態を残し、何を重複として拒むか」が変わる場合、その差を実際の仕事の欄に記述するか、判断待ちの問いとして残す。DBの列・NULL・キー・中間表は先に決めない。

**一件の記述単位はER上の関係ではなく、業務上の判断・結果差**である。関係の両端と多重度を列挙すること自体を目的にしない。例えば「社員と案件がN:N」という語だけでは、所属の期間、兼務、変更と承認の単位が決まらない。人数制限や所属期間が業務に必要なら、それぞれを該当する判断・状態とともに書く。

## 現行形式との照合

- [導入ガイド](adoption.md#authoring-and-checking-business-correlations)はObject.Informationを情報概念の概要とし、完全なcardinality、キー、型、テーブル対応を要求しない。[記述品質レビュー](business-design-quality-review.md)も同じ境界を置く。
- [review knowledge v0.3](phase2/review-knowledge-v0.3.md)のQ3は対象・意味・処理単位・保証、P1は複数件やまとまりの変化、P2は実装が固定した意味からの逆引きを扱う。Sは具体的な仕事の差がない追加要求を止める。既存原則で事後の問いは立てられるが、著者が最初から重要な構造的要求を明示するための具体例は薄い。
- [会議室予約](../business-design/meeting-room/README.md)では予約の識別、対象会議室・予約者、時間重複による拒否が業務語で表現されている。[備品購入申請](../business-design/purchase-request/README.md)では申請の識別、申請の品名・数量、申請単位の承認が示される。ただし後者は「一申請に複数明細を束ねられる」とは述べていない。複数明細対応を現状から推測してはいけない。

以下は**比較のために作った仮想例**であり、既存案件の確定要件ではない。Informationは概念、Inputは受け取る内容、Procedureは判断・更新、Resultは成立する状態、Exceptionは失敗・戻り、Whenは開始の契機として使う。複数の欄に同じ文を転記せず、それぞれ異なる役割だけを記す。

| 結果が変わる場面 | Business Designで確認できる記述例 | 決め打ちしないこと |
| --- | --- | --- |
| 一注文一品 / 複数明細 | 注文確定のProcedureに「一つの注文に複数の品目と各数量をまとめられる」。Resultに「注文全体が一件として確定し、各品目はその注文に属する」。Informationには注文内容・品目と数量の概念。 | 注文・明細の表数、PK/FK、行数上限。複数明細が業務に不要なら一品でもよい。 |
| 配送先必須 / 店頭受取では不要 | Inputに受取方法。Procedureに「配送では配送先を指定し、店頭受取では求めない」。Resultは受取方法と必要情報が揃った注文。 | nullable列か別表か、住所の物理表現。 |
| 1:N / N:N | 所属登録のProcedureに「社員は複数案件へ参加でき、案件には複数社員が参加できる。案件ごとに担当を変更できる」。Resultに案件ごとの有効な担当。 | 中間表、所属履歴の要否、上限の有無。単に人名一覧を置くだけでは独立変更可能性が伝わらない。 |
| 現在値のみ / 注文時点を残す | 受注のProcedureに「受注時の販売価格を確定する」。Resultに「後日価格表が変わっても受注金額を再現できる」。注文内容のInformationに確定時点の金額。 | 価格表の版管理、スナップショットの保存方式。将来の監査期間は別途確認する。 |
| 個別確定 / グループ単位確定 | 承認のInputに承認対象、Procedureに「申請に含む全品目を一件として判断し、一部だけ承認しない」。Resultに申請全体の承認状態。部分承認が実際に必要なら逆の条件を書く。 | トランザクション境界やUI選択方式。 |
| 単独一意 / 組合せ一意 | 会員登録のProcedureに「同じ組織の中では会員番号を重複登録しない。別組織では同じ番号を使用できる」。Resultに組織内で識別可能な会員。 | UNIQUE制約や主キーの列、番号の採番方式。 |

さらに、**同一性**は「氏名変更後も同じ会員として扱う」「取消後の再申請は元の申請と別件」のように継続・分離を必要とする仕事で表す。**履歴**は「何を、いつの状態として、誰がいつまで参照できるか」を必要な範囲で確認する。**処理単位**は判断や保証の単位をResultと後続のWhen/Inputで照合する。これらを全Objectへ機械的に必須入力させない。

## A/B/Cの比較

| 観点 | A: 現行欄へ置く | B: 既存欄へ定型行を追加 | C: 任意の専用欄 |
| --- | --- | --- | --- |
| 依頼者可読性 | 行為と結果のすぐそばで意味を読める | 情報のまとまりは見つけやすいが、判断との往復が必要 | 構造だけ一覧できるが、業務から離れた用語になりやすい |
| 記述負荷 | 実際に差が出る場面だけ書ける | 既存欄と定型行の配置判断が増える | 欄と元のActivityの両方の保守が増える |
| レビュー再現性 | Q3/P1/P2に具体例を与えれば、仕事の差から探せるという予測。Fresh比較は未実施 | 所在は明確になるが、定型行だけで操作・保証を読み取れるとは限らない | 見落とし防止の仮説はあるが、欄の有無を合否と誤認し得る |
| 二重管理 | 同一条件を複数欄へ複写しない限り低い | Informationの関係とProcedureの条件がずれる可能性 | 同じ要求をActivityと専用欄に二度書く可能性が最も高い |
| ER/DDLへの誘導 | 業務上の条件を起点にできる | 対応形式によって多重度・キーの先決を誘う | 欄名・テンプレート次第で網羅的ER設計を誘いやすい |

B/Cの利点は検索性と記述位置の明瞭さだが、その利点がAの業務場面別の例示を超える実測証拠はない。特にCは[品質要求の専用欄の試行](adoption.md#business-quality-requirements-belong-where-they-constrain-the-work)で見られたような意味の重複・帰属ずれを起こし得る。これは今回のCを実験で否定したという意味ではない。Aでも著者が構造による結果差に気づかなければ書けないため、記述指針とレビュー例を補う必要がある。

## レビューの境界と次の検証

1. 事前には、通常の一件、複数件、独立した変更、例外・再実行、後続への引継ぎで**結果差が現実に生じる場面**だけを確認する。根拠のない全関係の多重度・必須性の棚卸しは行わない。資料内で決まらない業務選択は依頼者への質問として残す。
2. 実装後はDDL、制約、コード、テストが実際に選んだ同一性・任意性・多重性・履歴・確定単位をP2で拾い、Business Designに戻してQ1〜Q3/Sで分類する。たとえば配送先が常時必須なら店頭受取ができないという確定不一致、申請の部分承認が仕様上未決なら具体的なBusiness確認、表の分割だけなら技術選択として扱う。
3. DB制約は確認済みの業務条件を強制する有力な手段だが、条件付き一意性、時点、権限、外部事実、並行更新などは列定義だけでは決まらない。Business DesignをDDLから逆算して合意した扱いにしない。

本研究は既存文書と六組の対照例に基づく**机上比較**である。独立したFresh author/reviewerによる発見率・再現性、依頼者の読解負荷、実案件での記述ドリフトは測定していない。Aの採用はこの限界付きの設計判断であり、強い効果主張ではない。後続Taskでは、まずauthoringとレビューの指針に短い観点と対照例を加え、同じヒアリング入力で現行指針と改訂指針のFresh比較を行い、問題が残るときだけB/Cを再検討する。Pluginやexportの形式変更はこの研究からは導かれない。
