# Business Designの構造を使うレビュー — PR #80試行候補

## 適用範囲

既存の[作成・相関確認](adoption.md#1-place-business-design-where-the-agent-can-read-it)と[任意の機能考慮探索](behavior-derivation/functional-considerations.md)を先に適用する。以下は追加の読み直し方の候補であり、欄の存在、単語の一致、全項目の網羅、機械的な合否判定を求めない。Business Designの意味を新たに決めず、具体的な誤読や受け渡し不能を示せる指摘だけ残す。

1. **Result ↔ When:** 正常終了で成立する状態と後続の通常開始理由を対で読む。任意の業務や例外復帰を必須の直列工程にしない。結びつかない場合も、独立した外部依頼なら欠落としない。
2. **I/O ↔ Procedure:** 各Objectから実際に読む内容と書く内容を、正常手順から逆引きする。更新時に既存の情報を読むならOutputだけではInputを代用できない。ラベルの逐語転記は不要。
3. **Object.Information ↔ I/O ↔ Procedure:** Objectが持つ概念、受け渡す情報、手順で使う情報に意味上の矛盾がないかを見る。Informationの全概念を毎回渡す必要はない。出力の対象属性を明示した業務では、その属性が元のObjectと手順に含まれるか確認する。
4. **Exception ↔ Exception When:** 発生側の返し先と受け側の再開理由が一致し、業務意味の修正を下流で確定していないか読む。正常のI/Oに例外を複製しない。
5. **Scope / Who:** 対象業務と隣接業務の責任境界、手順の実施主体と人間の意味確認を突き合わせる。Scope外に内部工程を追加しない。
6. **同一Objectの情報契約:** 一Activity内で同一Objectを同方向に複数回使う場合、その受け渡しが一つの短い契約として読めるか確かめる。異なる方向のInputとOutputは更新業務で自然に共存する。

指摘には原文の行、利用者が困る具体的な場面、既存ガイドでも見つかるか、新候補で初めて見えるか、誤検知の可能性を付す。既決の方針や既存資料で閉じる案は除く。この試行一例だけをもって一般的な検出率向上や恒久採用を主張しない。
