# Issue #5 実装判断・検証記録

## 入力と範囲

入力は `business-design/facilities-maintenance/README.md` と `initial-ddl.sql` の2点のみ。過去PR、研究ブランチ、過去実装、研究用acceptanceの内容は参照・流用していない。リポジトリ内にAGENTS.mdは見つからなかった。

5業務を永続化可能なローカルCLIとして実装した。UI形式の指定がないため、再現性を優先してCLIを選択した。Python標準ライブラリのsqlite3、argparse、unittestに限定し、外部パッケージや実行サービスを不要にした。

## 構造と整合性

- `maintenance/__init__.py`: 業務操作、ロール検査、日時正規化、SQLiteトランザクション。小規模な5業務のため、リポジトリ層やORMを追加せず、各操作で必要なSQLを直接実行する。
- `maintenance/__main__.py`: CLI入力とJSON出力。業務判断はApplicationに集約する。
- `maintenance/schema.sql`: 新規SQLite DB用の実行DDL。
- `tests/test_maintenance.py`: 業務仕様から構成した独立シナリオとCLI検証。

各書き込みをBEGIN IMMEDIATEで囲み、設備状態の読取から依頼更新まで他接続の書き込みを排他する。日程設定と安全閉鎖の競合で、確認時と書込み時の設備状態が食い違わない。例外時はロールバックする。複数テーブルの一覧も単一読取トランザクションとする。SQLiteのロック待ち上限は10秒で、超過時はエラーを返し自動再実行しない。

認証方式は入力設計で未指定。ロール検査は全業務で実装するが、CLIのロール宣言は信頼されたローカル実行用であり認証機能ではない。報告者名は業務入力として保持する。設備の初期登録と一覧は検証・ローカル運用用の補助コマンドとした。

## DDLの変更

初期DDLは設計入力として変更せず、実行DDLを別配置した。既存DBの移行は対象外。

| 差分 | 理由 |
| --- | --- |
| TIMESTAMPTZをTEXTにする | UTC固定形式の文字列をアプリで生成し、SQLite上で時点の大小比較を一貫させる |
| 主キーにNOT NULL、設備IDに空文字検査 | SQLiteのTEXT PRIMARY KEYでNULLを許す挙動を防ぎ、識別可能性を保持する |
| 報告者・症状に空文字検査 | 必須入力を永続化境界でも補強する |
| 状態と予定・完了日時の組合せCHECK | open/scheduled/completedの記録の整合性を保持する |
| completed_at >= reported_at | 完了が報告に先行しないことを補強する |
| 設備・依頼状態の索引 | 閉鎖時にscheduled依頼の存在を確認する |

外部キーを各接続で有効化。時刻形式とロール、操作順序、未来条件はApplicationで検証する。DDLだけで業務APIを迂回する任意SQLまで保証する設計ではない。

## 解釈・未決定事項

| 項目 | 判断・理由 |
| --- | --- |
| 予定より早い完了 | 許容。予定日時を保持する |
| 予定日時が現在と等しい | 拒否。「未来」は厳密に大きい時点とする |
| 報告日時が現在より未来 | 入力設計に禁止がないため報告自体は許容。ただし完了時点が報告日時に達していなければ変更せず拒否する |
| 時刻の取得 | UTCシステム時計をトランザクション内で取得。テストだけ時計を注入する。利用者による完了日時の入力は提供しない |
| 同一設備の複数報告 | 許容しUUIDで別依頼として記録する |
| scheduled依頼を持つ設備の安全閉鎖 | 未決定のため、変更せず未対応エラー。閉鎖の許可・取消・延期などの業務ルールを創作しない |
| 閉鎖済み設備への新規報告 | 未決定のため、変更せず未対応エラー |
| 同じ状態への閉鎖・解除の再実行 | 変更せず拒否。冪等成功とはみなさない。閉鎖→解除→閉鎖の正規の状態遷移は、各点検の判断が入力されたものとして許容する |
| 存在しない設備の閉鎖・解除 | 変更せずnot-foundエラー。設備を自動生成しない |
| 外部SQL等でclosed設備にscheduled依頼がある場合 | 完了も未対応エラー。通常APIからはこの組合せを作れない |
| 監査・通知・外部／オフライン完了 | 保留、実装対象外 |

未対応エラーは暫定の実行境界であり、業務上その行為が禁止と決定したものではない。安全閉鎖を実運用に適用する前には、特にscheduled依頼がある場合の扱いを人間が決める必要がある。現在定義済みの経路の実装には、その判断を先取りする必要はない。
