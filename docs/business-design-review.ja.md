# 会議室予約のレビュー事例 — 保存できても、仕事を続けられるか

[READMEへ戻る](../README.ja.md) · [相関チェック](business-design-correlation-check.ja.md) · [漏れのチェック](business-design-omission-check.ja.md)

Alderのレビューは、業務設計書と実際の振る舞いから、業務を続けるために人間が決めるべきことを具体的な問いにします。このページでは、会議室予約で見つかった「予約は保存されたが、利用者は予約IDを受け取れない」という事例を説明します。

これは[Issue #34のレビュー結果](https://github.com/mk3008/alder/issues/34#issuecomment-5632329045)に基づく、当時の実装との照合を含む事例です。READMEに掲載している記述例へ、意図的な欠陥を加えたものではありません。

## 何が起きたか

対象の実装は、予約をDBへ保存した後で、CLIから予約結果を出力していました。利用者は返された予約IDを使って、後から変更や取消を行う想定でした。

```text
予約をDBへ保存することに成功する
        ↓
利用者へ結果を出力する処理が失敗する
        ↓
予約は存在するが、利用者は予約IDを受け取れていない
        ↓
後から変更・取消をしたいとき、対象の予約をどう特定するか？
```

当時の検証では、保存後の出力にエラーを発生させても、DBに予約が残ることが確認されました。同じ予約をやり直すと、既存の予約との重複で拒否される可能性があります。空き一覧から会議室が消えたことだけでは、自分の予約が成立したのか、他の人が予約したのかは分かりません。

## 何を見て問いにしたか

| 見たもの | 分かったこと |
| --- | --- |
| 業務設計書の予約業務のOutput | 登録された予約を、利用者が受け取ることになっている |
| 変更・取消業務のInput | 後続の操作には、対象予約の特定が必要になる |
| 実装の保存と出力の順序 | 保存の成功と、利用者による結果の受領が分かれる |
| 利用手順と運用の説明 | 結果を受け取れなかった場合に、誰が照合して引き継ぐかは当時未確定だった |

ここでの問いは、成立した予約を誰がどう照合し、利用者へ引き継いで、変更・取消へ進めるようにするかです。DB保存の原子性だけでは、この責務は決まりません。

レビューでは、通常の一件を担当者としてたどるP1と、実装が選んだ振る舞いから設計へ戻るP2を使い、中断後の継続と、前後の仕事の受け渡しを確かめました。文書だけで行う相関チェックと、実装を参照した具体化の両方が、この問いにつながっています。

## 人間へ返した確認事項

たとえば、オペレーターが予約者・会議室・時間帯・目的などから成立済みの予約を照合し、正しい予約IDと現在の状態を利用者へ伝える運用で継続できるかを確認します。

その責任と手順が既存の運用で満たされるなら、そこで確認を閉じられます。満たされない場合は、結果を確認できる手段と担当を人間が決めます。レビューは、照会画面や特定の技術方式の追加を一律に要求しません。

これが「業務上の確認候補」として返す意味です。AIが仕様を増やすのではなく、成立済みの事実を保って仕事を続けるための判断を、責任者に返します。

## 自分の業務で使うには

まず、業務設計書の[記述品質](business-design-quality-check.ja.md)と[業務相関](business-design-correlation-check.ja.md)を確認します。必要に応じて、[未記載の条件を探索](business-design-omission-check.ja.md)します。実装後は、[導入ガイド](adoption.md)のレビュー手順で、実装・テストも設計に照らします。

問いへの答えを人間が決めたら、業務設計書へ反映して合意し、その内容から検査項目や実装を更新します。すべてのシステムに、この事例と同じ機能や運用を追加するという意味ではありません。

## 事例の出典と時点

- [Issue #34の報告](https://github.com/mk3008/alder/issues/34#issuecomment-5632329045)は、コミット`94f6f639b850a92ce5ad55812a4899e7a2c7bc33`を対象としたレビューです。保存後の出力失敗と、当時の照合責務の未決事項が報告されています。
- 後の[業務判断の記録](behavior-derivation/decision-packet.md)では、評価用の設計について、利用者自身が保存確認・対象特定・後続業務の継続を行う方針が承認されています。当時の指摘を、現在も未解決の不具合として紹介しているわけではありません。
- 同じ論点が毎回必ず見つかるわけではありません。後続レビューで主要論点として再現しなかったことも、[レビュー知識の検証記録](phase2/review-knowledge-v0.3.md)に残されています。
