# 購買改善の提案例

[READMEへ戻る](../../README.ja.md) · [業務改善の手順](../optimization-review.md) · [業務設計書の書き方](../business-design-structure.ja.md)

承認済みの購入申請が増えると、購買担当者は申請ごとに購入し、その結果を登録する作業を繰り返します。この負担を減らしたいとき、Alderは業務設計書から改善候補を考え、期待する効果と採用前の確認事項を整理します。

このページは、[購入申請の業務設計例](../../business-design/purchase-request/README.md)をもとに、改善レビューの入力と提案を説明するものです。以下の困りごとをユーザーと確認できた場合を想定しています。実際の導入では、現場の状況を確認して業務設計書へ記録してください。

## 1. 困りごとを記録する

該当する購入業務のActivityで、Resultの後に次のように記録します。

```markdown
## Problem

承認済みの購入申請が増えると、購買担当者が申請ごとに購入し、結果を登録する負担が大きい。

## Pain level

High
```

分かる範囲で、申請件数、作業時間、転記ミスなどの情報も添えます。不明な数値を補う必要はありません。AIは記録されたProblemを起点に、少数の改善候補を検討します。

## 2. 改善候補を比較する

### 条件の合う申請をまとめて購入する

品目や購入時期などの条件が合う承認済み申請を、同じ購入機会にまとめて手配します。購入操作や確認の繰り返しを減らせる可能性があります。

- **変更範囲（Scope）:** Narrow。まとめて購入でき、購入結果を申請別に記録できる案件に限定する。
- **変更の難しさ（Difficulty）:** 中。購買担当者の判断基準と、申請ごとの金額の扱いを調整する必要がある。
- **守る条件:** 申請の承認は個別に行い、実購入金額と購入日時も申請ごとに残す。
- **確認すること:** どの条件ならまとめてよいか。購入を待てるか。申請別の金額を確定できない場合は個別購入に戻すか。

### 定型的な申請の購入と結果取得を自動化する

人間が決めた条件を満たす承認済み申請について、購入と結果の取得・ひも付けを自動化する案です。対象案件で、購入操作や結果転記を減らせる可能性があります。

- **変更範囲（Scope）:** Narrow。対象条件と例外時の扱いを定められる定型案件に限定する。
- **変更の難しさ（Difficulty）:** 高。購入権限、外部との連携、失敗時の判断や再実行の責任を合意する必要がある。
- **守る条件:** 人間による承認を保つ。実際の購入成立と申請別の金額・日時を確認してから購入済みにする。
- **確認すること:** どの申請を自動購入してよいか。購入先から確かな結果を取得できるか。結果が確認できないとき、誰が対応し、重複購入をどう防ぐか。

### 購入事務を外部の購買サービスに委ねる

利用できるサービスがある場合に、承認済みの申請に基づく購入手配を委ね、申請ごとの結果を受け取る案です。自社の手配作業を減らせる可能性がありますが、依頼・照合・例外対応とサービス費用も考慮します。

- **変更範囲（Scope）:** Narrow。サービスが扱える品目・条件で、申請別の購入結果を受け取れる範囲に限定する。
- **変更の難しさ（Difficulty）:** 高。購入責任、契約、費用負担、結果報告の条件を社内外で調整する必要がある。
- **守る条件:** 承認権限を保ち、購買担当者が申請と購入結果を照合する。責任を移す場合は、その変更を明示して合意する。
- **確認すること:** 利用可能なサービスがあるか。何を委ねられるか。結果の正確さを誰が確認するか。費用に見合う効果があるか。

Difficultyは、役割・権限・関係者の調整を含む業務変更の難しさです。実装するコードの量では決まりません。この例の評価も、現場の条件を確認して見直します。

## 3. 人間が採否を決め、業務設計書へ戻す

この三案は、効果や実現性が確定した採用案ではありません。まとめられる申請の割合、購入先との連携可否、外部サービスの条件などを確認して判断します。AIは最大3件の有益な候補を示し、候補がない場合や、すべてを見送る場合もあります。

たとえば、まとめ買いを採用するなら、対象条件、待機できる期間、申請別の金額の記録方法を業務設計書へ反映し、ユーザーと再合意します。その後、影響する検査項目や実装・テストを更新します。

改善候補の期待効果やDifficultyを、そのまま現在の業務上の事実として業務設計書やJSONへ転記することはありません。採用した変更を反映した業務設計書が、次の分析・改善・実装の共通の正本になります。

レビューに渡すプロンプト、候補ごとの出力項目、検討を止める条件は[Optimization Review](../optimization-review.md)を参照してください。
