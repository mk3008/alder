# PluginでJSONの業務設計を扱う

JSONを正本にすると、業務の草案作成と更新をPluginへ依頼し、人間は業務内容と変更の判断に集中できます。型付きパッケージにはBDとCheckを一緒に保存し、ID・参照・版を検査します。生JSONの手修正は必要ありません。

この機能は開発候補です。現在の公開版を更新したり、正式JSON v1を採用したりするものではありません。候補Pluginを使う際は、取得したブランチcommitを記録してください。

## 草案を作る

ヒアリングや今の業務の説明を渡し、JSON形式を明示します。

> Alderで、このヒアリングから業務設計をJSON正本として草案にしてください。

Pluginは必要なIDを割り当て、5W1H・入出力・手順・結果・未決事項を直接JSONへ記録します。構造検査後に新しいファイルを保存し、確認してほしい業務内容を説明します。回答のない条件を補って合意済みにすることはありません。

直接JSONの操作にはNode 24以上を実行できるAgent環境が必要です。実行できない環境ではファイルを確定したことにせず、制約を報告します。新規でJSONを指定しなければ、現在のMarkdown向け経路を維持します。

## 内容を更新する

> このJSONの「受付台帳」を「持出受付台帳」に改名し、確認後の通知業務を追加してください。通知媒体は未決のままにしてください。

既存IDを保ち、追加要素だけに新しいIDを付けます。版とファイルhashの競合、不明な参照、不正な候補は保存を止め、最後の正本を保持します。既存IDの削除は現在の保存経路では扱いません。

レビューのみを依頼した場合は、ファイルや人間レビュー状態を書き換えません。

## Checkを作成・確認する

> この業務設計の内容に合意します。未決事項はそのまま残して、Check草案をJSON内に作ってください。

Checkは、対象のBD版について人間が業務内容に合意した後に作ります。草案は未レビュー、未決の意味は要確認として残ります。変更のない確認済み項目は維持し、一般保証を変えた場合は再確認へ戻します。実際の人間の発言がない状態変更は行いません。

共有保証、比較例、根拠、Test証拠も同じパッケージで保持します。構造検査やテスト成功は、人間の確認を代行しません。

## 既存Markdownを変換する

> このAlderのMarkdownをJSONへ変換してください。元のMDは残してください。

一方向コンバーターにはNode 24以上とPython 3.12以上が必要です。対応profileと原典版を検査して新しいJSONを書き出します。元MDの削除・上書き、旧MD全文のJSON内格納、JSON→MD同期は行いません。購買研究草案のMedium/SR Dependenciesなど未対応欄は、削除して通さず診断して停止します。

## 現在の範囲

状態遷移・概念モデルの正式Schemaや表示は未決です。現行ViewerへのJSON組み込みも別工程であり、この候補から表示済みとは扱いません。自動Skill選択やホストごとの実行能力は環境に依存します。
