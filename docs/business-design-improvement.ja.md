# 業務設計書から改善提案を得る

[文書構造へ戻る](business-design-structure.ja.md) · [購買改善の提案例](examples/purchase-improvement.ja.md)

成立している業務の負担や遅延を減らしたいとき、業務設計書に記録したProblemとPain levelから改善候補を考えます。困りごとがあるときに行う任意の使い方です。仕様の未決事項は、先に業務分析の問いとして扱います。

## 用意するもの

ユーザーと確認した現行の業務設計書と版、対象Activityに記録したProblem / Pain levelを渡します。困りごとが新しく分かった場合は、まず業務設計書へ記録・確認します。頻度や作業時間などの事実が分かれば添え、不明な数値は補いません。

## 検討する観点

| 観点 | 検討すること |
| --- | --- |
| 省く | なくせる作業、入力、確認、受け渡しがあるか |
| 簡単にする・まとめる | 重複や分断を減らせるか |
| 自動化する | 人間の定型作業を、安全に自動処理へ移せるか |
| 委ねる | 既存のサービスや別の責任主体へ任せられるか |
| 残す | 承認、判断、責任、利用者の体験など、維持すべきものは何か |

すべての方向で案を出す必要はありません。Problemに関係する候補について、変更範囲（Scope）をNarrow・Keep・Expandで示し、理由を添えます。変更の難しさ（Difficulty）は、役割、権限、他部署、外部サービス、契約などの調整から考えます。Pain levelは探索の深さを考える手掛かりであり、Difficultyとの固定対応表ではありません。

## AIへ依頼するプロンプト

プロダクトのルートから使う例です。山括弧の箇所を置き換えてください。

```text
../alder/docs/business-design-improvement.ja.md と
../alder/docs/optimization-review.md に従い、業務改善レビューをしてください。

業務設計書: <対象パスと版>
対象Activity: <業務名>
Problem / Pain level: 上記の合意済み業務設計書に記録した内容を使う
補足する観測事実: <件数・作業時間など。なければなし>

Problemに関係する範囲から、削除、簡素化・統合、自動化、委譲、維持の方向を検討してください。
現行業務の意味・承認権限・処理単位・保証を守り、
それを変える案は、人間の業務判断が必要な変更として明示してください。

有益な候補を最大3件示してください。候補ゼロも認めます。
現状の言い換え、実質的に重複する案、無関係な改善で件数を埋めないでください。
候補ごとに、名称、Problemとの関係、改善の方向、Scopeと理由、期待する効果、
Difficultyと調整上の根拠、影響する関係者・業務、守る意味と制約、
仮定・不明点、人間が判断・確認する問い、確信度を示してください。
利用可能なサービス、契約、件数、効果量を推測で事実にしないでください。
採用案は決めず、読み取り専用とし、業務設計書やJSONは変更しないでください。
```

## 結果の扱い

採否は人間が決め、すべて見送ることもできます。採用する場合は、業務設計書の手順・責任・条件を先に更新して再合意し、その後に影響する検査項目や実装・テストを更新します。提案の期待効果やDifficultyを、そのまま現在の業務上の事実として転記しません。

具体的な候補の読み方は[購買改善の提案例](examples/purchase-improvement.ja.md)、出力項目や停止条件の詳細は[Optimization Review](optimization-review.md)を参照してください。
