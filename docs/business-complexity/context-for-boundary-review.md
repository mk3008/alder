# 担当境界を見直すためのcontextをどこに書くか

[研究の結論](../../work/business-complexity/issue-151/RESULT.md) · [定義案](issue-151.md)

## 逆算した結論

**担当をまたぐ手順まで見直したいなら、現在の分担だけでなく、「何を達成すればよいか」「その分担が必要な理由」「どの条件なら分担を変えられるか」を区別して渡す。** 工程数や総所要時間を増やすだけでは、この区別を代替できない。

行政資料の例で足りなかったcontextは、特に「資料を利用可能にする」という目的と「別の担当へ画像化を渡す」という手段の関係だった。画像化が媒体の変換だけなのか、別担当による判断・照合も担うのか。担当分割は必要な統制なのか、過去の配置や設備の都合なのか。資料を扱う技能・道具・アクセス・時間を別の担当にも確保できるのか。これらで、検討できる変更と残すべき境界が変わる。

運用上は**判断に必要なcontextの不足**として具体化できる。ただし、前回の未到達の原因が情報不足だけだったと証明したわけではない。既存出力には、未知の統合を問わず、同じく未知の委譲は条件付きで提案する非対称がある。必要情報を整理することと、Skillがその情報で狙った結論を出すことの検証は別である。

本稿は既存Alderを使う際の入力の整理案。新しい必須欄や、採用済みSkill規則を追加するものではない。初稿後に行った仮想3条件の限定試行は、末尾の「限定検証からの補足」に分けて記録する。

## 三つの判断を分ける

| 段階 | 何があれば進めるか | 行政例での扱い |
| --- | --- | --- |
| 条件付きで検討する | 実在する仕事・受渡しとProblemへの関係。目的、守る保証、未確認条件を区別できること | 受領→画像化の受渡しと職員可用性による待ちは既にある。「その境界は何を守り、どの条件なら別の分担も可能か」を問う根拠になる。兼務が可能との証明までは要らない |
| 実行可能な案か見極める | 必要な権限・技能・道具・アクセス・容量、依存関係、保証・例外対応を、その案でも満たせる証拠 | 画像化の担当を変えても、必要な独立判断や資料の扱いを保てるか。訓練が必要なら、現在できることと訓練後に可能になることを分ける |
| 採用する | 責任ある人による価値・リスク・責任分担の判断。確認済みの変更をBDへ反映し再合意する | 妥当そうな候補や過去の他組織の成功だけでは採用済みにしない。必要なら小さな試行で効果・負担移転・保証を確かめる |

実行可能性が不明でも、根拠のある条件付きの問いは作れる。一方、問いを作れたことだけで「できる」とはしない。目的や保証さえ不明なら、その点を先に確認するが、現状の担当名を変えてはいけない条件へ自動的に置き換えない。

## 統合方向を支える条件は何か

逆算した、まだ事実として確認されていない条件の組合せは次の通り。

- 後続が必要とするのは適切に使える資料であり、画像化担当が別人であること自体は必要な保証ではない
- 画像化に含まれる独立判断・照合があるなら、その責任を別の形でも保てる
- 受領側が必要な道具・アクセス・技能を現在持つ、または承認された訓練等で取得できる
- 受領側へ移した仕事が容量や期限を破らず、別の大きな滞留を作らない

これらが根拠とともに確認できれば、受領側が画像化も担い、受渡しを減らす構成を実行可能性のある候補として比較しやすくなる。ただし、それで最善・採用と決まるわけではない。また、全条件の確認前でも「この境界を外すには何が必要か」という条件付きの問いは作れる。この組合せ一般の十分性は未確定であり、当該行政組織が改善前に満たしていたという主張でもない。後続の限定試行は、共通の作業条件を置いたうえで境界理由への感応性を調べている。

## 行政例の情報を分類する

「資料から未確認」は、現在確認した公開頁では分からないという意味であり、永久に知り得ないという意味ではない。[原報告頁57](https://www.results.wa.gov/sites/default/files/Lean_report_to_legislature_07_01_2014.pdf)の取得制限と照合範囲は[元の研究記録](../../work/business-complexity/issue-151/RESULT.md#入力資料の限界)を参照する。

| context | 状態 | どの判断を変えるか |
| --- | --- | --- |
| 聴聞用資料の受領と画像化への受渡し、担当可用性による待ち | 既存資料・入力にあり | 検討する接点を特定する |
| 原資料の「不要な受渡し・処理」という診断 | 資料にあるが比較入力から欠落 | 受渡し自体を疑う手掛かりになる。ただし、どの受渡しがなぜ不要かまで確定しない |
| 43工程、604分、年間約900件 | 既存context入力にあり | 規模を示す。待ちの場所、容量不足、担当変更の可否は決めない |
| どの時点で誰が待つか。待ちと実作業の内訳 | 資料から未確認 | 受領側の不在、画像化側の滞留、受渡し調整等を区別する |
| 後続で資料を使える成立状態と、そのための品質・期限・取扱い条件 | 一般的目的は読めるが、詳細保証は未確認 | 何を守れば分担・順序を変えられるかを決める。正確性や独立照合の具体条件は作らない |
| 画像化が媒体変換だけか、独立した判断・照合を含むか | 資料から未確認 | 作業の担当変更と、失ってはいけない責任・牽制を切り分ける |
| 担当分割の理由が法令・権限・情報保護か、配置・設備等の経緯か | 資料から未確認。「経緯だけ」は仮説 | 固定制約か、変更を検討できる手段かを区別する |
| 改善前の技能・道具・アクセス・余力、変更に必要な訓練・承認 | 資料から未確認 | 条件付き候補を実行可能な案へ進められるか判断する |
| 訓練と担当移管が実施されたこと | 改善後の事実 | 実施した改善の説明には使えるが、改善前から技能・権限があった証拠にしない |
| 必要な保証を保つ別の分担が可能、または境界が必須 | 現段階ではいずれも仮説 | 確認結果によって統合、境界維持、情報・タイミング改善等の方向が変わる |

この分類から「統合が正解」と逆算して空欄を埋めない。逆算するのは、**案の可否を分ける質問**である。

## 既存Alderのどこに書くか

参照版はmain `a58c970f3a78ac9a0ba91be3c6bfb05e4e2b1168`。[文書構造](../business-design-structure.ja.md)、[adoption](../adoption.md)、[Optimization Review](../optimization-review.md)の役割に合わせる。

| 情報 | 記載先 | 書き方と境界 |
| --- | --- | --- |
| 業務の目的、成立すべき結果 | ActivityのWhy / Result | Whyは仕事の目的。Resultは正常終了時の状態と後続で可能になる仕事。「別担当に渡すこと」自体を目的にしない。ただし独立判断が必要ならその保証は残す |
| 今の担当と実際の作業 | Who / HowのProcedure | Whoは短いロール名。担当による判断・操作・責任分担・運用条件はProcedureへ。現在のWhoは現状記述であり、それだけで将来も同じ担当に固定する指示にはならない |
| 受け取る情報、渡す情報、共通の資料 | Object.Information / Input / Output | 何の情報をどのObject経由で渡すか。普通の受渡しはActivity→Object→Activity。Input/OutputへActivity名を直接書いてつながりを代用しない |
| 順序依存、開始条件、受渡し完了、例外・復旧 | When / Procedure / Result / Exception / Exception When | 紙面で前に並べただけでは実行順序にならない。開始できる状態と、誰が何を確認するかを記す。正常の待ちを架空の例外へ変えない |
| 必要な職務分離、権限、保証とその根拠 | 関係するProcedureの説明、または冒頭の前提・未決事項 | 具体的に誰のどの判断が独立する必要があるかを示す。全体のルールなら適用範囲と参照先を示す。Whyを長い制約一覧にせず、新しい必須Constraints欄を作らない |
| 実測の待ち・誤り・負担、確認したPain | 関連ActivityのProblem / Pain level、根拠資料は補足 | 困りごとと仕様の未決事項は別。複数Activityをまたぐ場合は対象の接点と関連Activityを依頼に示す。一つのActivityに自然に属するProblemはそこで確認・記録し、同じProblemを機械的に全件複製しない |
| 今回どの分担・順序・手段を見直すか、変えてはいけない意味 | Optimizationへの依頼本文 | 事実の追加ではなく、検討範囲・制約・判断依頼として書く。案の実施権限まで与えたことにはならない |
| 技能・アクセス等の未確認事項 | BDの該当欄か冒頭の未決事項。候補側ではAssumptions / UnknownsとQuestions | 現行事実へ昇格させない。どの質問の答えで候補の可否・責任・保証が変わるかを示す |
| 新しい分担、期待効果、採否 | 未採用ならレビュー出力。採用後にBDを更新・確認 | 候補のExpected benefit、Difficulty、Confidenceを現行BDの事実に転記しない |

Howの直下に説明を増設せず、通常手順はProcedure、例外はExceptionへ書く。技能・権限・道具を全件棚卸しする義務はない。**その境界の見直しを左右する情報だけ**を、既存の欄・本文・資料参照で補う。

## 依頼時の補足例

以下は当該行政組織の事実ではなく、現場の確認内容を入れるための記入例。山括弧は空欄であり、事実を推測して埋めない。業務設計書全体の代わりではない。

業務設計書：〈現行BDの参照先と版〉

今回見直したいのは、〈資料を受け付けてから後続で利用できるまで〉です。
達成する結果は〈確認済みの成立状態〉で、〈品質・期限・取扱い等の必要な保証〉は維持してください。

現在は〈担当Aの作業と判断〉の後、〈渡す情報と完了条件〉を介して〈担当Bの作業と判断〉へ進みます。
この分担の理由は〈確認済みの理由と根拠資料。未確認なら未確認〉です。
〈独立した判断・確認を残す必要の有無と根拠〉は、〈確認済み／未確認〉です。

困りごとは〈誰が、どの時点で、何を待つ・やり直すのか〉です。
Pain levelは〈現場と確認したLow / Medium / High〉です。
測定がある場合は〈対象期間・件数・実作業と待ちの内訳〉を添えます。

担当者が使える道具・情報アクセス・技能と、担当変更に必要な条件は〈確認済みの事実〉です。
〈必要な条件のうち未確認なもの〉は、できるともできないとも決めないでください。

見直してよい範囲は〈分担・順序・記録等の検討範囲〉です。
現在の手順をそのまま固定条件とせず、守るべき意味と手段を分けて検討してください。
実行可能性を左右する情報が足りない案は、前提を作らず、その可否を分ける確認質問として示してください。
候補の実施・採用は決めないでください。

この例には「担当を統合する」という答えを入れていない。現場で確認した理由が強い独立性を要求すれば、境界を残す結論もあり得る。Problem / Painがまだ確認されていない場合は、埋め合わせずStructural Discoveryまたは現状記述の確認へ戻る。

## 次に検証するなら何を区別するか

この整理一般の十分性は未確定である。何を調べるかを決める際には、次を混ぜない。

1. **目的と手段の区別を明示する対照**：同じ確認済み事実のまま、Whoと現行手順が不変条件かどうか、実際の固定保証は何かを明確にする。単なる文量ではなく、探索範囲の解釈が変わるかを見る。
2. **実行可能性の事実を加える対照**：当時の記録や責任者確認を取得できた場合だけ、技能・権限・道具・容量の事実を追加する。公開頁にない事実を創作した対照で現実の再現能力を主張しない。
3. **境界を必須とする反対条件**：実際の根拠があるなら、独立した判断者・照合が必要な場合を別条件として固定する。資料がなく仮想条件を置くなら反実仮想だと明記し、元の行政例の事実・再現実験と分ける。適切な結果は、保護対象の責任を残すか、境界変更を確認へ戻すことであり、必ず統合案を出すことではない。

元資料の「不要な受渡し」という診断を戻す比較は、さらに別の診断手掛かりの条件である。目的・権限・能力の事実を追加した比較とは呼ばない。これらの各効果を別々に検証したわけではない。後続の3条件は作業条件と検討範囲を共通化し、境界理由だけを主な差にした限定比較である。

## 運用へ落とす際の提案

まずは正式Skillを変えず、実際に担当境界の見直しを依頼する場面で、上の記載先に沿って**目的・保証、分担の理由、変更条件、未確認事項**を区別して渡す。その結果を見て、なお現行手段を固定したり、根拠ある条件付きの問いを出さなかったりする場合に、入力不足と探索の問題を別々に検討する。

これは利用者に全ての案を先に考えて書かせる運用ではない。利用者が現場の事実と守る意味を提供し、AIが必要性・代替構成・不足する判断条件を問うという分担である。

## 限定検証からの補足

[仮想3条件の結果](../../work/business-complexity/issue-151/context-probe/RESULT.md)では、分担理由が未確認でも同一担当処理を条件付きで提案できた。別人実施が不要なら同方向の候補、別人実施が必要ならその保証を残す別案を返した。目的・保証と作業条件を示し、未知を確認条件として残す使い方を支持する一例である。

共通の技能・権限・余力等は研究用仮定で、以前の入力とも異なる。各情報の因果効果や実例の未到達原因は分離できない。すべての事実が揃うまで提案を止めるという運用にはせず、限られたcontext内の候補と、人間が採用前に確認する事項を区別する。
