# Alder 0.4.6 — 業務設計の欄分けとセキュリティ要件の引き継ぎ

## 変更

- 業務設計の草案作成・改稿で、元の要求の意味を保つことと、各欄へ適切に分けることを別々に確認する。文書全体のScopeには対象と境界を示し、操作の細部はHowへ、仕事の識別はWhatへ、開始条件はWhenへ分ける。
- 業務設計レビューで、Scopeへの操作手順の混入やWhatとWhenの混同を確認する。必要な対象修飾や開始イベントを残し、時間語の禁止やScopeの一文制限で代替しない。
- 実装への引き継ぎで、セキュリティ要件の出典・版・適用範囲を明示する。未提示、読取不能、未決を、理由のある非適用と区別し、不明な条件を「要件なし」や承認済みとして扱わない。
- セキュリティ要件をプロダクト側で整理するための任意の依頼例を追加する。全要件の完成を一律の開始条件にせず、不明な条件に依存する判断と、独立して進められる作業を分ける。
- 0.4.5で追加した、提供済みシステム要件と実装・DDL・テスト・実行証拠の照合を含む。要件の出典・版・範囲と証拠不足をレビューから記録更新まで保持する。

## 互換性

既存の10 Skills、起動文、書込み境界、Check ID、人間の確認状態を維持する。Business Graph JSONはv1、ドリフト診断の形式、review knowledge v0.3は変更しない。新しい必須成果物やAlder共通のセキュリティ要件一覧は追加しない。システム要件の作成、妥当性・完全性の確認はプロダクト側が担う。

既存のタグや配布済みパッケージは変更しない。以前の版へ固定したインストールはそのまま残る。0.4.6を利用する場合は、[GitHub Releases](https://github.com/mk3008/alder/releases/tag/plugin-v0.4.6)で公開を確認してから配布元を更新する。

## 検証範囲と限界

パッケージ、出典・ダイジェスト、リリース手順、Business Graph、ドリフト診断の検証は、配布内容の整合性と各ツールの対象範囲を確認するもの。実クライアントの全起動経路や、エージェントによるスクリプト実行を保証しない。

欄分けのガイダンスは、要求の意味を保ちながらScopeやWhat / Whenの混同を減らすための限定的な変更。曖昧な業務名を安定して自律検出する能力、5W1H全体の正しさ、一般的なレビュー精度の向上は未確認。セキュリティ要件の入口の明文化も、脆弱性の削減や要件の完全性を証明しない。未決の業務判断をAIが承認することはない。
