# 3領域の自動検証: 実行前計画

状態: 実行前固定。Alder #187の研究記録。2026-10-08 JST / 2026-10-07 UTC。

## 問いと境界

一つの架空の会議室予約アプリについて、要求の意味・合格条件・自動検査・実行証拠を結べるか。対象は選定した有限ケースでの検出可能性であり、要求の完全性、安全性全般、AIの性能比較ではない。Alder製品、Business Design → Check Item → Test、Skill、Torroneは変更しない。

既存の会議室題材を最小化して再利用する。過去のレビュー境界研究を反復しない。従来の文書レビューだけでは観測していない、実際のDB切断・直接API認可・運用失敗と更新回帰を今回の実測対象とする。

## 業務意味のSSOT（架空の想定合意）

- BD1: 認識済み社員aliceとbobが、自分の予約を作成する。予約は所有者・部屋・開始分・終了分・取消状態を持ち、開始分 < 終了分。本人だけが自分の予約を参照・取消できる。
- BD2: 同じ所有者が同じrequest_idと同じ内容で再送した場合、新しい予約を増やさず、同一予約の結果を返す。異なる内容の同一request_idは拒否し、元予約を変えない。
- BD3: サービスが確定した予約は応答が届かなくても有効。再送で元の結果を取得できる。
- BD4: 他人のIDを知っていても参照・取消は許可されない。要求本文のowner値を信用して主体を変更しない。
- 競合予約、空室検索、取消期限、管理者、実在組織の認証方式は今回の業務範囲外。必要になったら業務責任者へ戻し、技術側で独断補完しない。

業務責任者・システム責任者・セキュリティ責任者・運用保守責任者は**架空ケースの役割**。この記録は現実の人間による要件承認・残余リスク受容を意味しない。

## 代表要求と固定oracle

| 要求 / 想定承認者 | 合格条件と観測 | 違反注入 |
| --- | --- | --- |
| SYS1 / システム責任者: BD2/3の結果をDB接続切断後も保つ | commit前の実接続closeで未確定行0、再接続後の再送で1行。commit後・応答前のcloseで確定行1、再送で同じID/内容・合計1行。異なる内容の再送は409で元行不変。別所有者の同名request_idは独立 | 既存request_idの照会を無効にする。commit後の再送が正常結果を返せないことを検出する |
| SEC1 / セキュリティ責任者: BD1/4の所有者制限をサーバー側で守る | UIなしでalice作成、bobのGET/取消を403拒否。ID既知・body owner=aliceでも禁止。匿名/未知のトークンは401。拒否応答に予約内容を含めず、DB状態不変。aliceのGET/取消は成功 | 所有者認可を常に許可。bobの直接参照/取消成立を検出 |
| OPS1 / 運用保守責任者: 模擬依存関係の監視結果を失敗と区別し、安全な修正候補へつなぐ | 下記6ケースを固定時計・固定模擬advisory・同じアプリの回帰probeで判定。現行lockを書き換えない | 回帰失敗を無視してcandidate_readyにする。さらに失敗通知抑制・未実行通知抑制を別々に試す |

保守の6ケース（通知はローカルJSONイベントとして実際に生成する。メール・Slack配信はしない）:

1. clean: 正常scan、該当advisoryなし → clean、成功履歴更新、候補なし。
2. fixable: 現行fake-time 1.0にSYN-001、修正版1.1あり → 同じアプリの時間検証を候補1.1で実行し、成功時のみcandidate_ready、SYN-001と修正版と検査結果を記録、現行1.0のまま。
3. failed: scan例外 → scan_failed通知・失敗履歴。過去の成功を今回成功にしない。
4. missing: 予定間隔24時間＋猶予1時間を超えて成功履歴なし（又は古い） → overdue通知。ちょうど25時間は未超過、25時間+1秒で超過。これは独立監視関数の呼出時の判定であり、その関数自体の長期稼働を保証しない。
5. no_fix: SYN-002に修正版なし → manual_action通知、候補なし。cleanへ落とさない。
6. breaking: SYN-003修正候補2.0は模擬依存処理を実際に変更し、アプリの開始<終了判定を破る → 回帰probe失敗、candidate_blocked通知、現行version不変。回帰を単にfalseというfixtureで渡さず、アプリ操作で観測する。

## 実装・検査の最低契約

Python 3.12標準ライブラリのみ。外部install不要。SQLiteは一時ディレクトリのファイルDB。APIはネットワーク非公開のアプリ呼出境界でmethod/path/auth/bodyを渡す（HTTP transport、TLS、実認証は未検証）。架空トークンはfixture内のalice-token/bob-tokenだけ。liveサービスや実CVEは使わない。

`app.py` は `ReservationApp(db_path, dependency_version='1.0')`、`request(method, path, token, body=None, fault=None) -> (status, payload)` を公開。POST /reservations は request_id, room, start, end（HH:MM）、GET /reservations/{id}、POST /reservations/{id}/cancel。201作成/再送、200参照/取消、400不正時刻、401未認証、403他人、404なし、409同一request_id内容不一致。faultはbefore_commit / after_commitでDB接続をcloseし `ConnectionError`。各呼出で新接続を使い、外からSQLite行を照合できる。表reservationsはid, owner, request_id, room, start, end, cancelled。idは安定した整数。HH:MMの0<=HH<24、0<=MM<60を検証し、同じ日内でstart<end。

`maintenance.py` は入力を受けて模擬scan・候補回帰を実行し、状態・履歴・通知・候補を返す。固定入力は `fixtures.json`、期待結果は `oracle.json`。候補回帰は上記ReservationAppを候補versionで呼び、09:00→10:00は201、10:00→09:00は400であることを実測。fake-time 2.0は順序を反転する意図的な互換性破壊fixture。実ライブラリの安全性主張ではない。

## 実行順・証拠・変更規則

1. この計画・fixture・oracleを実装実行前に公開branchへcommitし、SHAで再取得する。
2. 実装と検査は別の担当で作り、実装者にoracle.jsonや検査コードは渡さない（要件とAPI契約は共有）。モデル間独立性・真の盲検・要件妥当性の独立承認は主張しない。
3. 通常実装を検査。結果が期待と違えばrawを保存し、原因を記録する。後から期待値を実装へ合わせて変えない。
4. 検査を変えず、別の一時コピーへ指定の実装差分を適用し、領域の検査を実行。非ゼロ終了と該当assertionの失敗を記録する。import失敗等は要件違反検出に数えない。
5. 同じコピーから差分を戻し、同じ検査を再実行して成功を記録。正常・違反・修正のコードhash、差分、stdout/stderr、終了コードを保存する。
6. 各領域を独立に評価し、他領域の成功を転用しない。固定oracleの変更が必要なら元を残し、理由と追加版を記録し、元の確認結果と分ける。

要求・oracle・検査code・実装・input・mutation・resultのhashとPython/SQLite/platform、コマンド、UTC時刻をmanifestへ保存する。乱数や壁時計の業務判定は使わない。完全な本番環境固定ではないので将来の環境差異を明示する。

## 比較する検証経路と停止判断

システムは文書/設定照合と実DB障害注入、セキュリティは画面E2E/静的検査と直接API否定試験、保守はcron設定と履歴・通知・回帰probeを比較する。今回は実行観測に適した後者を使う。ツール能力やコストの優劣の実験ではない。

一つのアプリ・上記代表ケースで経路成立と違反検出を判断できたら、この研究を完了し追加benchmarkを増やさない。実製品がない現時点で新Skill・共通framework・製品統合へ進まない。次は具体的な製品と責任者・実運用証拠が必要になった場合に限り、その領域を限定して検討する。
