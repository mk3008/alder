# Issue #107 結果：Quality 欄の恒久採用は追加検証

**現行 Business Design だけでも、今回の4例で必要な業務上の成立条件は表現できた。** 任意の Quality 表記は、給与の期限と窓口受付・月末報告の許容条件を拾いやすくする場合がある。ただし条件を既存の Procedure / Result / Exception と重複させる費用があり、treatment C では報告期限の発言者を資料にない形で集計担当へ誤帰属した。現時点で Skill・grammar・exporter を恒久変更しない。概念上は、根拠があるときだけ任意に業務成立条件をまとめる余地を認め、**欄の採用は追加検証**とする。

| ケース | 現行 baseline | Quality guidance treatment | 境界・差分 |
| --- | --- | --- | --- |
| A 給与振込 | 前書きと手順・結果・例外で指定日17時、二重払い禁止、振込先変更の追跡を保持。先月の翌朝振込と約2時間の対応は Problem、Pain Medium と区別。 | 期限・二重払い・変更履歴を Quality としてまとまって見られるが、手順や Object と重複。 | 二重払い禁止は再送・一部失敗にもかかる機能上の不変条件として手順・例外へも結び付ける必要がある。一部失敗後の扱いは未決のまま。 |
| B 会議室予約 | 重複拒否・変更・取消と空き再反映を既存欄で表現。 | Quality 見出しを設けず、根拠のない2秒応答等も作らなかった。 | Quality が不要な業務で optional が成立。ただし両 arm とも詳細質問はあり、treatment の同時申込質問は source にない精緻化で、質問が2件へ減ったことだけでは改善としない。 |
| C 窓口受付と月末集計 | 営業時間中の受付継続、紙運用への切替、翌営業日終了までの報告を別 Activity の欄に記述。 | 二つの許容条件が Quality で探しやすくなったが、期限の説明を集計担当の発言とする source fidelity の誤りがある。 | 業務継続は情報システムの無停止義務を意味しない。遅延実績や Pain は作っていない。誤帰属があるため treatment を無条件の成功としない。 |
| D 振込先変更 | 承認済みだけを支払先に使い、変更者・承認者・前後・時刻を2年間確認できる条件を既存欄で保持。 | Quality 欄に二条件を置くが Object と重複し、支払先利用時の業務との結び付きは baseline の方が読みやすい部分がある。 | AES-256-GCM、コンテナ3台、クラウドDBは未承認の技術案にとどめた。事故・Pain は捏造していない。 |

## 概念判断と次の検証

- **Quality:** 「その業務を許容可能とみなす条件」。資料に根拠があれば、既存の欄または任意の読みやすい記述で表せる。今回の比較だけでは専用欄の必要性を立証しない。
- **Problem / Pain:** A の現在の翌朝振込と約2時間・Medium は望ましい期限とは別の実績と負担。B/C/D では未達実績がないので、条件があっても Problem / Pain を追加しない。
- **Business / Technical:** 業務側の許容時刻・支払先承認・変更追跡と、暗号・DB・コンテナ等の実現手段を分けられた。受付の業務継続もシステム無停止の指定ではない。
- **下流:** 期限、重複禁止、2年追跡から Check Item や System Design の確認項目を検討できるが、baseline からも同じ根拠へ到達する。一部失敗後の具体手順など未決事項をテストで確定しない。

追加検証は、窓口業務のように複数の成立条件を持つ別業務で、人間が baseline / treatment の条件を見つけて正しく説明できるかを比べること、更新時に重複記述が食い違わないか、出典を誤帰属しないかを確認すること。大規模 NFR 分類表や全 Activity 必須欄、数値の自動生成は採用しない。1回の合成比較から汎用的な Authoring 信頼性や下流品質の向上は言えない。業務意味は依頼者の確認待ちである。
