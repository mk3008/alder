# 情報の存在を関連で表す論理モデル案

A案の要素タブで、購入申請・提出内容・申請品目・承認記録・差戻し記録・購入結果を表示する。情報項目の一覧は図の下。各項目またはエンティティを選択すると隣接する関連と情報を強調する。

業務上任意の属性と、後続業務がまだ行われていないため記録が存在しないことを区別する。承認・差戻し・購入の記録を独立させ、記録が存在すれば内部項目は必須とする論理設計案。現BDには業務上の任意項目を確定していないので、NULL可の任意属性を追加しない。これを一般的なNULL禁止規則や機械的な全属性分割にしない。

承認は提出時点の内容を対象とし、購入結果は必ず根拠の承認1件に属する案。購入申請と提出内容を分ける理由は、編集中の下書きと承認対象となった内容を区別するため。版・固定方法・履歴の保持は未決。下書きの不完全入力の保持方法も未決として明記し、任意項目と同一視しない。

関連の最大件数、品目数、権限判定の総額単位、購入結果0..1は引き続き未決。0..N/0..1は配置を読むための設計候補。正式業務ルール・Check期待値・物理DDLとして採用していない。

AIはBDと本人入力を根拠に論理構造を設計提案できる。Viewerは明示された案を表示し、関係や用語を推論しない。独立HTMLのみを変更し、正式BD・Plugin/Skill・parser・保存・本体は変更しない。詳細回帰/E2Eは未作成。草案・編集・レビューSkillにこの視点が必要かはroot #133の検討メモで管理する。

## 識別キーと参照

各カードにPK/FKの論理案を追加。購入申請ID→提出内容の購入申請ID、提出内容ID→品目/承認/差戻し、承認記録ID→購入結果の必須参照を示す。申請品目は提出内容ID＋品目番号の複合PK候補。他は各記録の識別ID。元のInformation一覧12項目に、確定済み業務項目としてIDを混入させない。型・採番・物理DDLは未定義。

購入結果のPKを承認記録IDにしないため、最大1件はキーで確定しない。1件制限を採用するなら承認記録IDの一意性が別途必要。品目数・履歴件数も未決。関連を示すだけで承認対象の内容固定や改変防止まで機械保証したと扱わない。
