# Issue #96 横断分析

3件のPain level Highは入力された仮定であり、業務設計書が負荷や待機時間を実測した結果ではない。設計書にある共通構造は、一意に識別できる購入申請を単位に、`submitted` で承認者が判断し、`approved` で購買担当者が購入し、実購入金額と購入日時をその申請に記録する状態遷移である。ただし、P2の待機の原因までP1・P3と共通だとは確定できない。

## 設計書上の根拠と因果関係

| Problem | 根拠 | 説明できることと限界 |
| --- | --- | --- |
| P1 | 業務4のInputは「購入した対象購入申請」と「実購入金額」を必須とし、`approved` の申請を確認して購入し、結果を記録する。購買担当者の責任として定義されている。 | 承認済み申請ごとに対象確認、購入、記録が必要になる構造は、件数増による作業量増加を説明する。ただし購入をまとめられるか、実際にどの工程が重いかは未記載。 |
| P2 | 業務1で申請が `submitted` となり、業務2・3では承認者がその申請を確認し、承認または却下を判断する。承認後に初めて購買対象となる。 | 申請ごとの判断が必要なことと、判断まで申請者が購入可否を待つ関係は説明できる。待機時間が長い原因が承認作業の量、承認者の稼働、判断材料の不足、処理順のどれかは設計書から分からない。 |
| P3 | 購入申請は一意に識別可能。業務4では購入した対象申請を選び、実購入金額と購入日時を記録して `purchased` にする。 | 購入結果を正しい申請へ結び付ける確認が必要な構造を説明する。ミスの実態・頻度や購入日時の取得方法は記載されていない。 |

## 横断Candidate

### 1. 承認済み申請と購入結果の対応を購入作業の前後で一貫して扱う（P1・P3）

購買担当者が購入対象の `approved` 申請を一意の申請単位であらかじめ整理し、購入時の対象と購入後に登録する結果の対応を保つ業務手順を定める。結果登録時に対象を改めて探して照合する作業を減らせればP1の作業負荷とP3の対応付け確認・誤登録の双方に効く。これは業務手順の候補であり、具体的な画面や連携方式は指定しない。

**維持する意味:** 承認済み申請に基づいて購買担当者が購入し、各申請に正しい実購入金額・購入日時を残してから `purchased` とする。申請ごとの購入可否の判断や `rejected` を購買対象から外すことも維持する。対象の整理だけなら承認権限や状態の意味を変える必要はない。複数申請を一括購入し一つの合計金額を配賦する案へ拡張するなら、申請別の実購入金額・購入日時をどう確定するかという新たな業務上の意味を決める必要があるため、現時点では含めない。

**未確認の仮定・人間への質問:** 実際の負荷は、購入前の対象確認と購入後の再照合に偏っているか。購入時点から結果登録まで、対象申請の識別を保てる運用か。対象が違う、購入できなかった、実金額をまだ確定できない場合は誰がどの状態で扱うか。これらが成立しなければ効果は限定される。

## 統合しないProblemと個別対応の位置付け

P2は上の横断Candidateには統合しない。P1・P3に共通する購入対象と結果の対応付けは、`approved` 後の業務4にある。P2はその前の業務2・3での判断待ちであり、購入結果の対応付けを改善しても承認判断までの時間を短縮する経路は示せない。承認者が申請ごとに確認する点は購買担当者の対象確認と形式上似るが、判断内容と権限が異なり、待機の原因も未確認である。

個別対応なら、P2の承認待ちについて、承認者の処理状況や判断に必要な情報を確かめたうえで承認業務を見直す。P1だけの購入作業の集約も検討対象になり得るが、購入先や発注などは未決定であり、可能性も効果も断定できない。P3だけの登録確認手順の強化は誤対応の抑制を狙うが、P1の作業を増やす場合がある。横断Candidateは、同じ申請と購入結果の結び付きを一度整えることでP1・P3の双方に効く経路を持つ点が異なる。いずれも採用決定ではない。
