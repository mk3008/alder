# 備品購入申請 — 業務設計

この文書は、社内で使用する備品の購入申請から購入完了までに必要となる業務を記述する。

業務設計者の書き漏らしや読み手との認識齟齬を減らすため、各業務を5W1Hを基礎にした共通形式で記載する。ここで記述するのは業務上の意味・前提・入力・手順・結果であり、画面部品、API、クラス、モジュール、データアクセス方法などの実装方式は規定しない。

各業務は次の観点を記載する。

- **What / なにを** — 業務名と、何を成立させる業務か
- **Why / なぜ** — その業務を行う目的
- **When / いつ** — 業務の開始契機、先行業務との関係、成立に必要な業務状態
- **Who / だれが** — 業務を行うロール
- **Where / どこで** — 場所・チャネルに業務上の意味がある場合の制約。規定がなければ「規定なし」
- **How / どうやって** — 業務で受け取るInput、業務手順、成立するOutput

Inputでは、業務担当者がその業務を行うために与える・選択する情報を記載し、必須・任意を明示する。

## 業務上のロール

- **申請者** — 業務に必要な備品の購入を申請する。
- **承認者** — 申請内容を確認し、購入を承認または却下する。
- **購買担当者** — 承認済みの申請に基づいて購入を行い、購入結果を登録する。

ロールは業務上の責任と権限を表す。

## 業務で扱う情報

### 購入申請

購入申請は、申請者が業務上必要とする備品の購入要求を、承認および購買の対象として扱うための記録である。

少なくとも次の情報を持つ。

- 申請者
- 品名
- 数量
- 希望購入金額
- 購入理由
- 申請日時
- 状態: `submitted` / `approved` / `rejected` / `purchased`
- 承認日時
- 却下日時
- 却下理由
- 購入日時
- 実購入金額

購入申請は一意に識別できるものとする。識別子の採番・入力方法はこの業務設計では規定しない。

---

## 業務1 — 備品購入を申請する

### What / なにを

業務に必要な備品の購入要求を、購入申請として登録する。

### Why / なぜ

購入の必要性と希望内容を記録し、承認者が購入可否を判断できる状態にするため。

### When / いつ

申請者が、業務上必要な備品を購入したいと判断したとき。

### Who / だれが

申請者。

### Where / どこで

規定なし。

### How / どうやって

#### Input

次の項目を入力する。**すべて必須**とする。

- 品名
- 数量
- 希望購入金額
- 購入理由

#### 業務手順

1. 申請者が購入したい備品と購入理由を入力する。
2. 希望する数量と購入金額を入力する。
3. 新しい購入申請として登録する。
4. 登録した申請を `submitted` として扱う。

#### Output

- 購入要求が `submitted` の購入申請として記録される。
- 申請者、品名、数量、希望購入金額、購入理由、申請日時が保持される。
- 承認者が購入可否を判断できる状態になる。

---

## 業務2 — 購入申請を承認する

### What / なにを

提出された購入申請について、購入を承認する。

### Why / なぜ

申請内容が妥当であることを確認し、購買担当者が購入を進められる状態にするため。

### When / いつ

`submitted` の購入申請について、承認者が購入してよいと判断したとき。

### Who / だれが

承認者。

### Where / どこで

規定なし。

### How / どうやって

#### Input

次の項目を選択する。**必須**とする。

- 承認する対象購入申請

#### 業務手順

1. 承認者が `submitted` の購入申請を確認する。
2. 購入してよいと判断した申請を選択する。
3. 対象の購入申請を `approved` とする。
4. 承認日時を記録する。

#### Output

- 対象購入申請が `approved` になる。
- 承認日時が記録される。
- 購買担当者が購入対象として扱える状態になる。

---

## 業務3 — 購入申請を却下する

### What / なにを

提出された購入申請について、購入しないことを確定する。

### Why / なぜ

購入を認めないと判断した申請について、購買対象から外すため。

### When / いつ

`submitted` の購入申請について、承認者が購入を認めないと判断したとき。

### Who / だれが

承認者。

### Where / どこで

規定なし。

### How / どうやって

#### Input

次の項目を選択・入力する。**すべて必須**とする。

- 却下する対象購入申請
- 却下理由

#### 業務手順

1. 承認者が `submitted` の購入申請を確認する。
2. 購入を認めないと判断した申請を選択する。
3. 却下理由を記録する。
4. 対象の購入申請を `rejected` とする。
5. 却下日時を記録する。

#### Output

- 対象購入申請が `rejected` になる。
- 却下理由と却下日時が記録される。
- 購買担当者の購入対象にはならない。

---

## 業務4 — 承認済み備品を購入する

### What / なにを

承認済みの購入申請に基づいて備品を購入し、その結果を登録する。

### Why / なぜ

承認された購入要求を実際の購入として完了させ、購入済みであることを記録するため。

### When / いつ

`approved` の購入申請について、購買担当者が対象備品を購入したとき。

### Who / だれが

購買担当者。

### Where / どこで

規定なし。

### How / どうやって

#### Input

次の項目を選択・入力する。**すべて必須**とする。

- 購入した対象購入申請
- 実購入金額

#### 業務手順

1. 購買担当者が `approved` の購入申請を確認する。
2. 対象備品を購入する。
3. 実購入金額を記録する。
4. 対象購入申請を `purchased` とする。
5. 購入日時を記録する。

#### Output

- 対象購入申請が `purchased` になる。
- 実購入金額と購入日時が記録される。
- 対象申請が購入済みとして扱える状態になる。

---

## 業務相関

現在定義している主な業務相関は次のとおりである。

1. 備品購入を申請すると、`submitted` の購入申請が成立する。
2. `submitted` の購入申請を承認すると、`approved` になる。
3. `submitted` の購入申請を却下すると、`rejected` になる。
4. `approved` の購入申請に基づいて購入すると、`purchased` になる。
5. `rejected` の購入申請は購買対象にならない。

## 現在の業務設計で未決定の事項

次の事項は現在の業務設計では定めない。

- 申請金額によって承認者や承認段階が変わる場合の扱い
- 在庫確認、発注、納品、検収、支払に関する業務
- 購入先の選定方法
- 購入後の備品管理、資産管理、廃棄
- 外部システムとの連携
- 監査履歴や通知に関する業務

これらは、現在の業務設計を実装するために決定済みであるとはみなさない。
