# 購入後の申請・購入結果の対応付けに関する業務最適化レビュー

対象: `mk3008/alder` main `5405a5069fc13e1a1e27de8b06e4a375a3653e5e` の指定 Business Design。実験条件として、購入後の実購入金額・購入日時の申請への対応付けに確認負荷とミスがある（Pain level: High）と置く。これは文書から確認された現状ではない。以下は比較する業務代替案であり、採用案の決定ではない。

## Candidate 1 — 購入の場で対象申請と実績を一体で確定する

- **Problemとの関係:** 購入後に実績から対象申請を探し直す必要がある場合、その照合を購入時点の対象選択へ寄せる。誤った申請への事後登録を減らす狙い。
- **Approach:** Simplify/Merge。購買担当者が承認済み申請を購入対象として特定した状態で購入し、その購入に対応する実購入金額と実際の購入日時を一続きの業務で確定する。申請の識別方法は業務設計で未規定なので定めず、購入と登録の間に時間差がある場合も購入時刻と登録時刻を混同しない運用を要する。既にこの形で行われていれば追加効果はない。独立した「購入後に申請を探し直す」工程が実在するかは不明であり、Eliminate の効果は条件付き。
- **Scope:** Keep。承認済み申請に基づく購入と購入結果登録という業務4の範囲内で、作業の順序と結び付け方を明確化するため。
- **Expected benefit:** 対象申請の再検索・照合の回数を減らし、購入先や金額が似た複数申請への誤対応付けを抑える可能性がある。実際の減少量は、現在の購入と登録の時間差や案件数次第。
- **Difficulty:** 低〜中。主な責任は購買担当者の購入・記録手順に収まるが、購入時点で申請を特定できない購買チャネルや、複数申請をまとめて購入する場合には運用上の調整が必要になり得る。それらの有無は未確認。
- **Affected parties / affected business:** 購買担当者、承認済み申請に基づく購入と購入結果登録。申請者・承認者の判断業務は維持する。
- **守る既存Business上の意味・制約:** `submitted` から承認者が承認して `approved` になった申請だけが購入対象。却下された申請は購入対象外。購買担当者が購入し、実購入金額・購入日時を対象申請に記録して `purchased` とする。希望購入金額を実購入金額の代わりにしない。根拠: 「業務2 — 購入申請を承認する」When/Who/How/Output、「業務3 — 購入申請を却下する」Output、「業務4 — 承認済み備品を購入する」When/Who/Input/手順/Output、「業務相関」2〜5。
- **Assumptions / Unknowns:** 現在、購入後に対象申請を再特定する工程があるか。購入時に申請が一意に判別できるか。複数申請にまたがる購入や購入の分割、取消・訂正の有無。文書は申請の一意識別のみを定め、識別方法を定めない（「業務で扱う情報 — 購入申請」）。
- **人間が判断すべき質問:** 購入時に対象の承認済み申請を確定できる購買形態か。購入と登録が離れる場合、実際の購入日時を何で確認するか。複数申請・分割購入の扱いを業務範囲に追加する必要があるか。
- **Confidence:** 中。業務4の手順に沿う提案だが、課題となる事後照合の実態は実験条件以外に根拠がない。

## Candidate 2 — 購入記録を申請に照合し、例外だけ購買担当者が確定する

- **Problemとの関係:** 実購入金額・購入日時の転記と対象申請の照合を定型部分だけ自動化し、対応先が曖昧な購入を人間に回す。高い確認負荷が繰り返し発生している場合の代替案。
- **Approach:** Automate。購入実績を示す信頼できる記録が取得でき、承認済み申請との一意な対応を確認できる場合に、金額・実際の購入日時・申請の候補を組み合わせる。一意に確定できないもの、金額・日時の根拠が欠けるものは `purchased` への確定を保留し、購買担当者が購入事実と対象申請を確認する。外部購買サービスや既存機能への Delegate は利用可能性が文書にないため、この案の必須条件とはしない。
- **Scope:** Expand。業務4の購入結果登録に、購入記録の取得・照合・例外確認という業務上の責任を加える。外部システム連携や監査履歴は未決定であり、必要となれば別途設計判断が要る（「現在の業務設計で未決定の事項」）。
- **Expected benefit:** 条件を満たす購入の手入力と全件目視照合を減らし、元の購入記録に基づく金額・日時の転記ミスを抑える可能性。例外確認の量と照合精度が効果を左右する。
- **Difficulty:** 高。購買担当者の責任に加え、購入記録を管理する業務・システム・担当部署または外部サービスとのデータ提供、記録の正しさ、照合不能時の責任分界を調整する必要がある。外部サービスを使う場合は契約や連携条件も確認が必要。これは実装工数ではなく関係先・責任の広さによる評価。
- **Affected parties / affected business:** 購買担当者、購入記録の管理者（存在すれば）、購入結果登録、例外時の確認業務。購入記録の提供元が外部なら外部関係者も該当する。承認者の購入可否判断は維持する。
- **守る既存Business上の意味・制約:** 自動照合結果だけを根拠に未承認・却下申請を購入済みへ変更しない。承認された申請に基づいて購買担当者が購入した結果としてのみ `purchased` とし、実購入金額と購入日時を保持する。曖昧な対応は人間が確定する。根拠: 「業務で扱う情報 — 購入申請」の状態・日時・金額・一意識別、「業務2 — 購入申請を承認する」Output、「業務3 — 購入申請を却下する」Output、「業務4 — 承認済み備品を購入する」What/When/Who/Input/Output、「業務相関」4〜5。
- **Assumptions / Unknowns:** 購入事実・実金額・購入日時を示す利用可能な記録があるか、申請と一意に紐付けられるか、記録へのアクセス権限と信頼性、複数申請をまとめた購入や訂正の有無。文書は購入先の選定、発注・支払、外部連携、監査履歴を未決定とするため、これらを既存業務として仮定しない（「現在の業務設計で未決定の事項」）。
- **人間が判断すべき質問:** 購入日時・実金額の正本となる記録は何か。照合不能・複数候補時に誰が何を確認して確定するか。購入記録の提供元と責任分界を合意できるか。自動確定を許す条件はどこまで厳しくするか。
- **Confidence:** 低〜中。業務4の登録負荷に直接効く可能性はあるが、購入記録と連携可能性は業務設計に記載がない。
