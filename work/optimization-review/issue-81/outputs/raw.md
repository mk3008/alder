# 業務最適化レビュー

対象版: `mk3008/alder main 5405a5069fc13e1a1e27de8b06e4a375a3653e5e`

対象Problem（実験専用の追加条件）: 承認済みの購入申請が増えると、購買担当者が申請ごとに購入を行い、その結果を登録する作業の負荷が高い。Pain level: High。これはBusiness Design本文に記載された観測事実ではなく、今回の検討条件である。

## Candidate 1 — 購入可能な承認済み申請をまとめて手配する

- **Problemとの関係:** 申請ごとに繰り返す対象確認と購入の手間を、互いにまとめられる申請について減らす。購入結果の記録は各申請に必要なので、その照合負荷も含めて設計する。
- **Approach:** Simplify/Merge。購買担当者が複数の `approved` 申請を確認し、同じ購入機会に扱えるものをまとめて購入する。購入後は、各申請に対応する実購入金額と購入日時を個別に確定し、各申請を `purchased` にする。注文を一本化できても金額を申請別に割り当てられない場合はまとめない。申請内容・承認判断自体は統合しない。
- **Scope:** **Narrow**。対象は品目、購入時期、購入先などの条件が両立し、結果を申請別に正しく帰属できる承認済み申請に限る。購入先の選定方法や発注・納品などは未決定のため、すべての申請を一括化する前提を置かない。
- **Expected benefit:** 条件が合う申請群では購入操作や確認の反復が減る可能性がある。件数、品目の重複、購入機会の分布が不明なので削減率は算定できない。
- **Difficulty:** **中**。購買担当者のまとめ買い判断に加え、申請者・承認者が認めた品名、数量、希望金額との対応、申請別の実購入金額の帰属を調整する必要がある。購入先・発注・支払をどう扱うかによって関係部署や外部関係者への影響が増え得るが、それらの現状は不明。
- **Affected parties / affected business:** 購買担当者の手配と結果登録、申請者ごとの購入要求、承認者の承認対象との対応。まとめる場合の購入先・支払に関わる相手は存在と役割を要確認。
- **守る既存Business上の意味・制約:** `submitted` を承認者が個別に妥当と判断して初めて `approved` となる。`rejected` は対象外。購入は `approved` に基づき、実際に購入した後に申請別の実購入金額・購入日時を記録して `purchased` とする。希望購入金額を実購入金額と同一視しない。
- **Assumptions / Unknowns:** 同時に購入できる申請が一定数あるか、同一品目の需要があるか、購入時期を合わせられるか、共通購入費を申請別に正しく配分できるかは不明。部分購入、価格差、配送費等の扱いも未決定。
- **人間が判断すべき質問:** どの条件なら別々に承認された申請を同一の購入にまとめてよいか。購入金額が申請ごとに判別できないときは個別購入に戻すか。まとめるための待機が許されるか。
- **Confidence:** **中**。業務4の反復削減には直接効くが、まとめられる申請の割合が不明。
- **文書の根拠:** 「業務上のロール」（承認者・購買担当者の責任）、「業務で扱う情報 > 購入申請」（品名、数量、希望購入金額、実購入金額、状態）、「業務2 — 購入申請を承認する」Output、「業務4 — 承認済み備品を購入する」When / Input / 業務手順 / Output、「業務相関」4・5、「現在の業務設計で未決定の事項」（購入先、発注・支払）。

## Candidate 2 — 定型の承認済み申請について購入と結果取得を自動化する

- **Problemとの関係:** 申請が増えるたびに購買担当者が購入操作と結果転記を繰り返す負荷を、定型案件で減らす。
- **Approach:** Automate。人間が定めた対象条件を満たす `approved` 申請について、承認後の購入実行と実際の購入結果の取得・申請への紐付けを自動で行う業務へ変更する。購入できなかった、申請との対応や実購入金額が確定できない場合は購買担当者が処理する。自動で `purchased` にするのは購入の成立と申請別の実購入金額・購入日時を確認できた場合に限る。購入先や連携手段は候補を検証するまで定めない。
- **Scope:** **Narrow**。対象条件と例外処理が定義できる定型品から始める。業務設計は購入先の選定と外部連携を定めておらず、全件に広げる根拠がない。
- **Expected benefit:** 対象案件で購買担当者の個別購入操作と結果転記を減らせる可能性がある。失敗・価格差・不確かな結果の人手対応は残る。適用件数と効果量は不明。
- **Difficulty:** **高**。購買担当者と承認者の権限境界、購入の責任者、例外時の判断・再実行の責任を合意する必要がある。購入先または外部システムが実購入結果を確実に返せるか、その利用条件や契約、購入・支払を扱う関係者との調整が必要になり得る。実装量の評価ではない。
- **Affected parties / affected business:** 購買担当者の通常処理と例外処理、承認者の購入許可、申請者の購入要求。購入先・外部システム・支払担当等との接点は現状不明であり、成立するなら影響先となる。
- **守る既存Business上の意味・制約:** 自動処理は承認を代行しない。承認者による `submitted` から `approved` への判断と承認日時は保持する。`rejected` は購入しない。購入が成立する前、または実購入金額が未確定の段階で `purchased` と扱わない。
- **Assumptions / Unknowns:** 定型的な品目・購入方法が存在するか、機械的な購入に必要な権限と購入先の受け入れがあるか、確定した購入日時・金額を申請別に取得できるかは不明。価格が希望額と違う場合、失敗・重複購入時の扱いも未決定。
- **人間が判断すべき質問:** どの承認済み申請なら人手の購入判断を追加せず購入してよいか。実購入金額の差異を誰がどの時点で判断するか。結果が確認できないときの責任者と再購入防止の運用をどうするか。
- **Confidence:** **中〜低**。負荷への直接性は高いが、適用可能な購入先・定型案件・結果取得手段が文書から確認できない。
- **文書の根拠:** 「業務2 — 購入申請を承認する」Why / When / Output、「業務3 — 購入申請を却下する」Output、「業務4 — 承認済み備品を購入する」Why / When / Who / Input / 業務手順 / Output、「業務相関」2〜5、「現在の業務設計で未決定の事項」（購入先、外部システムとの連携、発注・支払）。

## Candidate 3 — 承認後の購入事務を既存の購買サービスに委ねる

- **Problemとの関係:** 購買担当者が申請ごとに購入先で手配し結果を収集する作業を、委託先または既存の購買サービスの運用に移す。自社側には結果確認と例外対応を残す。
- **Approach:** Delegate。利用可能な購買代行・調達サービス等がある場合に限り、`approved` 申請を購入依頼として渡し、先方の購入完了報告を申請別に受け取る。購買担当者の責任で報告と申請を照合し、実購入金額と購入日時が確認できた申請だけを `purchased` とする。先方が結果を直接記録できるかは別途判断する。
- **Scope:** **Narrow**。サービスが扱える品目・購入条件で、申請単位の購入結果を返せる範囲に限る。Business Designに委託先や既存契約の記載はなく、適用可能性を先に確認する必要がある。
- **Expected benefit:** 対象申請で自社の購買担当者が行う個々の手配を減らせる可能性がある。一方、依頼の作成、結果照合、例外対応、サービス費用が生じ得るため、純便益は未確認。
- **Difficulty:** **高**。購買担当者の責任範囲、承認済み依頼を第三者へ渡す条件、外部関係者の購入権限、契約・費用負担、結果報告の粒度と時期を関係者で合意する必要がある。支払・購入先選定に関わる業務があればその担当者との調整も要るが、現状は不明。
- **Affected parties / affected business:** 購買担当者の手配・照合・例外処理、承認者の承認の効力、申請者の要求、委託先またはサービス提供者。契約・支払に関わる部署の有無は要確認。
- **守る既存Business上の意味・制約:** 委託しても、承認者が `submitted` を確認して `approved` とする権限は移さない。`rejected` は購入依頼に含めない。購入実績がない申請を `purchased` にせず、申請ごとの実購入金額と購入日時を保持する。購買担当者の既存の購入・登録責任を移す場合は、ロール定義自体の変更を明示的に決める。
- **Assumptions / Unknowns:** 利用できるサービスや契約があるか、対象備品を扱えるか、希望内容を引き継げるか、申請別の購入結果を証明できるか、費用対効果は不明。個人情報や購入情報を渡せる条件も未決定。
- **人間が判断すべき質問:** 委託できる品目と支出の範囲は何か。実際の購入責任と結果の正確性を誰が負うか。購買担当者の照合をどこまで減らせ、委託費用に見合うか。
- **Confidence:** **低**。購買担当者の直接作業を減らす方向は妥当だが、利用可能なサービス・契約について文書に情報がない。
- **文書の根拠:** 「業務上のロール」（承認者・購買担当者）、「業務2 — 購入申請を承認する」Output、「業務3 — 購入申請を却下する」Output、「業務4 — 承認済み備品を購入する」What / Who / Input / Output、「業務で扱う情報 > 購入申請」（状態、実購入金額、購入日時）、「現在の業務設計で未決定の事項」（購入先、発注・支払、外部システム）。

いずれも採用判断ではない。承認業務と購入成立の意味を残したうえで、購入をまとめられる頻度、定型案件の割合、利用可能な外部サービス、申請別の実績確認方法を確かめる必要がある。申請・承認工程そのものを削除する案は、購入可否の判断と却下申請の除外を損なうため提示しない。
