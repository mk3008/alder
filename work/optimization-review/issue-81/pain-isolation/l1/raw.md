# 業務最適化レビュー

対象: mk3008/alder main 5405a5069fc13e1a1e27de8b06e4a375a3653e5e

追加条件のProblemは「承認済みの購入申請について、購買担当者が申請ごとに購入を行い、その結果を登録している」、Pain levelはLow。以下はこの追加条件を前提とした候補であり、Business Designから購買件数や購入先、現在の作業時間を推定しない。採用判断や最適解の決定は行わない。

## Candidate 1 — 急ぎでない承認済み申請を購買作業の機会にまとめる

- **Problemとの関係:** 購買担当者が申請ごとに購入へ着手する頻度を減らす。複数申請を一度の購買作業の機会に確認・処理するが、購入実行と購入結果は対象申請ごとに扱う。業務4「Who」「How／業務手順1–5」、業務相関4に対応。
- **Approach:** 購買担当者が `approved` の申請のうち、待っても支障のないものを一定の機会にまとめて確認し、購入する。必要なら同じ品目などを同時に手配する。実購入金額と購入日時、`purchased` への変更は各申請に対応させる。これは処理のタイミングをまとめる運用案で、注文を必ず統合する案ではない。
- **Scope:** **Narrow**。急ぎでない、まとめても申請と支出の対応が明確に保てる承認済み申請だけを対象とし、急ぎの申請は個別に処理できる余地を残す。業務4の購入後記録と業務相関を保ちつつ、小さく試せるため。急ぎの扱いや購買期限は文書で未規定。
- **Expected benefit:** 購買対象の確認や購入作業に着手する回数が減る可能性がある。同じ品目をまとめて手配できる場合は、購入操作の重複も減る可能性がある。ただし申請単位の結果記録は残るため、その作業の削減幅は限定的。
- **Difficultyと根拠:** **低〜中**。主な調整先は購買担当者と申請者・承認者であり、待てる申請の判断や処理間隔を決める必要がある。注文を統合する場合は購入先との取引条件や申請別の実購入金額の対応も確認が必要になり、調整は広がる。外部関係者や契約への影響は現状不明で、必須の変更とはしない。これは実装工数の評価ではない。
- **Affected parties / affected business:** 購買担当者の購入順序と処理タイミング、申請者が備品を得る時期、承認者が許可した対象との照合。購入先への注文を実際に統合する場合のみ購入先も影響し得る。
- **守る既存Business上の意味・制約:** 承認者が `submitted` を確認し購入してよいと判断して `approved` にし、承認日時を記録する（業務2「Why」「When」「How」）。`rejected` は購買対象にしない（業務3「Output」、業務相関5）。購買担当者が `approved` に基づき購入し、対象申請ごとに実購入金額・購入日時と `purchased` を記録する（業務4「Why」「When」「Who」「Input」「Output」、業務相関4）。承認をまとめて省略したり、購入前に購入済みとしたりしない。
- **Assumptions / Unknowns:** 申請の量、緊急度、待機可能期間、同一品目の頻度、購入先と取引条件、複数申請を同時に購入した場合の実購入金額の対応付けは不明。購入先選定や発注・納品・検収・支払、外部システム連携は「現在の業務設計で未決定の事項」であり、ここで決定済みとは扱わない。
- **人間が判断すべき質問:** どの申請ならどれだけ待てるか。購買作業をまとめる頻度を設けるほどの件数・重複があるか。同時手配した場合、各申請の実購入金額と購入日時を誤解なく記録できるか。
- **Confidence:** **中**。申請単位の購買と結果記録は追加条件および業務4に明示されているが、まとめ処理の効果を左右する件数・緊急度・取引条件は不明。

Pain levelがLowであり、業務4は購買担当者の購入と申請別の結果登録によって成立する。現時点の資料だけでは購入や記録そのものを削除する根拠はなく、外部サービスへの移譲やシステム連携の調整負担を正当化する件数・削減効果も確認できないため、追加候補は挙げない（業務4「Why」「Who」「Output」、現在の業務設計で未決定の事項「外部システムとの連携」）。
