# 承認済み備品の購入・結果登録に関する業務最適化レビュー

対象: mk3008/alder main `5405a5069fc13e1a1e27de8b06e4a375a3653e5e`。追加条件として与えられたProblem「承認済みの購入申請について、購買担当者が申請ごとに購入を行い、その結果を登録している」、Pain level「High」を評価の起点とする。これはBusiness Design内で実測された処理量・所要時間を示すものではない。採用案や最適解は決めない。

## Candidate 1 — 承認済み申請をまとめて購買し、申請ごとに結果を対応付ける

- **Problemとの関係:** 申請ごとの購入行為を、同時に扱える承認済み申請のまとまりで減らす。結果の登録もまとまりで処理し、各申請の実購入金額・購入日時を個別に確定する。
- **Approach:** Simplify/Merge。品目・購入先・購入時期が両立する申請を購買担当者が束ねて購入する。共同購入の金額や数量を各申請に確実に割り当てられたものだけ `purchased` とし、残りは `approved` のまま扱う。個別購入が必要な申請は例外とする。
- **Scope:** Keep。申請、承認、購買、結果記録の業務範囲を維持し、購買の単位と結果登録の作業単位を変える。納品・支払等の未定義業務を導入する案ではない。
- **Expected benefit:** 購買操作と申請ごとの反復入力を減らせる可能性。まとめられる比率、購入条件、結果の配賦方法によって効果は変わる。
- **Difficultyと根拠:** 中。主に購買担当者の運用変更と申請者・承認者の希望内容との整合が必要。複数申請への数量・実額・日時の対応付けに責任が生じる。共通購入先や購入時期を約束するなら外部関係者との調整も必要になるが、現状は未確定。
- **Affected parties / affected business:** 購買担当者、申請者、承認者。承認済み申請の購入、結果登録、申請ごとの購入完了判断。
- **守る既存Business上の意味・制約:** `approved` の申請のみを購買対象とし、`rejected` は対象外。各申請に固有の品名・数量・希望購入金額・理由と承認結果を維持する。購入した申請ごとに実購入金額、購入日時、`purchased` を記録する。共同購入を理由に未購入の申請を購入済みにしない。
- **Assumptions / Unknowns:** 同時期に集約可能な承認済み申請が存在するか、購入価格を申請単位にどう配賦できるか、急ぎの購入を許容できるか不明。
- **人間が判断すべき質問:** どの条件なら申請を一括で購入してよいか。割引・送料等を含む実購入金額は申請ごとにどう確定するか。購入日時はどの取引時点とするか。
- **Confidence:** 中。反復購入を減らす業務上の筋は明確だが、集約可能性と効果は未検証。
- **文書根拠:** 「業務上のロール」の購買担当者、「業務で扱う情報」の購入申請の識別・状態・購入日時・実購入金額、「業務2 — 購入申請を承認する」のOutput、「業務3 — 購入申請を却下する」のOutput、「業務4 — 承認済み備品を購入する」のWhen、Input、手順、Output、「業務相関」4・5。「現在の業務設計で未決定の事項」に購入先選定等が挙がる。

## Candidate 2 — 定型的な承認済み購入を外部の購買サービスに委ねる

- **Problemとの関係:** 購買担当者による申請ごとの注文・結果転記が負担なら、対象を限定して定型品の購入実行と取引結果の提供を委ねる。
- **Approach:** Delegate。人間が定める対象品・上限・例外条件を満たし、かつ個別に `approved` となった申請だけを、既存の購買サービスや契約先に引き渡す案。サービス側が購入結果を返し、購買担当者が申請単位で照合・例外処理と完了責任を担う。サービスの存在や契約は現状の事実とはしない。
- **Scope:** Expand。購入実行と取引結果の受け渡しに外部関係者を加えるため。申請・承認の判断対象や在庫・検収・支払の業務まで広げる提案ではない。
- **Expected benefit:** 条件に合う購入について、購買担当者の個別注文や結果入力を減らせる可能性。対象品の割合と結果情報の粒度に左右される。
- **Difficultyと根拠:** 高。購買担当者と承認者に加え、外部サービス・購入先との契約、権限、価格・数量の逸脱時の責任、申請単位の取引結果を得る条件などの調整が必要。購入先選定と外部連携はいずれも未決定であり、関係先と責任分界が広い。
- **Affected parties / affected business:** 購買担当者、承認者、申請者、導入する場合の外部サービス・購入先。承認後の購買、購入結果の受領・照合・例外処理。
- **守る既存Business上の意味・制約:** `submitted` や `rejected` を購入対象にしない。承認者の購入可否判断を代行先に移さない。実際に購入されたことを申請ごとに確認してから実購入金額、購入日時、`purchased` を成立させる。購買担当者の完了責任の扱いを明文化する。
- **Assumptions / Unknowns:** 委託可能な品目、利用可能なサービス・契約、承認後の品目・価格変更の許容範囲、申請ごとの実額・日時が返せるかは不明。
- **人間が判断すべき質問:** どの購入を委ね、どの例外を購買担当者へ戻すか。希望金額と実購入金額が異なる場合に誰が購入を止めるか。外部の結果を誰がどの水準で検証するか。
- **Confidence:** 中低。対象を絞れば効果があり得るが、外部関係・取引情報の成立条件は文書にない。
- **文書根拠:** 「業務上のロール」の承認者・購買担当者、「業務2 — 購入申請を承認する」のWhyとOutput、「業務3 — 購入申請を却下する」のOutput、「業務4 — 承認済み備品を購入する」のWho、When、Input、Output、「業務相関」4・5。「現在の業務設計で未決定の事項」は購入先選定方法と外部システム連携を未決定とする。

## Candidate 3 — 購入結果を取引のまとまりから取り込み、申請単位で確認する

- **Problemとの関係:** 購入の実行が個別に必要な場合でも、各申請の結果登録を逐一手入力する作業を減らす。
- **Approach:** Automate / Simplify。購買取引の結果に申請を対応付け、実購入金額と購入日時をまとめて取り込む。対応が確定した申請だけ購入済みとし、対応不明・金額差・未購入は購買担当者が確認する。取引結果を取得できる仕組みは仮定であり、特定の実装方式を前提にしない。
- **Scope:** Keep。購買担当者が承認済み申請を購入し結果を登録する範囲内で、結果登録の作業を単純化する。外部連携が必要と判明すれば、その範囲は別途判断する。
- **Expected benefit:** 反復する結果入力を減らし、申請と取引の対応確認に購買担当者の時間を使える。購入行為そのものの件数は減らない。
- **Difficultyと根拠:** 中（取引結果を既に利用できる場合）。購買担当者の照合責任と、取引情報を保有する業務・システムとの受け渡しを調整する必要がある。新たな外部事業者や契約が必要なら高へ上がる。取引情報の所在は未決定。
- **Affected parties / affected business:** 購買担当者、取引結果を保有する担当者・部門・システムが存在する場合はその関係先。購買結果登録と誤対応・未対応の処理。
- **守る既存Business上の意味・制約:** `approved` から実際の購入を経て `purchased` になる順序を守り、`rejected` を除外する。各申請の実購入金額と購入日時を確定し、単に取り込みに成功しただけで購入済みとみなさない。
- **Assumptions / Unknowns:** 申請と取引を一意に照合できる情報、金額と日時の確かな取引結果、複数申請と一取引の関係、取消・差額への対応が不明。
- **人間が判断すべき質問:** 取引結果の正本は何か。申請との対応付けを誰が確定するか。曖昧な対応や実額差をどう扱い、どの時点で `purchased` とするか。
- **Confidence:** 中。結果登録の反復には直接効くが、取引結果の取得可能性は文書から確認できない。
- **文書根拠:** 「業務で扱う情報」の購入申請の一意識別・実購入金額・購入日時、「業務4 — 承認済み備品を購入する」のWhen、Input、手順3〜5、Output、「業務相関」4・5。「現在の業務設計で未決定の事項」は外部システムとの連携、支払等を未決定とする。
