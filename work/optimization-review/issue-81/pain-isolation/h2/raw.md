# 承認済み備品の購入業務に関する独立レビュー

対象: `mk3008/alder` main `5405a5069fc13e1a1e27de8b06e4a375a3653e5e`。本レビューは指定された Business Design と、実験条件の Problem / Pain level: High だけを根拠とする。件数、商品構成、購入先、既存サービス、購買契約は不明である。以下は採用順位や最適解ではない。

## Candidate 1 — 複数の承認済み申請をまとめて購入する

- **Problemとの関係:** 購買担当者が申請ごとに購入している場合、同じ購入先や備品をまとめられる範囲で購入操作を減らせる可能性がある。申請ごとの購入結果の記録は維持する。
- **Approach:** Simplify/Merge。承認済み申請を確認し、品目・購入時期・購入条件が合うものをまとめて購入する業務運用を検討する。まとめた購入と個々の申請の対応を確認し、各申請に実購入金額・購入日時を割り当てて `purchased` とする。割当方法や一部のみ購入できた場合の扱いは未決定事項として先に定める。
- **Scope:** **Keep**。対象は既存の承認済み申請の購入と結果登録に限る。まとめ買いのために新たな未承認需要を加えるなら Expand になるため、この候補には含めない。
- **Expected benefit:** 適合する申請が一定数あれば、購入先への操作や同種品の手配をまとめ、申請単位の繰り返しを減らせる。申請ごとの結果への配賦・照合が増える可能性はある。
- **Difficulty:** **中**。購買担当者と申請者・承認者の申請単位の責任を保ちながら、まとめた購入と各申請の数量・実購入金額・購入日時を対応させる調整が必要。購入先や会計・支払などの関係者への影響は現文書から確定できず、調整範囲次第で上がる。
- **Affected parties / affected business:** 購買担当者、申請者、承認者。業務4の購入と結果登録、業務2の承認単位および業務1の申請単位との対応。購入先や会計部門への影響は要確認。
- **守る既存Business上の意味・制約:** 承認者が `submitted` の申請を個別に判断して `approved` にし、`rejected` は購買対象にしない。購買担当者が承認済みの対象備品を購入した後に、各対象申請の実購入金額・購入日時を記録し `purchased` にする。まとめた購入を理由に未購入の申請を購入済みにしない。
- **Assumptions / Unknowns:** まとめられる申請の頻度、品目・数量・希望額の重なり、購入時期の許容範囲、複数申請への実額の割当基準、部分購入や取消の扱いは不明。
- **人間が判断すべき質問:** どの申請をどの期間・条件でまとめてよいか。まとめた購入額と購入日を各申請にどう確定するか。部分購入時に各申請をいつ購入済みとするか。
- **Confidence:** **中**。反復作業をまとめる因果関係は明確だが、実際にまとめられる申請があるか不明。
- **文書の根拠:** 「業務上のロール」購買担当者、「業務で扱う情報」購入申請とその状態・購入日時・実購入金額、「業務2」承認のOutput、「業務3」却下のOutput、「業務4」When / Who / Input / 業務手順 / Output、「業務相関」2–5。

## Candidate 2 — 条件が定まる定型品だけ購入実行を自動化する

- **Problemとの関係:** 承認後に購買担当者が申請ごとに行う購入操作のうち、商品・購入先・購入条件が事前に確定できる反復分を減らす。例外は購買担当者が扱う。
- **Approach:** Automate。申請ごとの承認を確認した上で、条件に合致する定型品の購入を自動的に進め、実際の購入成立を確認できた場合に限って申請ごとの実購入金額・購入日時を記録する業務へ変える。条件不一致、価格や数量の変動、購入失敗時は購買担当者の判断に戻す。自動化の技術方式はここでは決めない。
- **Scope:** **Narrow**。定型品かつ事前に人間が購入条件・例外基準を決めた承認済み申請だけを対象にする。それ以外の申請は従来の購買担当者による購入に残す。
- **Expected benefit:** 該当申請が多ければ、承認済みの定型品について購買担当者の申請ごとの注文操作と結果転記を減らし、承認後の待ち時間も短縮し得る。
- **Difficulty:** **高**。購買担当者の実行責任の扱い、承認者が認めた条件からの変更許容範囲、購入先との注文条件、失敗・重複注文・返品の責任分担など、関係者と統制の調整が広い。購入先や外部システムの存在・連携は未定義であり、実際の範囲は要調査。
- **Affected parties / affected business:** 購買担当者、承認者、申請者、条件次第で購入先および購買・会計等の関係部門。業務2の承認、業務4の購入と結果登録、および例外時の対応。
- **守る既存Business上の意味・制約:** `approved` になった個々の申請のみを購入対象とし、`rejected` を購入しない。申請ごとの購入事実を確認してから `purchased` とし、実購入金額と購入日時を残す。承認を自動購入の判定で代替しない。購買担当者の業務責任・権限をどのように運用するかは人間が明示的に決める。
- **Assumptions / Unknowns:** 定型品の量、購入条件と承認範囲、購入先の注文手段、取引・契約上の自動注文可否、結果確認の根拠、例外・取消・二重注文への対応は不明。
- **人間が判断すべき質問:** 自動購入を許す品目・価格差・数量差・購入先の範囲は何か。誰が条件を設定・変更し、失敗時の購入判断を担うか。購入成立を何で確認するか。
- **Confidence:** **低〜中**。反復購入への効果はあり得るが、対象件数や購入先・条件が設計にない。
- **文書の根拠:** 「業務上のロール」承認者・購買担当者、「業務2」Why / Output、「業務3」Output、「業務4」When / Input / 業務手順 / Output、「業務相関」2–5、「現在の業務設計で未決定の事項」購入先の選定方法・外部システムとの連携。

## Candidate 3 — 既存の購買サービスへ購入実行と結果収集を委ねる

- **Problemとの関係:** 既に利用できる購買サービスや購買代行がある場合、購買担当者による申請ごとの購入実行・結果収集をサービスの業務へ移し、担当者は承認済み依頼の引渡しと結果の照合・例外判断に集中できる。
- **Approach:** Delegate。承認済み申請の購入対象・数量・承認の事実をサービスへ渡し、サービスによる実購入の結果を申請単位に突合して記録する運用を検討する。購入失敗、価格差、誤購入、部分購入への連絡と判断の責任を決める。利用可能なサービスがあるという事実は前提にしない。
- **Scope:** **Keep**。委ねるのは既存の承認済み申請に対する購入と結果収集の実行部分。購入先選定、支払、検収等を新たな必須業務として含めない。サービス導入そのものが必要なら関係部署との調整範囲は拡がる。
- **Expected benefit:** 適合するサービス・契約があれば、購買担当者の申請ごとの注文操作と実額の収集を減らせる。照合と例外処理は残り、サービス費用や追加の引渡し作業が利益を相殺する可能性がある。
- **Difficulty:** **高**。購買担当者とサービス提供者の責任境界、承認済み申請情報と購入結果の受渡し、契約・費用・失敗時の補償、必要なら他部署や外部関係者との調整を要する。既存契約の有無によって難度は変動する。
- **Affected parties / affected business:** 購買担当者、承認者、申請者、存在する場合の購買サービス・購入先・契約や会計の担当部門。業務4の購入・結果登録とその例外処理。
- **守る既存Business上の意味・制約:** 委託後も承認者による申請ごとの承認が購入の前提であり、却下申請を渡さない。実際の購入と申請を照合し、実購入金額・購入日時を各申請に記録してから `purchased` とする。購買担当者の責任・権限の移し方は合意が必要。
- **Assumptions / Unknowns:** 利用可能な既存サービスや契約、取り扱える品目、購入成立の証跡、価格差・失敗・返金の扱い、結果データの粒度と費用は不明。
- **人間が判断すべき質問:** 利用できるサービス・契約はあるか。購買担当者と提供者の購入権限・誤発注責任はどう分けるか。申請ごとにどの購入結果を証拠として受け取れるか。
- **Confidence:** **低**。条件がそろえば直接の作業削減になるが、外部サービスの存在と適合性は未確認。
- **文書の根拠:** 「業務上のロール」購買担当者と責任・権限の説明、「業務で扱う情報」購入申請、「業務2」Output、「業務3」Output、「業務4」What / Why / When / Input / Output、「業務相関」2–5、「現在の業務設計で未決定の事項」購入先の選定方法・外部システムとの連携。
