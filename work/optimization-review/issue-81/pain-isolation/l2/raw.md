# 業務最適化レビュー（対象: mk3008/alder main 5405a5069fc13e1a1e27de8b06e4a375a3653e5e）

対象Problemは、承認済み申請を購買担当者が申請ごとに購入し、結果を登録すること。追加条件のPain levelは **Low** であり、頻度・処理時間・費用・遅延の実測値ではない。候補は小さく試せるものに限る。以下は採用判断ではない。

## Candidate 1 — 条件の合う承認済み申請をまとめて購入する

- **Problemとの関係:** 申請ごとに行う購入行為を、同時に扱える複数の申請についてまとめる。
- **Approach:** 購買担当者が `approved` の申請を確認し、同一または同時購入が妥当な備品だけを一つの購入機会にまとめる。申請単位の承認は再解釈せず、購入後は各申請に対応する実購入金額・購入日時を記録して `purchased` とする。合算購入額しか分からない場合の金額配賦を決められるまで、その申請はまとめない。単独購入を引き続き認める。
- **Scope:** **Narrow**。品目、時期、金額の帰属が明確な申請群だけに限定する。低い痛みを理由に、全件の購買方法や承認制度を変更しない。
- **Expected benefit:** 条件が合う案件では購入の繰り返しが減る可能性がある。削減量は購入件数と重複度が不明のため未確定。
- **Difficultyと根拠:** **低～中**。購買担当者内で試すなら関係先は少ないが、申請者の希望時期、購入先の注文条件、値引きや送料を各申請にどう配賦するかによって申請者・承認者・購入先との調整が生じる。実装工数の評価ではない。
- **Affected parties / affected business:** 購買担当者、申請者、承認者（承認範囲との整合確認が必要な場合）、購入先（まとめ注文が可能な場合）。購買と購入結果の記録に影響する。
- **守る既存Business上の意味・制約:** 承認者は `submitted` を確認して購入可否を判断し、`approved` のみが購買対象となる。`rejected` は対象外。購入は承認済みの要求に基づき購買担当者が行い、購入済みの各申請には実購入金額・購入日時を残す。根拠:「業務上のロール」「業務2 — 購入申請を承認する」Why/When/Output、「業務3 — 購入申請を却下する」Output、「業務4 — 承認済み備品を購入する」What/Who/Input/手順/Output、「業務相関」2～5。
- **Assumptions / Unknowns:** 同じ時期にまとめられる承認済み申請があるか不明。購入先選定、発注・納品・検収・支払は未決定。複数申請を一度に購入しても申請ごとの実購入金額を確定できるか、希望購入金額との関係や待機許容期間は未決定。根拠:「業務で扱う情報」購入申請の項目、「業務4」Input、「現在の業務設計で未決定の事項」。
- **人間が判断すべき質問:** 同時購入できる申請は実際にどれほど発生するか。まとめるために購入を待たせてもよい範囲は何か。送料や割引を含む実購入金額を各申請へどう帰属させるか。
- **Confidence:** **中**。個別記録を維持した統合は設計と整合するが、統合可能な件数と効果は資料から判断できない。

## Candidate 2 — 購入済み案件の結果登録をまとめて処理する

- **Problemとの関係:** 購入のたびに申請別に結果を登録する反復に直接対応する。
- **Approach:** 購買担当者が複数の承認済み申請を購入した後、購入の事実と各申請の実購入金額・購入日時を照合し、同じ作業機会にまとめて確定する。各申請の `purchased` への変更は、その申請の購入と金額が確認できてから行う。購入自体をまとめられない場合にも適用できる。
- **Scope:** **Narrow**。結果登録の作業機会だけを統合し、購入行為や承認判断の責任は変えない。少量なら現行の即時登録を維持できる。
- **Expected benefit:** 切替えや確認作業を減らせる可能性がある。ただしまとめて処理するほど購入済み状態の反映が遅れる可能性があり、実効性は件数と必要な即時性に依存する。
- **Difficultyと根拠:** **低～中**。主に購買担当者の作業順序の変更だが、他の業務が購入済み状態を直ちに参照する場合、申請者やその業務の担当者との調整が必要になる。誤った申請への金額・日時の紐付け防止も必要。実装工数の評価ではない。
- **Affected parties / affected business:** 購買担当者、購入済み状態を使う申請者その他の担当者（存在する場合）。購入結果登録と購入済み情報の利用に影響する。
- **守る既存Business上の意味・制約:** 各申請は一意に識別でき、`approved` の購入後に限り `purchased` とし、実購入金額・購入日時を記録する。承認と購買はそれぞれ承認者・購買担当者の責任である。根拠:「業務上のロール」、「業務で扱う情報」購入申請、「業務4」When/Who/Input/手順/Output、「業務相関」4～5。
- **Assumptions / Unknowns:** 購入済み状態に即時反映が必要か、複数件の結果登録が実際に発生するか不明。通知や監査履歴、外部連携は未決定であり、前提にしない。根拠:「業務4」Why/Output、「現在の業務設計で未決定の事項」。
- **人間が判断すべき質問:** 購入から登録まで許容される時間はどれだけか。一度に扱う件数はどの程度か。申請と実購入金額の照合を誰がどう確認するか。
- **Confidence:** **中**。登録の作業機会を統合できる余地はあるが、即時性と件数が不明で便益は確定できない。

自動購入や外部サービスへの移譲は、購入先・外部連携・契約条件等が未決定で、低い痛みに対して関係先が大きく広がるため候補化しない。承認判断、購買担当者の購入責任、各申請の購入結果記録を削除する案も、文書にある業務上の意味を損なうため候補化しない。根拠:「業務上のロール」「業務2」「業務4」「現在の業務設計で未決定の事項」。
