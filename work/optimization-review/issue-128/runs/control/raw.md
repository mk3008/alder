# Alder Optimization Review（独立レビュー）

公開入力 revision: `1aeb3ea71f354236c4bb1f1cd54e1f523fd51580`。各ケースの候補は業務判断の材料であり、採用判断ではない。効果、件数、連携先など未提示の事実は確認事項とする。

## ケース1：備品購入申請

**Problem:** 承認済み申請ごとの購入・結果登録の負担が高い。**Pain:** High。

参照：`purchase.md`「業務4 — 承認済み備品を購入する」の When、Who、Input、業務手順、Output、「業務で扱う情報」の購入申請、「業務相関」4・5、「現在の業務設計で未決定の事項」。承認と却下の意味は同文書「業務2」「業務3」を参照。

### 候補1：複数の承認済み申請をまとめて購買処理し、結果は申請別に確定する

- **Problemとの関係:** 一件ずつ購入手配と結果登録を始める負担を、まとめて処理できる部分で減らす。
- **方向:** Simplify / Merge。共通する購買手配や入力作業をまとめるが、申請と結果の対応は統合しない。
- **Scope:** Keep。対象は業務4内の購買実行と結果登録。申請・承認の業務境界は維持する。
- **期待便益:** 複数件を扱う機会があれば、着手や入力の繰り返しを減らせる可能性がある。実際の削減量は不明。
- **Difficulty:** 中。購買担当者の処理順と複数申請への金額・購入日時の割当方法を調整する必要がある。購入先側のまとめ買い条件が必要なら追加調整を要する。
- **影響する人・業務:** 購買担当者、購入を待つ申請者、業務4。購入先との取引条件に及ぶかは未確認。
- **守る意味・制約:** `approved` の申請だけを購入対象とし、`rejected` は含めない。`purchased` は各対象申請に実際の購入が成立したときだけ付け、各申請の実購入金額と購入日時を保持する。承認権限や承認対象の単位を黙って変えない。
- **仮定・未知:** 同時期にまとめられる承認済み申請の頻度、品目や購入先の重なり、まとめた支払額を申請ごとに確定できるか、購入日時の扱いは不明。
- **人が確認・決定する問い:** どの申請を同時に処理できるか。複数申請にまたがる取引の実金額と日時をどう根拠付きで申請別に記録するか。まとめることが購入期限や承認範囲を損なわないか。
- **Confidence:** 中。反復する手順には直接対応するが、まとめられる取引量と割当実務が分からない。

### 候補2：購入の確定情報から申請別の結果登録を補助する

- **Problemとの関係:** 購買担当者が購入後に同じ結果を申請へ転記する作業を減らす。
- **方向:** Automate。購入が成立したことを示す情報を対応申請へ取り込み、担当者が照合・確定する形を検討する。
- **Scope:** Expand。業務4の外にある購入の記録元と、申請IDとの対応関係を確認する必要がある。
- **期待便益:** 実購入金額・日時の再入力を減らせる可能性がある。購入実行そのものの負担は残る。
- **Difficulty:** 中から高。購入情報の保有者、連携や照合の責任、訂正と不一致時の扱いを決める必要があり、記録元が外部なら相手方との調整も必要。
- **影響する人・業務:** 購買担当者、購入記録の管理者、業務4。購入元のシステムや外部の相手があるかは不明。
- **守る意味・制約:** 各 `approved` 申請について実際に購入された結果だけを `purchased` とし、対象申請、実購入金額、購入日時を保持する。購買担当者の業務責任と承認済み申請だけを対象にする境界を、情報の自動取込だけで変更しない。
- **仮定・未知:** 再利用できる購入記録や識別子、金額・日時の信頼性、部分購入・複数申請にまたがる購入の有無、連携方式・権利は未決定。外部システム連携は設計上の未決定事項であり、既存機能とはみなさない。
- **人が確認・決定する問い:** 実購入結果をどこに、誰が確定しているか。各申請との対応と例外を誰が検証し、いつ状態を確定するか。費用に見合う反復件数があるか。
- **Confidence:** 中低。登録負担には直結するが、購入記録元の存在と質が不明。

### 探索的な極端な視点（候補外）

承認済み申請を一件ずつ購入する形そのものを見直し、共通備品の在庫から充当する業務モデルなら、該当品の申請ごとの購入作業が消える可能性がある。ただし購入前に在庫を持つ資金・所有・保管の責任、承認と在庫払出の関係が現在の意味から変わる。在庫確認・備品管理は `purchase.md` で未決定で、反復需要や保管条件もないため候補とはしない。対象品目に継続需要があるか、在庫の費用と責任を誰が負うか、既存承認を何の判断に変えるかを人が決める場合に再検討できる。

## ケース2：購入結果照合

**Problem:** 全件の数値照合を人間が繰り返す負担があり、「一部自動化する」案では残す責任が未整理。**Pain:** Medium。

参照：`composition.md`「Object」「Activity A — 購入結果を照合する」の Why、Who、When、Input、How、Output、「明示された制約と情報」および「Review input」。数量・金額の選択が独立しているため、部分案2件と双方を対象にする案をそれぞれ異なる責任範囲として示す。入力の正しさは対象外とする。

### 候補1：数量の上限比較だけを機械判定する

- **Problemとの関係:** 毎件の承認数量と実数量の比較を人間から外す。金額比較の負担は残る。
- **方向:** Automate / Preserve。確定済み数値の比較だけを委譲し、金額照合、証憑の真正性判断と例外解決は人間に残す。
- **Scope:** Narrow。Activity A の数量判定だけに限る。数量と金額の委譲は独立に選択可能と明記されている。
- **期待便益:** 数量比較の反復を削減しうる。照合全体の短縮量は不明。
- **Difficulty:** 低から中。購買担当者の確認分担、判定結果の保持、不一致を購買責任者へ戻す運用を調整する。承認権限の変更は含まない。
- **影響する人・業務:** 購買担当者、例外判断を行う購買責任者、Activity A。
- **守る意味・制約:** 実数量が承認数量以下、実金額が承認上限以下、真正な証憑であることの三つが成立した記録だけを照合済みとする。証憑は毎件人間が確認し、例外は修正または別途承認まで確定しない。申請ID、実数量、実金額、証憑、判断者を保持する。
- **仮定・未知:** 判定結果を担当者がどう確認し、誤った入力や不一致をどう訂正するか。今回、入力自体の正しさは改善対象外。
- **人が確認・決定する問い:** 数量判定の不一致通知・記録と責任者への引渡しをどう設計するか。金額と証憑の人間による確認をどう明示するか。
- **Confidence:** 高（比較の委譲可能性）、便益の大きさは不明。

### 候補2：金額の上限比較だけを機械判定する

- **Problemとの関係:** 毎件の実金額と申請別承認上限額の比較を人間から外す。数量比較の負担は残る。
- **方向:** Automate / Preserve。確定済み数値の比較だけを委譲し、数量照合、証憑の真正性判断と例外解決は人間に残す。
- **Scope:** Narrow。Activity A の金額判定だけ。数量の委譲とは独立して選べる。
- **期待便益:** 金額比較の反復を削減しうる。申請別上限を取り違えずに扱える可能性はあるが、発生している誤りや削減量は示されていない。
- **Difficulty:** 低から中。申請ごとに異なる上限額の正しい参照、担当者の確認分担、超過時の責任者への引渡しを調整する。
- **影響する人・業務:** 購買担当者、購買責任者、Activity A。
- **守る意味・制約:** 申請ごとの承認上限自体は変更しない。数量、金額、証憑の三確認がそろうまで照合済みにせず、証憑の真正性は毎件人間が判断する。例外は修正または別途承認を要し、申請ID、実数量、実金額、証憑、判断者を保持する。
- **仮定・未知:** 金額判定結果の提示・訂正・保管方法は未定。上限値と実金額の入力正しさは今回の対象外。
- **人が確認・決定する問い:** どの上限値に対して判定したかをどう記録するか。超過時、誰が別途承認まで確定を止めるか。数量と証憑の人間確認をどう残すか。
- **Confidence:** 高（比較の委譲可能性）、便益の大きさは不明。

### 候補3：数量と金額の両比較を機械判定し、証憑と例外の判断を人間に集中する

- **Problemとの関係:** 全件で繰り返す二つの数値比較をともに人間から外す。片方だけを外す候補とは、移す照合責任と残る通常時の作業が異なる。
- **方向:** Automate / Preserve。独立に委譲可能な二判定を組み合わせ、真正性判断は毎件人間が実施する。
- **Scope:** Keep。Activity A の二つの機械的判定を変更するが、三つの確認からなる照合の意味や周辺業務を広げない。
- **期待便益:** 数値比較の反復作業を両方減らせる可能性がある。証憑確認と不一致対応は残り、処理時間の実測はない。
- **Difficulty:** 中。二判定の結果を同一申請に結び、片方でも不一致なら照合済みにしない運用、担当者と責任者の責任分担を調整する。
- **影響する人・業務:** 購買担当者、購買責任者、Activity A。
- **守る意味・制約:** 数量・金額が各承認範囲内で、かつ領収書が真正と人間に確認されて初めて照合済み。両方の数値判定が成功しても人間の証憑判断を省略しない。例外判断は購買責任者、修正または別途承認まで未確定。申請ID、実数量、実金額、証憑、判断者を保持する。
- **仮定・未知:** 二判定の結果と人間の判断を統合して記録する方法、片方だけ不一致の場合の手順は未定。入力の正しさは対象外。
- **人が確認・決定する問い:** 双方の比較を一度に委譲する負担と効果は片方のみの案に比べてどうか。人間の証憑判断と例外処理の責任をどう明示するか。
- **Confidence:** 高（機械的比較と独立選択の根拠）、相対便益は未測定。

外部証憑認証サービスは利用可否・契約が不明で、さらに今回の人間による真正性確認を機械判定へ置換できないため候補に含めない。資産管理・採用人事にはProblemとの因果の根拠がない。

## ケース3：証憑確認

**Problem:** 一回の人間による真正性確認に手間がかかる。**Pain:** Low。

参照：`zero.md`「Activity」の Why、Who、How、Output、「制約とReview input」。

**候補：0件。** 真正性を責任者が一回だけ判断し結果を記録する現在の業務には重複がなく、記録支援も既に利用済みである。省略・委譲・機械化をしない固定条件の範囲で、提示されたProblemを改善する新しい手段は確認できない。外部サービス、反復需要、隣接業務の根拠を補って候補を作ることもしない。固定条件の変更権限も今回ないため、採否や業務変更は提案しない。
