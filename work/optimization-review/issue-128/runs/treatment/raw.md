# Alder Optimization Review — treatment

公開入力 revision: `1aeb3ea71f354236c4bb1f1cd54e1f523fd51580`。以下は3ケースそれぞれの独立したレビューであり、候補の採否は業務責任者が判断する。候補は未承認の検討事項であり、期待効果は測定済みの成果を意味しない。

## 1. 備品購入申請

**Problem:** 承認済み申請ごとの購入・結果登録の負担が高い。**Pain:** High。参照: `inputs/purchase.md`「業務上のロール」「業務で扱う情報／購入申請」「業務2 — 購入申請を承認する」「業務4 — 承認済み備品を購入する」「業務相関」「現在の業務設計で未決定の事項」。

### 候補1 — 複数の承認済み申請をまとめて購買処理し、申請別に結果を確定する

- **Problemとの関係:** 申請ごとに購買対象の確認から購入まで繰り返す作業を、条件の合う申請でまとめられる可能性がある。
- **方向:** Simplify / Merge。購入の実行単位・時点をまとめても、承認と結果の記録単位は申請ごとに保つ。
- **Scope:** Keep。業務4の購買実行の組み方を変える。複数申請の対応関係を扱うが、承認業務や未定義の在庫・支払業務を当然には変更しない。
- **期待効果:** まとめられる場合、購入操作の反復を減らせる。ただし品目、購入先、期限、価格条件によって成立件数は変わる。
- **Difficulty:** 中。購買担当者の作業と申請別の実購入金額・購入日時の割当て、部分購入や不成立時の扱いを関係者で決める必要がある。購入先の条件次第で外部との調整も増える。
- **影響する人・業務:** 購買担当者、申請者、承認者が参照する申請別結果、場合によって購入先。
- **維持する意味・制約:** `approved` だけを購入対象にする。承認権限は承認者に残し、`rejected` は対象にしない。購入済みとなる各申請には、その申請に対応する実購入金額と購入日時を保持する。まとめた発注それ自体を全申請の `purchased` と同一視しない。
- **仮定・未知:** 申請の頻度・品目の共通性、まとめ買いの許容期間、購入先・価格条件、実購入金額の配賦方法、部分購入・納品等の扱いは未確定。
- **人が確認・決定する質問:** どの申請をどの期間・条件でまとめられるか。合算支払の申請別金額をどう確定し、申請ごとの購入完了をいつ認めるか。
- **確信度:** 中。反復する購入業務への因果は設計とProblemに基づくが、実際の集約可能性と削減幅は未知。

### 候補2 — 購入結果を購買担当者の確認の下で申請別に取り込む

- **Problemとの関係:** 購入後の実購入金額・購入日時の転記や申請選択の反復を減らす可能性がある。
- **方向:** Automate / Simplify。購入結果が信頼できる形で得られる場合、申請との対応付けと登録の定型部分を補助し、担当者が申請別の実際の購入を確認して確定する。
- **Scope:** Expand。業務4の登録負担に直接関係する購入結果の発生元と申請IDの対応を扱う必要がある。外部記録・連携が存在するとは仮定しない。
- **期待効果:** 対応可能な購入の入力・転記の反復を減らせる。入力元がない場合や照合できない購入では効果がない。
- **Difficulty:** 中〜高。購買担当者の確定責任に加え、結果情報の保有者・形式・連携可否と、不一致や重複時の責任分担を決める必要がある。外部システムや契約が要れば難度は高くなる。
- **影響する人・業務:** 購買担当者、結果情報の管理者または購入先、申請結果を見る申請者・承認者。
- **維持する意味・制約:** 承認済み申請に基づく実購入のみが `purchased` となり、各申請の実購入金額と購入日時を保持する。購入の有無をデータ取込みだけで推定しない。承認・却下の権限と状態の意味を変えない。
- **仮定・未知:** 利用可能な購入結果記録、申請IDとの対応、情報の正確さ・更新時点、連携と契約、例外件数、現状の登録時間は不明。
- **人が確認・決定する質問:** 現在の購入結果はどこに記録され、申請別に特定できるか。担当者が何を確認した時点で `purchased` を確定するか。対応不能・修正・重複時は誰が解決するか。
- **確信度:** 低〜中。記録の反復はProblemと業務4に合うが、実現の前提となる情報源が未確認。

**探索の境界と停止理由:** 購入のまとめ方と結果登録の情報源は別々に変え得るが、同時採用が有利とは断定しない。申請者の承認要否、購入先、在庫・納品・支払を変更する枝は事実・責任境界が未確定で、追加候補として数えない。回数、時間、価格を推定せず、効果の優劣も決めない。

**Extreme perspective（探索用、候補ではない）:** 申請のたびに購入するモデルから、共通備品を在庫として先に確保し、個別要求を引当てるモデルに変えると、該当する要求ごとの購入作業は発生しなくなる可能性がある。一方、購入前の申請別承認という現在の意味、在庫の所有・購入権限・費用配賦が変わり、在庫業務自体も設計未決定なので実行可能な候補とは扱わない。反復需要と品目の共通性、在庫責任、事前購入を誰が承認するかを人が確認・決定した場合にのみ再検討する。参照: `inputs/purchase.md`「業務1」「業務2」「業務4」「現在の業務設計で未決定の事項」。

## 2. 購入結果照合

**Problem:** 全件の数値照合を人間が繰り返す負担。「一部自動化する」案は残す責任が未整理。**Pain:** Medium。参照: `inputs/composition.md`「Object」「Activity A — 購入結果を照合する」「明示された制約と情報」「Review input」。

数量と金額はそれぞれ確定済み入力との機械的比較が可能で、委譲判断は独立している。一方、承認数量・上限金額は別々の数値であり、上限額そのものを変更する案ではない。証憑の真正性はどの候補でも毎件人間が判断する。不一致は購買責任者に戻し、修正または別途承認まで確定しない。

### 候補1 — 数量照合だけを機械判定に委譲する

- **Problemとの関係:** 毎件の数量が承認数量以下かを担当者が比較する負担を取り除く。金額の人手照合は残る。
- **方向:** Automate / Preserve。数量の比較だけを委譲し、金額照合と証憑真正性の人間による確認を残す。
- **Scope:** Narrow。Activity Aの二つの数値判定のうち数量に限るので、変更する判断責任を限定できる。
- **期待効果:** 数量比較の反復を減らす。金額比較と証憑確認の負担は減らない。
- **Difficulty:** 低〜中。購買担当者と例外判断者で、判定結果の確認、誤対応・不一致の戻し方を決める。外部部門・契約への変更は入力にない。
- **影響する人・業務:** 購買担当者、購買責任者、申請別の照合結果。
- **維持する意味・制約:** 実数量が承認数量以下、実金額が承認上限以下、証憑が真正であることの三確認が揃った記録だけを照合済みにする。判断者と証憑を保持し、例外を責任者へ戻す。
- **仮定・未知:** 判定の提示・例外通知の運用、担当者の数量比較にかかる時間、誤対応の頻度は不明。入力値の正しさは対象外。
- **人が確認・決定する質問:** 数量の機械判定を誰が監督し、結果と例外をどう記録するか。残る金額・証憑の確認完了をどう合わせるか。
- **確信度:** 高（数量比較の委譲可能性）。効果量と運用の難度は未測定。

### 候補2 — 金額照合だけを機械判定に委譲する

- **Problemとの関係:** 毎件の実金額がその申請の承認上限以下かを担当者が比較する負担を取り除く。数量の人手照合は残る。
- **方向:** Automate / Preserve。金額の比較だけを委譲し、数量照合と証憑真正性の人間による確認を残す。
- **Scope:** Narrow。Activity Aの金額判断だけを変え、申請ごとに異なる上限額をそのまま使う。
- **期待効果:** 金額比較の反復を減らす。数量比較と証憑確認の負担は減らない。
- **Difficulty:** 低〜中。購買担当者と購買責任者で、上限額との対応、判定結果と不一致の戻し方を決める。金額の承認権限自体は変更しない。
- **影響する人・業務:** 購買担当者、購買責任者、申請別の照合結果。
- **維持する意味・制約:** 三確認が揃うまで照合済みにせず、真正性判断は人間、例外解決は責任者。承認上限額を変更せず、申請ID・実数量・実金額・証憑・判断者を保持する。
- **仮定・未知:** 申請と上限額の対応の運用、現状の金額比較時間、例外発生率は不明。入力値の正しさは対象外。
- **人が確認・決定する質問:** 上限額との機械比較を誰が監督し、不一致をどう戻すか。残る数量・証憑の確認完了をどう合わせるか。
- **確信度:** 高（金額比較の委譲可能性）。効果量と運用の難度は未測定。

### 候補3 — 数量・金額の両照合を機械判定に委譲する

- **Problemとの関係:** 人間が毎件繰り返す二つの数値比較をともに取り除く。
- **方向:** Automate / Preserve。確定済み値の二比較を委譲し、証憑真正性の毎件の人間判断と例外処理を維持する。
- **Scope:** Keep。Activity Aの数値照合全体を変更するが、証憑や隣接業務への責任拡大は不要。
- **期待効果:** 二つの比較の反復を減らせる可能性がある。候補1・2より負担削減の対象は広い一方、二判定と人間判断の合流を確実に運用する必要がある。効果量は不明。
- **Difficulty:** 中。購買担当者・購買責任者が数量と金額の別々の不一致経路、両判定の記録、証憑確認との合流を確認する必要があり、単独委譲より調整範囲が広い。
- **影響する人・業務:** 購買担当者、購買責任者、申請別の照合結果。
- **維持する意味・制約:** 数量は承認数量以下、金額は申請別上限以下、証憑は人間が真正と判断した場合にのみ照合済み。不一致は修正または別途承認まで確定せず、判断者を保持する。上限額と入力値の正しさの責任は今回変更しない。
- **仮定・未知:** 両比較の処理結果と人間判断の統合運用、例外頻度、現状の工数は不明。
- **人が確認・決定する質問:** 片方だけ不一致の場合を含め、誰がどの情報を確認して確定するか。二判定の委譲を同時に行う調整費用と削減効果は見合うか。
- **確信度:** 高（二比較の機械判定可能性）。純便益は未検証。

**探索の境界と停止理由:** 二つの独立判断を単独または両方委譲する三構成は、残る人手負担と調整範囲が異なるため比較した。数値の閾値を二値の委譲軸に分割せず、申請別の数量と上限額を保持する。真正性を機械化する枝は明示的制約に反する。外部認証サービスの可用性・契約は不明であり、隣接の資産管理・人事にはProblemとの因果がないので広げない。これらの候補が最適だとの主張はしない。

## 3. 証憑確認

**Problem:** 一回の人間による真正性確認に手間がかかる。**Pain:** Low。参照: `inputs/zero.md`「Activity」「制約とReview input」。

**候補: 0件。** 現状で確認と記録は一回だけ、記録支援も利用済みである。人間による真正性判断の省略・委譲・機械化は固定条件に反する。同じ確認を支援し直す案は既存設計の言い換えとなり、隣接業務や外部サービスによる効果を示す事実もない。低いPainに対して未確認の責任変更を広げる根拠はない。

**維持する意味と探索停止:** 証憑確認責任者が届いた証憑の真正性を一回判断し、判断者と結果を記録する。今回その条件を緩める権限がなく、さらなる分解で採否が変わる独立判断は見いだせない。確認に要する時間などの測定は与えられていないが、それだけで候補を作らない。極端な別モデルも固定条件と未知の反復需要を越えるため提示しない。
