# モデルと情報の存在条件

## 根拠の扱い

根拠の原典は[記録](evidence.ja.md#原典)に固定する。Bはレビュー中BDに記載済みの業務条件、Cはその後の本人指定、Hは今回の設計仮説、Uは未決を表す。BもBD全体の合意済みを意味しない。

| 区分 | 内容 | 原典の箇所 |
| --- | --- | --- |
| B1 | 一申請は複数品目を持ち、依頼全体の見積書と税抜小計合計で提出する | 購入申請の扱い／業務相関2／申請Procedure |
| B2 | 見積・購入理由・品目情報は提出時必須。下書きは未入力可。不適合・判定不能は提出不成立 | 申請Input／Exception、再申請Procedure |
| B3 | 確定内容は直接変更せず、再申請は別の提出版 | 購入申請の扱い／再申請Procedure4 |
| B4 | 準備前なら承認後も差戻し可。古い承認は無効。過去判断の履歴は必須でない | 承認Exception／業務相関3 |
| B5 | 準備は複数申請を束ね、申請を品目別に分割しない。番号・対象・確定内容は固定 | 準備Procedure2–4 |
| B6 | CSV失敗・紛失時も同じ番号・内容で再出力。CSV成功と購入完了は別 | 準備Exception／業務相関4 |
| B7 | 各回の入庫を複数登録。代替品・旧版・別申請の品目は不可 | 結果登録Procedure2・4 |
| B8 | 品目ごとに依頼＝入庫累計＋購入しない数量＋待ち。全品目待ち0で申請全体を一度だけ終結 | 結果登録Procedure3–5 |
| B9 | 全数購入なしも合法。終結後の訂正なし。同じ再送で実績を増やさない | 調達不能時の調整／結果登録Result |
| C1 | 保存時には必ず版と1品目以上。下書き専用概念を作らず、未確定版とする | root #133 Goal「モデル見直し（2026-10-20）」 |
| H1 | 0..1情報は条件付き属性にまとめる。独立した識別・履歴・複数性が必要なら分離 | 今回の本人依頼と本草案 |
| U1 | 破棄後の保存、再申請失敗後の編集中内容、代理申請、日付・実績金額、合意の記録粒度 | BDの未決・未確認事項 |

BD本文には「下書き品目0件不可」はまだ反映されていない。C1を後続指定として草案に適用するが、BDを更新済みとは扱わない。品目が存在することと、品名・単価・数量が入力済みであることは別である。

## 6つの業務概念

| 概念 | 一件の意味・必要最小限の情報 | 分ける理由 |
| --- | --- | --- |
| 購入申請 | 継続して追う一つの購入要求。申請の識別、申請者、進行状態、現在の判断対象版、現在判断、準備所属と対象版、終結結果 | 差戻し・再申請でも同じ要求を追う。終結もこの単位 |
| 購入申請版 | ある時点の依頼内容。申請内での版の識別、未確定／確定、購入理由、見積根拠、提出日時 | 複数の確定内容を区別し、旧内容を不変にする |
| 申請品目 | 一つの版に含まれる依頼の一行。版内の識別、品名、税抜希望単価、依頼数量、購入しない確定数量 | 複数の品目・数量を独立に照合する。同名品でも同一品目と決めつけない |
| 購入準備 | 同じ準備番号で渡す一まとまり。準備番号、確定した対象申請と各対象版、書き出し日時の情報 | 複数申請で共有する独立した業務番号。申請の0..1属性だけでは共有内容を説明できない |
| 入庫回 | 一申請に対する一回の入庫登録。回を区別する識別、対象申請、各回の内訳 | 分割納品の各回を消さずに残す。累計だけにしない |
| 入庫内訳 | 一入庫回の中で、元の申請品目へ対応する数量。回内の識別、元品目、今回入庫数量 | 一回に複数品目があり、同じ品目も別の回で入庫できる |

識別は「同じものか判断できる」という業務上の必要性を表す。採番方式や保存構造は選ばない。各操作の作業者は認証基盤から識別するが、全操作の監査属性を一律必須にしない。

入庫回は申請単位に置く仮説であり、一物理納品が複数申請にまたがる場合の共通伝票管理を追加しない。申請ごとの各回と内訳は保持できる。跨申請伝票としての識別が必要なら追加判断となる。

## 保存された情報の多重度

| 関連 | 左1件から見た右 | 右1件から見た左 | 根拠 |
| --- | --- | --- | --- |
| 購入申請 — 購入申請版 | 1..N | 1 | B3・C1。初回保存時から版あり |
| 購入申請版 — 申請品目 | 1..N | 1 | B1・C1。未確定品目の値は未入力可 |
| 購入準備 — 購入申請 | 1..N | 0..1 | B5。未準備申請は0、確定準備は空にしない |
| 購入申請 — 入庫回 | 0..N | 1 | B7・B9。準備後に限り存在可 |
| 入庫回 — 入庫内訳 | 1..N | 1 | B7・H1。入庫を伴わない調整で空の入庫回を作らない |
| 申請品目 — 入庫内訳 | 0..N | 1 | B7。準備対象版に属する元品目に限定 |

0件は登録前の一時入力状態にもあるが、この表は保存に成功した状態を表す。破棄後の保存表現はU1であり、保存状態の多重度を根拠に物理削除・墓石記録を選ばない。

## 分離しない条件付き情報

| 情報の置き先 | 存在条件・値のまとまり | 存在しないことの意味 |
| --- | --- | --- |
| 申請版：購入理由・見積根拠・品目入力値 | 未確定なら未入力可。確定時は全て成立。見積は依頼全体の根拠を特定し、確定後に文書内容も変わらない | 入力途中。見積取得不要という意味ではない |
| 申請版：提出日時 | 確定時に存在し不変 | 未確定で未提出 |
| 申請：現在の判断対象版 | 初回提出成功後に0..1。必ず同じ申請の確定版。再申請成功時に新しい版へ切替 | まだ提出していない |
| 申請：現在判断 | 0..1のまとまり。対象版、承認／差戻し、判断日時。差戻しなら理由必須 | 判断待ち、または新しい提出版への切替で旧判断が無効 |
| 申請：準備所属・準備対象版 | 準備確定で同時に存在。対象版はその時の現在版かつ承認対象版。以後不変 | 未準備。CSV生成失敗を理由に消さない |
| 申請品目：購入しない確定数量 C | 準備前は対象外、準備後は0以上。0は購入なしを確定した数量がない。増やす場合は申請者との調整済み | 未入力と0を同一視しない。準備前は結果数量そのものが未適用 |
| 購入準備：書き出し日時 | 成功したCSV書き出しがあれば説明可能。失敗だけなら成功日時なし。複数成功時に初回／最終／全履歴のどれを保持するかは未決 | 準備が存在しない、購入していない、という意味ではない |
| 申請：終結結果 | 全品目の待ちが0で一度だけ存在。全数入庫／一部入庫と残り購入なし／全数購入なし | まだ全数量の結末がそろっていない |

見積書を独立概念にしないのは取得・改版管理が本システムの業務ではないため。根拠を不変に特定する値として版に含める。同じ外部見積を別の申請や版で参照してよい。依頼全体の根拠一式を表し、添付ファイルを必ず1個に制限しない。複数添付の上限は未決。

現在判断は確定内容そのものとは分けて変更できる情報であり、版に含む希望内容を編集する意味ではない。古い判断の履歴保持を要求しないが、再申請後に古い承認を流用できない。無効化の実現方式は指定しない。

NULL可否はここに記した業務情報の存在条件を意味する。列のnullable、別構造への分離、複製、参照ポインタ等は実装時の選択である。

## 導出と整合条件

品目ごとに Q＝依頼数量、R＝各回の入庫数量の累計、C＝購入しない確定数量、W＝Q−R−C とする。準備後はR・C・Wが0以上で、R＋CがQを超えない。準備前の結果数量は業務上未適用。税抜希望合計は全品目の単価×数量の合計とする。数値の上限・精度・端数処理は未決であり、例の整数だけを許す規則にしない。

1. 確定した版の購入理由・見積根拠・品目・希望単価・依頼数量・提出日時を変えない。結果側のCや入庫追記と区別する。
2. 準備は現在有効な承認を持つ未準備申請のみ。承認対象版＝現在の判断対象版＝準備対象版を同じ申請内で満たす。
3. 準備番号・対象申請・対象版は一貫して確定する。差戻しと準備確定の同時成功、別準備への重複所属を許さない。
4. 入庫内訳の元品目は、その申請の準備対象版に属する。別申請・旧版・代替品への入力を禁止する。
5. 一品目でもWが正なら未終結。全品目W＝0で申請全体を一度だけ終結する。申請全体の数量合計で過不足を相殺しない。
6. 同じ登録の再送で入庫を追加しない。終結済みの再送も同じ結果として扱い、新規実績や別の終結を作らない。終結後の新規訂正は扱わない。

図と属性だけでは、状態を確認する時点、数量集計、競合、再送や外部見積の同一性を保証しない。これらも業務成立条件として後続設計へ渡す。排他・トランザクション・DB制約の方式は本草案で選ばない。
