# 旧モデルとの比較と作成上の知見

## 業務から選び直した境界

最初に、継続して追う要求、固定された内容、複数の品目、複数申請で共有する準備番号、各回の入庫とその内訳を抽出した。その後で旧モデルと対応させた。独立して見える状態や未発生情報を、すべて別の記録へ変換することはしない。

比較対象はPR #254の固定版にある**全工程の15概念のモデル文書**。直近のERラフは申請〜承認に限定した6概念であり、全工程モデルと同じ範囲ではない。数だけを比べて6から6へ変化なしとは評価しない。

| 旧モデルの15概念 | 新しい表現 | 残す情報／省くものと理由 |
| --- | --- | --- |
| 購入申請 | 購入申請 | 継続した要求の同一性を維持 |
| 下書き入力 | 未確定の購入申請版へ統合 | 入力途中の理由・見積を保持。独立した下書きの同一性は不要 |
| 下書き品目 | 未確定版の申請品目へ統合 | 未入力を許す品目。旧文書の0件保存はC1により採用しない |
| 見積書 | 版の見積根拠という値 | 不変な文書根拠・再利用を保持。取得・文書管理の独立業務は範囲外 |
| 確定提出版 | 未確定／確定を区別する購入申請版 | 確定内容・提出時点を保持。版の分離は複数の確定内容のため |
| 申請品目 | 申請品目 | 複数品目と独立数量を保持 |
| 現在提出版 | 申請の現在対象版という関連 | 現在対象0..1を保持。実現方式に依存した中間概念は不要 |
| 現在判断 | 申請の条件付き判断情報 | 対象版・承認／差戻し・日時・差戻し理由を保持。旧判断の履歴は必須でない |
| 購入準備 | 購入準備 | 共有番号と固定対象群が独立するため維持 |
| 購入準備対象 | 準備と申請の所属、申請ごとの準備対象版 | 所属と不変な対象版を保持。所属自体に独立履歴・識別の要求がない |
| CSV出力試行 | 準備の書き出し日時の情報 | 再出力できることと成功日時を保持。試行全件の履歴は未決のため必須化しない |
| 入庫実績 | 入庫回 | 各回の区別を維持。登録日時等の粒度は未決に戻す |
| 入庫明細 | 入庫内訳 | 一回の複数品目と元品目の対応を維持 |
| 購入しない数量 | 品目の結果側属性C | 入庫と別の確定数量。独立した調整履歴は未決 |
| 申請終結 | 申請の条件付き終結結果 | 一度の終結・3分類を保持。独立した履歴・後続操作はない |

15概念を6概念へ整理するが、物理テーブルを9個減らす提案ではない。必要な情報は属性・関連・成立条件へ移る。旧文書で設計案だった権限判定スナップショット・試行履歴・再送識別方式は、正式業務の必須事項へ昇格させない。

## 3概念で止めない理由

準備を申請内の番号だけにすると、共有する1件の準備とその固定対象を説明しづらい。入庫を累計だけにすると各回の履歴を失う。入庫の品目別数量を一つの単純な値にすると一回に複数品目を登録できない。準備・入庫回・内訳は、今回の複数性を説明するため残した。

入庫回と内訳を「各品目の入庫記録」1種類にまとめる5概念案も考えられる。ただし同じ回の複数品目というまとまりを別の属性で再導入することになる。この草案では各回を読むことを優先して6概念を推奨する。6が普遍的な最小数とは主張しない。

## 人間へ返す判断と質問

| 論点 | 推奨・今回の扱い | 違う判断になった場合 |
| --- | --- | --- |
| 6概念と条件付き情報で購買業務を追えるか | この候補を図と工程表でレビューする。15概念への復帰を前提にしない | 欠落する具体的な仕事・情報を示して境界を再検討 |
| 入庫の一回は申請ごとの登録として十分か | 申請ごとの回を採用する仮説。跨申請の納品伝票管理は導入しない | 一物理納品を跨申請で追う必要があるなら別の同一性を検討 |
| C1：保存時に版と1品目以上 | 先の本人指定を維持。品目の入力値は未入力可。BD本文は未改稿 | 品目ゼロ保存も必要なら明示的な変更として多重度と例を更新 |
| 日付・実績金額の粒度 | BD未決を維持。入庫日＝登録日時＝発注日としない | 必須条件と単位が決まれば属性または反復情報を追加 |
| 購入しない数量の合意者・理由・変更履歴 | 調整済みであることは条件。詳細の必須保存は未決 | 複数の合意・改訂を保持する必要があれば分離理由が成立 |
| 破棄と再申請失敗後の保存 | 対象外化／提出不成立までを表現。削除・保持を選ばない | 確定版の保持範囲と編集中版の残し方を具体化 |
| 書き出し日時の意味と試行履歴 | 書き出しが分かることを保持。初回・最終・全履歴は未決 | 全試行履歴が業務上必要なら複数の出力記録を検討 |

未決を全部解消するまで構造候補のレビューを停止する必要はない。ただし、日付・金額・破棄後の扱い等を未決のまま最終実装仕様として渡すことはできない。

## 将来のSkillへ持ち込む候補手順

1. BDの対象版を固定し、各Activityで「何を一件とするか」「何が次へ渡るか」を先に抜き出す。既存ERの名称・分割を起点にしない。
2. 同じ要求の継続、複数の独立内容、履歴の必要性を根拠に境界を提案する。Nを見つけてもリストの各値を自動的にエンティティにしない。
3. 0..1は「未発生」「未入力」「対象外」「値0」を区別し、存在条件を列挙する。分離する場合は独立識別・ライフサイクル・複数履歴の必要性を説明する。
4. 所有する全版と、現在有効な版・判断を分ける。固定する内容と後から追加する結果情報も分ける。確定内容を含む概念に状態属性を置くだけで不変性を証明したとしない。
5. Activityごとに参照・登録・更新を埋め、作られる情報が後続で読めることを確認する。図の局所省略と条件の省略を混同しない。
6. 0件・1件・複数件の正当例と、旧版混入・過剰数量・競合・再送等の反例を対で当てる。減らした結果、正当な業務が不可能になっていないかも確認する。
7. 業務既決、後続の本人指定、設計仮説、未決を別々に示す。実装方式で埋めず、必要な業務判断だけ具体例で返す。
8. 初めて旧モデルと照合し、削除ではなく情報の移し先まで説明する。人間レビューで「判断しやすいか」「情報不足はないか」を確認する。

観測できたのは、この購買草案で0..1専用概念を減らしながら必要情報の対応を説明できること。読みやすさ向上・最適な分割・他業務への一般化・Skillの有効性は未検証。将来のSkillは図の生成だけでなく、存在条件と正当例／反例を返す必要がある、という仮説を得た。正式Skill・Pluginの規則にはまだ反映しない。
