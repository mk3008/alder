# データ構造の保存契約案

業務設計書、状態遷移、概念モデル、Check Item を、それぞれ版を持つ文書として一つの JSON パッケージに収める案。これは構造のレビュー用草案であり、正式なスキーマや業務内容の合意ではない。現行の `alder-document-package/0.4` は概念モデルを受け付けず、Viewer も任意の概念モデルを読み込めない。

## 文書の責務と参照

| 文書 | 決めること | 参照するもの |
| --- | --- | --- |
| 業務設計書 | Activity・Object の切り出し、業務が成立する流れ、相互の入出力 | 起点。下位文書を正本として参照しない |
| 状態遷移 | 対象 Object の状態と、明示した Activity・条件による遷移 | 業務設計書の文書 ID・版、Object・Activity・例外 ID |
| 概念モデル | 論理サブシステム、業務情報のまとまり・関連、担当者が確認するビューと例 | 業務設計書の文書 ID・版、Object・Activity・ロール ID。実際に根拠とする状態遷移がある場合はその文書 ID・版と要素 ID |
| Check Item | 成立させることと検証すること | 業務設計書の文書 ID・版。状態・構造を根拠にする項目は、その文書 ID・版と該当要素 ID も参照 |

状態図やモデルを見て業務設計に不足が見つかれば、業務設計書へ明示的に戻して修正する。これは編集のフィードバックであり、JSON に循環参照を置くことではない。Check Item は、業務設計の対象版に対する人間の合意を経て草案化する。実装テストや Viewer の表示成功を業務上の合意とは扱わない。

現行購買データでは、業務設計 `purchase-bd / bd-v2-beta-5`、状態遷移 `purchase-states / states-v2-beta-6`、概念草案 `purchase-concepts / concepts-v2-beta-7` が対応する。Check Item の正式な購買 V2β 文書はまだない。業務設計と状態遷移は形式 0.4、概念モデルは別ファイルの試作形式であり、以下の案に自動移行されたわけではない。

## 概念モデルの中身

| 要素 | 保持すること | 購買の例 |
| --- | --- | --- |
| 論理サブシステム | ID、名前、目的、責任範囲、関連 Activity | 稟議、入荷予実 |
| 概念 | ID、名前、所属、情報のまとまり、必要な理由、関連 Object・Activity・出所 | 購入申請、購入申請版、申請品目など６概念 |
| 概念間の関係 | ID、両端、件数、成立する条件、根拠 | 申請と版、版と品目 |
| 境界を越える受け渡し | ID、送り元・受け先のサブシステム、渡す情報、根拠、向き | 承認済みの版・品目、入荷・未購入の結果 |
| レビュー範囲 | ID、タイトル、説明、既存ロール、関連 Activity、範囲内の構造と利用者向け説明 | 購入要求・申請内容など４分類 |
| できること・できないこと | 見出し、説明、根拠。できないことには理由 | 入力途中を保存、条件を満たす内容を提出 |
| データ例 | 対応する「できること」の下に、場面、表、列、行、値、表示上の対応キー | 品目がない下書き、２品目の提出 |

論理サブシステムは情報の生成・変更と業務の成立に責任を持つまとまり。４分類は担当者が業務を遂行できるかを確認する範囲であり、サブシステムでも、物理テーブルやサービスの分割でもない。レビュー範囲は他の範囲やサブシステムで生成した情報を含めてよい。その場合も情報の出所と対象時点を明示する。稟議の提出版・品目を購入対象のビューで併せて示すのが例である。

概念内の情報は列名まで分解することを必須にしない。識別や関数従属が業務上必要なら、その単位、必要な理由と根拠を構造上の判断として持つ。例えば「版内の品目の識別」は残すが、実装の主キー、外部キー、テーブルや索引の決定とはしない。識別子や関係がまだ決まらない場合は仮説・未確認として保持し、存在しない情報を完成済みとして補わない。

レビュー担当者は業務設計書の既存ロール ID で参照する。購買の各範囲は現在１ロールだが、将来の複数担当を許す配列とする案とし、１ロール１ページ・１ Activity １ページを強制しない。意味としてのレビュー責任と Activity の作業者は別に扱い、存在しない役職を Viewer が追加しない。

## JSON の形

既存パッケージに `conceptModel` 文書種別を追加する案。以下は要素間の参照を示す**部分例**であり、現行 0.4 にそのまま入力できる JSON ではない。実際の要素・版 ID と表示例を使い、省略した項目は `…` で示す。

### 表示用ビューと情報の正本

個別の構造図には、概念全体の情報をそのまま複写せず、各表示行がどの情報 ID に基づくかを明示する案とする。表示名はレビュー相手に必要な場合だけ個別に持つ。１つの情報のまとまりから「品名」「税抜希望単価」の２行を表示する場合や、複数概念の情報を１カードにまとめる場合もあるため、表示行は１つ以上の情報 ID を参照できるようにする。条件付きのビューにはその条件とビュー固有の関係を持たせ、全体の関係から勝手に件数を変換しない。

例えば、購買の概念 `item` は情報 `item-information-2` として「品名・税抜希望単価」を持ち、レビュー図では２行に分けられる。各行が同じ情報 ID を参照すれば、名前や意味の変更時に影響先を探せる。表示名の個別変更を自動で上書きするのではなく、参照元の変更を通知してレビューする。

各例の列は対応する情報 ID を参照し、表間で同じものを指すセルには場面内で共通のキーを持たせる。キーの色は表示上の識別であり、DB のキーや他の場面との色の一致を意味しない。例は「できること」の下に一度だけ持つ。例の数を自動で削減する規則は今回決めない。

### 件数と状態

関係の件数は、業務上「一つか複数か」「存在が必要か」を判断するために持つ。例の `N` は複数を許すが最小件数は未確定、`0..N` は０件も可能、`1..N` は少なくとも１件必要という区別を保持する。数値が不明なら不明のまま明示し、Viewer が `N` を `1..N` に変えない。データ量見積りや物理的な索引のための件数は、この契約では求めない。

下書き保存は入力内容・品目数・申請の状態を問わず可能。保存によって既存の申請・承認・購入準備を変えず下書きを区別する扱いは未合意の仮説として残す。保存できることだけから全状態の自己遷移を生成しない。

## 変更と照合

1. 参照元と各文書に安定した ID と revision を持たせる。名称変更で ID を変えない。表示名は同一の情報から解決するか、出所付きの明示的な別名とする。
2. 業務設計書の版が変わったら、その版を根拠とする状態・概念・Check の参照と、要素 ID 単位の依存先を検査する。版が違う参照は黙って現行版に更新せず、影響箇所として報告する。
3. 名前だけの変更では、ID参照先の表示名を更新し、明示した別名と人間の判断に影響がないか点検する。提出条件や品目の意味を変えた場合は、関連する状態遷移、情報、条件付きビュー、できること、例、Check を点検し、変更した期待は再レビューへ戻す。
4. 正しい参照先を確認してから下位文書の版と `basedOn` を明示的に更新する。参照できない ID、古い版、別文書の同名要素、未申告の要素消失は保存時に検出する。チェックは構造と参照を検査するもので、文章の意味や業務上の合意の証明ではない。

表示時は、パッケージ内の明示データから全体図・個別図・概要・例を組み立てる。推論や不足する業務規則の補完は、作成・レビューの工程で仮説として行い、結果を保存してから Viewer へ渡す。業務設計から文書を一方向に生成し直すことを必須にせず、下位文書で具体化した内容と人間の判断を維持する。

## 既存デモから正式契約にするために必要な作業

- 現在の図中の表示文字列を、概念の情報 ID や、別概念から組み立てた情報と対応付ける。現状は文字列だけの行があるため、単純なコピーでは変更影響を追えない。
- 受け渡し情報と状態・Activity・Object の根拠参照を、利用できる ID と版に結び付ける。分からないものは未確認として残す。
- Check Item の参照先に状態遷移・概念モデルの要素を含められる新しい契約を定める。現行 Check は業務設計の参照を前提としている。
- 新契約の型・参照・版の検査、競合を防ぐ編集、既存データからの明示移行、任意 JSON の Viewer 読込みと表示を実装する。互換境界では旧 0.4 と V1 を保持する。
- 購買以外の業務でも検証し、どこまでを必須にするかを調整する。今の購買デモだけを全業務に共通する最終形としない。
