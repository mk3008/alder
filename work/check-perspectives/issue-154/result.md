# Check Item探索視点の比較結果

## 結論

**不採用: 今回の視点補助promptを現行c3の標準へ昇格しない。** 既存2ケースの各arm1runでは、設備保全で「選択後に安全閉鎖された場合」という有用な確認場面を1件具体化できた。一方、購入申請では他申請の非変更や購入済み再実行はControlの本文・詳細に既にあり、同時判断の項目には根拠以上の成功保証へ読まれる危険がある。Controlだけが独立して示した購入前の禁止もある。全面的な性能優位や非劣性は示していない。

この判断は補助観点が一切役立たないという結論ではない。現行c3にも状態・境界・接続・不変条件の探索があり、今回の観測では追加promptの標準化を正当化できない。正式Skill・仕様・Business Design・Plugin・READMEは変更していない。Research Decision Indexへ研究判断だけを追記する。

## 同じ成立条件の確認を具体化できたか

| 例 | 観測と意味境界 |
| --- | --- |
| 設備保全 Treatment M2-04 | `open`依頼の選択後、日程設定の成立前に独立した点検で設備が閉鎖される場面を示した。BD119–121、146–148、229、255–257行の非閉鎖条件と閉鎖中不成立を組み合わせたもの。Control A2-04/A4-04は閉鎖済みの禁止を含むが、この間の変化を具体化していない。新しいpolicyやロック方式を作らず、確認シナリオを明確にした増分である。 |
| 購入申請 Treatment X-02 | 別申請へ結果を誤適用しないという独立表示は読みやすいが、Control末尾にも「その対象にだけ各結果を成立させる」とある。主表だけで比較すると増分を過大評価する。意味上の固有増分には数えない。 |

「固有」はこの4出力間での具体的シナリオの提示差であり、既存c3から導出不可能という意味ではない。Treatmentの別視点欄は由来の自己申告として追えるが、promptが差を生んだという因果証明ではない。

## 意味逸脱・質問・レビュー負荷

- 購入申請 Treatment X-01は、単一の状態値が`approved`と`rejected`を同時に持たない範囲ならBDに根拠がある。しかし「近接する承認と却下の双方が成功を報告しない」保証、優先順位、裁定時点、原子性は未定義。この強い読みを有用な追加保証に数えず、採用前の要確認とする。rawの「強い導出/高/未レビュー」という表示だけでは、この曖昧さを解消できない。実際の業務承認をしたわけではないが、未決の並行実行policyをCheckへ持ち込む危険が1件ある。
- 設備保全 Control A3-04の詳細は「報告日時以前」という条件を置き、BDの「報告日時より前にならない」よりも等値を狭める。主表の早期完了許可は根拠があるが、詳細には局所的な意味逸脱1件がある。Treatmentを安全、Controlを危険と一般化しない。
- 明示的な質問はControlが購入後の登録失敗1件、Treatmentがそれに数量・金額の値域を加えた2件。値域を勝手に決めず質問に留めた点は維持されたが、質問の増加は確定Checkの改善と分けて扱う。設備保全は両armとも新質問0件。明示的な保留事項の再質問は観測していない。
- 技術的実装方式の要求化、全観点×全業務の固定チェックリスト展開、形式手法の導入は観測していない。重複/細分化は残り、生成結果をそのまま承認済みにできない。

## Check ItemをOracleと呼べる範囲

Business Designから導出し、人間が意味を確認したCheck Itemは、下流Testが照合する**期待の基準**と説明できる。ただしAI初稿を業務意味の決定者、Checkリスト自体を実装完了の証明器として扱わない。

実装後はTestのassertionが確認済み期待を表すかを照合し、実行証拠と不足を別に確認する。恒久traceabilityはBusiness Design ↔ Check Item ↔ Testまで。Codeへの物理mappingは追加せず、DB制約・property-based test・形式検証等は下流の検証手段として選ぶ。起点記事の本文はpilot実行時には未取得であり、生成・評価条件には使用していない。以上は、その時点のAlderの現行文書に基づく解釈である。後続Chatでは記事本文を別途確認したが、その確認をpilotの入力・結果・採否へ遡及反映していない。

## 実験条件と限界

- 元revision: `a58c970f3a78ac9a0ba91be3c6bfb05e4e2b1168`。既存公開の備品購入申請・設備保全をbyte-identicalに固定。実運用で成果を測ったケースではない。
- 生成前公開precommit: [`25ec5216cbc2561d5c60e93ade22118c7f621272`](https://github.com/mk3008/alder/tree/25ec5216cbc2561d5c60e93ade22118c7f621272/work/check-perspectives/issue-154)。完全prompt・入力・guidance・rubric・hashを先に公開し、SHA指定取得を確認した。
- generatorは各armのpromptと当該BD、凍結guidanceだけを読み、他arm・別case・過去raw・実装・Testを渡していない。requested model `gpt-6-sol` / effort `medium` / fork `none`。実効model/effortは独立にattestできず未確認。4生成を追加反復しなかった。
- BD合意/相関レビュー完了の独立証跡がなく、その点を両armの指示とrawに明示した。確定済み設計handoffの本来条件を検証したとはいえず、意味固定された公開記述からの導出pilotである。この制約を完了済み・承認済みという語で隠さない。
- 一次評価はarm keyと生成promptを伏せたが、内容からarmを推測できる可能性がある。さらに評価launchはrawを見た調整者が作り、単一状態と並行成功、選択時と成立時を区別する注意を追加した。分類rubricは事前固定だが、完全事前登録/完全盲検の評価ではない。全文launchを保存した。
- 元評価後、調整者がControl末尾と等値境界の根拠を示し、同じ評価者が訂正overlayを作成した。元score/rawは保持する。1名のAI評価と調整者の根拠確認であり、人間の意味承認を代替しない。
- 調整者の応答に一時的capacity中断があった。再開時にIssue/PR/保存ファイルを確認し、4生成を再実行しなかった。生成設定・入力・出力に変更なし。

## 再検討条件と残作業

現行c3が実利用で、BDに明示された業務成立時条件の選択後変化を繰り返し落とす証拠が得られたときに、該当場面だけを説明する最小補足を別Taskで検討できる。その場合も、未定義の同時処理policyを質問へ戻す境界を先に固定する。現在は追加生成、正式変更、実装Taskを必須にしない。

研究成果のレビューは残る。PRのマージは人間の明示許可がある場合だけ実施する。研究結果の保存と正式guideへの採用、実際の負荷低減はそれぞれ別状態である。
