# 備品購入申請 — 業務設計

草案（採用した改善方針を反映した変更後の業務案。全体の人間レビュー・合意前）。

社内で使用する備品の購入申請、承認、購入準備、調達不能時の調整、分割入庫と申請全体の終結の記録を記述する。実際の仕入れ・発注・在庫確認はシステムのスコープ外で行う。調整の相談手段や合意をシステムへどこまで記録するかは未決である。

業務上の意味・前提・入力・手順・結果を記述し、画面部品、API、クラス、モジュール、データアクセス方法などの実装方式は規定しない。

## 業務上のロール

- **申請者** — 業務に必要な備品の購入を申請する。
- **承認者** — 申請内容を確認し、購入を承認するか、申請者へ差し戻す。
- **購買担当者** — 承認済み申請の購入準備を確定してCSVを出力し、外部で見積書を取得し、調達不能なら申請者と購入しない数量を調整し、分割入庫の実績と申請全体の終結を記録する。
- **総務** — 基幹システムの役職別上限額に関する情報を管理する。
- **人事** — 基幹システムの従業員情報を保守する。

ロールは業務上の責任と権限を表す。

## 作業者の識別と認証

各業務の作業者は、外部の認証基盤を利用したシングルサインオン（SSO）でログインし、一意に特定する。認証済みセッションは複数の画面・操作で継続利用する。パスワード等の資格情報を各業務へ配布する意味ではない。具体的な製品・サービス名は指定しない。

各業務はスコープ外のObject「認証基盤」から認証済み作業者の識別情報を受け取る。申請時・再申請時には、その利用者に対応する従業員情報・役職を基幹システムから参照する。認証基盤と基幹システムの具体的な属性・キーの対応付けは、SR・実装側で具体化する。

作業者と申請者が異なる代理申請を認めるか、その場合に誰の役職で判定するかは別の業務上の未決事項である。作業者を一意に識別できることから、代理申請の可否は推定しない。

認証・セッション管理は一般的なWebアプリのセキュリティ要件に沿うものとする。具体的な技術条件はシステム要件（SR）で定める。認証プロトコルやセッションの有効期限等の詳細は未定である。

## 購入申請の扱い

購入申請は、申請者が業務上必要とする備品の購入要求を、承認および購買の対象として扱うための記録である。

購入申請は、後述のObject 購入申請のInformationに挙げる情報を少なくとも持つ。

購入申請は一意に識別できるものとする。識別子の採番・入力方法はこの業務設計では規定しない。

一つの購入申請には複数の品目を含められる。各品目の希望金額は税抜希望単価×数量で算出し、申請全体の税抜合計額を申請者の役職別決裁上限額と比較する。

提出して確定した内容を直接変更しない。差戻し・再申請では、何をいつ確定したか識別できる別の提出版を用いる方向とする。版の識別方法や下書きとの関係はレビュー中の設計候補である。

## 業務相関

1. 購買担当者がシステム外で見積書を取得して依頼部署へ返す。依頼部署は見積条件で経費を使うか判断する。見積取得機能は本システムに設けない。
2. 申請者は依頼全体の見積書を添え、複数品目の品名・税抜単価・数量と購入理由を提出する。全品目の税抜小計の合計が役職別上限以下と自動判定できた場合だけ申請が成立する。見積書なし、権限不適合・判定不能では成立しない。下書きは必須値が未入力でも保存できる。今回は見積条件どおりの価格を前提とし、権限に収まらなければ別の人が申請するか見積内容を変える。代理操作の許可を意味しない。
3. 承認者は申請内容を判断し、承認または差戻しを行う。承認後も購入準備確定前は差戻し可、準備確定後は不可。確定提出版を直接変更せず、再申請で別の確定版を区別する。旧承認判断の業務履歴は不要だが、古い判断を現在の購買根拠として使わない。
4. 購買担当者は複数の承認済み申請を申請単位で一つの準備番号へまとめる。一申請を品目別に別準備へ分割しない。番号・対象・差戻し不可を一貫して確定する。CSV失敗・紛失でも同じ番号・同じ凍結内容で再出力する。書き出し日は分かるが発注日ではなく、出力で購入完了にはしない。
5. CSV書き出し後の発注管理は購買側システムが行う。本システムで発注日を管理せず、発注情報の追加受信を前提にしない。
6. 倉庫への分割納品を扱い、購買担当者が各回の入庫結果を登録する。代替品は今回禁止する。調達不能時は購買担当者と申請者で購入しない数量を調整し、元の承認者は介入しない。元の提出内容・準備内容を上書きしない。
7. 全依頼数量を品目ごとに入庫済み・今後購入しないと確定・未入庫待ちに区別する。待ちが残れば作業中とし、全数量の結末がそろったら申請全体を一度だけ終結する。全数入庫、一部入庫と残り購入なし、全数購入なしの3つを区別する。最終終結の訂正は扱わない。分割納品を別発注による分割購入の許可と解釈しない。
8. 下書き・差戻しから再申請または破棄を選べる。再申請にも見積書必須と税抜合計の権限判定を適用する。

## 調達不能時の調整

依頼10個に対して5個入庫・5個待ちなら作業中、5個入庫・残り5個を購入しないと確定すれば終了する。8個入庫・2個待ちを完了にしない。代替品は購入しない。全数を購入しないと決めた場合は入庫実績0件でも終結できる。数量減・購入なしの調整に元の承認者は介入しない。調整理由・合意者などの保存範囲は未決である。

## 現在の業務設計で未決定の事項

次の事項は現在の業務設計では定めない。

- 申請金額によって承認者や承認段階が変わる場合の扱い
- 見積取得、在庫確認、実発注・発注日の管理、検収、支払、倉庫内の在庫・払出管理（分割納品の入庫結果登録は対象）
- 購入先の選定方法
- 購入後の備品管理、資産管理、廃棄
- 基幹システムからの従業員情報・役職別上限額の参照、外部認証基盤によるSSO、購入用CSVの出力以外の外部システム連携
- 監査履歴や通知に関する業務
- 役職別上限額の具体的な値、基幹システムを参照する際の運用条件
- CSVに含める列・出力形式・配布管理・再出力の担当と履歴、最終調達結果の入力方式（手入力・CSV取込等）。ただし購入準備番号と同番号での再出力は合意済み
- 調達不能時の申請者との合意確認・記録範囲。数量減・購入なしの調整に元承認者は介入せず、代替品は禁止とする
- 数量・金額の数値範囲、端数、最終的な実購入金額の税区分
- 一括却下・一括結果登録の採用（今回の改善では採用していない）

これらは、現在の業務設計を実装するために決定済みであるとはみなさない。

## 確認が必要な事項（未確認）

承認と差戻しの業務境界はF01、購入準備と購入結果登録の分離はF02、認証基盤からの作業者識別情報の受取りはF03に解消内容を記録する。代理申請の可否・適用する役職は、F03とは別の業務上の未決事項として残す。

- **購入できない場合・結果登録できない場合**：購入しない数量を申請者と調整し、入庫済み数量と区別する。合意記録の粒度は未決。技術的な失敗時の重複防止と安全な再試行は設計・実装で保証する。購入日時・入庫日・登録日時を同一と定めない。
- **入力不足・状態が変わった場合**：提出には見積書と品目情報が必要で、権限判定不能なら成立しない。下書きは未入力可。承認・差戻し・準備確定は処理時にも状態を再確認し、差戻しと準備の同時成功を認めない。数量・金額の具体的な範囲・精度は未決。

基幹システムの役職別上限額に不適合または判定不能の場合の申請不成立と、承認業務中の差戻し、差戻し・下書きからの再申請または破棄は後述のとおりとする。それ以外の未記載の操作結果は未決である。

- **破棄・再申請不成立の扱い**：申請中断時の下書き保存と、その下書きからの再開は後述のとおりとする。破棄時の物理削除・履歴保持、再申請が権限判定で成立しなかった後の元の申請内容の扱いは未確認である。下書きの自動保存や、破棄後の保存期間は規定しない。

## 参照する基幹システム

基幹システムは、従業員の識別情報・役職と、役職ごとの決裁単位の上限額を提供する外部システムである。決裁単位は購入申請1件とし、申請者の役職に対応する上限額を用いる。従業員情報は人事、役職別上限額に関する情報は総務が管理する。

今回の業務は基幹システムから必要な情報を参照し、その保守は扱わない。内部のテーブル単位にはObjectを分けない。具体的な上限額や参照時の運用条件は未確認である。認証済み利用者と従業員情報の具体的なキー対応はSR・実装側で定める。

# Scope

社内の備品購入について、基幹システムの役職別上限額に基づく申請可否の自動判定、申請と中断時の下書き保存、承認と購入準備前の差戻し、下書き・差戻しからの再申請または破棄、承認済み申請の購入準備番号の確定と購入用CSV出力・再出力、調達不能時の申請者との調整に基づく最終クローズ、および最終結果の登録を扱う。見積取得、実際の購入・在庫確認・発注管理・発注日・交渉手段はシステムのスコープ外とする。代替品の購入は禁止し、倉庫への各回の入庫結果登録と全数量の終結は対象とする。交渉後の合意記録とシステムでの結果確定の境界は人間レビュー前の草案である。購入申請はこの業務で成立・更新する記録である。申請者・承認者・購買担当者のObjectは、各業務で情報を入力・選択する人を表し、人自体を成立・管理する業務は扱わない。基幹システムは従業員情報・役職別上限額を提供するスコープ外のObjectであり、内部のテーブル構造や同システムの保守は今回の業務に含めない。認証基盤もスコープ外のObjectとして利用し、認証済み作業者の識別情報を受け取る。利用者登録・認証基盤の管理、独立したログイン業務は今回扱わない。前述の対象外業務や未採用の一括却下・一括結果登録は含めず、未確認の条件を決定済みとはみなさない。

# Activity 備品購入を申請する

## Scope

true

## Why

購入の必要性と希望内容を記録し、承認者が購入可否を判断できる状態にするため。

## When

申請者が、業務上必要な備品を購入したいと判断したとき。

## Who

申請者

## Where

規定なし。

## How

### Input

- 基幹システム — 従業員の識別情報 / 役職 / 役職ごとの決裁単位の上限額
- 申請者 — 複数の品目（品名 / 税抜希望単価 / 数量） / 購入理由 / 依頼全体の見積書（提出時は見積書と品目情報を必須とする） / 申請を中断して下書き保存する選択
- 認証基盤 — 認証済み作業者の識別情報

### Procedure

業務に必要な備品の購入要求を、購入申請として登録する。認証基盤から受け取る認証済み作業者の識別情報で作業者を一意に特定する。代理申請の範囲は、前述の未決事項に従う。

1. 申請者が必要な品目ごとの品名・税抜希望単価・数量と購入理由を入力し、外部取得済みの依頼全体の見積書を添付する。1申請で複数品目を指定できる。見積なしでは提出を成立させない。
2. 各品目の税抜小計を税抜希望単価×数量で算出し、全品目の小計を合計して申請の税抜希望合計金額を求める。
3. 申請者に対応する基幹システムの情報から、申請者の役職を確認する。
4. 申請全体の税抜希望合計金額が、その役職に対応する基幹システムの役職別上限額以下であるか、自動判定する。
5. 適合すると判定できた申請を、新しい購入申請として登録する。
6. 新規Object「購入申請」を状態「申請済み」で保存する（作成前 → 申請済み）。

### Exception

- **権限判定不成立** — 基幹システムの役職別上限額に適合しない場合、または規定の矛盾・必要情報の不足などで適合すると判定できない場合は、申請を成立させず、`申請済み` の購入申請を作成しない。この申請不成立を、承認業務による差戻しとは扱わない。

- **作業中断** — 申請者が提出前に申請業務を中断し、下書き保存を選んだ場合は、申請者と入力途中の内容を購入申請へ「下書き」の状態で新規保存する（作成前 → 下書き）。提出時の必須項目が未入力でも下書き保存できる。下書き保存では `申請済み` の成立や権限判定の通過を意味せず、承認・購入の対象にしない。保存した下書きは「購入申請を再申請・破棄する」で再開し、内容を整えて提出するか、破棄するかを選べる。

### Output

- 購入申請 — 提出時は申請者 / 複数の品目（品名・税抜希望単価・数量） / 申請の税抜希望合計額 / 購入理由 / 申請日時 / 確定した提出版と根拠の見積書 / `申請済み` の状態。中断して下書き保存した場合は申請者 / 入力途中の申請内容 / 下書きの状態

## Result

- 基幹システムの役職別上限額への適合を自動判定で確認した購入要求が、`申請済み` の購入申請として記録される。
- 申請者、申請品目ごとの税抜希望単価・数量、申請全体の税抜希望合計、購入理由、申請日時が保持される。
- 承認者が購入可否を判断できる状態になる。

# Activity 購入申請を承認する

## Scope

true

## Why

申請内容が妥当であることを確認し、購買担当者が購入を進められる状態にするため。

## When

購入申請が `申請済み` として提出されたとき。または、承認済みの申請について、**購入準備がまだ確定していない**段階で承認者が差戻しを判断したとき。

## Who

承認者

## Where

規定なし。

## How

### Input

- 承認者 — 承認可否を判断する対象購入申請の選択（必須） / 差し戻す場合の差戻し理由（必須）
- 認証基盤 — 認証済み作業者の識別情報
- 購入申請 — 対象購入申請の確定した提出内容と、`申請済み` または購入準備未確定の `承認済み` の状態

### Procedure

認証基盤から受け取る認証済み作業者の識別情報で、承認業務の作業者を一意に特定する。提出された購入申請の購入可否は、承認者が業務中に人間として判断し、その責任を負う。以下は承認する場合の正常手順である。

1. 承認者が、対象となる `申請済み` の購入申請を選択し、その内容を確認する。
2. 購入してよいと判断する。
3. 対象Object「購入申請」の状態を「申請済み」から「承認済み」へ変更する。
4. 承認日時を記録する。

### Exception

- **差戻し** — 承認者が業務中に購入を認めないと判断した場合は、対象購入申請を `申請済み` から `差戻し` へ変更し、差戻し理由・日時を記録して申請者に再申請・破棄の選択を戻す。この場合は承認を成立させない。
- **承認後差戻し** — すでに `承認済み` でも**購入準備番号が未確定**なら承認者は判断を変更して `差戻し` にできる。以前の承認を現在有効な購買根拠から外し、再申請・破棄の業務へ戻す。過去の承認判断の業務履歴は必須としない。購入準備確定後の差戻しや、同時に両操作を成立させることは認めない。

### Output

- 購入申請 — 承認の結果（`承認済み` の状態 / 承認日時）、または差戻しの結果（差戻しの状態 / 差戻し理由 / 差戻し日時）

## Result

- 対象購入申請が `承認済み` になる。
- 承認日時が記録される。
- 購買担当者が購入対象として扱える状態になる。

# Activity 購入申請を再申請・破棄する

## Scope

true

## Why

下書きや差し戻された購入申請を、再び承認に進めるか、不要な申請内容を破棄するか確定するため。

## When

申請者が、保存済みの下書きの購入申請から作業を再開するとき。

## Exception When

- 備品購入を申請する — 作業中断：申請者が提出前に作業を中断して下書き保存し、その下書きから作業を再開するとき
- 購入申請を承認する — 差戻し：購入を認めないと判断され、購入申請が申請者へ差し戻されたとき
- 購入申請を承認する — 承認後差戻し：購入準備番号が未確定の承認済み申請を、承認者が判断変更して差し戻したとき

## Who

申請者

## Where

規定なし。

## How

### Input

- 基幹システム — 従業員の識別情報 / 役職 / 役職ごとの決裁単位の上限額
- 申請者 — 再申請または破棄の選択 / 再申請する品目（品名・税抜希望単価・数量、複数可）と購入理由 / 依頼全体の見積書
- 認証基盤 — 認証済み作業者の識別情報
- 購入申請 — 対象の申請内容 / 下書きまたは差戻しの状態 / 差し戻された場合の理由

### Procedure

認証基盤から受け取る認証済み作業者の識別情報で作業者を一意に特定する。申請者は対象の申請内容について再申請または破棄を選ぶ。代理申請の範囲は前述の未決事項に従う。以下は再申請する場合の正常手順である。

1. 下書きまたは差し戻された対象購入申請の内容を確認する。差し戻された場合は、その理由も確認する。
2. 再申請する複数の品目（品名・税抜希望単価・数量）と購入理由を入力し、依頼全体の見積書を確認・添付する。見積なしでは再申請を成立させない。各品目小計の合計を求める。
3. 基幹システムから申請者の役職を確認し、申請全体の税抜希望合計金額が役職別上限額以下であるか自動判定する。
4. 適合すると判定できた内容を、従前の確定内容を変更せず新たな提出版として確定し、対象Object「購入申請」を再申請する。状態を「下書き」または「差戻し」から「申請済み」へ変更し、申請日時を記録する。

### Exception

- **申請内容の破棄** — 再申請せず破棄することを選んだ場合は、対象の申請内容を破棄する。破棄した内容を以後の承認・購入の対象にしない。対象Objectは「購入申請」、変更前は「下書き」または「差戻し」。処理後の保存状態は未決である。
- **再申請不成立** — 基幹システムの役職別上限額に適合しない場合、または必要情報の不足や矛盾等で判定できない場合は、再申請を成立させず、`申請済み` の状態へ変更しない。その後の元の申請内容の扱いは未確認である。過去に確定した提出版を直接編集しない。

### Output

- 購入申請 — 再申請した確定提出版と根拠の見積書 / `申請済み` の状態 / 申請日時、または対象の申請内容の破棄

## Result

- 対象購入申請が権限判定を通った内容で `申請済み` として再申請され、承認者が再び可否を判断できる。

# Activity 購入を準備する

## Scope

true

## Why

承認済みの購入要求を複数まとめ、後から同一内容を再出力できる購入準備として確定し、システム外の購入作業へ渡すため。

## When

購入申請が `承認済み` で、まだ購入準備番号を確定していないとき。

## Who

購買担当者

## Where

規定なし。

## How

### Input

- 認証基盤 — 認証済み作業者の識別情報
- 購入申請 — 対象申請の識別情報 / 確定した提出内容 / 現在有効な承認 / 準備未着手であること
- 購買担当者 — 購入準備対象の承認済み購入申請（複数可）

### Procedure

1. 認証済み作業者を一意に特定する。
2. 購買担当者が承認済みの購入申請を選択する。一つの申請の品目を別々の準備へ分割しない。
3. その購入準備に一つの購入準備番号を発行し、選択した申請を同じ番号に紐づける。番号と対象の確定後は承認者の差戻しを認めない。差戻し操作と準備確定が競合したら、両方の成功を許さない。
4. 確定した購入準備番号と同じ申請内容を使って購入用CSVを出力し、システム外の購買へ渡す。出力完了だけでは購入済みにしない。

### Exception

- **CSV再出力** — CSVの生成失敗または紛失があった場合、購入準備番号と対象を取り消さず、**同じ番号・同じ確定内容**で再出力する。通常の失敗時の安全な再試行や二重処理防止は設計・実装で保証する。
- **購入準備競合** — 対象申請が同時に差し戻された、またはすでに別の準備に組み込まれた場合は、重複した準備確定を成立させない。具体的な通知とやり直し操作は未決。

### Output

- 購入用CSV — 購入準備番号 / 対象購入申請の識別情報 / 購入準備確定時の申請内容
- 購入申請 — 購入準備番号とその番号に属する対象申請。元の提出内容は変更しない

## Result

購入準備番号と対象が確定し、承認者の差戻しができない。CSVの成否と区別して購入準備の確定を保持し、失敗時も同じ準備を再出力できる。

# Activity 購入結果を登録する

## Scope

true

## Why

分割納品の各回の入庫結果と購入しない数量を記録し、全依頼数量の結末がそろった申請を終結するため。

## When

購入準備済みの申請について倉庫への入庫があったとき、または購買担当者と申請者が今後購入しない数量を確定したとき。

## Who

購買担当者

## Where

規定なし。

## How

### Input

- 申請者 — 調達不能時の数量減・購入なしについての合意（記録方法は未決）
- 認証基盤 — 認証済み作業者の識別情報
- 購入申請 — 確定提出版と品目・依頼数量 / 購入準備番号 / 既存入庫累計 / 購入しない確定数量 / 終結の有無
- 購買担当者 — 対象申請 / 各回の入庫品目と数量 / 今後購入しない確定数量。実績金額・日付の詳細な粒度は未決

### Procedure

1. 認証済み作業者を一意に特定し、準備済みで未終結の対象申請と、変更不能の提出内容を確認する。
2. 各回の入庫結果を元の申請品目へ対応させて登録する。分割納品では複数回登録できる。代替品を登録せず、元の品名・数量・単価や準備内容を上書きしない。
3. 調達できない残数は購買担当者と申請者で調整し、今後購入しない確定数量として入庫実績とは分けて記録する。元の承認者は介入しない。
4. 各品目で「依頼数量＝入庫累計＋購入しない確定数量＋未入庫待ち」を確認する。過剰数量や別申請・旧版の品目への登録を成立させない。
5. いずれかの品目に待ちが残れば作業中を維持する。すべての品目の待ちが0なら申請全体を一度だけ終結し、全数入庫／一部入庫と残り購入なし／全数購入なしを区別する。終結後の訂正は扱わない。

### Exception

- **調達不能・購入断念** — 申請者との調整で、残数量または全数量を購入しないと確定する。入庫0件でも終結できる。承認拒否や再申請への差戻しとは扱わない。

### Output

- 購入申請 — 各回の入庫結果 / 品目別入庫累計と購入しない確定数量・未入庫待ち / 作業中または申請単位の終結結果

## Result

各回の入庫と今後購入しない数量が元の確定品目に対応して記録される。待ちが残る申請は作業中となり、全数量の結末が確定した申請のみ終結する。失敗後の再送で実績を重複させず、二重の最終結果を作らない。
