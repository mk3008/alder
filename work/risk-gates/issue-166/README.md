# 変更リスクと人間ゲート — Issue #166

研究・設計判断の記録。**現行Alderの規則を変更しない。** 研究の採否、実装、実運用での効果は別の判断である。

## 調べた問い

自動テストと独立Alderレビューを維持し、変更がもたらす結果に応じて、人間が判断しないと進めない箇所を説明できるか。Low / Medium / Highという分類を必須にせず、既存レビューの中で扱えるか。

## 現行の仕事と境界

実在する流れは、業務設計の合意 → Check期待の人間確認 → 実装・テスト → 独立実装レビュー → 必要な修正・人間判断 → 権限に従った適用である。Alder自身の結果返却でも依頼者が目的・意味・採否を判断する。この研究は、それらの確認を削除して「人間なしでmergeできる」とするものではない。

- [詳細設計の位置づけ](../../../docs/detailed-design.ja.md)は、業務意味、永続データ、外部契約、後から変えるコストの高い制約を先に明示する。局所的な可逆選択をすべて人間に決めさせない。
- [実装レビュー](../../../plugins/alder/skills/alder-review-implementation/SKILL.md)と[read-only stage](../../../plugins/alder/skills/alder-review-implementation/references/read-only-review.md)は、意味の不一致、Business confirmation、技術改善、十分を区別する。技術上の所見を無条件に業務承認へ変えない。
- [review knowledge P2 / S](../../../docs/phase2/review-knowledge-v0.3.md)は、実装が選んだ意味を業務設計へ戻し、同じ根拠の重複要求を止める。
- [結果返却の業務設計](../../../business-design/ai-result-review/README.md)と[返却guide](../../../docs/result-review.ja.md)は、既存のChat / Issue / PR応答に根拠・未完了・必要な判断を添える。固定の報告成果物は不要。
- [maintenance risk研究](../../../docs/maintenance-risk-review/results.md)は構造選択・保守変更の限定的観察であり、人間ゲート判定や認知負荷低減を立証してはいない。

したがって問うべき差分は「全変更に新しい承認欄を足すか」ではなく、既存ゲートで覆われない具体的な残余判断があるか、その影響が発生する前に誰が何を判断するかである。

## 実験と証跡

[protocol](protocol.md)、[入力](inputs/cases.json)、[manifest](manifest.json)、[評価基準](rubric.json)、[raw](raw/)を参照。

- 安全な合成12ケース。内部関数、schema、個人情報、金銭・予約、bulk更新、UIの6系統を各2条件にした。
- 同じnullable列追加をsandboxと本番・運用情報欠落で比較。金銭機能の同値refactorと意味変更、連絡先の表示修正と公開範囲変更も区別した。
- 入力は実行前に公開commit `26171a3eee45d169640c3a2d858a1da7f3653692`へ固定・再取得。現行資料の基準は `f716c1a1ea8fa8b3adebb9001d9762eee89eadb0`。
- 分類式と直接判断式を、それぞれ2個の履歴forkなしFresh contextで実行した。48判定だが独立な実行単位は4。ケース順は固定、同一batchに対の条件が見えるため対比が手掛かりになる。
- 要求設定はrepository AGENTSどおり `gpt-6-sol / medium / fork_turns: none`。呼出しは受理されたが、実効モデル・effortを独立に検証できない。
- 入力は業務設計・Check・変更・運用条件の短い要約。コードやDBを検査して潜在経路を発見する実験ではない。独立Alderレビューを実行したとする証拠でもない。
- 判定基準は実行前に作成・digest固定したoperatorの期待であり、人間が承認したgold labelではない。二つのarmはいずれも実験promptであり、現行guidanceだけの対照群はない。

## 結果と判定上の限界

運用上のリスクを業務意味変更と同一視しない。D2は業務意味が合意済みのまま本番lock・互換・復元・権限が未確認というケースであり、既存のBusiness confirmationだけでは技術的な適用可否は決まらない。技術調査後に既存運用基準を超える停止・復旧条件が判明すれば、運用責任者の判断が残り得る。今回、その条件が既知になった後の追加ゲートを独立ケースでは試していない。

4実行とも、F1 / D1 / P1 / B1 / M1 / U1を追加ゲート不要、F2 / P2 / B2 / M2 / U2をrequired、D2をunresolvedとした。分類式の2実行はいずれも前者6件をLow、後者5件をHigh、D2をMediumとした。ケースごとの根拠と実際に問う内容は[評価表](evaluation.json)からrawへたどれる。

この入力では危険な継続、既存ゲートの省略、明らかに局所・可逆な6ケースへの余分な人間ブロッカーは観測しなかった。D2では全実行が本番適用を保留し、技術調査を先に行い、新たな業務判断の有無はその後に確かめた。分類式と直接式のゲート結論は全ケースで一致した。これは固定分類の優位を示さず、直接式の一般的優位や同等精度を立証する結果でもない。

具体的に得た説明:

- F2は1行のprivate関数でも識別キーの同一性と送金先へ届く。表示だけのテストは根拠にならない。
- P2はUI非表示でもserializerから匿名client / cacheへ届く。flagを戻しても配信済み情報は回収できない。
- B2 / U2はコードや画面のrollbackと、予約確定・請求・取消という外部結果の回復を区別した。
- D2は「nullable追加」「空DBで成功」だけから、本番のlock・互換・復元・権限を補完しなかった。
- B1 / P1は金銭・個人情報という領域名だけで新しい承認を要求しなかった。

### 観測した弱点: 「人間判断が必要」と「新しいゲートが必要」の混同

全4実行が5ケースを `additional_human_gate: required` とした。しかし、その説明の中心は未承認の業務意味・公開・保持・同意の変更であり、現行のBusiness confirmationや既存権限でも止める対象である。多くの出力は二重計上を避けると書く一方、何が**既存ゲートでは覆われない追加判断なのか**を特定していない。20件のrequired出力を「新設すべき20ゲート」と数えることはできない。

また、合意済み挙動へ戻す修正と、変更後の意味を採用する判断が常に明瞭には分かれていない。たとえばU2は料金表示と明示確認を復元する技術修正で解消できる場合がある。「UI変更なのでHigh、よって全作業を人間待ち」とすると、AIで進められる修正まで止めてしまう。label-1は一部ケースで現行条件を維持する経路を明記したが、全出力の共通した分岐にはなっていない。

これは危険なLow判定の観測ではなく、判定欄の意味と停止範囲の設計上の弱点である。出力の`required`だけをworkflowへ機械接続しない。既存の分類、停止対象、未決の意味を読んで判断する必要がある。

### 未検証のFailure Mode

次は今回の入力が支援したため検出できた経路であり、実環境の検出率は不明:

1. caller・serializer・外部作用の事実が入力から欠落すると、局所diffだけを根拠にfalse-lowへ落ちる。
2. 実装者の「可逆」「低リスク」や成功テストを、影響経路・復元の証拠の代わりに受け入れる。
3. rollbackできるコードと、回収不能な公開・金銭・消去結果を同一視する。
4. 既存承認の対象、環境、revisionを確認せず、新しい変更にも承認済みとみなす。
5. 安全な判定後に対象DB・人数・公開先が変わっても、その判定を使い続ける。
6. 機械の不明点を人間へ丸投げする、または高影響領域というだけで同値変更を止める。

今回は危険なfalse-lowの実例を発生させたわけではない。重要情報が明示された合成事例に限る成功を、安全保証や見落とし率の推定へ広げない。事実を伏せた隠し事故、長いrepoの探索、悪意ある入力、第三者承認の真偽、現場の認知負荷は評価していない。

## 研究としての結論

**固定Risk fieldや、新しい一律の人間承認工程は現時点で導入せず、現行フローを維持することを提案する。追加ゲートの自動適用は保留する。** 直接「誰が、何を、どの結果が発生する前に決めるか」を既存レビューで説明する方法は候補になる。ただし今回、現行規則を超える新ゲートが必要だったという独立の証拠は得ていない。

各問いへの回答:

1. 提示された影響経路から具体的な根拠・問いを説明することは、この限定入力で観測した。実repoから必要事実を発見する信頼性は未検証。
2. 恒久的なRisk fieldや独立成果物なしに、既存のreview finding / Chat / PR説明へ収められる。実験JSONは比較用であり利用者への必須成果物ではない。
3. 危険なLowの観測は0だが、未提示の影響経路や可逆性の誤解が残る。実際に観測したのは既存ゲートと追加ゲートの混同。
4. 安全側へ倒すのは「不明なら全作業停止」ではなく、不可逆な結果へ進む根拠・権限が不足する**該当する適用段階**。調査・テスト・合意済み挙動への修正は、権限内で継続できる。未知をAIが調べられるかと、人間が決める必要があるかを分ける。
5. 必要な問いへ説明を絞れる可能性はあるが、人間の認知負荷・時間・誤りは測定していない。改善実証とは呼ばない。
6. 「後から変えるコスト / 可逆性」を、事前の設計判断とレビュー後の適用判断で共有できる。判断する時点と実世界の結果を示す必要があり、Risk等級へ縮約する必要は示されなかった。

### 人間が採用を判断する場合の最小候補

新Skillや必須欄を作らず、既存のread-only review stageの所見返却（step 4）に、次の趣旨を短く統合する候補とする。**以下は提案であり現行の規則ではない。**

> 変更が現在または後続の業務意味・外部責任・回復可能性に及ぼす具体的な結果を示す。既存ゲートで覆われる判断と、なお残る人間判断を区別し、必要な判断の対象・担当・発生前に止める段階を述べる。技術調査や合意済み挙動への修正で解消できる所見を、新たな業務承認に変えない。追加判断がない場合も、テスト、独立レビュー、既存の合意・Check確認・実行権限を維持する。

最小導入先は `plugins/alder/skills/alder-review-implementation/references/read-only-review.md` の既存所見返却。共通review knowledgeを増やす前に、現行P2 / Sで足りるかを確かめる。採用された場合だけ別Taskでcanonical sourceとbundled referenceの同期・package検査・必要な利用説明を行う。現在のPRではSkill、review knowledge、Business Design、Check、release、READMEを変更しない。

採否の問いは「固定分類や新しい承認工程を増やさず、所見の説明で既存ゲートと残る判断・停止段階を区別する、この最小補足を試すか」。現状維持も妥当な選択である。これを採用しても自動merge、権限拡張、既存の人間確認省略を許可しない。

## 再現・検査

`python3 work/risk-gates/issue-166/audit.py` は入力digest、48判定の構造とIDを確認する。意味の採点器ではない。[checks](checks.txt)に実行結果を保存する。package関連の既存27テストも実行したが、研究提案の有効性を証明するものではない。productionコードを変更していないため、アプリケーション動作の新しい合格は主張しない。

公開前に合成入力とrawを点検し、個人・顧客データ、秘密、private管理Issueや会話URLがないことを確認した。rawは修正せず保存した。Fresh実行の完全な環境再現はできず、第三者は公開入力・prompt・出力を検査し同条件で再実行できるが、同一出力を保証しない。
