# 共通読込後の検証分担とBループ再修正

対象はPR #285、差し戻し6360147350。測定基準は固定head `441dfb8b2fbf36bb4215ec885852dc14fa6a3e59`。今回、製品ソース／Graph v1／Schema／Plugin／承認済み余白は変更しない。

## 原因と元の目的

元の6357185181は、MDを旧入力互換へ縮退し、詳細／Check／状態／復元と二重検証の負担を減らす依頼だった。6357297220の設計案は、旧MD専用の二重撮影を縮退候補とし、assertの移管先と故障検出を先に示す方針だった。しかし実装後のdocument-loading.ja.mdでは「11図の座標・配線・PNG比較自体は現状維持」とし、共通モデルを通ることと独立配置oracleを組み合わせれば何を代替できるか検証せず、旧二重撮影を残した。設計案の方向は妥当でも、保証別の移管を完遂していない。

詳細／Check／状態／復元の旧後段は縮退済み。入力文法・形式検査・元原文・旧参照／人間状態の保護は必要な互換境界であり残す。残存したMD/JSON×2幅×11図の二重表示は、共通後段の変更負担削減という目的との照合が漏れた。高速11図検証のMD側も旧parseDesignのままで、実際の共通DocumentModel入口を守っていなかった。

前回報告はRoleの独立11図再撮影とCI先行6群の削減を計上したが、それは別の重複削減である。jsonLayout 12.9→13.1秒、全Chrome634.4→636.7秒は主目的の速度改善を示さない。今回の効果へ振り替えない。

Scope保存の失敗は、独立保存イベントが完了する前に不正保存fixtureを注入した競合。caption変更の失敗は、native labelLayout内の旧範囲assertを影響先として拾わなかったこと。製品実装だけを中心に影響を追い、テスト内の前提（保存待機／数値定数）と元Goalの両方を自己確認しなかった。AGENTSや本人の判断不足へ転嫁しない。

## セルフレビュー手順と記録

1. 修正後、元GoalとDoneを一項ずつ照合した。単にMDを減らすだけだと、JSON両入力で共通のSVG線欠落を見逃すため、全JSON図の実SVG対モデル照合と線欠落の負例を追加した。
2. MD側をparseDocumentへ移しただけでは独立期待値にならない点を再確認。既存の手書き情報fixtureと固定ポート／24px算術oracleを併用し、同一production関数の出力比較を独立証拠と呼ばない。
3. 移管後にも全11図PNG同値を主張する古い説明が残るため、validation／document-loadingを保証表と合わせて修正した。
4. native数値前提と非同期を自己確認：既存Scopeの保存待機、caption101pxのassertは変更しない。新SVG期待値はcaption左端と中心を区別する。ブラウザーでの線数／ラベル位置の検証は最終CIで確認する。
5. Before/Afterは同一runner内で測定し、対象群・関連高速・全47群を別に集計する。Role／先行群の旧削減を成果に混ぜない。測定結果と追加修正／未達はIssue #274・PR #285へ追記する。

Skill化は別判断。今回は新SkillもAGENTS追加も行わず、既存の影響範囲・保証移管・元Goal照合を実際に適用する。

## 比較ハーネスの失敗と追加修正
