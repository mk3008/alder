# Issue #104 結果：H5（入口の必要性は判定保留）

新規の市民資料館シナリオで、Oracle の SHA-256 を Authoring 前に固定し、Plugin 0.2.6 による顧客・設計者対話から同じ current-state Business Design を作った。既知 K、未認識 U1、人間確認後の U3、Problem なし control を別 Fresh context で実行し、raw を固定してから Oracle を開示した。詳細な独立評価は `evaluation-raw.md`。

| 観点 | 観測 |
| --- | --- |
| K | Discovery なしで保存条件の早期照合と変更後の影響連絡へ到達。後段確認・二つの承認を保持。 |
| U1 | 保存条件の時点差（Oracle 対応）を観察。別に展示と館外貸出の期間相互照合も挙げた。承認経路と返却連携に関する二件は人間役が保留。 |
| U2 | 人間役が二件を調査対象として確認し、追加確認で Optimization Review に渡すと明示。失敗の実証とは扱わない。 |
| U3 | 保存条件の変更伝達について K の横断 Candidate と作用点が重なる。別の期間照合問題は別 Fresh Review に分けた。 |
| Control | 講演会名が共通するだけの二業務から Observation 0 件。異なる承認・現物確認の統合もなし。 |

専用 Structural Optimization の必要性はこの事例で確認できなかった。確認済みの Problem を既存 Optimization Review に渡すと横断 Scope Expand を扱えた。ただし一般的に不要とまでは言えない。

**判定制限**：Authoring Skill が保存条件の早期確認と変更連絡を設計書の未確認事項に既に表面化させた。U1 は白紙からの発見ではなく、設計書にある手掛かりの横断的な再解釈である。K は早期照合＋変更連絡、U3_2 は変更連絡のみ、U3_1 は別の期間照合という Problem 範囲差がある。U1 は未確認を「未定義」と強く書き、返却時の照合結果が保存担当へ伝わると推測した。最後の推測は Authoring 草案の Output にも根拠なく入っていた source-fidelity 欠陥であり、独立評価まで固定した raw と設計書は書き換えない。顧客役が当該 Observation を保留したため、U3 に昇格しなかった。

したがって二入口が役に立つ局所的な兆候はあるが、**二入口が必要**という H1 や常時 Discovery という H2 を実証しない。事前登録した H5 を採る。件数、損失、運用実態や承認の順序は未確認で、一例を一般化しない。次の判定には、Authoring が事前に表面化させた問いと Discovery 固有の寄与を分離できる事例、既知と未認識の Problem 範囲を揃えた比較が要る。新しい seed を本件の結果に合わせて追加しない。
