# Alder保存形式の比較結果

## 結論

次の検証候補は**整形済み単一JSON**を推奨する。単一ファイルのまま要素ID・参照検査を持てて、JSONLより変更箇所を行単位で確認しやすい。JSONLの部分取得が有利になるのは、索引・配信側のRange対応など追加条件がある場合である。今回の全体読込では、その条件を前提にしない。

Markdownは原文の読みやすさと容量に利点がある。見出しと参照が増えたときの編集負担を形式変更だけで解決できるかは未確認である。JSONへの移行にもViewerや編集支援が必要であり、人間が直接JSONを保守しやすくなると結論しない。**採用・merge・release・デプロイは行っていない。**

### 現物で確認した互換性の差

1. 固定購買BDには`## Medium`と`## SR Dependencies`があり、現在の正式Graph/Viewer parserは拒否する。PoCは全文を保持し、Graph検査用の投影だけでこの2欄を除く。その投影は保存正本として使わない。
2. 0.4.8のCheck見本は一般保証・例を上位へ置き、各IDの`条件・期待結果`から参照する。現行Viewer `parseChecks`は各IDに独立した`条件`と`期待結果`を要求して拒否する。PoCは保証の断片リンクと状態を検査するが、業務上の正しさは承認しない。
3. 現行ViewerのURL取得は`application/json`と`application/x-ndjson`を拒否する。今回のJSON/JSONLはGraph v1でもなく、Viewerへ直接渡せない。
4. 既存の旧BDと旧Checkを同じ現行parserへ渡す検査は成功。これは互換性を保つ移行の基準であり、全旧文書やGUI操作を検証したという意味ではない。

詳細は`results/compatibility.json`。既知の拒否は現行挙動の観測であり、新形式の不具合として数えたり、今回修正したりしていない。

## 3方式と保持情報

比較用の論理内容は同一である。MDはBD全文＋明示的な文書境界＋Check全文の単一ファイル。境界はPoC専用であり、現行BD構文への追加ではない。MDの各文書を切り出す薄い読込adapterを用いる。

JSONとJSONLは同じ論理レコードを使う。文書と要素を区別し、`kind`・固定ID・見出し・本文行配列を保存する。BDのInput/Output/Exception WhenとGraph exceptionsに限って、名前参照をIDトークンへ変換し、表示時に名前を解決する。整形JSONは2スペース、JSONLは先頭メタデータ行＋1要素1行。どちらにも同じ件数を置き、途中で行が欠けたJSONLを成功扱いしない。

**本文はMarkdownを含むハイブリッド試案**である。Why・Procedure、Information、Checkの保証と例をすべて独立した型付き属性へ正規化した仕様ではない。形式の情報保持と参照の違いを小さく検証するための構造であり、その制約下の結果として読む必要がある。

| 情報 | MD | JSON / JSONL | 検証・限界 |
| --- | --- | --- | --- |
| BDタイトル、前提、Scope、5W1H、Procedure、Exception、Result | 原文 | 見出しと本文行 | 全文のバイト一致。Graph v1だけではProcedure等を失うため、Graphは保存形式にしない |
| Object Information / Medium / SR Dependencies | 原文 | 本文行 | 未対応欄も保持。Medium/SRはGraph投影からだけ除外 |
| 入出力・例外の対象、ラベル | 名前参照 | 同じ情報を固定ID参照 | 改名時は対象名が解決される。本文の自由記述中の名称は自動で書き換えない |
| Findingsの根拠・状態・対象 | 原文 | 本文行 | 4 Findingsを保持。Targetsの自由記述はID化していないため、Activity改名では別の整合確認が必要 |
| Check ID、人間状態、一般保証、比較表、未決、根拠、Test証拠 | 原文 | Checkと保証節のレコード | 6 IDと全文を保持。原典に実Test証拠はなく「未収集」を保持した検証。実在Testの意味照合は未検証 |
| 共有Checkと保証節への参照 | headingリンク | 同じリンクを本文に保持 | 内部fragmentの存在検査、依存節の部分抽出を実施。GitHub全slug規則の実装ではなく、この入力の文字集合に限定 |
| 異なる原典世代のCheckとの対応 | 未合意の原文 | 未合意の原文と文書版 | 不一致診断を返す。Activity名の一致だけで合意済み対応へ昇格しない |
| 状態遷移・概念モデル | 今回同梱しない | 今回同梱しない | 将来の文書型拡張で収容する案だけを示し、内容・正式スキーマは定義しない |

## Web・部分取得・編集の比較

| 観点 | 現行MDの束 | 整形済み単一JSON | 要素単位JSONL |
| --- | --- | --- | --- |
| 単一ファイルURL/ローカル | 薄い境界adapterが必要 | envelopeを一度解析 | headerと各行を解析 |
| PoCのURL検査 | loopback HTTPのバイト一致・解析成功 | 同左 | 同左 |
| 現行Viewerへの直接入力 | 束のままは未対応。固定原典自体にも前述の差がある | 未対応 | 未対応 |
| 未索引の部分取得 | 見出し境界と参照名を走査 | 全体parse後に抽出 | 逐次走査可能。ただし後方破損・重複ID・参照整合性は先頭一致だけでは保証不能 |
| 索引済み取得 | メモリ内ID索引で可能 | 同左 | 同左。行別byte offsetを持つ索引は今回未実装 |
| Activity/Object/Check抽出 | 全体検査後にID指定。Checkは保証節・例のfragment依存も取得 | 同左 | 同左 |
| 名前変更 | 宣言と全参照行を更新する必要 | IDトークンは維持、見出し名を更新 | 同左。ただし変更した要素の行全体が差分になる |
| Gitでの局所変更 | 本文行単位 | キー・本文行単位 | 1要素が長文1行。小変更でも大きな行の差分になる |
| AI編集 | 通常の文章・見出しを扱える。境界や参照名の破壊リスク | 構造検査しやすい。引用・配列・カンマを壊すリスク | 行ごとの置換は容易。長文行、行欠落、末尾破損、headerとの不一致に注意 |
| 人間の直接保守 | 生の文章を読みやすい。参照更新は手作業が増える | 行は読めるがエスケープ・構造管理が増える | 長い1行が多く、直接レビューは不利になり得る |

AI編集欄は机上評価。別モデル・別Agentによる固定プロンプト実験、成功率、推論時間、費用の比較は**未実施**である。固定4課題は同じ決定的な変換で実行し、意図外のレコード変更・情報欠落がないか検査した。これをAI編集の実験成功とは呼ばない。

URL検査はPythonのloopback HTTPであり、外部HTTPS、CORS、認証付きURL、ブラウザーFile picker、実機スマホ、ストリームの通信途中切断は未検証。現行の2MiB制限や匿名CORS方針も変更していない。ファイルの形式を変えるだけでは、これらの制約は解消しない。

## 保存契約と版管理の最小案

このPoCの`format: "alder-storage-poc"`、`formatVersion: "0.1-poc"`は正式仕様でないことを明示する実験用識別子である。

| 概念 | 最小案 | 今回の実装・未決 |
| --- | --- | --- |
| formatVersion | 互換性を決める保存構文・意味の版。製品版やGraph版から推定しない | PoCは完全一致だけ受理。正式な型・SemVer方針・minor互換規則は未決 |
| 要素ID | 作成時に付与し、名称・表示順の変更で再生成しない。Check IDは既存値を保持 | PoCは初回import時の連番を保存。その後の構造化編集で維持。MD再importでは順序変更で別IDになり得るため、永続allocatorや対応のレビューが必要 |
| 文書リビジョン | ファイル内容の版。合意したBD版・Checkの参照原典版も別に記録 | `documentRevision`と`documents[].revision`を分離。後者は凍結した資料の版であり、業務承認ではない。更新競合のCAS/ETag・合意版の保存は未実装 |
| Graph v1 | 表示名をidに持つ従来の投影を別契約として出力 | 既存validatorを変更せず利用。安定IDをGraphのidへ流用しない。Procedure等をGraphに足さない |
| 将来の2モデル | 独立した文書型とpayload版を持たせ、包みの参照先にできる構想 | 今回のloaderは未知文書・kindを拒否。モデルの正式構文・意味・循環可否は定義しない |

`documents[].revision`だけでCheckが新BDに適合したと判断してはいけない。Checkが参照するBDの文書ID・内容版・合意状態の関係は、正式化前に型付きで追加検討する必要がある。今回の異世代試料は全文と診断で保留しており、見かけ上の整合を作っていない。

### 失敗時の扱い

| ケース | 観測または案 |
| --- | --- |
| 未知format/version/kind/field、重複ID・JSONキー | PoCで拒否。版不明のJSONを旧MDへ再解釈して処理継続しない案 |
| JSON破損、JSONL途中行破損・終端改行なし・完全行欠落 | PoCで拒否。JSONLは全件数照合も行う。全体が成立するまで採用しない |
| 欠落参照・対象型不一致、Check fragment切れ | PoCで拒否。旧原典と新BDの意味対応の不一致は診断と保留。外部URLやTestの存在は検査していない |
| 循環参照 | 一律に禁止しない。Graph v1が許す明示例外の自己再開、Check→保証節→Checkの循環は終了性を保って処理する。業務としての妥当性は承認しない |
| 要素順序の変更 | 完結したActivityの順序変更でGraphは一致。JSON/JSONLのIDは維持。表示順は配列/行順を保つ。任意行並べ替えの意味不変や全体の順序独立性は主張しない |
| 曖昧な旧MD変換 | 本PoCは境界重複・未閉鎖fenceを拒否。LF・末尾改行ありの試料へ限定。任意MDの見出し/slug/改行/コメント対応は未完。推測修復せず原本を保持し、要確認へ返す案 |
| 更新中の破損・競合 | 本番では一時ファイルへ保存→全体検査→期待する旧revision/hashとの比較→原子的置換を検討。PoCに安全な汎用writerはない。JSONLを追記イベントログとしては扱わない |

全件数は途中欠落の検知用であり、改ざん検出や旧版上書きの防止にはならない。失敗時に最後の描画を保持し、エラーを表示し、壊れた内容で原本・確認済み状態を上書きしないViewer方針を移行時にも維持する案である。今回はViewer本体に実装していない。

## 旧Markdownを開き続ける移行案

1. 現行MD読込経路と既存fixtureを保持し、新形式の識別・検証adapterを別経路で追加する。拡張子だけで判定せず、既知の識別子と版を検査する。旧MDを一括変換することを導入条件にしない。
2. 新形式を読み込む場合は、完全検査した後に内部表示用へ投影する。現行Graph v1をそのまま維持し、Procedure・Findings・Checkは別の詳細情報として引き渡す。Medium/SRと0.4.8 Checkの読込差は別途対応・テストする。
3. 変換は明示操作で別ファイルへ出力し、元MDを残す。全文復元、参照先、レビュー状態、根拠、Check原典の版を比較して、人間レビュー前の情報を確認済みに変えない。ID対応に確信が持てなければ自動確定しない。
4. 改名や構造変更を経た新形式からMDへ戻す際は、安定IDを現行MDへそのまま埋め込めない問題を明示する。旧MDの直接閲覧は維持できるが、IDを含む双方向無損失編集を保証したことにはならない。
5. 正式採用前に、小さな読込adapterで外部HTTPS/CORS/ローカルFile、既存MD全回帰、破損時の描画保持、0.4.8保証と共有Checkの表示を検証する。GUIを変更する段階では本人の操作レビューを行う。

今回のPoCは既存のBD/Check/Skill/Viewer/Graphを変更せず、別研究の状態遷移・概念モデル設計にも介入していない。既存PR #254/#266は変更していない。

## 未決事項と次の判断

- 整形JSONを次の検証へ進めるか。JSONLは巨大入力の逐次処理や外部索引という具体的な要件が生じた時に再評価できる候補として残す。正本として不成立とは断定しない。
- MDに可視ID・版欄を追加する代案は残る。現行profileの変更となるため今回未実装で、比較した現行MDが改善不能という意味ではない。
- ハイブリッド本文をどこまで型付きにするか。型付きにするほど機械検査は増やせるが、Markdownと構造化参照の二重管理を作らないことが必要である。
- Check原典文書ID/版、合意版、保証・例・根拠・Test参照のどこを機械的に管理するか。今回は原文保持までで、実Test証拠の更新や履歴追跡を実証していない。
- 永続ID発行、Findings/Check内の名前やfragmentの改名追従、文書間参照、未知の任意拡張の読み取り専用保持方針。
- 部分編集をAIに頼む実験は、モデル・同一課題・回数・採点・費用を固定して別途行う。人間による読みやすさ・編集負担も観測する。

PoCのテスト成功は形式の正式採用や業務上の合意を意味しない。今回成立しなかったのは「3方式を現行Viewerへそのまま投入する経路」であり、いずれもadapterが必要である。「JSONLなら単一ファイルから安全に即時部分取得できる」という無条件の主張を支える証拠も得ていない。
