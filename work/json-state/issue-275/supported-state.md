# 備品購入申請 — 業務設計

草案（採用した改善方針を反映した変更後の業務案。全体の人間レビュー・合意前）。

社内で使用する備品の購入申請、承認、購入準備、購入結果の登録を記述する。実際の購入作業はシステムのスコープ外で行う。

業務上の意味・前提・入力・手順・結果を記述し、画面部品、API、クラス、モジュール、データアクセス方法などの実装方式は規定しない。

## 業務上のロール

- **申請者** — 業務に必要な備品の購入を申請する。
- **承認者** — 申請内容を確認し、購入を承認するか、申請者へ差し戻す。
- **購買担当者** — 承認済みの申請を購入用CSVへ出力し、システム外で購入した結果を登録する。
- **総務** — 基幹システムの役職別上限額に関する情報を管理する。
- **人事** — 基幹システムの従業員情報を保守する。

ロールは業務上の責任と権限を表す。

## 作業者の識別と認証

各業務の作業者は、外部の認証基盤を利用したシングルサインオン（SSO）でログインし、一意に特定する。認証済みセッションは複数の画面・操作で継続利用する。パスワード等の資格情報を各業務へ配布する意味ではない。具体的な製品・サービス名は指定しない。

各業務はスコープ外のObject「認証基盤」から認証済み作業者の識別情報を受け取る。申請時・再申請時には、その利用者に対応する従業員情報・役職を基幹システムから参照する。認証基盤と基幹システムの具体的な属性・キーの対応付けは、SR・実装側で具体化する。

作業者と申請者が異なる代理申請を認めるか、その場合に誰の役職で判定するかは別の業務上の未決事項である。作業者を一意に識別できることから、代理申請の可否は推定しない。

認証・セッション管理は一般的なWebアプリのセキュリティ要件に沿うものとする。具体的な技術条件はシステム要件（SR）で定める。認証プロトコルやセッションの有効期限等の詳細は未定である。

## 購入申請の扱い

購入申請は、申請者が業務上必要とする備品の購入要求を、承認および購買の対象として扱うための記録である。

購入申請は、後述のObject 購入申請のInformationに挙げる情報を少なくとも持つ。

購入申請は一意に識別できるものとする。識別子の採番・入力方法はこの業務設計では規定しない。

## 業務相関

現在定義している主な業務相関は次のとおりである。

1. 申請内容が基幹システムの役職別上限額に適合すると自動判定できた場合に、`申請済み` の購入申請が成立する。不適合または判定不能の場合は申請を成立させない。申請者が提出前に作業を中断する場合は、入力途中の内容を下書きとして保存し、後から再開できる。下書き保存だけでは申請を提出したことにしない。
2. `申請済み` の購入申請を受けて承認業務を開始し、その業務中に承認者が可否を判断する。正常に承認すると、`承認済み` になる。
3. 承認業務中に購入を認めないと判断した場合は、例外として購入申請を申請者へ差し戻し、再申請・破棄の業務へ戻す。
4. `承認済み` の購入申請を購入用CSVへ出力し、システム外で実際の購入作業を行う。CSV出力だけでは購入済みとせず、購入結果の登録により `購入済み` になる。購買側で承認済み申請を拒否する業務は設けない。
5. 差し戻された購入申請と下書きの購入申請について、申請者は再申請するか、申請内容を破棄するかを選ぶ。再申請でも権限判定を通し、`申請済み` として承認業務へ渡す。差戻し・下書き・破棄された申請内容は購買対象にならない。

## 現在の業務設計で未決定の事項

次の事項は現在の業務設計では定めない。

- 申請金額によって承認者や承認段階が変わる場合の扱い
- 在庫確認、発注、納品、検収、支払に関する業務
- 購入先の選定方法
- 購入後の備品管理、資産管理、廃棄
- 基幹システムからの従業員情報・役職別上限額の参照、外部認証基盤によるSSO、購入用CSVの出力以外の外部システム連携
- 監査履歴や通知に関する業務
- 役職別上限額の具体的な値、基幹システムを参照する際の運用条件
- CSVに含める列・対象のまとめ方・再出力、購入結果の入力方式（手入力・CSV取込等）
- 一括却下・一括結果登録の採用（今回の改善では採用していない）

これらは、現在の業務設計を実装するために決定済みであるとはみなさない。

## 確認が必要な事項（未確認）

承認と差戻しの業務境界はF01、購入準備と購入結果登録の分離はF02、認証基盤からの作業者識別情報の受取りはF03に解消内容を記録する。代理申請の可否・適用する役職は、F03とは別の業務上の未決事項として残す。

- **購入できない場合・結果登録できない場合**：購買側の承認拒否は設けないが、システム外で購入を完了できない場合や、購入後に結果登録できない場合の扱いは未確認である。購入日時の受け取り方・記録方法も未確認であり、結果登録日時と同一とは定めない。
- **入力不足・状態が変わった場合**：基幹システムの役職別上限額への適合を判定できない情報不足は申請不可とする。それ以外の必須入力不足時の具体的な扱い、数量・金額の有効範囲は定めていない。承認業務の対象は `申請済み`、購入準備・購入結果登録の対象は `承認済み` としているが、選択後に対象が別の状態になった場合や、再実行時の結果は定めていない。

基幹システムの役職別上限額に不適合または判定不能の場合の申請不成立と、承認業務中の差戻し、差戻し・下書きからの再申請または破棄は後述のとおりとする。それ以外の未記載の操作結果は未決である。

- **破棄・再申請不成立の扱い**：申請中断時の下書き保存と、その下書きからの再開は後述のとおりとする。破棄時の物理削除・履歴保持、再申請が権限判定で成立しなかった後の元の申請内容の扱いは未確認である。下書きの自動保存や、破棄後の保存期間は規定しない。

## 参照する基幹システム

基幹システムは、従業員の識別情報・役職と、役職ごとの決裁単位の上限額を提供する外部システムである。決裁単位は購入申請1件とし、申請者の役職に対応する上限額を用いる。従業員情報は人事、役職別上限額に関する情報は総務が管理する。

今回の業務は基幹システムから必要な情報を参照し、その保守は扱わない。内部のテーブル単位にはObjectを分けない。具体的な上限額や参照時の運用条件は未確認である。認証済み利用者と従業員情報の具体的なキー対応はSR・実装側で定める。

# Scope

社内の備品購入について、基幹システムの役職別上限額に基づく申請可否の自動判定、申請と中断時の下書き保存、承認業務中の承認・差戻し、下書き・差戻しからの再申請または破棄、承認済み申請の購入用CSV出力、購入結果の登録を扱う。実際の購入作業はシステムのスコープ外とする。購入申請はこの業務で成立・更新する記録である。申請者・承認者・購買担当者のObjectは、各業務で情報を入力・選択する人を表し、人自体を成立・管理する業務は扱わない。基幹システムは従業員情報・役職別上限額を提供するスコープ外のObjectであり、内部のテーブル構造や同システムの保守は今回の業務に含めない。認証基盤もスコープ外のObjectとして利用し、認証済み作業者の識別情報を受け取る。利用者登録・認証基盤の管理、独立したログイン業務は今回扱わない。前述の対象外業務や未採用の一括却下・一括結果登録は含めず、未確認の条件を決定済みとはみなさない。

# Activity 備品購入を申請する

## Scope

true

## Why

購入の必要性と希望内容を記録し、承認者が購入可否を判断できる状態にするため。

## When

申請者が、業務上必要な備品を購入したいと判断したとき。

## Who

申請者

## Where

規定なし。

## How

### Input

- 認証基盤 — 認証済み作業者の識別情報
- 申請者 — 品名 / 数量 / 希望購入金額 / 購入理由（提出する場合はすべて必須） / 申請を中断して下書き保存する選択
- 基幹システム — 従業員の識別情報 / 役職 / 役職ごとの決裁単位の上限額

### Procedure

業務に必要な備品の購入要求を、購入申請として登録する。認証基盤から受け取る認証済み作業者の識別情報で作業者を一意に特定する。代理申請の範囲は、前述の未決事項に従う。

1. 申請者が購入したい備品の品名と購入理由を入力する。
2. 数量と希望購入金額を入力する。
3. 申請者に対応する基幹システムの情報から、申請者の役職を確認する。
4. 購入申請1件の希望購入金額が、その役職に対応する基幹システムの役職別上限額以下であるか、自動判定する。
5. 適合すると判定できた申請を、新しい購入申請として登録する。
6. 新規Object「購入申請」を状態「申請済み」で保存する（作成前 → 申請済み）。

### Exception

- **権限判定不成立** — 基幹システムの役職別上限額に適合しない場合、または規定の矛盾・必要情報の不足などで適合すると判定できない場合は、申請を成立させず、`申請済み` の購入申請を作成しない。この申請不成立を、承認業務による差戻しとは扱わない。

- **作業中断** — 申請者が提出前に申請業務を中断し、下書き保存を選んだ場合は、申請者と入力途中の内容を購入申請へ「下書き」の状態で新規保存する（作成前 → 下書き）。提出時の必須項目が未入力でも下書き保存できる。下書き保存では `申請済み` の成立や権限判定の通過を意味せず、承認・購入の対象にしない。保存した下書きは「購入申請を再申請・破棄する」で再開し、内容を整えて提出するか、破棄するかを選べる。

### Output

- 購入申請 — 提出時は申請者 / 品名 / 数量 / 希望購入金額 / 購入理由 / 申請日時 / `申請済み` の状態。中断して下書き保存した場合は申請者 / 入力途中の申請内容 / 下書きの状態

## Result

- 基幹システムの役職別上限額への適合を自動判定で確認した購入要求が、`申請済み` の購入申請として記録される。
- 申請者、品名、数量、希望購入金額、購入理由、申請日時が保持される。
- 承認者が購入可否を判断できる状態になる。

# Activity 購入申請を承認する

## Scope

true

## Why

申請内容が妥当であることを確認し、購買担当者が購入を進められる状態にするため。

## When

購入申請が `申請済み` として提出されたとき。

## Who

承認者

## Where

規定なし。

## How

### Input

- 認証基盤 — 認証済み作業者の識別情報
- 承認者 — 承認可否を判断する対象購入申請の選択（必須） / 差し戻す場合の差戻し理由（必須）
- 購入申請 — 対象購入申請の内容と `申請済み` の状態

### Procedure

認証基盤から受け取る認証済み作業者の識別情報で、承認業務の作業者を一意に特定する。提出された購入申請の購入可否は、承認者が業務中に人間として判断し、その責任を負う。以下は承認する場合の正常手順である。

1. 承認者が、対象となる `申請済み` の購入申請を選択し、その内容を確認する。
2. 購入してよいと判断する。
3. 対象Object「購入申請」の状態を「申請済み」から「承認済み」へ変更する。
4. 承認日時を記録する。

### Exception

- **差戻し** — 承認者が業務中に購入を認めないと判断した場合は、例外として対象購入申請を申請者へ差し戻す。対象Object「購入申請」の状態を「申請済み」から「差戻し」へ変更する。差戻し理由と差戻し日時を記録し、購入申請を差戻しの状態とする。「購入申請を再申請・破棄する」へ戻し、申請者が再申請または破棄を選べるようにする。この場合は正常な承認結果を成立させず、購買対象にしない。

### Output

- 購入申請 — 承認の結果（`承認済み` の状態 / 承認日時）、または差戻しの結果（差戻しの状態 / 差戻し理由 / 差戻し日時）

## Result

- 対象購入申請が `承認済み` になる。
- 承認日時が記録される。
- 購買担当者が購入対象として扱える状態になる。

# Activity 購入申請を再申請・破棄する

## Scope

true

## Why

下書きや差し戻された購入申請を、再び承認に進めるか、不要な申請内容を破棄するか確定するため。

## When

申請者が、保存済みの下書きの購入申請から作業を再開するとき。

## Exception When

- 備品購入を申請する — 作業中断：申請者が提出前に作業を中断して下書き保存し、その下書きから作業を再開するとき
- 購入申請を承認する — 差戻し：購入を認めないと判断され、購入申請が申請者へ差し戻されたとき

## Who

申請者

## Where

規定なし。

## How

### Input

- 認証基盤 — 認証済み作業者の識別情報
- 申請者 — 再申請または破棄の選択 / 再申請する品名・数量・希望購入金額・購入理由
- 購入申請 — 対象の申請内容 / 下書きまたは差戻しの状態 / 差し戻された場合の理由
- 基幹システム — 従業員の識別情報 / 役職 / 役職ごとの決裁単位の上限額

### Procedure

認証基盤から受け取る認証済み作業者の識別情報で作業者を一意に特定する。申請者は対象の申請内容について再申請または破棄を選ぶ。代理申請の範囲は前述の未決事項に従う。以下は再申請する場合の正常手順である。

1. 下書きまたは差し戻された対象購入申請の内容を確認する。差し戻された場合は、その理由も確認する。
2. 再申請する内容を入力する。品名、数量、希望購入金額、購入理由を必須とする。
3. 基幹システムから申請者の役職を確認し、購入申請1件の希望購入金額が、その役職に対応する基幹システムの役職別上限額以下であるか自動判定する。
4. 適合すると判定できた内容で対象Object「購入申請」を再申請する。状態を「下書き」または「差戻し」から「申請済み」へ変更し、申請日時を記録する。

### Exception

- **申請内容の破棄** — 再申請せず破棄することを選んだ場合は、対象の申請内容を破棄する。破棄した内容を以後の承認・購入の対象にしない。対象Objectは「購入申請」、変更前は「下書き」または「差戻し」。処理後の保存状態は未決である。
- **再申請不成立** — 基幹システムの役職別上限額に適合しない場合、または必要情報の不足や矛盾等で判定できない場合は、再申請を成立させず、`申請済み` の状態へ変更しない。その後の元の申請内容の扱いは未確認である。

### Output

- 購入申請 — 再申請した内容 / `申請済み` の状態 / 申請日時、または対象の申請内容の破棄

## Result

- 対象購入申請が権限判定を通った内容で `申請済み` として再申請され、承認者が再び可否を判断できる。

# Activity 購入を準備する

## Scope

true

## Why

承認済みの購入要求を、システム外の購入作業へ渡せる状態にするため。

## When

購入申請が `承認済み` となり、購入準備の対象になったとき。

## Who

購買担当者

## Where

規定なし。

## How

### Input

- 認証基盤 — 認証済み作業者の識別情報
- 購買担当者 — CSV出力の対象購入申請の選択
- 購入申請 — 対象購入申請の識別情報 / 申請内容 / `承認済み` の状態

### Procedure

1. 認証基盤から受け取る認証済み作業者の識別情報で作業者を一意に特定する。
2. 購買担当者が対象の承認済み購入申請を選択し、その内容を購入用CSVへ出力する。購買側で購入可否を再審査して拒否する業務は設けない。
3. 購入用CSVを、システム外で行う実際の購入作業へ渡す。CSV出力によって購入申請を `購入済み` に変更しない。

### Output

- 購入用CSV — 対象購入申請の識別情報 / 購入準備に使用する申請内容

## Result

承認済みの購入要求を購入用CSVから参照して、システム外の購入作業を進められる。CSV出力時点では購入完了を意味しない。

# Activity 購入結果を登録する

## Scope

true

## Why

実際の購入結果を対象の購入申請へ反映し、購入済みとして扱える状態にするため。

## When

システム外の購入作業が完了し、その結果を登録するとき。

## Who

購買担当者

## Where

規定なし。

## How

### Input

- 認証基盤 — 認証済み作業者の識別情報
- 購買担当者 — 購入した対象購入申請の選択 / 実購入金額（すべて必須）
- 購入申請 — 対象購入申請の識別情報 / 申請内容 / `承認済み` の状態

### Procedure

1. 認証基盤から受け取る認証済み作業者の識別情報で作業者を一意に特定する。
2. 購買担当者が、システム外で購入した対象の承認済み購入申請を選択する。
3. 対象購入申請へ実購入金額と購入日時を記録する。購入日時の受け取り方・記録方法は未確認であり、登録時刻で置き換えるとは定めない。
4. 対象Object「購入申請」の状態を「承認済み」から「購入済み」へ変更する。

### Output

- 購入申請 — `購入済み` の状態 / 実購入金額 / 購入日時

## Result

- 実際に購入した対象購入申請が `購入済み` になる。
- 実購入金額と購入日時が記録される。
- 対象申請が購入済みとして扱える状態になる。
