# 業務設計JSONの正規化候補

これは `alder-document-package/0.7` のBusiness Designに対する独立した検討用JSONと、概念モデルSkillの候補です。実際の0.7 Schema、保存器、旧JSON、Check、State、0.7候補の概念モデルは変更しません。`alder-normalized-business-design-study/0.1` は実製品で読み書きする形式ではありません。

今回の目的は、既存JSONの入れ子をそのままER図にするのではなく、実際に共有・識別するものと参照、属性、値、未決を区別してレビューすることです。概念図は通常、物理ERの全項目を要求しませんが、描いた関連は業務の意味と一致させます。今回はJSON定義のレビューなので、候補の項目と関連を実際の試作へ対応付けます。

## 現行JSONと図の切り分け

| 対象 | 現行0.7 | 図・候補 |
| --- | --- | --- |
| Roleの共有 | BDの `roles` をIDで参照し、同じRoleを複数Activityで共有できる。 | 旧図はActivity内のWhoを1:1の箱として示し、全体図ではWho自体も省略していたため、共有が読み取りにくい。候補はWhoとActivityの多対一を示す。 |
| system／schedulerの共有 | 各Activityの `who` に種類と名前を直接持ち、共有主体のIDがない。同一の主体を複数業務から参照したことを記録できない。 | 入れ子の図示だけの問題ではない。候補は明示された主体IDによる共有を示し、同名から同一性を推測しない。 |
| Who未決 | `who` は必須項目で、値の `null` が未決。 | 旧図のWho内の「未決」は説明として作った項目であり、実際のWhoの属性ではない。候補はActivityの参照の未決として扱う。 |
| 判定行の参照 | `decisionId` と `rowId` を併記し、検証器が行の所属を照合する。現行は行IDがパッケージ内で一意なので、行IDから判定表を特定できる。 | 候補は行IDを持ち、判定表を行からたどる。既存の所属検査を省いてよいという意味ではない。 |

JSON配列の存在だけでは非正規化と断定できない。現行の重複にどんな意味や更新保証があるかを確認し、図の誤表示と保存上の問題を区別する。

## 実際の例とビュー

- [元の画面例をもとに追加した架空の変換前JSON](example-source.json)：未レビューの合成例。モルック例に同じ記録係の2業務とWho未決の業務を追加。
- [正規化した候補JSON](example-normalized.json)：主体を共有し、業務・手順・判定等をIDと関係の行に分けた実データ。
- [正規化候補の概念モデルJSON](../../business-design/alder/json-normalized-model-review.json)：既存Viewer用の独立した表示候補。旧0.7構造の図とは別。
- [構造名の検討案](naming-proposal.ja.md)：情報項目・項目グループを含む25構造の役割、名称と現行JSONとの対応。保存形式の変更や名称の採用は未確定。
- [全関係の一覧](relationships.ja.md)：全ての関連・多重度と条件を記す。

正規化候補の概念モデルは `meta.relationNames` に、関係IDをキーとした出発側からの名前を記録します。例えば、受渡しから手順行への「対応する手順」と、前提から手順行への「前提の手順」を区別します。この名前は概念上の役割であり、`meta.fieldMappings` にある物理項目名とは独立しています。名前は未レビューの候補であり、関係の両端・種類・多重度・既存の人間確認状態は変えていません。構造エクスプローラーは同じ概念モデルJSONから名前を読みます。`create-review.mjs` は再生成時にこのJSONの名前を保持し、未登録や余分な関係IDを検出します。

同じ概念モデルの `meta.conceptNames` は、概念IDごとに型名と論理名を分けて記録します。例えば主体は型名 `Who`、論理名 `主体` です。構造エクスプローラーは関係先に型名を表示し、全体図の従来の表示名は両者から生成します。未レビューの概念上の名前であり、物理JSONの型定義ではありません。別の名前が定義されていない概念は既存名を保持します。

全体図は25概念と54関係を対象にする。画面サイズによっては、現行Viewerの一角配線で一部の線や件数ラベルを配置できず、該当する関係を画面の警告に示す。固定した大きさを使った個別図の検査でも、Step・判定表・判定行・例外は一部の線、Object・Data・Stepは件数ラベルに課題が残る。関係自体はモデルと一覧に残る。Who／Activityの個別図と、元の13概念の抜粋図は同じ限定検査で全線を描ける。抜粋図では関連する子をまとめることで線の交差を6か所から0か所に減らせるが、全25概念で交差ゼロを保証するものではない。

## 確認した関係

| 事実 | 保存の候補 | 例 |
| --- | --- | --- |
| 一つの主体が複数の業務を担当できる | `actors` に一度定義し、各 `activities.whoId` が参照 | 「記録係」が2業務を担当 |
| WhoはRole・system・scheduler | `actors.kind` で種類を保持。RoleのID・名称・色はそのまま移す | 自動処理に人間Roleを作らない |
| 業務のWhoが未決 | `activities.whoId: null` | 「未決」という主体は作らない |
| 手順とDataの関係 | 手順、Data、対象Data／受渡しDataの関連を分ける | 同じDataを複数手順から参照 |
| 判定表と判定行 | 業務→判定表→軸／行。条件は行と軸に対応し、結果の種類・内容は行の属性 | 1行を指す参照から所属する判定表をたどる |
| 判定行とCheckの対応 | `rowChecks` で両方のIDと対応範囲を保持 | 同じCheckを複数の判定行から参照 |
| 例外と中断・再開 | 例外は業務に属し、中断・再開は存在する場合だけ別に保持 | 実際にない中断や再開を作らない |

図の多重度 `Activity：Who = 0..N：0..1` は保存上、未使用の主体とWho未決の業務を許すことを表します。確定した一つのActivityには一つのWhoが対応します。`null` を「主体が存在しないと確定した」と解釈しません。

主体ID→種類・名前・色、Activity ID→そのActivityのWho参照、判定行ID→所属する判定表と結果、DataとInformationの組→構成条件という依存を確認しています。`whenDecision` の判定表IDは、検証済み判定行IDからたどれるため、試作では判定行IDを保持します。現行0.7の対応が不正なら変換前に拒否し、元を変えません。

`ordinal` や、未記載・`null`・空配列を区別する状態は、もとのJSONを情報落ちなく再構成するための記録です。手順の説明上の順番と依存の意味を分けます。採用前には、保存順序や文書境界を含む関数従属性・候補キー、全参照・複合制約、既存利用経路をさらに照合します。現段階で全体が第三正規形に確定したとは扱いません。

## 変換と確認

`normalize.mjs` は既存0.7検証を通した入力だけを対象に、手順／結果／例外／判定／Dataを複数の関連行へ分け、元形式へ戻せるか確認します。既存RoleのIDを保持します。旧形式のsystem／schedulerには共有可能なIDがないため、各Activityについて主体IDと根拠を明示しなければ変換しません。同名だけで統合せず、明示された同一主体の名称・種類が矛盾すれば拒否します。入力ファイルは変更しません。

0.7のCheck等の別文書は元の内容・版・人間状態のまま試作に添えます。新しいBusiness Design版に対する合意や正式な移行を意味しません。実際の移行では旧原本と版を保持し、Check／State／概念文書の原典・意味・確認状態を別途照合する必要があります。

```sh
node work/normalization-candidate/create-review.mjs
node --test work/normalization-candidate/normalize.test.mjs
cd web-viewer && node web/test-normalized-review.mjs
```

旧保存器で通常は拒否する未解決Findingを読み取り検討するケースだけ、既存の `allowUnresolvedFindings` を明示指定します。指定なしの通常検証は緩めません。正負例、元データの往復、元ファイル不変、人間確認状態、Who／Activityの図と選択強調を限定確認します。Skillの本文や例に基づく自己照合は、実際のAgentによる能力評価の代わりにはなりません。
