# 境界分解思考のFresh比較 — Issue #132

2026-10-02。境界分解規則の追加で質問の粒度は具体化したが、一般的な探索性能の優位は確認できなかった。小規模な比較の主採点では軸回収が40.0%から46.7%へ上がる一方、出力文字数は80.6%増えた。曖昧な採点の解釈によって回収率差は逆転し得る。

## 固定条件と証跡

6ケース、各条件2回、計24回。Generator全回と別の評価agentに **gpt-6-sol / reasoning effort medium / fork_turns none** を要求した。実効モデル・エフォートの独立証明は得られず、要求値として記録している。実行clientはChatGPT Workの`collaboration.spawn_agent`。agent名、全文prompt、実行順、入出力SHA-256、未加工の最終応答を[runs.json](runs.json)に保存した。coordinatorの正確なmodel/effortは非公開で取得できない。

生成前に[事前登録](preregistration.json)を公開commit `40f084543c54aef3fe5f0f7dba9cb25a9e8a7f82`へ保存し、公開SHAから再取得できることを確認した。全generatorに、当該caseと自条件promptだけを与えた。他case、oracle、過去出力、外部情報・ファイル・tool参照を禁止し、新規agentを使用した。生成はControl/Treatmentを交互に起動した。物理的なfilesystem隔離や、プラットフォーム内部contextの独立監査は実施していない。

生成後、seed 132の固定shuffleでarm・実行回・agent名を伏せた[評価パケット](blind-packet.json)をcommit `2fd5459f6b1a1aeed506ca0cdbe5523f3277deea`へ保存した。別のFresh評価agentはこのファイルだけを一度読み、元のoracle/rubricで採点した。[評価prompt](evaluator-prompt.txt)、[無修正の採点](evaluator.json)、[provenance検証](verification.json)を公開する。評価者へ条件名は渡していないが、文章の特徴から条件を推測できなかったことまでは証明できない。生成と同じ要求modelの評価なので、モデルをまたぐ独立評価ではない。

評価packetの`source_revision`は事前登録の出典を指す。評価agentはこれをpacket自身のrevisionとの不一致と報告した。coordinatorは指定公開commitと評価者が読んだlocal fileの全byte一致を検証した。元の採点・指摘は書き換えず、[verification.json](verification.json)へ確認結果を追加した。

## 主採点

数値は各条件2回の合計。回収率の分母はoracle軸数×2。N1/N2には未決軸がないため回収率を計算しない。

| Case | Controlの回収 | Treatmentの回収 | Control文字数 | Treatment文字数 | 主質問数 C / T |
| --- | --- | --- | ---: | ---: | ---: |
| P1 人間関与の束 | 0/10（0%） | 0/10（0%） | 144 | 415 | 1 / 6 |
| P2 経費精算の一部自動化 | 6/8（75%） | 8/8（100%） | 265 | 540 | 4 / 8 |
| H1 会議室の利用停止 | 2/8（25%） | 3/8（37.5%） | 299 | 617 | 5 / 9 |
| H2 図書館の貸出制限 | 4/4（100%） | 3/4（75%） | 289 | 345 | 4 / 5 |
| N1 単一閾値 | 停止2/2 | 停止2/2 | 92 | 102 | 0 / 0 |
| N2 決定済みの独立軸 | 停止2/2 | 停止2/2 | 77 | 87 | 0 / 0 |
| 合計 | 12/30（40.0%） | 14/30（46.7%） | 1,166 | 2,106 | 14 / 28 |

軸ごとの具体的質問への到達も12/30対14/30。曖昧に束ねた質問は1件対2件、根拠のない追加軸は0件対1件、未決値の無断確定は両群0件。N1/N2の停止は両群4/4。重複質問は両群0件だった。文字数は改行・空白を含むUnicode code point数で、最終応答だけを数える。質問数は主質問単位であり、独立した回答欄や疑問文の節数ではない。caseを等重みとした平均回収率は50.0%対53.125%で、軸数で重み付けした合計とは異なる。

oracle外の根拠ある判断は、延べ5件対13件として別枠記録された。P1の責任・例外条件やH1の操作権限などを含み、case内の異なるrun間で重複する。新しい有用軸を13種類発見したという意味ではなく、この数だけで探索優位を主張しない。

## 改善・非改善・副作用

**表現精度:** P2のTreatmentは4段階を毎回別質問にし、承認と支払対象確定の決定主体を明示した。Controlの1回目でも4段階を列挙した質問により全軸を回収している。新しい4軸をTreatmentだけが発見したとは言えない。

**探索能力:** H1はTreatmentの1回目だけが停止中の新規予約を発見した。検索候補への表示と停止会議室への変更は両群で発見できず、2回目のTreatmentにも新規予約の明確な質問はなかった。P1では両群とも具体的なインフラ・DB・サービス・言語・互換性へ分けられなかった。Treatmentは一般的な委任範囲や例外条件の質問を増やしたが、oracle軸の回収は改善していない。

**停止性・無断決定:** N1/N2は両群とも追加質問なしで停止。無断の業務値確定も両群0件。Controlが既に守っているため、改善を示す差はなかった。H2のTreatmentには「遅延0日も対象か」という入力の遅延時scope外と採点された問いが1件あり、過剰探索が完全に抑えられたとは言えない。

**コスト:** 最終出力は全体で80.6%増、主質問は2倍。P2では個別の判断と影響を繰り返し明示するため長くなる。読みやすさ、人間の回答時間、レビュー時間、token数、実行時間は測定していない。文字数増から認知負荷の改善・悪化を直接結論しない。

## 採点感度と限界

主採点は評価agentの結果を変更していない。以下は評価者が残した曖昧さを使う別枠の感度分析であり、新しい主基準ではない。

- B09（P2 Control 2）の「読み取りとルールの確認結果」を独立回答できる列挙と読めば、Controlは2軸増え、P2の回収率差は消える。
- B14（H2 Treatment 1）の会員別閾値質問を組合せごとの許否に相当すると読めば、Treatmentは1軸増える。「遅延0日」を正当な境界確認と読む場合はUnsupportedも0になる。
- B18（H1 Treatment 1）の「既存予約は引き続き利用できるか」を既存予約の維持・取消と異なる問いと読むと、Treatmentは1軸減る。

この3点の独立した解釈差だけで、合計回収率差は **−3.3〜＋10.0 percentage points** となり得る。主採点の＋6.7 pointsは頑健な性能差ではない。P1の包括的な質問を具体的対象の発見とみなす余地も評価者が指摘しており、表現と発見を区別するoracleの妥当性自体にも課題がある。入力に未登場のサービスやAPIを想像して増やさない規則と、これらを期待するP1 oracleの間には緊張がある。今回の0%を能力一般の欠如とは扱わない。

2回ずつの意図的に選んだ6ケースであり、統計的な優位・一般的非劣性・実務効果を主張しない。今回は混合結果と測定限界をそのまま報告する。主結論は性能優位の未確認であり、追加runで採点上の曖昧さを解消できるわけではないため、結果に合わせた追試・oracle修正は行っていない。

H2は[公開RDRA sample](https://github.com/tango238/rdra/blob/be7b56578b65a9582ede2684009dafeab9933c79/example/library/rdra.yml)のUC・貸出制限・variation・descriptionを絞った固定抜粋。出典は生成後にcoordinatorが確認した。数値表記を読みやすく正規化し、他の業務や状態情報は入力から除いている。RDRAやAlderの手法全体・Pluginを実行した比較ではなく、同一modelへの探索規則追加の比較である。

[既存#128 trial](../../../docs/optimization-review/issue-128.md)では候補方向が同じで説明が明確化し、出力が約7.4%増えた。今回も具体的質問への表現差と出力増を観測した点は整合する。ただしタスク・prompt・caseが異なるため、7.4%と80.6%を直接性能比較しない。
