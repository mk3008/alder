# 状態遷移を明示宣言から再現する小規模検証

購入申請の状態と遷移を明示すれば、自然文の意味推論を使わずに同じ表・図を生成できた。今回の結果は**記法候補のPoC**であり、Alder正式書式、業務判断、Viewer機能の採用ではない。

原典は[購入申請BD 6f0b5d4](https://github.com/mk3008/alder/blob/6f0b5d492f02a8659ca2836afa84aba18606a531/business-design/purchase-request/README.md)。依頼元は[root #133の設計コメント](https://github.com/mk3008/root/issues/133#issuecomment-6279005462)と、その後の「対応してください」。main f9a9708eから分離し、製品コード・正式BD・Check・Skill・Viewer配信は変更していない。

## 比較と推奨

| 候補 | 人間の確認 | 機械処理 | 今回の判断 |
| --- | --- | --- | --- |
| [案A：Object内の表](candidate-a.md) | 遷移元・条件・遷移先を横に比較できる。スマホでは横スクロールが必要 | ヘッダー・列数を検証。PoCはセル内のパイプと改行に非対応 | 次の採用検討の第一候補 |

どちらも、Object・状態一覧・開始候補・終端未決・部分定義・各操作の責任Activity/条件/結果/根拠を一か所で宣言する。2案は同じ対象の**代替案**であり、併用する二重原典ではない。正式化する場合は一方だけをBD内の原典とし、Viewerの表・図を派生表示にする。今回の生成物は[generated.md](generated.md)、手動の原典対応は[evidence.md](evidence.md)。

条件は不透明な文字列として保持する。条件の真偽や相互排他性を機械が判断する意味ではない。

## 購入申請で確認できたこと

保存状態は原典どおり、下書き・差戻し・submitted・approved・purchasedの5つ。13操作行の内訳は、確定した状態変更7行、初回不成立1行、結果の制約はあるが遷移先未決5行。下書きと差戻しは操作の入口が異なるので別行にした。

| 操作 | 宣言できる結果 | 補完しない事項 |
| --- | --- | --- |
| 初回提出 | 作成前→submitted | 作成前を保存状態にしない |
| 中断・保存 | 作成前→下書き | 自動保存・保存失敗 |
| 初回権限不適合/判定不能 | submittedを作成しない | 存在しない記録の自己ループにしない |
| 承認/差戻し | submitted→approved / 差戻し | 選択後の状態変更・再実行 |
| 再申請成功 | 下書き/差戻し→submitted | 再開するだけで保存状態が変わるとはしない |
| 破棄 | 以後の承認・購入対象外 | discardedという状態、物理削除、保存期間・履歴 |
| 再申請失敗 | submittedへ変更しない | 元の状態・入力内容を維持するとは決めない |
| CSV出力 | purchasedへ変更しない | approvedの完全な自己ループを宣言するには不変の明記を追加確認 |
| 購入結果登録 | approved→purchased | 購入日時＝登録時刻、購入失敗時の扱い |

CSVは設計コメントでは「状態不変」を想定している。一方、固定BDの明文は「purchasedに変更しない」なので、今回は保守的に制約だけを転記した。正式採用時に「CSV出力では購入申請の状態を変更しない」と明記すれば、推論せずapproved→approvedの自己ループを生成できる。構文の自己ループ対応は合成入力でテスト済みだが、原典にその宣言を追加したとは扱わない。

`@new`は記録作成前の開始候補、`@none`は作成不成立の結果、`@unknown`は未決の遷移先であり、いずれも保存する業務状態ではない。終端は未決とし、purchasedを吸収状態にしない。作業再開は既存Activityの入口であり、保存状態の更新が確定しない限り独立した状態遷移を創作しない。

この状態集合と操作行は**部分定義**。線がない操作を禁止と判定しない。全状態×全操作の網羅性や禁止操作を定義する場合は、別途、人間が完全性と各結果を明示する必要がある。

## Informationを段階的に具体化する例

以下は原典の情報と不足点の整理。追加の業務要件を採用した表ではない。

| 情報 | 現時点の意味・タイミング | 未決として保持する点 |
| --- | --- | --- |
| 申請者 | 購入要求を出す人。下書き保存時にも保持 | 認証済み作業者と同一か、代理申請を認めるか。SRのキー対応と業務判断を分ける |
| 希望購入金額 | 購入申請1件の役職別上限額判定に使用。提出・再申請時に必須、下書きでは未入力可 | 通貨・税込税抜・複数明細がある場合の集計単位。数値型やDB列型は要求しない |
| 実購入金額 | 外部購入後の結果登録時に必須。希望額とは別の意味 | 申請1件に購入結果1件か、分割購入を認めるか。0..1を決定済みにしない |

購入結果を別Objectへ分割することや、新たなER工程・SQL物理設計は今回要求しない。情報不足が業務判断を変える箇所から具体化する。未決管理は既存Findingsへの集約が候補だが、今回F01〜F04の変更、新IDの採番、前書きとの二重台帳化はしていない。

実行：`python3 -m unittest discover -s work/explicit-state/issue-133 -p 'test_*.py' -v`

10テスト成功（初回0.006秒）。2候補の正規化結果/生成文字列一致、生成物の再現、自然文の非抽出、未記載≠禁止、未決の保持、作成不成立と不変の区別、明示的な自己ループ、重複ID/未知状態/不正効果/不正列の拒否を確認。ネットワーク・LLM・ブラウザー起動を使わない。Viewer変更がないため、長時間の全体ブラウザーCIは実行していない。この時間は小さなPoCのローカル実測であり、既存検証の高速化効果を測った値ではない。

同一Agentの別工程で原典との意味対応と未決の扱いをセルフレビューした。独立Freshレビューではない。

- 修正・保留：CSVを無条件に自己ループ化しない。破棄を終端状態にしない。再申請失敗を旧状態保持にしない。
- 境界：抽出器は宣言の構文と状態参照を検証する。Activity名・根拠IDの存在照合、Procedure/Resultとの意味矛盾、条件の抜け/重複はまだ自動検出しない。evidenceの対応は手動である。
- 表示：Mermaidテキストと表の生成・一致まで検証。Mermaid実レンダラー、スマホの視認性、Viewerドロワーへの統合は未検証。
- 汎用性：購入申請1Objectの検証。複数Objectの同時更新、条件式の形式化、完全な状態機械の検証は対象外。PoCは不明な終端・部分定義のみを受け付け、完成済みライフサイクルへの一般対応はしない。

## 次に人間が判断する点

第一候補は「Object内に状態一覧と遷移表を置き、Activityは既存名で参照する」案。表示側はその宣言だけを読み、未決は未決として出す。意味判断は設計・レビューに残す。

正式書式の採否、CSVの状態不変の明記、未決のFindingsへの集約方針を確認した後、採用された範囲だけを正式BD/書式/Skillへ反映し、既存Object詳細での表表示からViewerを検討する。ここまでのPoC成功は、その採用やBD全体の合意を代行しない。
