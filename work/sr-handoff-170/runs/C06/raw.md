# C06 read-only implementation review

**Definite BD–SR conflict, with a current SR mismatch.** Agreed BD-1 §Record says different partners may independently submit the same external reference; confirmed CHK-02 expects a second saved order and distinct identifier. Current supplied SR-F-1 (`product/system-requirements.md`) instead requires `external_ref` to be unique across *all* partners and rejection even for a different partner. The technical owner supplied it without saying it supersedes BD-1. Both cannot be satisfied for that case. IMPL-1 follows BD-1: `order_register.py` lines 5–11 declare `UNIQUE (partner, external_ref)`, and `register` lines 22–32 inserts by partner/reference, so a different partner's reuse is permitted. This conflicts with SR-F-1's global-uniqueness constraint, but is not evidence that the agreed business meaning was changed. Smallest decision: the business owner should confirm whether cross-partner reuse remains intended or whether BD-1/CHK-02 are to be changed; if it remains intended, the technical owner should reconcile SR-F-1. Do not change the unique key to global scope, or claim CHK-02 accepted under SR-F-1, before that decision. This affects whether a different partner's genuine order is saved and which guarantee the clerk receives downstream.

**CHK-01: sufficient within the prototype.** BD-1 and CHK-01 require a repeat for the *same* partner to be rejected without a new ID or row. The compound unique constraint and `sqlite3.IntegrityError` branch (`order_register.py` 10, 22–30) support that. The mapped test (`test_order_register.py` 13–21) asserts created first result, duplicate second result, absent second ID and one total row. E-1 reports it passed. This also matches the unchanged same-partner part of SR-F-1. The test's row count is a test of this single scenario, not a general operational guarantee.

**CHK-02: implemented and locally observed for BD-1, contested by SR-F-1.** `test_order_register.py` 23–29 asserts two created statuses, distinct IDs and two rows for partners A/B sharing `PO-17`; E-1 reports it passed. The assertion is meaningful for CHK-02 and the observed local result supports it, but the unresolved SR conflict prevents a single overall conformity verdict or dependent confirmation of the cross-partner policy.

**CHK-03: sufficient within the prototype.** BD-1/CHK-03 require exact receipt text using supplied ID and reference. `receipt_text` (`order_register.py` 35–36) formats them without storage; the mapped test (`test_order_register.py` 32–36) asserts `Order 17: PO-17` and another value pair. E-1 reports it passed. SR-F-1 does not change receipt formatting.
