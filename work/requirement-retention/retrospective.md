# 振り返り

## GoalとDone

業務要求とユーザー要求レベルのシステム条件を混在させ、公開済み0.4.4の単一初回草案で保持・部分欠落・意味追加を観測した。SR文書の新規生成を正解にせず、実装方式設計やSkill改修へ広げなかった。入力・oracle・全dispatch・package・未加工raw・評価・訂正・digestを保存し、全66要求を対応した。対話への回答・再草案化はしなかった。

## 介入と原因

この実行中に新たな人間の訂正を受けたわけではない。実行前のcoordinatorレビューで、準備した会話末尾に保持・配置を促す研究側の誘導を見つけて削除した。変更前を保存し、Authorが見る前に固定した。合成入力が評価目的を露出しやすいという準備上のリスクであり、利用者の永続的な嗜好や業務ルールにしない。

初回評価は数値や文言が残ったことを重視し、BDの担当・Outputに混ざった未根拠の意味を見落とした。coordinatorが責任・情報の実際の受渡しを原発言と照合し、別評価者が限定的に再判定した。初評原本は保持。反対にサインイン未決のロスト断定は、一般的な本人確認という妥当な別解釈を考慮して部分保持へ弱めた。どちらも評価そのものの誤り・見落としとして明示し、oracleやrawを都合よく変えていない。

## 再発防止の扱い

既存の公開authoring guidanceに、Whoの責任、実際のI/O、発言にない業務意味を補わない基準がある。新しい恒久ルールやSkill変更は今回の範囲に含めず、既存基準によってこの出力を判定した。「文字が残ること」と「置いた欄が意味を変えないこと」を別に確認すれば、今回の未根拠追加は検出できた。

単一ケースから一般的なモデル特性、再現頻度、修正効果を断定しない。既存Skillへ対策が必要かは別の採否・範囲判断であり、この証跡を根拠として相談できる。追加実験を自動開始しない。

## 実行上の制約と復帰

git proxyはInvalid Git namespaceでfetchできなかったため、利用可能なGitHub connectorのGit data APIで既知mainを親・base treeとして証跡パスだけ公開した。過去のCLI/bwrap失敗のsandbox調査は再演しなかった。入力・rawは公開commitへ固定し、主要内容の読戻しを確認した。共有filesystemの指示ベース隔離と実効設定未証明は限界として残る。

このWorkerは証跡保存・検証後にReviewer Chatへ返す。管理IssueはそのレビューまでOpenに保つ。merge、release、記事、Skill改修はしていない。業務の採否判断は人間に残るが、この合成草案を実業務として承認してもらう必要はない。
