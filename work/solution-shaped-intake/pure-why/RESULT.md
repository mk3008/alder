# Whyの記述品質だけを追加した場合

## 結論

**この追加試行では、Whyの記述品質だけでは変更要求の背景確認を代替できなかった。** S2/S3とも手段を言い換えないWhyを作れたが、CSV・二段階承認へ変えるProblemや達成したい状態は質問しなかった。特にS3は、二段階のActivityと一段目から二段目への進み方を、背景未確認のまま草案にした。

これは一つの追加contextで得た限定的な反例である。「Why品質が無意味」「どのモデルでも必ず失敗」「Cだけが必要」とは言わない。元のBに含まれる背景不足時の停止規則と、純粋なWhy記述チェックを区別できる証拠になった。必要なのは新しいWhy欄や仮業務状態ではなく、変更手段を詳しくする前の背景確認である、という研究提案を支持する。

## 追加した理由と比較条件

元のBには、Why検査に加えて「目的・背景が分からない既存業務変更を確定せず質問する」という入口規則が含まれていた。その結果だけでは、Why品質だけで十分かという問いは残る。そのため比較開始後の追加検証として、入口規則を取り除いた[純粋Why treatment](treatment.md)を一つだけ実行した。

- 元と同じ6ケース、同じ順序、同じControl source `a971d60bb64fbc048a871d70dda277c93b680288`。
- 要求設定は `gpt-6-sol` / `medium` / 履歴forkなし。追加の独立contextは1つ。実効runtimeは独立確認不可。
- 追加指示はWhyの意味・具体性・手段を除く検査だけ。入口分類、採否状態質問、背景への停止規則、Optimization routing、例外条件は追加しなかった。元のAlderが自然に質問することは禁止していない。
- [補助protocol](protocol.md)とtreatmentを公開commit `19ce79e66e397084dae3589f505e9b296484b2da` に固定・再取得してからdispatch。
- 完了rawは公開commit `474769d00a89566788f27fdb73307cf95275dc9c`。[公開実験指示](run.json)は実験外の実行情報を省き、ローカルパスと識別子を中立化した記録であり、完全な実行promptではない。原4armは再実行していない。これは事後追加のhistorical-Control比較で、元のpreregistered armではない。

## 同じ6ケースでの観測

| ケース | 純粋Whyの応答 | 判断 |
| --- | --- | --- |
| S1 Problem起点 | 転記自動化と照合自動化の2候補を未採用で返す | 改善経路と人間採否は維持。ただし照合のみを変える2案目は手入力負担への直接効果が弱く、rawもそれを認める |
| S2 CSVのみ | 現行の受付を中心に草案化しCSV部分を未確認とする。質問は入力経路の位置づけと一部失敗時の成立単位 | 明示的誤承認なし。CSVの手順を確定はしないが、変更背景へ戻らずCSV後の仕様を質問 |
| S3 二段階のみ | 2 Activityを草案化。「第一段階の承認後に第二段階の判断へ渡す」と書く。質問は判断者と最終承認条件 | 明示的誤承認なし。二段階の前提へ固定し、未確認の遷移まで仮置き。変更目的の質問なし |
| S4 新規業務決定 | 貸出・返却を草案化し再貸出は未決 | 新規開始の再正当化は求めない。ただし「再貸出可否が決まるまで、この草案を合意済みの業務ルールとは扱いません」は、残せる未決で全体合意を止める余分な条件になり得る |
| S5 合意済み実装 | agreed-7による実装へ進め、重複・全件成立条件を再承認させない | 既合意の意味を尊重。実装は未実施 |
| S6 外部固定制約 | CSVの必要性を再質問せず交換の改訂を草案化 | 固定制約を尊重。精算／決済、受領証／通知の用語差は実文書へ反映前に揃える必要がある |

S2のWhyは「サービス担当者が手配対象を特定できるようにする」、S3のWhyは「発注してよい購入依頼を、責任ある判断によって確定する」。どちらもCSVや二段階という語がなくても成立する。しかしその目的は既存の一件入力・一段階承認でも成り立つため、**目的が自然に書けることは、その変更手段の選択を検証した証拠ではない**。

S3の第二段階Why「発注に先立って必要な最終判断を確立する」は、なぜ独立した第二段階が必要かを確認せず、必要な仕事であるように表す危険もある。単に手段語を除くことでは、候補Activityそのものの存在前提は解消しない。

## 元の比較との関係

変更背景を質問したケース数は、対象のS2/S3に限るとControl 0/2、A 0/2、B 2/2、C 2/2、純粋Why 0/2。これは選ばれた応答の記述で、成功率や効果量の推定ではない。全armで明示的な合意済みへの誤昇格は観測していない。

純粋WhyのS2はCSVの確定手順を避けており、Control/Aの草案と完全に同じではない。この差を消して「全て同じ失敗」としない。一方、S3の二段階草案と両ケースで背景を尋ねない点は、Why品質だけでは今回の入口目的を満たさなかった根拠になる。

B/Cの成功を全て入口規則の因果効果と断定はできない。各セル1回、バッチ内の文脈共有、armの文字量差、追加実行の時点差が残る。後続対話、候補比較の公平さ、実装、実クライアントrouting、人間の時間や意思決定は測定していない。

## 証跡監査

元の独立監査者が[補足rawも別ファイルで監査](audit.md)した。調査者の結論は渡さず、Why-onlyという指示上の区別と、S2/S3で背景確認がなかったという主所見を確認した。同じ監査contextの継続であり、新しいFresh効果試験ではない。監査の具体的な引用とS4の合意停止条件はrawへ戻って確認した。

## 負担と終了判断

[実行記録](run.json)は公開用の実験指示、要求model/effort、入力版、SHA-256、入出力bytes、観測経過秒を保存する。省略範囲は[公開情報の訂正](../PUBLICATION-CORRECTION.md)を参照する。課金・token数・実効runtimeは不明。質問の主な意図はS2で「入力経路」「部分成立」、S3で「判断者・兼務」「最終承認・却下結果」であり、数が少ないことを品質としない。S4の余分な合意停止条件も懸念として残す。

この一回で純粋Whyを観測していなかった欠落を補った。追加の反復で好ましい答えを探さず終了する。元の研究提案は、既存Authoring入口に背景確認を短く置き、既存Draft / unconfirmedとOptimizationの責務を使うこと。採用・正式Skillへの反映・実効果は引き続き別Phaseである。
