# 解決策型要求の入口：背景確認前の草案固定を防ぐ

## 結論

**現行のDraft / unconfirmedは合意の誤認を防いだが、解決策への早期固定は防がなかった。** ControlはCSVと二段階承認を未合意の草案と明記しながら、変更の背景を尋ねず、その手段の登録単位・承認者・成立条件へ進んだ。今回再現したのは「AIが合意済みと偽ること」ではなく、**未採用の手段を草案と質問の前提にすること**である。

研究上の提案は、**既存のAuthoring入口へ短い背景確認を足し、既存Draft / unconfirmedを維持すること**。新しい「仮業務」成果物・状態や専用Skillを増やす根拠はない。Whyの目的記述は補助になるが、良いWhyがあるだけでは変更手段の選択理由は分からない。候補比較が必要になった段階では既存のOptimization Reviewへ渡す。

[純粋Whyだけを追加した補足比較](pure-why/RESULT.md)でも、S2/S3の変更背景は質問されなかった。S3では二段階の草案へ進んだ。元のBに含まれる入口停止規則との区別を、この追加1contextで確認した。

これは未採用の提案である。製品Skill・正式guidanceを変更していない。下記の短縮案・組み合わせをそのまま実測したわけではなく、**試したB/Cの振る舞いと既存責務を合わせた最小変更案**として人間の採否へ返す。

## 比較したもの

- Control：main `a971d60bb64fbc048a871d70dda277c93b680288` のAuthoring Skill、Optimization Skill、同梱authority、記述品質・構造guidance。両Skillのbundled authority元版は `9d67d886de8317ad4d884ba8e06c356b44370c9a`。moving mainで置き換えない。
- A：現行合意と未採用案をDraft / unconfirmedで明示的に分ける。
- B：手段を外しても成立するWhyを確認し、目的・背景が不足する既存業務変更を確定せず質問する。
- C：未採用の解決策型要求を入口で識別し、現在業務・Problem / 意図・採否状態を確かめてから既存の工程へ渡す。

[6ケース](cases.md)は合成入力。S1はProblem起点、S2はCSVのみ、S3は二段階承認のみ、S4は新規業務の明示決定、S5は合意済み実装、S6は外部I/Fで固定された手段。[入力・protocol](protocol.md)を公開commit `96056c2341a1e905951be7cf2c967e58a037c8c1` へ先に固定し、4ファイルをSHA指定で再取得・一致確認してから実行した。[raw](raw/control.md)は公開commit `a3aa24f72f3fe3d37885015be6f64c26f5b35147` に保存した。[公開用の実験指示・metadata](runs.json)は、実験外の実行情報を省き、パスと識別子を中立な表記へ置き換えたもの。完全な実行promptではない。訂正範囲は[公開情報の訂正記録](PUBLICATION-CORRECTION.md)を参照する。

要求設定は各armとも `gpt-6-sol` / `medium` / `fork_turns: none`。元の比較の独立開始は4 contextsであり、各context内で同順序の6ケースを処理した。補足の純粋Whyを含む実行総数は5 contexts・30応答だが、事後追加であり同時の5arm試験ではない。**24独立試行ではない**。実効model・effort、内部routing、token使用量、課金は独立に確認できない。これは提供テキストを読ませた初回応答比較で、installed pluginの自動routingや対話完了、実装、実利用の試験ではない。

## 何が再現したか

- Control S2：「CSV一括登録を追加した変更後の業務設計の草案」「CSV一括登録を追加する予定」と書き、質問は照合と一部失敗時の成立単位へ進んだ。Whyは「サービス手配に進められる受付を確定する」で自然だが、**なぜ手入力からCSVへ変えるか**は未確認。
- Control S3：「購買申請を二段階で承認する」をActivityに置き、Whoと承認結果を質問した。Whyは「発注してよい申請を判断する」。これも現行一段階業務の目的として成立し、二段階化の背景を識別しない。
- A S2は「現行設計を置き換えません」と言う一方で、Procedureを「CSV一括登録を用いて」にした。A S3も未確認と明記しつつ段階別Activityへ展開した。**authority区別と前提探索は別の性質**だった。
- B S2は「現行業務で何を変えるためのものか」が不明として目的を質問し、S3も「二段階にする目的」を確認した。新フローの草案は先に作らない。ただし目的への返答前に登録単位・段階別結果の質問も載せている。
- C S2/S3は対象現業務を述べ、手段を案として保持し、目的と採否状態を聞いた。S3の段階別質問は「採用済みなら」と条件化した。Cが一番よい回答や低負荷を生むことまでは確認していない。

根拠：[Control](raw/control.md)、[A](raw/A.md)、[B](raw/B.md)、[C](raw/C.md)。各セルの判断と質問意図は[観測記録](observations.json)に分けて残す。

## A / B / Cの採否に向けた判断

### A：既存の表現を使う。独立した新制度にはしない

Draft / unconfirmedと現行合意の区別は必要で、現行Controlにも既にある。今回Aを追加しても、解決策を先に詳しくする挙動は残った。新しい仮業務台帳、別の承認状態、二重のSSOTは未検証であり、今回の目的には不要な保守面を増やす。**既存の区別は維持、Aだけで入口問題を解決する案は採らない**。

### B：Whyの文章品質だけでは足りない

現行の「手配できる受付を確定する」「発注可否を判断する」は手段に依存しない目的だが、CSVや二段階に変える理由を含まない。よいActivity目的と、変更案の背景の理解は一致しない。

一方、今回のBは単にWhyを推敲する指示ではない。**背景が不足する変更を確定せず質問する停止規則を含む**。Bの2件の改善を「Why欄だけで十分」の証拠にしてはいけない。この停止規則はCの入口原則と重なり、B対Cは純粋な構成要素の切り分けではない。そこで追加の1contextに、入口停止規則を含まない純粋Why指示を同じ6ケースで与えた。S2/S3は手段に依存しないWhyを書いたが、変更背景は質問せず、S3は二段階を草案化した。この限定条件ではWhy記述品質だけで十分とは判断しない。Whyの検査は補助として残し、Problemを捏造したり「なぜ」を反復する儀式にしない。

### C：独立Skillより既存Authoring入口の短い原則として提案

Cは不足が現れる地点に合う。Authoringが依頼文を材料へ変換する前に、**既存業務への検討中の手段なのか、責任者の確定決定なのか**を区別できる。現行Optimizationは具体的なProblemと対象業務を必要とするため、CSVという言葉だけでOptimizationへ自動転送してはならない。

- Authoring入口：手段の候補性、対象の現行業務、足りない背景を確認する。正当な新規決定・既合意・固定制約はそのまま進める。
- Why / 記述品質：目的と手段を区別する。変更の背景が分からないことを、既存業務の自然なWhyで隠さない。
- Optimization：現行業務と具体的Problem / Painが揃い、比較が有用な場合に既存のread-onlyレビューを使う。人間が採否を決める。
- Authoring改訂：採用された業務上の意味を記述・確認する。候補を合意済みにしない。

**C中心の最小統合案を採否に出すが、現行C paragraph自体をそのまま採用することは求めない。** Bの有効部分とCの責務境界を一箇所へ置き、規則を二重化しない。

## 最小変更案（未採用・未実装）

Authoring Step 2の「明示された事実と未決の意味を分ける」箇所へ、次の趣旨を追加する。正式authority側へ一つの原則を置き、Skillはその参照と実行順を担う。

> 既存業務への変更が機能・手段・新フローだけで提示された場合、責任者による採用済み判断や固定制約が明示されていなければ、有力な解決案として保持する。対象の現行業務と変更で達成したい状態・実際のProblemが分からないときは、案を詳しい変更要件へ展開する前に、その選択を変え得る背景を短く確認する。既存ActivityのWhyを言い換えるだけで背景確認の代わりにしない。具体的Problem / Painが揃い比較が必要なら既存Optimizationへ進み、採否後に業務設計を改訂する。明示的新規業務決定、合意済み意味の実装、外部制約で確定した手段は再正当化させず、残る具体的な意味の未決・矛盾だけを扱う。

新しい必須欄・成果物・全件チェックリスト・毎回の採用状況質問は追加しない。文脈が採用済みと示している場合は再質問しない。「変更理由が説明されていない」ことと「変更決定がない」ことも同一視しない。

短縮文はこの研究の分析的成果であり、4armのどれかと同一ではない。人間が採用を選ぶ場合の後続Phaseで、正式guidance・Skillへの配置と相互参照を実装し、その差分にだけ必要な確認を行う。元4armを再試行せず、Why-onlyの成分を観測する1contextだけ追加した。総当たりや好ましい結果を求める反復は行わない。

## 負担、反例、限界

- S2/S3でB/Cは背景確認を増やした。これを自動的な負担削減と呼ばない。Bは目的確認と解決策後の質問を混ぜ、Cには曖昧な全要求へ機械的に採否状態を尋ねる危険が残る。C S5の「agreed-7の実体」要求も、合意内容が十分に提示された合成ケースでは余分な戻しになり得る。実装時の原典照合の有用性とは区別する。今回の明示的S4–S6ではその差戻しは観測しなかっただけ。
- 新しい入口管理用の恒久成果物・ライフサイクル状態は4armとも要求しなかった。一方、独立監査はC S6の草案が「送付した結果を記録する」手順と「送付・受領記録」を追加した点を指摘した。受領証を送付結果へ対応づける元の意味から、別の送付記録を当然の義務へ強めてよいとは限らない。未採用草案中の追加記述であり、自動承認ではないが、「Cに副作用なし」とは評価しない。S4の資料状態・記録のモデル化にも未決の表現選択がある。全草案の完全性・業務上の承認は未検証。
- ケースは同じ調査者が目的に合わせて作った。S4–S6は例外条件を明示しており、実際の曖昧な会話より容易。各armは一度だけ、同じ6件のバッチなので順序・文脈持越し・確率変動・出力量差を分離できない。rawの手段名が前のケースへ出たことだけでは事実持越しと断定しない。
- A/B/Cは文字量が違い、BとCは背景不足時の停止と例外規則を共有する。純粋Whyは補足の単回応答を観測したが、各成分や組み合わせの因果効果は未測定。Cの優越・無害性・必要質問数の最適性は主張しない。
- 初回応答のみ。依頼者案が後続の比較で公平に扱われるか、質問へ答えられない場合にどう止まるか、背景確認後の採用、実装可能性、実際の人間負荷、効果は未確認。
- 出典は9ファイル・133,132 bytesの配布packetで、実際に読む範囲はSkill指定による。[費用代理値](costs.json)は追加指示bytes、応答bytes、観測経過秒を記録する。出力長や経過時間は説明的な代理値で、課金や読解負荷ではない。
- 公開repoのcommit/filesはGitHub connectorで再取得済み。匿名Web取得の追加確認はcache missで成功せず、独立した匿名取得の成功までは主張しない。
- 先行#47のqualitative記録は開始前に確認した。Research Decision Index全体と#49のbehavioral記録の確認は比較開始後だった。これは研究運用上の順序逸脱として残す。#49は合意された技術手段の早期トレードオフ通知を対象にし、今回の未採用業務案の入口とは異なるが、「質問の追加・早期化だけで効用としない」という限界を引き継ぐ。既存試行の主張は変更しない。

## 関連する既存知見と責務

[Authoring](../../plugins/alder/skills/alder-draft-business-design/SKILL.md)は草案と合意を分け、未決を質問し、Optimizationを同時実行しない。[Optimization](../../plugins/alder/skills/alder-optimize-business/SKILL.md)は現行業務・具体的Problemを入口に未採用候補を返す。今回の提案はその境界での入口処理を補うもので、Review knowledgeや実装時の一般的な要求再審査を広げない。

先行の[#47](../../docs/requested-means/results.md)と[#49](../../docs/means-behavior/results.md)は技術手段の変更提案を恒久化しなかった。その結論を覆す研究ではない。今回も実装済み・合意済みの手段に単なる好みで別案を強制する根拠はない。

## 独立監査

[監査記録](audit.md)は同じ要求model / effort、履歴なしの別contextで作成した。調査者のRESULTや先行結論は渡さず、ケース・protocol・全arm raw・必要な固定sourceを読ませた。明示的な誤承認は未再現、Control/Aの早期固定、B/Cの背景確認という主所見は一致した。C S5/S6の余分な要求・記録候補を限界へ追加した。これは非盲検の証跡監査で、第二の効果試験ではない。調査者がC S6の引用を再確認するよう求め、監査者は最終rawに実在すると確認した。最終rawと公開manifestの一致を保ち、都合のよい応答への置換はしていない。要求promptと追確認は[監査条件](audit-run.json)に残す。
