## Primary observations

* **No explicit false promotion to agreed requirement in S2/S3, in any arm.** Control S2 says `変更はまだ合意済みと扱いません`; Control S3 likewise says `二段階承認はまだ合意済みとは扱いません`. A marks `草案・未確認`; B omits the changed activity and explicitly says it is not agreed; C calls each change a candidate and asks first. Therefore an alleged Control failure of outright approval was **not reproduced**. A Draft label does not itself settle the separate anchoring question.
* **Candidate-first anchoring is observable despite draft caveats in Control and A.** Control S2 offers a `変更後の業務設計の草案` with `CSV一括登録を追加する予定` in Procedure; A S2 goes further with a new Activity `申請を一括で受け付ける` and Procedure `CSV一括登録を用いて受付台帳に申請を登録する`. Neither first establishes a Problem or intended condition for the change. Control S3 drafts `購買申請を二段階で承認する` and Procedure `第一段階と第二段階でそれぞれ承認判断と判断者を申請に記録する`; A S3 drafts first- and second-stage Activities. These remain proposals rather than explicit approvals, but they put the requested means into the reviewable design before its reason or status is established.
* **B and C separate that missing background at intake.** B S2 asks for `現行の1件ずつの入力で実際に困っていること、またはCSVを追加して実現したい業務上の状態`; B S3 asks `二段階にすることで満たしたい業務上の条件`. B drafts only current work. C S2 asks what current reception is meant to improve and whether CSV is adopted or still a candidate; C S3 asks the same two kinds of questions for two-stage approval. This is a visible difference in first-response behavior, not evidence that an actual user would answer or choose differently.
* **Candidate preservation and useful comparison:** C explicitly calls CSV `有力な変更案` (S2), and retains two-stage approval as a change candidate (S3); B S2 calls CSV a `変更手段` but does not offer future comparison as explicitly. Control and A preserve the means by drafting it; they do not erase it. In S1, where a concrete High-pain Problem exists, all arms route to read-only Optimization and preserve human adoption. Control offers one automate-transcription candidate; A and B each offer two variants, the second extending toward automated matching/exception handling; C offers one candidate and explicitly keeps CSV as a possible implementation means rather than assuming it. Candidate count by itself is not quality or outcome evidence.
* **Human proposal/decision boundary survives in all arms.** For example, Control S1 asks the responsible person to choose `採用、修正、保留、却下`; A S1 says its alternatives are `未承認`; B S1 says `現時点ではどちらも採用しません`; C S1 waits for the responsible person's adoption decision. S2/S3 Control/A request later confirmation of drafts rather than claiming adoption. B/C defer the changed design until background/status is clear.

## Legitimate-decision controls and questions

* **S4 new business:** All four arms produce a reviewable lending draft based on the responsible person's explicit decision and leave post-return re-lending undecided. Control S4 says `再貸出可否はご指定どおり未決` and does not re-ask it; A/B/C behave similarly. None forces a pre-existing Problem or alternative search. Additional questions about the eventual re-lending condition or record mechanics are framed as deferred unknowns rather than immediate blockers. Several drafts introduce an explicit loan-status representation (`貸出中`) or a separate availability record; this is consistent with preventing lending while out, but its exact maintained form was not given, so it remains a design choice to verify, not a proven business requirement.
* **S5 agreed implementation:** Every arm directs the request to implementation rather than Optimization or a new business decision. Control S5 says `合意済みの判断をもう一度業務承認にかける必要はありません`; B S5 likewise does not re-ask the purpose or CSV choice. Requests for a repository/work environment are operationally necessary to actually implement. C S5 additionally requests `agreed-7 の実体`; the case already supplied the agreed meaning, so asking for the document as a prerequisite to even start is a possible redundant return in this synthetic setting, though seeing the authoritative file could be useful during implementation. No implementation occurred under the protocol.
* **S6 fixed external constraint:** All four keep the established reconciliation purpose and use CSV without requiring a fresh Problem, alternatives, or adoption vote. Control S6 says API/manual routes are already excluded; C S6 says `CSV採用の再判断は行いません`. Asking for schema and transport settings is deferred to technical requirements, as the case directs. Control S6 and A/B/C mention review of a revised excerpt; that is ordinary draft review, not automatically reopening the stated manager decision. In C S6's *sending* Activity, the draft Procedure says `送付した結果を記録する`, and its Output says `送付・受領記録へ送付した結果`; a separate *receipt* Activity records the returned receipt against that sent result. The input calls for recording the returned receipt against sent results, but does not explicitly call for a separate at-send recording step or combined `送付・受領記録` Object. Thus the draft may add a maintained step/representation; it does **not** establish that the arm treated a new send log as an already adopted or mandatory business requirement. That distinction would need clarification before incorporation into an agreed design. A and B S6 use `受領確認を待つ状態`, which can describe the process without proving a newly maintained state.
* **Questions and returns:** Control S2 asks about matching/completion and file failure; Control S3 asks roles, rejection routing, and release conditions. Those are meaningful downstream design questions, but neither asks the missing background that could change the means. A S2 likewise spends three questions on CSV source, matching, and failure policy; A S3 on stage mechanics, without first eliciting the reason for the change or decision status. B S2 asks background and matching now, and flags failure-unit treatment for later; B S3 asks purpose and stage mechanics now. C S2/S3 keeps its immediate questions to background and adopted-versus-candidate status, with mechanics contingent on adoption. The latter two avoid some premature detail burden. The case supplies no actual user answers, so necessity can only be judged against the information given and possible next decision, not measured interaction cost. Counts of question marks would be misleading; these are grouped question intents.

## Limits and interpretation

The design has four independently started contexts, **not 24 independent observations**: each arm answers S1–S6 in one fixed-order batch. Within-batch carryover and order effects remain possible despite instructions to keep cases separate. The cases were investigator-designed and may favor the anticipated distinction; this is one sampled first response per cell. Longer or more explicit treatments, response length, and the shared dispatch wrapper may influence behavior; the raw responses do not isolate wording mechanisms. Model `gpt-6-sol` and `medium` are requested in the run manifest but effective runtime is not independently attested; token and billing cost are unavailable. The manifest records source and input revisions, raw hashes and bytes, and timestamps, but some completion timestamps are null. The source packet was explicitly provided, so the result cannot establish automatic skill routing, installed plugin behavior, production adherence, or human decision quality. No external actions, documents, or code were changed in the cases. Most importantly, this comparison supports a narrower claim: B/C visibly check missing background before drafting S2/S3, while Control/A anchor the candidate in a clearly unapproved draft; it does **not** show Control falsely asserting that the proposal was already agreed.
