# Scope・5W1H分解の現行baseline

## 結論

この小さな現状確認では、**草案作成でのScopeへの手順混入と、品質レビューでの誤分解の見逃しを、別の入力・contextで観測した。** 名前の読みやすさだけの問題には縮めない。

- 草案A：条件登録と定時の一覧作成を分け、Scope・What・When・Howを今回の意味上の期待に沿って記述した。
- 草案B：What / Whenは分離したが、文書Scopeへ複写の具体条件、表紙付与、受取棚への配置、台帳記録まで再掲した。
- Aの1回改稿：並び順に関係するProcedureとOutputの2箇所だけを変更し、Scope・名前・開始条件・未決を保持した。
- 独立した品質レビュー：固定Case 1のScopeへの手順混入と、Whatへの開始条件混入を両方検出せず、「両Caseとも修正を要する指摘はありません」と返した。別題材の正常Case 2は保持した。

これは2草案・1小改稿・独立2文書のreview各1回の観測である。作成のWhat/When混同は今回再現していないが、作成側に問題がないという結論にはならない。新candidateや修正後比較は実施していない。

## 工程別の根拠

### A：条件登録と定時一覧作成

[入力](authoring/a.txt)は、設定保存直後には一覧を作らず、別の自動担当が毎朝7時に保存条件と在庫台帳から一覧を作ると指定している。

[初稿](runs/authoring-a/draft-initial.md)のScopeは「条件の登録と不足一覧の作成まで」と、在庫更新・発注が対象外であることを示す。対象倉庫、抽出判定、整列、保存の全手順をScopeに再掲していない。仕事名は「一覧作成条件を登録する」「不足一覧を作成する」で、導入・見直しと毎朝7時はそれぞれWhenにある。保存直後には作成しないこと、台帳の範囲外管理、必要な一覧項目、保存期間未決も残った。

[改稿依頼](authoring/a-change.txt)は商品名順から商品コード順への変更だけである。[改稿版](runs/authoring-a/draft-revised.md)との差分はProcedureとOutputの並び順2箇所だけで、元の初稿・初回返答のSHA-256が改稿前の値から不変であることを確認した。商品名という出力項目は削除されていない。

この結果は小変更の保持に限る。全体の作り直しや複雑な追加要求への改稿でも分解が安定することは示していない。また、今回の主要判定はScope / What / Why / When / Howと明示要求の保持であり、すべてのI/O表現やロール名が唯一の適切な表現であるとは評価していない。

### B：複写物の準備

[入力](authoring/b.txt)は複写と受取棚への準備を対象に、受付・承認・引渡しを外側に置いている。[初稿](runs/authoring-b/draft-initial.md)は、What「教材を複写して準備する」、When「承認された申込票と原本が揃ったとき」、Howの複写・表紙・棚・台帳の手順を記述し、判読不能時の扱いを未確認に残した。

一方、Scopeに「指定ページを指定部数だけ複写し、申込番号付き表紙を各部に付けて…作業台帳に準備完了を記録するまで」と、具体的な操作列をほぼ再掲した。問題は文字数ではなく、**対象・境界を示す欄へHowの細部が集積したこと**である。受付・承認と引渡しを除く境界は必要で、短くするために消してよい意味ではない。

元要求の事実自体は主に保持されている。したがって、これは意味を落としたことと、情報を適切な欄へ割り当てなかったことを分けて評価すべき例である。

### 品質レビュー：固定入力

[review入力](review/designs.md)のCase 1では、Scopeの中に読取・部署台帳との照合・集約・整列・保存が含まれ、同じ操作がProcedureにもある。What「到着明細受領後の配布リスト作成」の前半は、その仕事を始める条件であり、Whenにも記されている。Scopeは境界を示し、開始条件はWhenへ保持し、操作はHowへ委ねるという役割の確認が対象だった。

[実際の回答](runs/review/final-response.txt)は、入出力と手順と結果のつながり、不要な分割がないことを根拠に、両Caseとも修正不要とした。**Scope / Whatの割当について必要な2所見はなかった。** 情報が失われず業務としてつながることの確認が、適切な欄へ配置されたことの確認を代替していた、と出力上は整理できる。モデル内部の原因は断定しない。

Case 2のScopeにある特別展開催期間・他館からの借用・展示中という条件は対象境界であり、Whatの「展示中の借用資料」は点検対象を区別する。reviewerはこれらを不要な時間語として削除せず、保存期間も未決のまま保った。正常対照の保持と、不良Caseの未検出は分けて記録する。

## 最小修正案：まだ未実装

責任を生成またはreviewのどちらか一方へ寄せず、既存の共有定義と各工程の確認へ分ける。

1. **共有定義：文書構造guide**
   文書全体のScope（対象・境界）とObject / ActivityのScope値（管理責任）を明示的に区別する。Scopeで操作を再説明せず、必要な詳細をHow等へ保持することを具体化する。Whatは行為・仕事の識別、Whenは開始条件という既存定義を、必要な対象修飾との境界も含めて使えるようにする。文字数や時間語禁止を新規規則にしない。
2. **authoring / 改稿の最終確認**
   元要求の事実を保持したかに加え、Scopeの文が対象・境界を表すか、手順や開始条件をそこへ詰め込んでいないかを確認する。既存のSkill最終確認から共有guideの割当原則を適用する最小変更を検討する。今回Aで混同が再現しなかったWhatを、生成側の確定故障として扱わない。
3. **quality reviewの観点**
   現行品質表の「欄の役割」はWhy / When / Output / Resultを列挙し、「用語と範囲」のScopeは管理責任を問う。ここへ**文書Scopeの役割とWhat / Whenの割当**を、入出力の整合とは別の確認として接続する。業務の事実として整合していても、欄が過剰な詳細を抱えている所見を返せることを検証する。

定義のSSOTは正式guideに置き、同じ説明をSkillやrootへ複製しない。必須の新しいユーザー向け表・成果物は追加しない。提案の効果は未検証であり、ここでcandidateを作ったことにはしない。

## 限界・返却

入力2題は短く、review文書も小さい。既存の実案件や長い改稿の失敗を完全に再現するものではない。source-factの保持と欄の割当は定性的に、事前固定した期待に照らして評価した。文字列一致、文字数、指摘総数、一般的な成功率へ置き換えていない。

このbaselineは既存PR179の結果を変更せず、現行main起点の別branchに証跡だけを保存した。コード・Skill・guide・配布物は変更していない。追加試行、修正後比較、merge、release、installed更新は行わず、観測と上記の最小案を親Chatへ返す。
