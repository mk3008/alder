# 事前期待：小規模な5W1H分解の現状確認

このファイルは生成・改稿・レビューの実行者には渡さない。実行前に作成した、完全合成入力の事実と意味上の期待を記録する。候補guideとの比較、改善効果の実証、一般的な性能推定は行わない。各期待は意味で判定し、語句の完全一致、文字数、Activity数、指摘数では採点しない。異なる自然な表現・構成でも、必要な境界、修飾、開始条件、責任、情報の受け渡しと未決が維持されていればよい。

## 共通の確認観点

- 文書Scopeを読めば主要対象と対象外が分かる。手順や並べ方をScopeへ集積していない。必要な対象限定や期間の限定は削らない。
- Whatに相当するActivity名は仕事の行為を示す。開始条件を文章として業務名へ混ぜず、Whenで説明する。対象の種類や状態を区別する修飾を、開始条件と一律に扱わない。
- Whyは仕事の目的、Whenは始める契機、Howは実際のInputから判断・作成・記録を経てOutputまでの手順となる。
- Input/Outputは実際に渡す・読む・書く内容を表す。Object参照を保ち、単に画面・台帳・相手の名前があるだけで未提示の受け渡しを追加しない。
- 与えられた未決を勝手に確定せず、確定済みの事実と区別する。未決を再質問せず保留して草案を返すことは適切である。新たな問題を挙げる場合は、原文の事実と推測を分ける。
- 形式の自己検査は意味の良否を証明しない。今回の観測対象を、未提示の例外や実装方式の網羅性へ拡大しない。

## Authoring A：条件登録と後刻の不足一覧作成

### Source facts

1. 欠品の見落としを防ぐために不足一覧を自動作成することは決定済み。
2. 倉庫担当者は導入時と条件の見直しが決まった時に設定画面を使う。入力は対象倉庫と共通の基準在庫数で、出力は保存済みの条件。
3. 条件を保存した直後には一覧を作らない。集計システムは毎朝7時に仕事を始める。
4. 自動集計で実際に読むものは保存済み条件と在庫台帳。台帳の管理は別業務。
5. 対象倉庫のうち基準在庫数を下回る商品について、コード・商品名・在庫数を商品名順の不足一覧にして社内の一覧保管先へ保存する。
6. 対象は条件登録と不足一覧作成。在庫更新と商品発注は対象外。
7. 一覧の保存日数は明示未決。

### 正しい役割と変えない意味

- Scopeは条件登録と不足一覧作成の境界が端的に分かればよい。時刻、抽出判定、項目、並び順、保存手順をすべてScopeに再掲しない。
- Whatは、たとえば条件を登録する仕事と不足一覧を作成する仕事。具体的な名称や一律の分割数を指定しないが、設定者による今の操作と自動担当による後刻の開始を混同しない。
- 条件登録のWhenは導入・見直し決定、自動作成のWhenは毎朝7時。保存操作を自動作成の開始条件にしない。
- Howには画面での入力・保存、保存条件と在庫台帳の読取、対象倉庫と基準による抽出、商品名順への整列、一覧保存が残る。
- 条件保存が可能にするのは後の定時集計。保存直後の生成、台帳更新、発注、外部への送信を追加しない。
- 倉庫担当者と集計システムの責任、在庫台帳の範囲外管理、一覧の実際の情報が残る。
- 保存期間を勝手に決めず、未決として残す。基準値、ゼロ件時や実装方式等の未提示詳細を確定事項にしない。

## Authoring Aの1回改稿：整列順の変更

### Source facts

- 変更は不足一覧の整列順だけ。商品名順から商品コード順へ変更し、ほかの条件は維持する。

### 正しい役割と変えない意味

- 既存草案の整列手順とそれに依存する説明を矛盾なく更新する。並び順は主にHowの処理条件であり、Whatや開始時刻へ変質させない。
- 出力項目の「コード・商品名・在庫数」はそのまま。商品名を出力から削除する変更ではない。
- 対象倉庫、基準未満という抽出、共通の基準在庫数、倉庫担当者と集計システムの役割、設定契機、毎朝7時、保存直後には作らないこと、社内保管、対象外業務と保存期間未決を維持する。
- 変更に関係しない業務名・Scopeなどを全面的に再設計しなくてよい。不正確な説明の修正は許容するが、原文にない業務判断を追加しない。

## Authoring B：研修教材の複写準備

### Source facts

1. 目的は社内研修で使う人数分の教材を揃えること。
2. 複写担当が、承認済み申込票と社内教材原本の両方を受け取った時に始める。片方だけの到着を開始条件にしない。
3. 申込票から申込番号・指定ページ・部数を読み、原本の指定ページを複写する。
4. 申込番号を記した表紙を各部に付け、完成一式を資料室の受取棚へ置く。
5. 作業台帳に申込番号・部数・準備完了を記録する。
6. 対象は受領後の複写と受取棚への準備まで。申込の受付・承認と完成品の引渡しは別業務。
7. 原本に読めないページがある場合の扱いは明示未決。

### 正しい役割と変えない意味

- Scopeは複写準備とその前後の業務境界を示す。指定ページの確認、表紙付与、台帳記録などの手順をすべてScopeへ寄せない。
- Whatは複写物・研修教材を準備する等の行為。承認済みであることや両入力が揃うことを長い開始文として業務名に混ぜない。
- Whenは承認済み申込票と原本が揃った時。Why、When、Howを相互に置換しない。
- 実際のInputは申込票と原本。複写物の受取棚への準備と作業台帳への記録の両方を表し、完成品を申込者へ引き渡した結果に強めない。
- 原本の判読不能時に、独断の推測補完、申込取消、自動差戻し等を決定済みにしない。未決が残っていても既知の正常手順は記述できる。

## Review Case 1：社内便の配布リスト

### Source factsと観測したい箇所

- 対象は本社宛て社内便の配布リスト作成。社外郵便と実物の配達は範囲外。
- 確定した到着明細を受け取るのが開始契機。配布担当は封筒番号と部署コードを読み、総務管理の部署台帳から部署名を照合する。
- 部署コードごとにまとめ、部署コード順、同じ部署内は封筒番号順に整え、物流室のリスト保管先へ保存する。
- すべての対象部署コードが台帳登録済みという前提がある。保存期間は未決。
- 文書Scopeの第2・第3文は、範囲の限定ではなく入力の読取、照合、集約、整列、保存というProcedureの反復になっている。
- Activity名の「到着明細受領後の」は開始条件を表し、すでにWhenに書かれた内容である。

### 期待

- Scopeの問題を単に「長い」とせず、境界説明と処理手順の役割混入として認識する。
- Activity名に含まれる開始条件とWhatの役割の違いを認識し、開始条件をWhenに保ちながら行為を業務名で識別できるようにする方向を示す。
- 二つの問題を別々に述べても一つの記述整理として述べてもよい。実際に両方を識別したかを確認する。
- 手順、入力・出力、担当、場所、対象外、登録済み前提、保存期間未決を消さない。発見を業務上の誤動作や合意済みの変更と誤認しない。

### 非提示の修正文例

Scope：本社宛て社内便の配布リスト作成を対象とする。社外郵便と実物の配達は対象外とする。

Activity名：配布リストを作る。

When：集荷担当が確定した到着明細を受け取ったとき。

Procedure：既存の読取、台帳照合、部署別集約、部署コード順・封筒番号順への整列、保存の手順を維持する。

これは一例であり、この文面への一致は求めない。

## Review Case 2：展示中の借用資料

### Source factsと観測したい箇所

- 対象は特別展開催期間中に展示している他館からの借用資料の状態点検と記録。自館収蔵品、展示前後の検品、修復、貸借契約変更は範囲外。
- 開始契機は毎日の開館前点検の開始時刻。展示担当者が会場で、借用資料台帳の資料番号・展示場所・展示開始時の状態写真を使って現物の状態を確認する。
- 変化の有無にかかわらず、資料番号・点検日・観察状態・写真との差異を点検簿に記録する。資料管理担当の後続判断で参照可能になる。
- 保存期間は未決。
- Scopeの開催期間と展示状態は業務の境界であり、実行手順ではない。
- Whatの「展示中の借用資料」は点検対象の状態と種類を区別する修飾であり、「開館前点検の開始時刻になったら」という開始条件ではない。

### 期待

- このScopeやActivity名を、長さや「展示中」という時間に関わる語だけを理由に不良扱いしない。
- 語句を整理する場合も、特別展・他館借用・展示中・期間内という対象限定と対象外を失わない。
- 「資料を点検する」とだけ残して自館収蔵品や展示前後の検品まで含むように読ませたり、「展示を開始した時」をWhenにして日々の開館前点検を変更したりしない。
- 明示未決の保存期間について触れることは許容するが、それをScope/Whatの混入検出として数えない。その他の妥当な問いがある場合も、この対照の狙いとは分ける。
- 既存表現の維持、または必要修飾を残す別表現を許容する。指摘を無理に作らず「この観点では問題なし」とすることも適切。

## 読み分けと観測の限界

- authoring/a.txt と b.txt は、正解の欄割当や修正文例を含まない自然な要求説明である。a-change.txt はAの初稿と同じ生成contextで一度だけ使う。
- review/designs.md は独立した2文書をCase単位で同梱したもの。それぞれ元要求、独立したScope、Object群、Activityを持ち、相互参照しない。ファイル全体を一つの業務設計書として扱わない。
- reviewの入力には不良／正常のラベル、問題の指示、採点基準、上記の修正文例を含めない。
- この2題・1改稿・2レビューだけでは、反復時の安定性、実案件への汎化、candidateによる改善を主張できない。今回の判断は、各ケースで役割混入や意味の保持がどう現れたかに限定する。
