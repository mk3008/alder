# 初回 Business Design 草案の評価（Execution #172）

## 結論

この１件の架空発言録（T001–T072）では、草案は業務の中核である「予約した型・台数の確保 → 個体の準備・貸出し → 店での返却受領 → 倉庫での機材別検収 → 確認済み料金の経理への引渡し」を概ね発言根拠に沿って再構成した。とくに、返却を受け取っただけでは再貸出し不可という訂正・合意（T028, T030, T069–T070）を `raw/draft.md` L3, L464–556 で保った。４活動の評価参照を11活動に分けたこと自体は減点しない。初回草案として人が確認できるが、業務承認済みとは扱えない。

重大な境界の取り違えや、根拠ある中核工程の丸ごとの欠落は見つからなかった。最も重要な創作は、予約番号と請求先の**記録先を予約表と特定**したこと（L45–46, L178, L628）。T008 は予約表の既知の欄を述べ、T068 はそれらの情報が必要なことを述べるが、保存先は述べていない。人の確認前にデータ項目の配置を実装条件へ昇格させないことが必要である。

## 根拠と品質

- `verify_evidence.py` の全チェックは通過した。入力・出力ハッシュ、72発言、118個の一意なオラクルID、許可された helper 経由の読込、入力凍結が整合する。`raw/output-freeze.json` は `2026-10-06T22:33:14.635510Z` に評価前の凍結を記録する。公開の raw commit `ccfced7780b9c67ad51efa1bc015889f573b9e2f`（Draft PR #173）は評価者起動後だが、ローカル凍結の後で同じ raw を公開した。ただし読込ログは他経路の不存在を証明せず、実効モデル・reasoning・全ランタイム文脈の独立証明でもない。
- Who/When/Where/Why/How/Input/Output/Result は、予約、準備、受渡し、返却、検収、計算の各段階でおおむね具体的である。What は独立欄より Activity 名と手順で表現される。物理機材・付属品を独立 Object にしない構成でも、箱、管理番号、黄色い札、修理担当への移動が L397–411, L446–458, L484–552 に残るため妥当な別分解である。
- 主要受渡しは、予約確定→倉庫準備（L178–183→L391）、準備した箱・貸出票→受付照合（L397–411→L439–447）、返却受領→倉庫検収（L496–503→L521–542）、検収済み分→計算担当→経理（L542, L613–645）に追える。準備の Output L404–407 は受付への現物引渡しを明示せず、検収の Output L548–552 は計算担当を明示しない。本文にはあるため、これは独立した業務欠落ではなく欄間の照合しにくさである。
- 同じ予約でも正常に検収された機材だけ料金計算を進める点（T061–T062 → L541–556, L634–645）と、利用者の内訳確認が経理依頼の条件である点（T064–T066 → L635–645）は保持した。修理作業、請求書発行、入金追跡を範囲外に置く L15 も T036/T068 に合う。

## 修正・確認が要る箇所

重複する台帳行は一つの業務命題として統合した。以下は独立した内容単位であり、行数ではない。
