# 発言録から初回Business Design草案を起こす検証

状態: 実行前条件。2026-10-06。Execution: https://github.com/mk3008/alder/issues/172

## 問いと範囲

Alder向けに整理されていない一つの架空相談発言録から、業務境界を含むBusiness Design全体をどこまで発言根拠に沿って草案化できるか。単一の合成ケース・単一の初回出力を対象とする軽量な実践検証であり、統計的な性能比較ではない。

題材は機材レンタル、依頼者は実際の運用知識を持つ架空の担当者、聞き手は通常の力量の設計者とする。両者の発言はAIが一つの対話として生成する。実在人物の録音・実測・ASR出力ではなく、合成対話を入力時のまま保存した「架空発言録」である。役割・規模は研究実行上の仮定であり、能力比較の軸ではない。50–80発言程度を目安とする。

記事構成・執筆・公開、Skill変更、Check生成、最適化案の評価、ASR精度、依頼者や設計者の能力比較、merge、releaseは行わない。

## 事前オラクルと入力の準備

評価側だけで3–4の絡み合う活動について完全な期待BDを定める。Who / When / Where / What / Why / How / Input / Output / Result、Object、受渡し、条件・例外・制約を対象とする。期待BDの各要素へ一意なIDと発言番号、観測可能性を付ける。未発言の設定、訂正前後、提案と採否、合意、矛盾・未決を区別する。

想定分解は唯一の正解ではない。異なる活動名・分解でも、独立した目的・開始・責任・成果と受渡しを保持すれば妥当と評価する。未発言の真実を偶然断定しても成功には数えない。

発言録は話題の戻り・言い直し・具体例・省略を持つ一つの対話とし、活動単位やAlderの欄順に整理しない。出力を見る前に自然さを確認し、修正があれば原版と理由を残してから確定する。初回出力を見た後に入力・オラクルを都合よく変えない。後からオラクルの誤りを発見したら、原本を保持して評価で訂正する。

## 対象版

実際にインストールされているAlder authoring Skillと必須の標準資料をskills.readで取得する。取得内容をrelease `plugin-v0.4.4` / `eb177dab8d30383f0a5e084ad22a8eca59455d27` の同じファイルとバイト単位で比較した。manifestと各digestはprovenance/package-manifest.jsonへ保存する。

- Authoring guidance revision: `02093f4d4e957ae851f7812e958aab3827190f31`
- Business Design structure guidance revision: `9cf192c5bced1eeb872795eec8ced21b7bcbf492`
- 証跡を載せる作業ブランチの起点: main `9cd3d9a3de9a19973af32412e281841fab9f246c`

証跡ブランチの起点は、Skillの版ではない。後続のmain変更を公開済み0.4.4の内容として扱わない。取得・書出し時に末尾改行が一つ増える問題を凍結前に検出し、skills.readの文字列そのものへ戻して全ファイルの一致を再確認した。これは草案化試行ではない。

## 文脈分離

草案化は会話履歴を引き継がない新規native agentで実行する。中立的なタスク名と`/workspace/shared/session-p7/`を使う。入力は発言録、普通の短い草案依頼、固定した標準Skill資料のみ。今回のIssue、計画、期待業務数・名称、オラクル、事前の議論、他研究結果、scenarioを渡さない。

native agentは共有filesystemと共通のツール・カタログを持つため、OSによる強制隔離ではない。提供inputディレクトリ以外の読込み・listing・検索・外部参照を禁止する明示指示を使い、ファイル読込みはopen.py経由でパス・範囲・sha256を記録する。ログは実際にhelper経由で読んだファイルの証拠であり、あらゆる経路の不存在を証明しない。agentの参照申告も別に残す。共通のランタイム指示とツール/Skillカタログは残るため、全contextが発言録とSkillだけになるとは主張しない。保存する完全なプロンプトは実際のtask dispatch全文であり、共通system/developer設定を再現するものではない。今回固有の事前議論と解答情報を履歴forkで渡さないこと、読込対象の限定を検証する。

より強い隔離の実行可能性を業務入力なしで事前確認したが、通常CLIはread-only filesystemで初期化できず、bwrap内CLIはネストしたfilesystem sandbox helperがNETLINK_ROUTE Operation not permittedで起動前に失敗した。ログをprovenanceへ保存する。セキュリティ設定を変更せず、この経路は使用しない。失敗したのはruntimeの起動検査であり、発言録を使ったauthoring runではない。

## 実行と凍結

Fresh authorと別評価者の指定は、repository AGENTS.mdの既定に従い`gpt-6-sol` / `medium` / `fork_turns: none`。指定値、toolによる受理、独立に確認できた実効値を区別し、独立確認できない実効model/reasoningはunknownとする。input/scenario作成側はnative既定モデル（実効値不明）、指定reasoning xhigh。異なるコンテキストでも同系モデルの利用と合成者バイアスは残る。

開始前に完全なdispatch、入力、標準Skill、オラクル、設定、digestを保存し、公開可能な証跡をimmutable commitへ固定する。草案化側にはその研究ディレクトリやcommitの閲覧を許さず、同一バイトの中立ディレクトリだけを渡す。

最初に返された草案と質問を、修正・回答せずにそのまま保存しsha256を固定する。評価者は固定後に初めて出力を読む。原文をより良い草案で上書きしない。今回の権限では質問回答・追加草案化をしない。

## 評価

期待BDの各要素IDについて、発言番号→出力見出し/行→判定を追えるようにする。

1. 根拠のある要素を正しく草案化した: grounded success
2. 入力で確認できない重要要素を不明・要確認とした: uncertainty success
3. 根拠がないことを断定した: unsupported assertion（隠れた真実との一致でも失敗）
4. 根拠のある重要要素を落とした: important omission
5. 入力自体の不足、オラクルの誤り、同等な別分解は別に記録する

境界発見、各BD要素、受渡し・共有資源、発言状態、照合容易性を評価する。重要欠落・創作は具体的な内容単位で数え、同じ欠陥の重複計上を避ける。簡単な総合点で誤りを隠さない。唯一の正解文字列や活動数一致を合格条件にしない。

## 結論の限界と停止条件

一件の合成対話で初回草案化を観測した範囲を超えて一般化しない。実顧客会話への成功率、人間工数削減、モデルや方法の優劣、最適化効果、完全な独立検証は主張しない。草案の業務意味は人間未承認である。

初回出力・別評価・公開安全確認・証跡とhashの照合・振り返り・Issueへの返却が済めば、この実行を終了する。新たな草案化、Skill改修、記事作成やmergeは別判断とする。
