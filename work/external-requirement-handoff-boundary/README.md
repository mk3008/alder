# Business Design外の要求を残す最小の引き渡し境界

2026-10-07。既存の合成発言録を読み直した比較検討。**提案であり、方式の採用、Skill改修、標準ループ変更は行っていない。**

## 結論

要求を残すために仕事を作ってはいけない。発言から分かる業務成立条件は、既存のActivity / Object / Result等の該当箇所へ残す。そこで決まっていない担当・開始条件・情報の受渡しを補わない。業務成立条件としての意味が不明なら、条件自体を失わず、配置・責任の未決を明示する。

BD外に残る条件には、**BDと別の返答部分に、発言箇所、条件・適用範囲、BD外と見た理由、未決事項を短く返す**案を推奨する。継続して検討する場合は、プロダクト側の既存の検討Issueや資料の一か所へ引き渡し、以後はそこを参照する。新しいSR台帳や専用ファイルを毎回作る案ではない。

この候補は業務意味のSSOTでも、確認済みCheckでも、承認済みSystem Requirements（SR）でもない。プロダクト側が妥当性・採否・適用範囲を決め、必要な条件を自分たちのSRとして実装へ渡す。引き渡し先が未定なら「候補を抽出済み、外部引き渡し未完了」と残す。抽出しただけでロスト防止が完了したとは扱わない。

- 現行境界はmainの固定版 `9cd3d9a3de9a19973af32412e281841fab9f246c` で確認した。公開0.4.4で行った初回観測の採点に、後の規則を遡及適用しない。

以下は元入力の意味からの**配置提案**であり、実際の草案修正や依頼者の業務承認ではない。一般的な「非機能」という名前や数値の有無では振り分けない。一つの発言に業務条件・道具条件・未決が混在する場合は、意味の単位で分ける。

### 実装候補と未決

- **実装・方式候補:** [T075–T076][t075]（R063）の二つのクラウドは、設計者の案で、依頼者は「まだ採用は決めません」。費用と営業時間の条件を踏まえた比較の候補にとどめる。必要台数・特定製品・冗長化方式へ昇格させない。[T007–T008][t007]のバーコードも採否未決であり、読取りだけで貸出可にする案は明示的に拒否されている。「候補は全部未決」とまとめて拒否を失わない。
- **境界も未決:** [T042][t042]（R033）は、顧客が触れられるPCで「5分間操作がなければ」非表示・操作不能、再開時に本人確認という具体的条件。顧客に触らせない業務保証と画面保護の条件が混在する。5分が店の運用上の必須基準か、道具の設定目標かは発言だけでは切り分けられない。環境はBDに残し、5分・非表示・操作不能・本人確認を一組の未決境界として外部検討にも見える形で保留する。勝手に一般的な離席注意へ弱めず、受付に横断的保護責任を負わせない。
- **業務判断の未決:** 代理受取 [T028][t028]、遅延確認間隔 T058、料金表の具体額 T060、修理代の負担判断 T062、催促間隔 T064、住所削除 T068、紙処分 T078。BDの関連箇所／未決事項に残す。発言で先送りが明示されており、この比較のために今すべて回答させる必要はない。
- **技術・利用条件の未決:** 電子化範囲 T006、サインイン方式 T040、離席後の本人確認手段 T042、端末版 T018、性能計測 T014/T074、可用性計測 T048、復元依頼者・時点 T052。採否未決と測定条件未決を、要求自体が存在しないことと混同しない。
- **検討の進め方:** T080–T082（R066）の「皆で読んで」「実際の一件と照らす」は草案の確認方法。貸出し業務の新Activityへ入れず、人間未承認・現行と新運用の区別として保つ。

### 返す内容の最小例

形式を標準化する提案ではなく、情報が失われない程度の短さを示す例である。

> 外部検討候補（未承認、BD／Checkの一部ではない）  
> T014・T074：画面化する場合、型・期間入力から空き候補まで普段3秒以内を最大8人同時利用まで含める。電話受付で待たせないための道具の目標。記録件数・年数、「普段」の割合、試験方法は未決。これを受け入れる業務担当・評価結果の保存先は発言から確定しない。  
> 引き渡し先：プロダクト側の既存の技術検討場所へ。まだ場所が決まっていなければ、候補返却済み・引き渡し未完了とする。原文は固定版のT014・T074を参照。

実案件では読める発言資料の版・箇所を添える。引用・意味・訂正・否定・条件を残せばよく、毎回この欄を埋める固定様式や新しいIDは要らない。未決を確定に変える更新は、根拠となる判断を受け取ってから行う。

## 現行Alderとの整合

1. **業務意味のSSOT:** [adoptionの業務品質条件][quality]は、期限、再試行時の不変条件、継続、権限、追跡期間を既存欄へ置く。上のBD配置はこれを維持する。外部候補一覧は業務条件の代替正本にならない。
2. **存在する仕事だけを記述:** [文書構造][structure]と[adoption][adoption]のWhereは業務に影響する環境、I/Oは実際の情報受渡し。要求の存在だけからWhoやOutputは導けない。rawの記録保全（767–814行）、道具評価（816–861行）の受付固定と、準備の予約表Output（251行）は引き継がない。
3. **Checkの導出元を増やさない:** 候補一覧からAlderのCheckを直接作らず、BD→Check→Testの関係を維持する。業務意味と判明した条件だけ、通常のBD更新・合意を経て影響するCheckへ進める。外部候補→Check／Testの新しい対応表は作らない。
4. **SRの責任は外部:** [Alder自身のBD][alder-bd]ではシステム設計と実装はScope=false。候補抽出はプロダクト側のSR作成・妥当性・完全性確認を代行しない。[詳細設計][detail]にある責務を変更しない。
5. **mainのSRレビュー引き渡し:** [adoptionの実装後レビュー][review]では、実装で使用したprovided SRの読める情報源・版・適用範囲を独立レビューへ渡す。候補を返しただけではこの引き渡しを満たさない。SR未提供・読めない部分は未確認であり「制約なし」ではない。候補が正式に採用される場合はプロダクト側の既存の指示・SR・判断記録で明示し、その版を渡す。
6. **衝突・変更:** BDとSRが食い違えば両方を保存し、影響と必要な判断を該当責任者へ返す。無関係な作業は継続する。版・適用範囲の変更は影響範囲を再レビューする。一般NFRチェックリスト、SR Check台帳、新たな人間ゲートは追加しない。

## 未決・限界と次の判断

推奨するのは情報を失わず返す最小境界であり、Authoringの必須出力として採用するかは未決。候補の名称、固定フォーマット、必須保存場所、管理ID、受入確認の制度化は今決めなくてよい。T042等の境界は業務側の意味が分かるまで保留する。

既存の一入力・一初回出力からの再解釈なので、分類の一般的正確さやロスト防止効果は保証しない。原文自体の完全性、要求の妥当性、実現性・費用、システム品質の達成も検証していない。特に候補の抽出漏れは、保存形式を設けるだけでは防げない。

追加PoCは実施しない。将来必要と判断するなら、同じ凍結入力のT014/T074、T042、T052、T068/T070だけを用い、既存BDの意味を守りながら別返答で条件・訂正・未決を残せるかを一度比較する案がある。確認対象は「未根拠なWho / I/Oが増えない」「BDの2年条件が外部へ流出しない」「3秒・8人・30日・5分を勝手に確定／弱化しない」「保存先未定を引き渡し完了と呼ばない」。採用・Skill修正の根拠にするかは、その結果を見た別判断とする。

今回の再確認では、問題を「要求が消えた」に単純化せず、「条件は残るが仕事を創作した」と捉えることが重要だった。対策案も、新しい記録・担当・確認工程を無条件に作らない。既存の境界規則で表せる部分と、今後効果を確認すべき返却案を分けて保存した。
