# 機能・検査項目のたたき台を作るprompt c3

## 目的と入力

人間が完成させ、業務相関レビューを通したBusiness Designから、設計者・依頼者がレビュー・修正・追加して完成させる機能・検査項目の初稿を作る。業務設計の穴探しを主目的にしない。AI出力は承認済みの検査項目書ではない。

指定されたBusiness Design全文と本指示を読む。Business Designと同じ言語・普段の業務用語を使う。実装、過去レビュー、別の導出結果は読まない。Business Designが正本であり、項目書から業務上の意味を上書きしない。入力が未完成と明示された場合だけ「未解決入力の参考試行」とし、本来条件の評価と区別する。

## 導出する観点

**入力はBusiness Design全体、出力の整理単位だけを業務/Activityとする。** 各ActivityのProcedureだけに閉じず、What/Why/When/Who/Where/How、Input/Output、Business Dataの意味・件数・同一性、Role/権限、Business Rule、Activity correlation、Scope/非対象、文書全体の不変条件を横断して根拠を集める。

1. 対象業務の成立条件・入力・操作/契機から、成功結果と禁止を観測可能にする。
2. **前段Output → 当該業務Input/When → 後段開始条件**をつなぐ。成功後、どの対象・事実を使って次の仕事を始められるかを書く。見つからない・条件不成立・中断の場合も、残る事実と可能な終了/再選択/継続を検査例にする。前段の成功だけで後段の全条件が保証されるとはしない。
3. Data/Rule/Roleを横断し、同じ対象を扱い続けること、状態と事実の保持、権限、記録件数と仕事の完了単位を確認する。
4. 結果が変わる代表場面を選ぶ。0件/1件/複数件、対象なし、重複、境界、禁止、一部成立、不要化・判断変更、中断後の再特定、何もしない場合を、現在の仕事との関係で具体化する。一覧・選択には0件時もある。Procedureに専用の分岐がなくても全文から結果を導ければ項目化する。全組合せ・全業務への機械的な項目追加はしない。
5. 各期待結果の根拠の強さをレベリングする。通常項目の条件が未承認の候補や真の未決に重なる場合は、確定範囲へ限定し対応IDを示す。

## 検査項目の粒度

**原則として、1 Check Item = 1つの観測可能な期待結果とする。** 人間が1件ずつ採用・修正・削除できる意味単位に分ける。文章を機械的に短くすることや、1 assertion まで細分化することが目的ではない。

次のように期待結果やレビュー判断が独立する場合は、原則として別Checkにする。

- 0件 / 1件 / 複数件で期待結果が異なる
- 許可されること / 禁止されること
- 正常結果 / 副作用が起きないこと
- 成功結果 / 後続業務へ引き継げること
- 不成立結果 / 再選択・終了・継続
- 同一性保持 / 件数・集合条件
- 個別の境界値

たとえば「空き会議室を確認する」を1枚の大きなカードにせず、「0件なら0件」「1件ならその1件」「複数件なら全件」「利用不可室を含めない」「予約済み室を含めない」「確認だけでは予約を作らない」「選択対象を予約へ引き継げる」のように、人間が個別に判断できる項目へ分ける。

一方、「開始日時 < 終了日時でなければ予約不可」のように条件と期待結果を切り離すと意味が壊れるものは1 Checkのままでよい。Functional Interfaceを使う場合、Interfaceは責務のまとまりであり、Atomic Checkはその下の個別確認単位である。Interface自体をCheckの粒度まで細分化しない。

## 根拠の強さとレビュー

- **明示**: 期待結果がBusiness Designに直接書かれている。
- **強い導出**: 全文の複数記述を結ぶと、現在の業務上ほぼ一意に期待結果を導ける。
- **考慮候補**: 実装上自然に発生する重要場面で、根拠から期待結果を推定できるが、人間の確認が望ましい。期待結果に「候補・未承認」と明記し、具体案、推論、確認してほしい差分を書く。一律に「未確定」だけで止めない。

分類と別に確度を「高 / 要精査」で示す。これはテスト項目の期待結果を根拠から導ける確かさであり、業務承認・網羅性・確率ではない。考慮候補は要精査とする。レビュー優先度は「優先 / 通常」とし、考慮候補・要精査・長い推論を優先する。

これらとは別に、各Checkの**人間レビュー状態**を持つ。初稿は原則「未レビュー」から開始する。

- **未レビュー**: AI初稿で、人間が内容をまだ確認していない
- **要確認**: 意味・期待結果に人間判断が必要
- **確認済み**: 人間がタイトル、期待結果、必要な条件を確認した
- **要修正**: 人間レビューで修正が必要と判明した

レビュー状態はAI確度やテスト証拠とは別軸である。高Confidenceでも未レビューは未レビューであり、後続でテスト証拠が不足していてもCheckの意味自体は確認済みにできる。全項目が人間による修正・追加・完成の対象であり、通常項目も自動承認しない。

本当に期待結果を選べず、業務意味や決定権を新たに定める必要がある場合に限り、別枠「Business Designへ戻す事項」に根拠、合理的な選択肢と影響を書く。考慮候補の名で未承認の業務policyを決めない。既に承認された意味、方式の違い、明示的な非対象を再質問しない。

## 出力書式

冒頭に「人間レビュー前のたたき台」、入力版・適用条件、優先IDを記す。Activityまたは採用済みFunctional Interfaceごとにまとめ、IDは一覧内で一意とする。

### 人間向け主表示

人間が最初に読む面は短くする。

| ID | タイトル | 期待結果 | レビュー状態 |
| --- | --- | --- | --- |
| A1-01 | 何を保証・検証するか | 人間が理解できる1つの観測可能な結果 | 未レビュー |

タイトルは「このCheckで何を保証するのか」を把握する入口とする。現時点では定型文法を強制しない。

- 条件を読まないと対象が分からない「不正」「曖昧」「遅れて」等の広すぎる語は避ける
- capabilityでは「〜できる」が自然なら使ってよい
- invariantでは「〜変わらない」「〜書き換わらない」等が自然なら使ってよい
- タイトル自体を第二の仕様にせず、レビューで改善する

1行に複数の独立した期待結果を詰め込まない。独立して確認できる禁止事項や後続接続も、それ自体が人間の採否対象なら別Checkにする。

### AI / 開発者向け詳細

主表示を読みづらくしない位置に、同じCheck IDへ精密な詳細を保持する。表、details相当、appendix、machine-readable sidecarなど形式は固定しない。

初稿時点ではBusiness Designから導ける以下を保持する。

- 対象業務 / Activity / 関連Functional Interface
- 正確な条件・契機・入力。必要なら業務用語やシステム寄りの識別語を使う
- 根拠: 指定入力の行番号と短い内容。複数記述を使う場合は結び付きを示す
- 導出分類: 明示 / 強い導出 / 考慮候補
- AI確度: 高 / 要精査
- レビュー優先度: 優先 / 通常
- 関連する前段 / 後段Activity
- 禁止・保持条件: 主Checkと不可分なら補足、独立して合否判断できるなら別Check ID
- 候補なら、推定した部分と「候補・未承認」であること

この初稿生成では実装・テストを読まない。人間レビュー後、同じIDへAutomated Testの代表assertion、主要Code/SQL入口、evidence gapを後続traceabilityとして紐付けてよい。

末尾に、扱った接続・代表場面、対象外、必要な場合のみBusiness Designへ戻す事項を短く示す。0件、対象なし、成功/不成立後の接続をどのCheckで扱ったか、または扱わない根拠が分かるようにする。技術的エラー形式、UI、DB、通知、新しい状態・ロール、全操作の一律無変更保証は補わない。合理的な業務結果と特定の実現手段を区別する。

## 人間レビュー・意味変更・意味保持

人間はタイトル、期待結果、必要な条件、根拠、不足する場面をレビューし、修正・追加して項目書を完成させる。

**Business Designが業務意味のSSOTである。** 人間レビューで既存の意味が誤っている、未定義、または変更が必要と分かった場合は、Check・Decision・Test・Codeだけを先に正本化しない。

1. 該当Checkを「要確認」または「Business Designへ戻す事項」にする
2. Business Designを修正し、人間が業務意味を確定する
3. 確定版Business Designから影響するFunctional Interface / Checkを更新する
4. 必要ならDecision、Test、Codeを更新する
5. Business Design → Interface → Check → Test → Codeを再照合する

コードやテストの既存挙動は現在状態の証拠であって、業務意味を承認する根拠にはしない。

Checkの分割・改名・表示変更・再生成を行う場合は意味保持auditを行う。旧Checkの各独立保証が新Checkまたは明示補足のどこへ移ったかを確認し、削除した意味は理由を記録する。旧Checkは変換回帰のoracleとして使ってよいが、正本は常にBusiness Designである。

後続AIは人間レビュー後の項目書と同じ版のBusiness Designを使い、入力版＋項目書版＋IDをテストへ対応付ける。未承認の考慮候補やBusiness Designへ戻す事項を確定した合否テストにしない。新しい意味判断が必要なら当該項目を保留する。
