# 品質化で未記載の機能条件を探す — 試行用prompt

## 目的と境界

完成・業務相関レビュー済みのBusiness Designを、現実のシステムとして具体化するときに決め忘れ得る条件を、設計者・依頼者へ提示する。PoCの「この業務は回るか」や前後業務の成立性レビューは完了済みとする。ここでは「この機能の性質から、通常起こり得る条件を決めなくてよいか」を探す。

これは[c3による根拠付きCheck導出](candidate-c3.md)を置き換えない任意の探索であり、全項目を通過させる必須ゲートではない。Business Design全文、適用範囲、既に承認された判断・共通契約を読む。製品実装を未記載要件の正解として扱わない。

## 発見する

1. 対象の機能が何を受け取り、何を読み、何を変え、いつ結果を確定するかを、入力の記述から短く捉える。これは適用性の手掛かりであり、期待結果の根拠とは区別する。
2. その性質を持つ類似機能の知識、技術上の既知の現象、前提への問い直し等を使い、通常の一度きりの実行では隠れる具体的な場面を考える。手法は固定しない。外部資料が必要なら対象の性質に関係する一次資料を選ぶ。資料や一般知識が述べる現象と、この製品への適用推論を分ける。
3. 文書にない条件を発見したと思ったら、**既存の規則を満たしながら、人間から見た結果が異なる複数の扱いが成り立つか**を具体例で確かめる。成り立たなければ、既存要件の展開・実装方法の違い・推論誤りの可能性を先に調べる。一般論の項目名を並べただけでは候補にしない。
4. 全文の既決事項・非対象・共通契約と照合する。既に答えがあるものはその根拠で閉じ、再質問しない。未提示の利用環境を仮定した場合は条件付きと明記する。新たな業務や対象者を必要とするだけの案、結果の違いを示せない実装方式、重要性の低い遠い仮説は提案から外す。

固定の網羅チェックリスト、候補の最低件数、全非機能要件の棚卸しは要求しない。具体的な結果差を持つ少数の論点を検討可能にできたら止める。類似製品の採用機能を、この製品にも必要という根拠にしない。

## 出力する

最初に対象版、適用範囲、「人間レビュー前の考慮候補」を記す。次の2種類を分ける。

- **文書内の導出**: 既存記述から期待結果を決められる。必要ならc3へ渡す。
- **文書外の知識を使った未記載論点**: 文書は関連性の手掛かりにすぎず、答えは決めていない。以下の情報を持つ候補として提示する。

候補には、ID、対象機能、具体的な発生場面と結果差、適用性を示す文書箇所、既存判断で決まらない部分、発見に使った一般知識・資料と推論、最小限の選択肢と影響、未提示の前提を含める。「候補・未承認 / 要確認」とする。資料がない推論を引用済みの事実に見せない。関連性の行番号を、提案した期待結果の根拠へすり替えない。

「今回は不問」とする案も示してよい。その場合に保証しない範囲・影響と、既存の確定保証はなお守ることを示す。未記載だから不問と確定してはいけない。人間が結果の扱いを選ぶ必要があればBusiness Designへ戻す事項とする。日常的な可逆の技術選択まで人間へ返さない。

閉じた論点・見送った論点は理由を短く残す。既決事項の再質問、一般論の押し付け、未承認の要件化も評価対象にする。網羅性や欠陥発見率を主張しない。

## 決定後

外部知識は問いを作る材料であり、業務意味の承認根拠ではない。人間が意味・保証を追加または変更する場合は、まずBusiness Designへ反映し人間が確定する。確定版から影響するInterface / Checkを導出し、Test / Codeへ追跡する。未承認候補は確定アサーションにしない。既存の意味変更・承認手順は[c3](candidate-c3.md#人間レビュー意味変更意味保持)に従う。

このpromptは[Issue #71の探索的試行](issue-71-discovery.md)で使う候補であり、独立実行での発見率向上や人間の有用性は未実証。
