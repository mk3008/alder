# Issue #71 — 実行条件（出力作成前に固定）

## 問いと比較対象

完成・業務相関レビュー済みの入力を、機能として具体化する際の検討条件を現行c3で表現できるか。Alder baselineは `bbb88d125fcfd9c48dd857ace9131a2fdc778107`。対象は同版の `docs/behavior-derivation/candidate-c3.md`。stage4当時のc3とは粒度・表示等が異なるため、過去24件と今回の件数差を効果としない。

主入力は既存 `work/behavior-derivation/stage2/inputs/meeting-room.md` 全389行。入力の末尾に人間判断と業務相関の確認範囲がある。穴あり設備保全・購入を完成済みと見なさず、入力を追加・改変しない。新規ベンチマークは作らない。

Velvet `5d9872221b1e3f67cef671f644aacff69810efb1` は、Issueの参考論点を既存仕様・対象外・未承認に分ける資料照合のみ。完成済み新規導出試験には数えず、コード・テスト・文書を変更しない。

## 実施方式と既知の制限

主担当 `/root` が現行c3の適用例を1回作成し、全項目を入力へ照合する。追加Agentなし。モデル/effortはセッション継承で、ランタイムから独立確認した識別情報はない。Astra指定を独立検証済みと装わない。

主担当はIssue、過去のstage4評価、stage5粒度例、Velvet PR #44の情報を既に読んでいる。**c3の「過去レビュー・別導出を読まない」入力隔離条件を満たさない、既知文脈での適用probe**である。Fresh試験、盲検、初稿で自発的に気づく率の測定と呼ばない。期待結果の根拠には会議室入力のみを使い、過去出力を正本にしない。会議室実装・テストは読まない。

適用指示全文は `launch.txt`。生成物は `outputs/meeting-room.md` に1回保存し、評価開始後は書き直さない。誤り・不足は別の評価記録に残す。候補を採用した体のBusiness Designも作らない。

## 評価軸

1. 各Checkについて、条件・期待結果を引用範囲へ照合。明示/強い導出/候補を混同していないか。件数増は得点にしない。
2. 正常・0/1/複数・時間境界・対象不在・同時実行・別対象の分離から、仕事に関係する具体的な保証を示せるか。全観点の一律適用・網羅要求はしない。
3. 未記載場面は、人間が判断できる具体案・根拠・影響を示すか。候補・真に意味判断を戻す事項・既決対象外を分けるか。未記載を理由に不問と確定しない。
4. M1/M2、利用不可中の予約維持、代理・通知・監査等を再質問しない。前後業務の成立性の再レビューへ戻らない。
5. 新規方針の確定、必須技術方式の発明、根拠のない無変更保証、自動承認、未承認候補のテスト化を探す。

有用性は具体的なCheck/候補と根拠で説明し、人間の有用性評価・レビュー時間は未計測とする。機械検証はhash、ID、参照範囲、証拠保全を扱い、意味の正しさを証明しない。

## 採否と停止

現行で具体化でき、規則の不足を裏付ける失敗がなければc3を変更しない。ただし入力隔離を欠く本probeから「通常の新規初稿生成に十分」とは結論しない。失敗があれば原文を保持して範囲を特定し、変更案と別出力を比較する。評価条件を緩和して救済しない。

1回の適用と参考資料照合で、今回の変更要否を決める。独立試験・実利用レビューの不足は未検証として残す。大量反復、全業務完成、製品実装、テスト基盤・GUIの追加をしない。
