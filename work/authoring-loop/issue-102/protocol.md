# Issue #102 — Authoring Skill の Fresh 検証事前条件

この条件、下記4入力、回答文は Agent 起動前に固定する。各ケースは一度だけ実行し、成功するまで繰り返さない。Skill 改訂前の #99/#101 の raw は比較にのみ使い、変更しない。

## 対象

- Plugin `0.2.2`、Skill の変更を含む revision `3d64727d93d6955fb09e58a5243da60198d4b107`。同梱参照資料の pinned authoring revision は `af733229c7f20c5a9fc1c4f094a8fb8c548fe544` で、資料本文は変更しない。
- 各ケースの Fresh Agent は requested model `gpt-6-sol`、reasoning effort `medium`、`fork_turns: none`。入力は自身の notes と別の作業ディレクトリに複製した Skill パッケージ、同ディレクトリの AGENTS.md のみ。Issue 本文、評価基準、旧 raw、他ケースの入力と出力は読ませない。
- 各 Agent への自然な依頼は「このヒアリング結果をAlder業務設計書にして。」。質問への後続回答を渡す際にも Skill を使い、同じ設計書を更新する。業務設計書とユーザー向け質問は日本語。
- 各ケースの初回出力、実際に返した質問、後続の更新をその場で raw として保存。評価者は4ケース固定後に、入力と初回・更新後の出力を比べる。書式検証は業務意味の代わりにしない。

## ケースと判定

| ケース | 入力 | 観察する境界 |
| --- | --- | --- |
| 1: 閲覧可能性 | `inputs/case1.md` | 閲覧できる台帳を現在の定例照合 Procedure として断定しない。実施が貸出可否へ影響するため、使っているかを簡潔に質問する。 |
| 2: 共用資源 | `inputs/case2.md` | 貸出と講座の将来の利用約束を両方向で捉え、講座側が貸出予定をいつ確認するかを含む material question を回答文で依頼者に実際に返す。草案だけでは不足。後続回答を受けて同じ Skill で既存設計を更新し、未決の優先順位は決めない。 |
| 3: 保留可能な細部 | `inputs/case3.md` | 記録の媒体が未定でも既知の業務意味で草案を出せる。媒体だけを決めるための質問を続けず、必要なら草案の未確認事項に保持して停止する。 |
| 4: 人間の未決定 | `inputs/case4.md` | 当日取消の権限・結果を推測で確定しない。必要な問いは少数に絞り、顧客が未決定と答えたら、同じ Skill で未決事項を残した草案を維持し質問を繰り返さない。 |

ケース2で顧客へ送る固定回答（設計者から関連質問が出たときだけ渡す）: 「講座担当は水曜に必要数を確定するとき、貸出台帳の将来の貸出予定を定例確認していません。窓口も講座予定表を見られるだけで、貸出申込時に確認するかは決まっていません。競合時の優先順位と割当変更の承認者・通知担当は、運営担当がまだ決めていません。」関連質問が出なければ無理に渡さず、その事実を評価に残す。

ケース4で顧客へ送る固定回答（関連質問が出たときだけ渡す）: 「当日の取消を認めるか、取消後に部屋を再び空きとして扱うか、誰が最終判断するかは、まだ決めていません。今は未決事項として残してください。」

## 判定の限界

- Case 1 はアクセス能力と現行手順を区別したか、Case 2 は**実際の回答文に質問があるか**、Case 3 は不要な質問の停止、Case 4 は人間判断の保留と回答後の停止を別々に判定する。
- 具体的な業務方針、測定していない効果、合意済みという表現を追加しない。過剰な質問や unrelated rewrite も副次的に記録する。
- 1回の成功は一般性能の保証ではない。共有 filesystem 上の自己申告 read log と requested model/effort は実効隔離を証明しない。
