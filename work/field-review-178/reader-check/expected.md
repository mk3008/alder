# 事前固定した期待と判定方法

このファイルは評価者用。readerには渡さない。4件は実在の組織・資料に依存しない完全合成例であり、既存の非公開文書や候補guideの例文からの転載ではない。

## 比較条件と入力

1. 両armへ同じ汎用の業務設計reviewを依頼し、対象ファイルは `designs.md` だけを指定する。candidateにだけ親promptで名前先読みを強制しない。
2. `names.md` はfixture作成時の確認用であり、readerには渡さない。並び順はCase 1〜4と対応する。
3. 本文前にActivity名だけを抽出し、暫定的な読みを保持してから本文と照合する手順を、適用対象のSkillから自発的に実施できるかも観測する。
4. 名前からの読みは仕事の短い言い換えで足りる。自然に浮かぶ別の読みがあれば併記でき、不明は不明のままでよい。
5. この期待、分類、修正例、他armのSkillや他readerの回答は、review終了までreaderへ渡さない。各armにはそのarmのSkillだけを使わせる。

名前だけからWho、When、Where、操作手順などをすべて当てる課題にはしない。本文にしかない条件を推定しなかったことは誤読に数えない。全文を読んだ後の説明を、名前だけで理解できた証拠として扱わない。

## 取得順の観測限界

- tool履歴で見出しだけの取得、暫定読解の記録、本文取得の順を確認できる場合と、最終回答が名前先読みを自己申告しただけの場合を区別する。
- 最初に全文を取得した場合、後から名前だけを抜き出しても、本文を知らない読みを観測したとは扱わない。推測した内的な読書順序で補わない。
- 暫定読解を外に記録していない場合は「取り違えなし」ではなく「事前の読みは未観測」とする。本文後の競合解釈や明瞭化案の品質は、それとは別に評価できる。
- この比較は同一readerへの外部的な二段階提示ではない。取得順を確認できても、独立した人間の第一印象や実務での誤読率を検証したことにはならない。

## Case 1：設定と実行を取り違え得る候補

- 名前：閉館後の入館を制限する
- 合意された仕事：運営担当者が、次回以降の閉館後に適用する入館制限を管理画面で保存する。
- 競合解釈の仮説：閉館後に、受付担当者や入口装置がその場の入館を断る仕事。
- 名前は「制限する」という広い動詞で設定の効果を自然に表せる。設定場面を述べた本文との明白な文法矛盾を仕込んだものではない。
- 明瞭化の候補：閉館後の入館制限を設定する。
- 守る意味：今行う設定保存と、後の入館判定を区別する。「閉館後」という適用対象は落とさない。

## Case 2：設定と実行を取り違え得る候補

- 名前：休業日の着信先を切り替える
- 合意された仕事：窓口担当者が、今後の休業日に適用する着信先を事前に登録する。
- 競合解釈の仮説：休業日に現在の着信先を手動で切り替える仕事、または個々の着信を別の窓口へ回す仕事。
- 「切り替える」は登録された方針の変更にも使えるため、設定を説明する本文として成立する。操作時点が休業日だとは本文で合意していない。
- 明瞭化の候補：休業日の着信先を設定する。
- 守る意味：今行う着信先の登録と、後の着信への適用を区別する。「休業日」という適用対象は落とさない。

## Case 3：対象識別に必要な時期修飾の正常例

- 名前：来月開始の講座を募集一覧に載せる
- 合意された仕事：現在の募集更新作業で、開始月が来月の講座だけを募集一覧へ掲載する。
- 「来月開始」は対象講座を選ぶ条件。掲載操作を来月行うという意味ではない。
- 名前はそのままでよい。「講座を募集一覧に載せる」への短縮は対象範囲を広げるため不適切。
- 明瞭化を提案する場合も、来月に開始する講座という対象条件を残す。名前に実行日や担当者を追加することを必須にしない。

## Case 4：対象識別に必要な保存状態修飾の正常例

- 名前：保存済みの見積書を複製する
- 合意された仕事：一覧に保存されている見積書を元に、別条件を検討するための新しい見積書を作る。
- 「保存済み」は元の見積書の状態。保存のたびに複製するという時点条件ではない。
- 名前はそのままでよい。「見積書を複製する」への短縮は未保存の編集中内容を含み得るため不適切。
- 同等の表現への変更は許容するが、保存済みの原本を使うことが読み取れなければ必要な修飾を保護できたとは扱わない。

## 観測と判定

- Caseごとに、観測できた名前先読みの原文、本文との対応説明、具体的な競合解釈、修正案または変更不要の判断を保存する。
- 名前先読みを観測できた場合は「合意された仕事と両立」「競合する仕事を主な読みとして提示」「読みを確定しない」を区別する。設定にも実行にも読めるという回答は、実行への断定と区別する。
- Case 1・2は、本文取得前の記録で競合する仕事を主な読みとして提示したときだけ、名前先読みで取り違えを観測したと記録する。仮説の競合解釈を評価者が後から補って誤読扱いしない。
- 本文を読んだ後に具体的な競合解釈と意味を保つ修正が示された場合は、明瞭化候補を得たと記録する。名前先読みの誤読を防いだ証拠とはしない。
- Case 3・4では、修飾を実行時点へ移さず、対象条件として保てたかを見る。「全件短くする」ために必要な修飾を削った場合は副作用として記録する。
- 4件とも観測した名前先読みで取り違えがなければ、その結果を採用する。追加例や誘導質問で失敗を作らない。先読みが未観測の場合も含め、誤読防止の効果を確認できていなければ、その限界を明記する。
- 正確な修正語句の一致、指摘数、全件での要修正判定は成功条件にしない。本文の業務条件の変更や新しい統制の追加は、名称明瞭化と分けて記録する。
- 結論は「取り違えの観測」「競合解釈と修正の具体性」「正常例の対象条件の保護」を分ける。4件の合成例から実務全般の有効性や業務上の承認を主張しない。

この期待はreader実行前に固定する。後から変更する必要があれば旧版を残し、変更理由と変更前後の結果を分ける。
