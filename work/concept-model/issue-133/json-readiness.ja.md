# 現行JSONから概念モデルを描けるか

**今回の概念モデルの全体図・Activity別の個別図は、現行JSONだけから推論なしには生成できない。** この試作は、未採用の6概念草案を人がレビューするため、別の描画用データを手作業で与えている。既存JSONから変換した結果ではない。

確認した正本はmain `adb06adcf493c7f4c09fac52c2c4a14b85207593` の[保存Schema](../../../tools/document_storage/schema.mjs)、[保存契約](../../../docs/document-storage.ja.md)、[JSON正本の契約](../../../docs/json-native-contract.ja.md)。現行の外側0.4はBD/0.3・Check/0.1・状態遷移/0.2を受け入れるが、conceptModel文書は未対応。未知kind／未知フィールドは拒否する。

## 今ある情報で分かること

| JSONの情報 | 推論なしに使えること | 分からないこと |
| --- | --- | --- |
| BDのObject ID・名前・Information | Object一覧と情報文の表示 | 一つのObjectを申請・版・品目等へ分けるか、概念の独立性 |
| Activity ID・名前 | Activityの識別・選択先 | どの概念を作成・更新・対象外化するか |
| input/output関係のID・接続先・label | Object↔Activityの業務相関図 | 概念↔概念の関係・両端多重度。inputは参照専用とは限らず、outputも新規作成とは限らない |
| Procedure・Information等の文章 | 原文・条件文をそのまま表示 | 文の意味を解釈しない概念分割・所属先・操作分類・数量制約の抽出 |
| 状態文書のstates・transitions | 明示済みの状態遷移図 | 状態を独立概念にするか条件付き属性にするか。状態遷移は概念間多重度でもCRUD一覧でもない |

たとえば購入申請Objectと「購入結果を登録する」Activityが接続されていても、それだけでは「入庫回と入庫内訳を作り、品目の購入しない数量と申請の終結結果を更新する」という4概念への分解は決まらない。新しい6概念の採否は、表示処理や単なるJSON形式変換へ委ねない。

## 別途明示して出す必要がある情報

以下は**次工程の入力要件案**であり、正式Schemaの追加・採用ではない。AIが業務設計を基に草案を作り、人間が意味をレビューした上で保存する。Viewerはその明示済み情報を読む。

| 必要な情報 | 内容 | 使用先 |
| --- | --- | --- |
| 概念の一覧 | 安定ID、名前、何が一件か、保持する情報。条件付き情報には存在条件・未決の区別 | 全体・個別のカードと詳細 |
| 概念間の関係 | 安定ID、両端の概念ID、**両端それぞれの多重度**、必要な関係の意味・適用条件 | 全体図。個別図は表示対象同士の関係だけを投影 |
| Activityと概念の操作対応 | Activity ID、概念ID、作成／更新／対象外化／参照の区別。複数操作・複数作成元も許す | 個別図の対象選定、作成Activityへの移動 |
| 原典との対応 | 元BDのID・revisionと根拠の参照。Objectと概念の対応が必要なら多対多を明示 | 版の整合確認、根拠への移動。Objectと概念の1対1を仮定しない |
| 詳細で見せる条件・未決 | 対象の概念／関係／Activityへの明示的な関連付けと表示文 | 内容をViewerで解釈せず表示 |

作成元は操作対応の「作成」から機械的に集められるため、別に二重管理しなくてよい。候補が複数なら選択肢を出し、先頭一件へ勝手に飛ばさない。「対象外化」は業務上の破棄等を表し、物理DELETEの指示ではない。

個別カードをさらに「このActivityで変更する項目だけ」に絞る場合は、概念単位の操作対応だけでは不足する。情報項目の安定IDと、Activity／場面別にどの項目を作成・変更するかの対応も必要になる。今回の個別図は**参照概念の非表示まで**であり、この項目単位の省略は実装していない。

## 推論しない描画の範囲

- 全体図：明示された概念と関係をすべて描く。件数条件や概念分割を生成しない。
- 個別図：対象Activityに作成・更新・対象外化の対応がある概念だけを抽出し、両端とも表示する関係だけを残す。参照だけの概念は非表示。参照条件そのものは詳細へ保持する。
- 階段配置：座標計算と線の配線は描画算法で行える。これは業務意味の推論ではない。ただし、複数関係のうちどれを親子の主軸にするかを業務の意図として保証するなら、**主たる所属関係／表示上の親関係**を明示する必要がある。一般的な多重度だけでは、その選択は一意に決まらない。
- 表示順・座標は表示設定として分離できる。毎回すべての座標をAIに出させる必要はない。主軸を明示しない場合も、決定的な配置規則で描画は可能だが、意図した主軸と同じという保証はしない。

必要情報がそろえば、原典の文章をLLM等で読み直さず全体・個別を同じモデルから機械的に投影できる。情報がない場合は「未定義」と表示し、空図を完成扱いにしたり、Object名・文章・Scopeから埋めたりしない。

この情報を既存パッケージ内の新kindとして持つか等の保存契約、validator／Plugin／Viewer統合は未実装。今の0.4 JSONに独自フィールドを足して読み込めるという提案ではない。
