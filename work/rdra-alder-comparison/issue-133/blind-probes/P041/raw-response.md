# 確認済みの業務上の期待結果

1. 社員は購入物品と申請金額を入力して申請を作成する。提出時にその両項目を含む必須内容を確認し、揃った申請を提出すると「上長承認待ち」となる。入力時の不足表示と提出前の確認が画面要求である。【packet.md 3–8行、117行、129行】
2. 上長は申請物品と金額を審査し、承認または却下を判断する。却下された申請は購入対象外となり、「上長承認待ち」から「却下」に移る。【packet.md 9–11行、92行、118行、132行】
3. 金額の境界は**10万円以上**と**10万円未満**である。10万円未満で上長承認済みの申請は「購入待ち」となり、購入が許可される。【packet.md 101行、119–120行、130行】
4. 10万円以上は上長承認の後に「部長確認待ち」となり、部長の追加確認が完了してから「購入待ち」に進む。購買担当は上長承認済みで部長確認待ちの対象を識別し、部長は対象の物品・金額を確認できる。【packet.md 16–24行、93行、103行、119行、121行、131行、133行】
5. 購買担当は金額区分、上長承認、必要な部長確認の完了を確かめて購入可否を判断する。10万円未満は上長承認済みかつ購入待ち、10万円以上は上長承認・部長確認がともに完了して購入待ちの場合に購入可能である。却下や必要な承認・確認が未完了なら購入を認めず、購入画面でも購入操作を進められない。【packet.md 25–34行、120–123行】
6. 購入可能な申請の物品を購入すると申請は「購入待ち」から「購入済み」となる。その後、実際に購入した物品と金額を申請に紐づく購入記録に残す。購入申請と購入記録の項目は資料に列挙されている。【packet.md 30–38行、111–112行、124行、134行】
7. 購買担当は申請内容と購入記録、または却下の状況を確認し、購入した場合は購入記録を含む結果を、却下して購入しなかった場合はその結果を申請者へ伝える。伝えた後に連絡済みを記録し、「購入済み」または「却下」から「結果連絡済み」へ移る。【packet.md 39–46行、94行、104行、125行、135–136行】
8. 申請者、上長、部長、購買担当の役割を識別する社員情報を扱う。資料は購入申請、購入記録、社員情報の属性を列挙するが、属性だけから追加の業務判断を導かない。【packet.md 91–94行、110–113行】

# 明示された未決事項・資料から確定しない事項

- **明示された未決**：購入結果を申請者に伝える手段と期限。メール、画面通知等の手段や送信期限を実装上の確定ルールにしない。【packet.md 43–46行、125行】
- **資料に規定がないため確定しない**：部長が追加確認で否認する場合の処理、購入不能・購入失敗時の状態、申請額と実購入額が異なる場合の許容・再承認条件、通知手段以外の運用詳細。これらの決定を示す状態遷移・条件は掲載されていない。部長確認からは完了後の「購入待ち」、購入待ちからは購入済み、通知は購入済み・却下からの遷移が示されるにとどまる。【packet.md 121–125行、129–137行】

# 資料内の矛盾・対応関係の不整合

- Artifact 001では「購入申請を承認する」UCの説明が「10万円未満の申請を承認し、購入を待つ状態に進める」と限定される。一方、状態モデルは**同じUC**で10万円以上を「部長確認待ち」に進める。高額申請の上長承認をそのUCが含むか、UC説明の範囲を確認する必要がある。【packet.md 12–16行、130–131行】
- Artifact 001のアクティビティ名は「購入申請を承認または却下する」だが、その対応UCの行は「購入申請を承認する」のみである。一方、条件と状態モデルには却下判断および「購入申請を却下する」UCによる「却下」遷移がある。却下操作のアクティビティ・UC・画面の対応が表の上で欠けているため、実装範囲を確認する必要がある。【packet.md 12–16行、118行、132行】
