# 資料から確認できる業務上の期待結果

根拠位置は、渡された `packet.md` 全体の先頭から数えた物理行番号です。

1. **空室検索**：希望日・時間帯で検索し、利用停止中の会議室と、予約済みで有効な予約が時間帯に重複する候補を除外する。利用可能な会議室と時間帯を比較でき、取消済み予約の時間帯は占有されていない空きとして表示する。〔3–11行、134行〕
2. **新規予約**：検索結果から会議室と希望時間帯を選び、内容を確認して申し込める。会議室が利用可能で、有効な予約済み予約と時間帯が重複しなければ成立し、予約情報を「予約済み」として記録して会議室・時間帯・状態を確認できる。取消済み予約との重複は妨げにならない。利用停止または有効な予約との重複で成立しない場合は、その理由を区別して表示する。〔12–28行、136行、146行〕
3. **予約時間変更**：既存予約を選んで変更先時間帯を指定できる。変更先の会議室が利用可能で、変更先時間帯が他の有効な予約済み予約と重複しない場合は、既存予約の時間帯を更新し「予約済み」を維持する。変更不可なら理由（利用停止または時間重複）を表示し、元の予約を維持する。〔29–44行、137行〕
4. **予約取消と再利用**：社員は自身の予約を選んで、当日を含め期限なく取消できる。取消により状態を「取消済み」にし、時間帯の占有を解く。取消済みとなった時点・取消直後から、空室検索と新規予約に反映され、その結果を確認できる。〔45–55行、135行、138行、147行〕
5. **会議室の利用停止**：管理者は対象会議室を選んで利用停止にできる。停止中の会議室は空室検索・新規予約・予約時間変更先から除外するが、停止前に成立した予約済み予約は取り消さず、予約情報と予約者の利用権を維持する。停止前の予約に基づく実際の利用はシステム操作を伴わない。〔56–66行、139行、143–145行〕
6. **記録・状態**：会議室、予約、社員の情報項目が列挙されている。予約は「予約済み」で成立し、「取消済み」へ遷移する。会議室は「利用可能」から「利用停止中」へ遷移する。〔127–130行、143–148行〕

# 明示された未決事項・まだ確定してはいけない事項

**「未決」と明示して列挙された項目はありません。** 以下は資料で規則・解釈が定義されていない事項であり、実装者が独自に業務ルールとして確定してはいけません。

- 「時間帯が重複」の端点の扱い、最小予約単位、予約可能期間、会議室の利用開始・終了時刻をどのように判定に適用するか。時間重複の判定と時刻属性は示されているが、これらの詳細は書かれていない。〔127–129行、134行、136–137行〕
- 当日以外の過去予約や、利用終了後の予約を取消できるかどうか。「当日を含め期限なく」は示されているが、過去分や利用後の扱いを明記していない。〔45–47行、138行〕
- 予約時間変更で会議室そのものの変更を許すかどうか。フローは「時間変更」と「対象会議室」を述べ、条件文には「変更先の会議室」が現れるが、会議室IDの更新や変更対象の範囲は明記されていない。〔29–44行、129行、137行〕
- 利用停止中からの復旧、取消済み予約の復活・再変更について。状態表はそれぞれ他の状態への遷移を定義していない。これを禁止という追加ルールに読み替えず、未定義のまま扱う。〔145行、148行〕
- 外部連携・通知の要否。外部システム表には具体的なシステムが記載されておらず、通知規則も示されていない。〔123–124行〕

# 資料内の矛盾・表記不一致

- **会議室利用状態の値**：バリエーションの値は「利用可、利用停止」だが、状態モデルでは「利用可能、利用停止中」。同一の状態モデル・バリエーションとして関連付けられているため、正式な値・対応を確認する必要がある。〔72–73行、81行、119–120行、143–145行〕
- **利用停止担当者の呼称**：業務フローの画面上のアクターは「会議室管理者」、アクター一覧・役割表では「会議室利用管理者」。同一人物・権限を指すか、どちらが正式名かは確定できない。〔57行、61行、65行、70行、104行、110–113行〕
- **予約状態の所属コンテキスト**：バリエーションと予約情報は「予約管理」に置かれる一方、状態モデル表の予約状態の行は「会議室管理」と記載される。所属の定義を確認する必要がある。〔72行、76行、119–121行、127–129行、146–148行〕
