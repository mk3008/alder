## 文書外の知識を使った未記載論点

### MR-01 — 日時の解釈と夏時間境界（候補・未承認 / 要確認）

- 対象機能: 空き確認、予約、変更。発生場面と結果差: 利用者が夏時間の切替日にローカル時刻「01:30–02:30」などを指定し、同じ表示時刻が二度存在する地域で予約する。前半の01:30と後半の01:30を別の時点として扱えば異なる予約枠になり得る。日時を一律に一つの時点へ解釈したり曖昧な入力を受け付けなければ、表示上同じ指定の空き結果・予約可否が異なる。存在しないローカル時刻の扱いも受付・拒否・補正で異なる。
- 適用性の手掛かり: Business Data の「利用開始日時」「利用終了日時」、Activity 1–3 の日時入力・前後関係・重複判定、Business Rule 3 の境界一致。文書は日時の表現・解釈を規定していない。これは提案した扱いの根拠ではない。
- 発見に使った知識と推論: 一般的な地域時刻には夏時間切替による重複・欠落があるという知識から、日時の比較・重複判定へ影響を推論した。外部資料は参照していない。利用場所・入力形式が未提示で、夏時間がない時間体系だけを用いるならこの場面は適用しない。
- 最小限の選択肢と影響: 時差・地域または曖昧さの区別を指定させて別時点として扱う／曖昧・存在しないローカル時刻を拒否する／業務上の固定時間体系を定めて解釈する。どれも空き表示と予約可否に影響する。人間が日時の意味を決めるならBusiness Designへ戻す。「今回は不問」なら夏時間境界での一貫した利用者向け解釈は保証しないが、解釈後の前後関係、境界一致、予約重複防止は守る。

### MR-02 — 同一予約への競合変更（候補・未承認 / 要確認）

- 対象機能: 予約変更。発生場面と結果差: 同じ予約について予約者が二つの画面から、会議室A・10–11時からそれぞれB・10–11時、C・10–11時への変更をほぼ同時に送る。どちらも対象予約が `reserved` で、変更先は空いている。先に一方を確定し、もう一方も現在の予約への変更として成立させれば、両方に成功が返って最終内容は後者となる。一方、最初に見た予約内容から変わった後の要求を競合として不成立にすれば、一方だけが成功し、もう一方には元の予約内容を基準とする変更が成立しないと分かる。既存の同室・同時間帯の重複禁止では、別の変更先への競合は解決しない。
- 適用性の手掛かり: Activity 3 の対象予約、条件確認、変更成立時の会議室・時間帯の更新、不成立時の元予約維持。Business Rule 6–7 は不成立時の保持と同一時間帯への複数予約成立防止を定める。既存予約のバージョンに関する条件や、同一予約に対する競合変更の結果は定めていない。これらは特定の競合方針の根拠ではない。
- 発見に使った知識と推論: 複数の操作が同じ可変データを読んで更新すると、古い状態を前提にした後続の更新が先行更新を上書きし得るという一般的な並行処理の知識から推論した。外部資料は参照していない。二画面・複数要求経路が可能かは未提示の利用環境上の前提である。
- 最小限の選択肢と影響: 各変更を現在の状態に順次適用して後の成功で上書きする／最初に見た内容からの変更が既に確定していれば後の要求を不成立にする。利用者が成功応答を受けた後の予約内容と、再試行・確認の必要性が異なる。後者を採るための版番号などは実装手段であり、ここでは指定しない。「今回は不問」なら同一予約への競合変更時に先行成功内容が維持される保証は追加しないが、確定した予約の重複禁止と、各不成立の変更で元の内容を維持する既存保証は守る。

## 文書内の導出・閉じた論点

- 同時に同じ会議室の重なる枠を予約しても複数成立させないことはBusiness Rule 2、7で既決。原子的な確定方法は技術選択であり、再質問しない。
- 利用不可化した会議室の既存 `reserved` 予約は維持され、別の利用可能な部屋への変更と取消はでき、再開後は維持予約が占有する。Activity 3–6、Business Rule 8–9、Human Decisionで既決。実際の利用を保証する案はここでは出さない。
- 終了と次の開始が同一時刻の予約は重複しない（Business Rule 3）。変更が不成立なら元の予約を維持する（Activity 3、Business Rule 6）。いずれも文書内の期待結果として必要ならc3へ渡せる。

## 見送った論点

- 繰り返し予約、通知、参加者、履歴、予約期間上限、定員・設備、代理操作は「現時点で決めないこと」に明記されている。新たな対象・業務を足す提案はしない。
- 利用不可化と予約の競争だけを独立候補にはしない。先に予約が成立すれば既存予約として維持し、先に利用不可が確定すれば予約不成立という既存の規則で結果を説明できる。処理順の技術方式だけを候補にしない。
