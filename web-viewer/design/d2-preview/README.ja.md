# 既存Viewerで構造を比較する

業務の手順・担当・結果・入出力を項目に分けたD2案を、従来のViewerで確認できます。通常Viewerと同じヘッダー、エクスプローラー、タブ、カード・配線、ズーム、右詳細を使います。未採用の構造を読む確認版で、正式な保存形式は変更しません。

`d2.html`を開いて図のActivityを選び、右詳細の「0.4表現」「D2構造案」を切り替えます。同じ欄で、Procedureは番号付き手順、ResultとI/Oは独立項目、担当・適用条件・順序は補足として読めます。Activity間の依存はWhen・Result・Objectによる入出力で読み取ります。右詳細の「例」で五つの限定例を切り替えます。例の選択と0.4/D2切替は検証専用で、正式採用時には表示しません。

同一Procedure内で入替可能と明示された複数Stepだけに同じ※番号を付け、末尾に短い注記を表示します。Activity横断の順不同・順序制約は別の構造として保持しません。待ち合わせは後続ActivityのWhenに書きます。業務分析の妥当性をこの表示から保証せず、自然文条件を自動判定しません。Resultの条件は結果と一文にまとめて表示します。担当未確認と外部業務をそのまま保持します。複数Roleを持つ場合は担当欄へ全件を示し、既存の単色Roleバッジで主担当を新たに推定しません。

比較JSONは`public/d2-examples.json`です。0.4側は同じ焦点情報を現行形式で表した比較草案で、研究原典全体の移行ではありません。架空例は名前に明示しています。D2モードのGraphは候補JSONから直接投影し、0.4側のGraphを流用しません。

`?source=<匿名取得できるHTTPSの比較JSON>&case=molkkyCross&mode=d2`で固定入力を指定できます。この入口だけで研究形式を検査し、既存の共通表示モデルへ投影します。投影値は保存packageではなく、元の候補構造から詳細を導出します。文書・表示状態をIndexedDBへ読み書きせず、通常Viewerの文書を変更しません。エクスプローラーの開閉等の一時設定は、このページのsessionStorageを使います。

Step IDと順序検証の規則は内部に保持し、通常表示には出しません。Inputは「受取元 → データ名」、Outputは「データ名 → 渡す相手」と表示し、構成項目はData欄で確認できます。投球のInputは凍結原典の関係IDを保持して復元しています。

候補D2.2ではBusiness Designのdataに名前付き定義を一度だけ置き、各Input/OutputはdataIdで参照します。名前と構成項目はActivityごとに上書きできません。項目の名前・説明は従来のObject.Informationを正本とし、data.itemsはそのIDと条件だけを参照します。図のラベル、I/O、Data欄も同じ定義から導出します。例えば「投球結果」は投球側のOutputと記録側のInputが同じ定義を使い、「投球記録」は別定義のまま保持します。

比較JSONはversion 3、候補はproposalVersion D2.2です。正式0.4契約の変更や旧JSONの自動変換は行いません。version 1/2の比較JSONは旧固定Previewで確認でき、新入口では明示的に拒否します。廃止したcrossActivityOrderRules、他ActivityのStepを指す局所順序ルール、同名の複数Data定義、無効なData/情報ID、Object所有者不一致、関係へのlabel/items再定義は機械検証で拒否します。名前の意味と構成項目が業務上正しいかは意味レビューの対象です。

各手順で「必須」と同じ担当・担当未確認を繰り返しません。任意・適用条件や、複数主体の中で手順の担当が分かれる場合だけ補足します。順不同の長い説明と折りたたみ欄は表示せず、対象Stepの※と短い注記だけを表示します。適用条件・任意・担当の補足は手順本文の括弧内にまとめます。

Resultの専用conditionフィールドは現候補に残していますが、Check Itemや実装で分離自体の効果を確認できていないため、正式採用は保留です。条件の意味は文章からもCheckへ利用でき、独立した項目で保持する必要性とは区別します。
