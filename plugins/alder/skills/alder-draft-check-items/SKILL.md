# Draft and maintain Alder Check Items

Read the bundled [current Check Item guidance](references/check-item-traceability.md) in full and [adoption](references/adoption.md#draft-and-review-check-items-required) through the optional Functional Interface section. For initial derivation, read [c3](references/candidate-c3.md). Current adoption and traceability take precedence over historical c3/f1 passages: permanent mappings stop at Test/assertion, never Code, file, SQL entry point or line. Do not fetch newer authority or ask the requester to supply Alder's internal documents.

## Locate the work and choose the requested operation

Read project instructions, then locate the requested Business Design, current Check list and feedback from the request or established project paths. Use `docs/business-design/` only if no project location is declared. Ask only for unreadable or genuinely ambiguous product inputs. Record design/list revisions or precise working-tree scope.

Use the requester's working language and the Business Design's business terms in the original saved artifact and review response. For Japanese review, write Activity names, Check titles, conditions, expected results, questions and supporting explanations in Japanese, not just headings. Preserve stable IDs, technical identifiers and literal values; do not change meaning or human review states when adjusting language. Retain source-established proper business names when translating them would change their identity; explain them in the review language when needed. Ask only if the review language is genuinely unclear. Before returning, inspect the saved artifact itself against this language requirement. An internal English fixture may remain English; a later chat translation is not evidence that the original artifact met the review-language requirement. Follow [language for agreement](references/adoption.md#language-for-agreement).

- Initial draft: read the whole applicable completed, business-correlation-reviewed Business Design. Do not read implementation, tests, prior reviews or another derivation to invent its expected results. If the input is explicitly unfinished, offer only a clearly labeled unresolved-input reference draft; never describe it as ready for handoff. If agreement is unknown, ask whether this is the agreed design before representing it as such; independent draft work may proceed as unconfirmed.
- Update: read the existing list, same-ID detail and actual feedback. Preserve stable IDs, human review states and existing Business Design/Test mappings unless an evidenced change requires repair. Existing tests or mappings do not authorize business meaning. Compare before/after guarantees when splitting, regrouping, renaming or regenerating; record intentional removals and their basis. Do not silently discard supporting detail or unrelated Checks.
- Consistency review only: report evidence, missing derivation or feedback conflicts without editing files or changing review states. This is not human confirmation.

Derive one independently reviewable observable expectation per Check using whole-design conditions, connections, roles, data meaning and relevant representative cases. Keep inseparable condition/result pairs together; do not force one Check per assertion or enumerate every combination. Follow the current traceability guidance's human-facing view rather than copying historical c3's table/detail layout: show the selected Activity's stable ID/title, precise condition, expected result and human review state once; keep source evidence, derivation class, confidence, connections and Test evidence/gaps reachable under the same ID without repeating those primary fields. Separate explicit, strong derivation and unapproved consideration candidates. Show priority questions in the response as well as the artifact.

Start with an Activity index using existing Business Design names, purpose and source-established connections. Use source-established full Activity names in visible references; do not invent shortened aliases or position-based names. Do not add display-order numbers to ActivityName. When the current Business Design declares `# Activity ActivityName`, use that declared ActivityName throughout; do not substitute historical headings or add an old-name correspondence table. Follow the [GitHub Markdown document layout](references/check-item-traceability.md#github-markdown-document-layout) for the four-column index, direct Check links, display-name/source-quotation distinction, and separate Activity sharing versus old-Check correspondence. For a historical source with no explicit name contract, use a human-confirmed display-name correspondence; without that confirmation, quote the historical source’s full heading while retaining the existing source and link targets and report the naming uncertainty. Do not guess a shortened name, rename the source or retrofit a different Markdown profile. Show only the current Activity's review group in conversation, then continue to another Activity as requested. In a document, keep the Activity index and Activity sections in the same order: use same-level Activity headings and place each Check one level below (for example, H2 Activity and H3 Check). Do not split the document into current versus other Activities. Link the index to the same Check items rather than duplicating them. Keep a clearly related unresolved item within that Activity as an unresolved matter without changing its meaning or state; do not guess genuinely unknown membership. Shared Checks keep one ID, item and review state across all Activity references; show unassigned candidates separately without guessing a mapping. Navigation order is not business order unless the source says so.

Give each unresolved item its own visible kind, for example `種別：未決事項（候補）`, rather than relying on a surrounding heading. Keep kind distinct from derivation class, AI confidence and human review state. Preserve source-undecided versus AI-proposed origin and the unapproved expected result; do not infer a new classification or decision. This display cue adds no required schema or parser.

For initial drafts and requested presentation updates, use the [shared conditions, expressions and examples view](references/check-item-traceability.md#conditions-expressions-and-examples): H3 `ID — title`, visible human state, H4 条件と期待する結果 / useful サンプル / applicable 未決事項 / 参照情報, ordinary Markdown and heading links without HTML or human/AI copies. Separate condition, labelled expression, action and result; do not presuppose success. Distinguish necessary conditions from guarantees and constraints from unspecified failure responses. Add concrete comparable examples, including material unresolved cases; use tables only where useful. Preserve existing guarantees and supporting text during a display update, without enlarging a limited list. Repair changed fragment links. Treat model/property-like terms as business vocabulary, not required physical names or structures. Apply that guidance during the return-time quality check.

Group examples sharing evaluation axes in a summary above their individual Checks, within the Activity section, so condition-satisfied and condition-unsatisfied cases can be compared together. Link rows to the applicable Check IDs and link those Checks back; retain one primary body/state per ID without repeating example tables. Separate comparison axes into columns and put explicit common values/business actions before the table. Keep known judgments distinct from undecided responses; a failed condition does not decide rejection. Keep short scenarios where a table adds no value. Inspect the rendered result and these references during the return-time review, disclosing unavailable rendering or human review; do not treat text checks as proof of comprehension. Follow the linked guidance for scope and meaning preservation.

For a retained legacy GitHub Markdown layout outside a requested presentation migration, keep Check supplements in default-closed `<details><summary>` blocks without an `open` attribute; keep the ID/title, condition, expected result, human review state, anchors and shared references outside. For unresolved items, keep questions, alternatives and effects visible with the primary fields; collapse only supplemental source evidence, derivation class, AI confidence, related Activities and Test evidence. Never put a pending decision inside a collapsed block. Preserve all supporting text, use a summary containing the Check ID and a descriptive label, and blank lines around the Markdown body, and check the target view. Other Markdown viewers may not fold the content.

Use “all of the following” bullets only for explicit AND, labelled “any of the following” groups only for explicit OR, and nested groups for mixed conditions. Preserve boundaries, negation, exceptions, exclusivity and priority. If a relationship is ambiguous, retain the original wording and return a focused 要確認 question instead of deciding it. Keep an existing human-confirmed state when only presentation is uncertain; do not silently reset it. A real unresolved or changed business meaning follows the Business Design loop below. Multiple condition bullets do not create multiple Checks.

Ask for confirmation, correction or deferral by exact Check ID. Activity changes, opening an item, silence and resuming are not approval. Retain the current Activity and next ID as optional navigation context without changing item states or requiring a new progress artifact. These presentation rules add no mandatory schema, viewer or ledger, and do not demonstrate human comprehension or review-time gains.

New AI drafts start 未レビュー; an unresolved meaning is 要確認. Apply 確認済み only to the exact title, condition and expectation actually confirmed by a responsible human. High confidence, a passing test, a prior confirmed version, or a generic approval of the drafting task is not confirmation of changed meaning. A materially changed expectation requires renewed human review. Keep human feedback requesting correction as 要修正 until the correction is made; correction alone does not assert renewed confirmation. Do not downgrade unchanged human-confirmed meaning merely because Test evidence is missing.

If feedback changes business meaning, conditions or guarantees, or exposes a genuinely undecided outcome, mark the affected item 要確認 and return a focused Business Design question with alternatives and effects. Do not settle it inside Checks. Business Design must be revised and human-confirmed first; only then re-derive affected Checks. Continue independent items. Do not repeatedly solicit explicitly deferred decisions.

## Before returning Check Items

For the GitHub Markdown layout with explicit `# Activity ActivityName` source declarations, run the bundled read-only literal-name diagnostic before returning, including in Consistency review-only mode:

```sh
python3 scripts/check_activity_names.py --design <business-design.md> --checks <saved-checks.md>
```

Resolve the script relative to this Skill directory. Inspect its raw declared names, headings and index labels; do not strip words from displayed headings to turn a mismatch into a match. Exit 1 reports a literal mismatch, not a business-policy decision. Exit 2 means the narrow profile was not verified. If execution is unavailable or a declared alias/human-confirmed correspondence requires manual comparison, disclose that limit and compare the raw strings explicitly. This diagnostic does not check guarantees, shared links, source evidence or human states; continue the full Consistency review. It reads files only and requires no new product artifact/schema.

After author checks, execute this Skill's Consistency review-only operation as a [distinct read-only review and repair phase](references/check-item-traceability.md#distinct-consistency-review-and-repair), using a separate reader agent or fresh context when supported. Give the reader the saved candidate, whole Business Design and applicable guidance/revisions (plus the previous list and actual feedback for updates), without a completed answer specimen or expected findings. Require the two source-led passes: declared names and required shared references; general source guarantees versus primary conditions/results and separate examples. The author validates findings against the source, repairs supported defects and requests an actual re-review of the saved revision. Report unsupported findings, undecided meaning, failed/unavailable review or non-improving repetition without claiming a pass. If separate review is unavailable, use a distinct same-context phase and disclose its lack of independence. A Consistency review-only request never edits, repairs or recursively reviews. No new report artifact or human approval is implied.

Reconcile source-explicit unresolved conditions affecting the selected Activities with the saved draft, not just with newly discovered missing-input cases. Retain those pending meanings visibly and limit overlapping normal expectations; do not silently drop them or force every out-of-scope policy into a Check. For presentation updates, preserve established source URLs/revisions when the Business Design content is unchanged: the supplied checkout revision identifies the run, not a reason to repin evidence links. Bind each example's result-relevant inputs and judgments explicitly, and state the expected result of the action without adding “if registration/approval succeeds” as a new premise.

For actions with required inputs but unresolved sufficient success conditions, use a necessary-condition expression plus the direct expected result. Omit an unsupported guarantee formula; never replace it with “successful completion ⇒ result”. Keep source-established invariant or complete condition/result guarantees.

For every initial draft and update, run the [return-time quality check](references/check-item-traceability.md#before-returning-a-draft-or-update) as part of the ordinary request, without asking the requester to invoke another review Skill. Verify source labels and anchors or line ranges against the referenced revision, especially after a Business Design format migration; do not carry old source locations into a new revision. Check applicable description-rule conformance first; report evidenced NG findings separately from undecided business meaning and optional wording suggestions, without making NG a human review state. Correct only source-grounded, meaning-preserving defects within scope, then re-read the final saved artifact and repeat the affected checks. Return genuine business decisions and unperformed checks explicitly; quality checking does not grant human approval. For consistency-review-only requests, use the same gate without edits. An Interface-only request still does not authorize generating or changing Checks.

## Optional Functional Interface index

Use this mode only when requested or when the requester has chosen it to improve navigation. Read [f1](references/prompt.md) sections 1–2 and 4, subject to the current Test-only boundary above. A small Interface describes observable responsibility, actor, input/precondition, result, preserved facts, source and related Check IDs; it is not a required API, function or file. Preserve existing reviewed interfaces and IDs. Do not generate Checks as a side effect of an interface-only request, and do not turn a draft interface into approved meaning. Direct Business Design → Check → Test needs no extra index where already clear.

Write only the requested Check/Interface artifact(s), using the established format and location. Report changed IDs, retained guarantees, review questions and unresolved items. The design handoff comprises agreed Business Design and human-reviewed Checks with revisions/IDs; it does not require evidence from newly created Tests. When preparing that handoff, apply [security requirement intake](references/adoption.md#carry-security-requirements-into-implementation): carry provided sources, scoped non-applicability and unresolved security inputs separately. Do not convert unknown technical policy into business Checks or claim security readiness. A Check-only draft can continue without a complete SR and does not authorize writing or approving SR. Missing Test evidence is separate from business uncertainty. After implementation, the separate follow-up maintains assertions/evidence; this skill does not implement code or tests or accept an implementation.

Record the installed Alder version from `../../plugin.json`, authority revision/digests from [provenance](references/provenance.json), product inputs and plugin commit when known. Stop with a reviewable draft or requested update, never an AI declaration of human agreement.
