# 業務設計書の品質チェック

[文書構造へ戻る](business-design-structure.ja.md) · [相関チェック](business-design-correlation-check.ja.md)

業務設計書を読んだユーザーが、誰が何をするのかを理解し、意味の違いを指摘できるかを確かめます。ここでは、文章と各欄の役割、同じActivity内の説明の整合を扱います。前後の業務の成立性は相関チェック、未記載の機能条件は[漏れのチェック](business-design-omission-check.ja.md)で扱います。

これらのページは目的別の使い分けです。毎回、別担当者によるレビューや別々の報告書を作ることを要求しません。

## 用意するもの

対象の業務設計書のパスと版、適用範囲、既に合意した判断を渡します。本文のユーザー言語も明示します。JSONだけではProcedureやExceptionの本文が欠けるため、元のMarkdownを使います。

## 確認する観点

| 観点 | 確かめること |
| --- | --- |
| 読み手と主体 | ユーザーが使う言葉か。Whoの担当者が、何を受け取り、判断・更新するか分かるか |
| 欄の役割 | Whyは目的、Whenは開始条件、Outputは受け渡す情報、Resultは正常終了時の状態になっているか |
| 手順と入出力 | Inputをどう使うか、Outputをどう作るかがProcedureにあるか。手順で扱う情報の出所・行き先を逆にたどれるか |
| 正常と例外 | 正常手順はProcedure、進められないときの扱いはExceptionに分かれているか |
| 業務のまとまり | 一つの仕事を過度に分割していないか。異なる責任や待ち時間を一つの曖昧な手順に隠していないか |
| 用語と範囲 | 同じ役割・Objectに同じ名前を使っているか。Scopeが管理責任を表しているか |
| 合意の記述 | 意味の確認が必要な仕事では、依頼・返答・修正・合意が読み取れるか。送付しただけで承認済みにしていないか |

たとえばResultが「予約情報を出力する」だけなら、Outputの説明と重なっています。「予約が成立し、その予定で会議の準備を進められる」と書くことで、仕事が終わった後の状態を示せます。文言だけを見て機械的に合否を決めず、実際の手順に照らします。

## AIへ依頼するプロンプト

プロダクトのルートから使う例です。`<対象パス>`・`<版>`・`<合意済み判断のパス、なければなし>`を置き換えてください。

```text
../alder/docs/business-design-quality-check.ja.md に従い、記述品質を確認してください。
欄の定義は ../alder/docs/business-design-structure.ja.md を参照してください。

業務設計書: <対象パス>
対象版: <版>
合意済み判断: <合意済み判断のパス、なければなし>
本文の言語: 日本語

文書全体を読み、全Activityについて、主体、各欄の役割、
Input / Procedure / Outputの双方向の整合、正常と例外の分離を確かめてください。
Objectの名前と説明、Scope、Activityのまとめ方も確認してください。

各指摘に、対象箇所、読み手が誤解する点、根拠、修正案を示してください。
意味を変えずに直せる記述と、人間の業務判断が必要な問いを分けてください。
好みだけの言い換えを必須修正にせず、問題がなければその旨を示してください。
確認した範囲と、確認できなかった範囲も報告してください。
今回は読み取り専用とし、ファイルや業務上の合意を変更しないでください。
```

## 結果の扱い

意味を変えない修正は、前後の説明と合わせて反映します。責任、条件、保証が変わる指摘は、人間が判断してから業務設計書へ反映します。AIの品質評価は、業務上の承認を代行しません。

見出しや参照の構文は[Business Graph exporter](business-graph.md)でも検査できます。構文が通ることと、読み手に意味が伝わることは別です。

詳細な記述観点の根拠は[Business Design記述品質レビュー](business-design-quality-review.md)を参照してください。
