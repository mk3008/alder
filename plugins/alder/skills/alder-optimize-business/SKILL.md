# Alder Optimization Review

Read the bundled [Optimization Review](references/optimization-review.md) in full as the authority before reviewing. It is a byte-identical copy from the pinned source revision in [provenance](references/provenance.json); do not fetch the latest guidance or require the user to select internal documents. Historical evidence links are background, not required review inputs.

1. Read the target repository's `AGENTS.md`. Find current Business Design at the explicit request path, the project's declared path, or conventional `docs/business-design/`. Ask a focused target question if several designs remain plausible; ask for a readable design if none exists. Record its revision or explicit working-tree state. Read the whole relevant design and its connected Activities and Objects before locating the Problem.
2. Resolve the specific Problem and Pain level from the current design or explicit requester context. Keep prompt-only research/PoC input distinct from agreed current-state facts. If either input is missing, ask only for the material missing context; do not invent a Problem or Pain. A vague burden request needs the current work that causes it, not an assumed report to shorten. Where the requested workflow lies outside the source model, identify the gap and return current-work confirmation instead of inventing Activities.
3. Apply the authority's Review behavior, boundary decomposition, output fields and stopping conditions. Ground alternatives in actual work and explain the change from existing responsibilities. Keep observations, burden hypotheses and expected benefits distinct. Software or library development and Alder's own operation can be targets when described. A research-only intermediate artifact is not established operational work.
4. Return at most three useful candidates, including zero where appropriate, and only useful separate Extreme perspectives. Name the current work, evidence, responsibility change, preserved meaning, assumptions and decision-relevant questions using the authority's existing fields. Do not send source-settled facts or uniquely derived technical corrections back as new human business approvals. State the source/search limits and keep effects unmeasured unless evidence establishes them.
5. Keep this review read-only. Do not edit Business Design, generate a maintained intermediate artifact, change JSON, Checks, code or tests, write GitHub, select or approve a candidate, or treat silence as adoption. A human acceptance starts a separate design revision and re-agreement before downstream updates. Include `Alder plugin 0.3.0`, the bundled authority revision/digest, target design revision and installed plugin commit if known.

Requests to draft/revise Business Design belong to `alder-draft-business-design`; requests to review Business Design's quality or correlations belong to `alder-review-business-design`; completed code/DDL/test review belongs to `alder-review-implementation`. A request for structural questions without a known Problem uses the authority's optional Structural Discovery boundary in a separate inquiry, not invented Optimization input.
