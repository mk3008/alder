# Alderの概念モデルを検討する

対象の業務設計、既存モデル、実例、依頼された設計制約と利用可能なJSON契約を確認する。業務理解を共有し、誤りや未決を具体例で質問・回答できるモデルにする。既存の入れ子や表示を実体の定義と決めつけない。概念・論理・既存の物理構造・表示投影を区別し、どれを作ったか示す。概念図はテーブル設計の細部を網羅しなくてよいが、示した関連と共有の意味は業務上の根拠と一致させる。未確認の件数は確定させない。

1. **意味と識別を探る。** 何を一件とし、どんな場合に同じ対象を複数の業務が参照でき、いつ別件かを確認する。所属・独立変更・存在条件・履歴・時点を具体的な操作や結果と照合する。IDや名前の一致だけで業務上の同一性を確定しない。
2. **属性と関係を決める。** それぞれの情報が何によって決まるかを検討し、同じ事実を独立に更新する重複を避ける。関係の所有・参照・組合せを分け、確認できた最小・最大件数を根拠とともに示し、未確認はそのまま残す。0..1だけを理由に別実体を作らず、未決と「存在しない」、値と属性を混同しない。N:Nの関係自体に事実・識別・履歴がある場合は関係の実体化を検討する。
3. **論理と物理をつなぐ。** 正規化を求められたら、候補キー・関数従属性、更新時の不整合、必要な一意性を検討し、根拠と未決を明記する。単独ID、自然キー、FK、JSON配列やDB表を一律に強制しない。配列や入れ子は表現方法として扱い、意味的な独立性と共有の可否を別に説明する。履歴や確定時点の保存は必要な事実として残す。
4. **例で反証する。** 少なくとも共有・複数・未決・異なる対象を区別する例と、重複・誤参照・不正な多重度の例を用意し、許す／拒む理由を業務上の意味と照合する。テストが通ることを業務合意と見なさない。未知の主体、応答、条件や履歴を作って埋めない。
5. **既存の構造から変更する場合。** 現行と候補の項目・ID・関係・順序・未決・確認状態を対応付け、明示的な版と別出力の移行方法を示す。名前や似た値だけで既存の主体を統合せず、曖昧な同一性は確認する。既存CheckやStateの原典・人間判断を自動的に移さない。
6. **レビューできる形にする。** 使える既存の概念モデルJSONとViewerがあれば、それぞれの出所と版を保った候補を作る。全体図で隠した概念は隠していると分かるようにし、個別図と同じ関係・多重度を示す。関係先を名前から推測しない。出力時に、確定・仮説・未決、正常例と反例、旧形式との対応、実際に検証した範囲を分けて返す。

業務設計書そのものを改稿する依頼は既存のBusiness Design用Skillへ、JSON文書の既存形式での編集・保存はJSON管理Skillへ渡す。既存モデルのレビューだけを求められた場合は原本を変更しない。データモデリングを常に独立必須工程としたり、特定のDB構成を業務要件として決めたりしない。
