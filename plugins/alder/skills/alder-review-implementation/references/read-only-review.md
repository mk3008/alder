# Read-only implementation review stage


Use this installed plugin's bundled [review knowledge v0.3](review-knowledge-v0.3.md) in full. Its text is copied without modification from Alder `docs/phase2/review-knowledge-v0.3.md`; the plugin package version is in `../../../plugin.json`. Do not fetch the latest Alder repository or ask the project to copy review knowledge.

1. Locate the product repository and its `AGENTS.md`; follow project instructions. Resolve Business Design from the declared path, or the conventional `docs/business-design/`. If neither exists, ask for its readable location. Determine the requested change's scope from the request and repository diff/commits; ask for a target only if that scope remains ambiguous. Never assume the entire product is being reviewed.
2. Record the Business Design's revision and the implementation revision (commit IDs, or explicit working-tree state when uncommitted). Read the applicable Business Design **first**, including connected activities and their actual inputs and outputs. Read relevant Decision Records, documented assumptions, confirmed Check Items and provided System Requirements (SR) / related project constraints **second**. Record each supplied SR source, revision and applicable scope, including the version used for implementation; pin uncommitted inputs with paths and content digests. Read implementation, DDL, tests and available execution evidence **third**. A missing optional artifact is not evidence of a missing business guarantee.
3. Apply every part of the bundled review knowledge, including its boundaries and stopping conditions. Walk representative work from each participant's perspective, then trace the implementation's business-significant choices back to the design. Business Design is the authority for meaning; Decision Records, Check Items, tests and current code are evidence, not independent authority to approve unresolved meaning.
4. Compare the provided SR constraints applicable to this change with implementation, DDL, tests and available execution evidence. Cite the source clause and evidence or gap; static code, a passing unit test or a configured target does not prove an unobserved operational guarantee. SR authoring, validity and completeness remain the product's responsibility. Distinguish not provided, unreadable and not applicable (with a scope reason); missing SR means unverified constraints, not no requirements. Ask for location or scope only when needed for a concrete affected finding, and continue unaffected BD/Check review without demanding a new NFR checklist or SR Check ledger.
5. If BD and SR are ambiguous or conflict, preserve both sources and explain the affected meaning and technical constraint. Do not silently let either overwrite the other. Return the smallest needed decision to the relevant business/technical owner; do not turn an agreed technical fix into a new business-approval gate. Classify by the requirement's meaning and responsibility, not labels such as security or availability. If an input revision or scope changes, label conclusions tied to the old pin and re-review affected scope before claiming current conformity or supporting dependent record updates; continue genuinely unaffected work.
6. Report each material finding with its evidence and current/downstream effect. Classify it as a definite mismatch, Business confirmation, technical improvement, or sufficient. Name the smallest decision or confirmation and its responsible party when needed. Do not manufacture business rules, prescribe an architecture, or turn every undocumented detail into a finding. State what could not be checked.
7. Include the installed Alder version from `../../../plugin.json`, review knowledge v0.3, the reviewed source revisions and the installed plugin source commit if known, especially for a moving development branch. The bundled knowledge's source commit and digest are in [provenance.json](provenance.json). Review only; do not edit product files or convert findings into approved business decisions. Return the findings to the caller. This review stage cannot invoke follow-up or authorize changes; the caller may separately maintain records under the original request.

The plugin supplies review meaning and procedure. Existing deterministic tools may verify syntax, graph export or traceability when relevant and available in the project; passing them does not establish business correctness. This review needs no MCP server or runtime dependency.
